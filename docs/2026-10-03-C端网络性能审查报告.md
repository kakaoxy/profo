## 三、并发表现

| 场景 | 结果 |
|---|---|
| 列表接口 10 并发 | 单请求延迟 0.19–0.48s（基线 0.09s，放大 ~4×） |
| 列表接口 50 并发 × 30s（ab） | 94.6 RPS；但 **2813/2838 请求为 429**（触发 60/min 限流），数据不代表真实容量 |
| 详情接口 20 并发 | 0.39–0.66s/请求 |
| stats 20 并发 | 0.24–0.33s/请求 |
| 小区搜索 10 并发 | 0.13–0.24s/请求 |

**容量判断**：服务器 2 核 + uvicorn 默认 2 worker（`WEB_CONCURRENCY` 未在 docker-compose 中显式配置）。并发 10–20 时延迟已放大 3–6 倍，估计舒适容量在 **并发 ~10–20**，与 C端获客工具的预期流量（低频、低并发）匹配，但余量不大。⚠️ 未做极限探测（避免影响生产）。

**限流实测**：`RateLimits.PUBLIC_PROJECT_LIST = 60/minute`（按 IP，Redis moving-window）。串行连发 70 次即触发 429，且 moving-window 惩罚持续整窗。ab 的 30s 内近全部请求 429，说明该阈值对"浏览"场景非常紧（见 P0-2）。

## 四、发现（按优先级）

### P0-1 ｜ API JSON 响应未启用 gzip 压缩

**证据**：`curl -H "Accept-Encoding: gzip"` 请求 `/public/projects` 返回 `content-length: 5686`，无 `content-encoding` 头。后端 `main.py` 未挂 `GZipMiddleware`；Nginx 未配置任何 `gzip on` 指令（静态 JS 的 gzip 来自 Next.js standalone 自带压缩，非 Nginx）。

**影响**：详情接口 24KB JSON 裸传（gzip 后估 ~4–6KB，省 ~75%）；列表 5.7KB→~1.5KB。移动端弱网下每个 API 请求多耗 3–5 倍传输时间。C端所有接口均命中。

**修复**（二选一，推荐 ①）：
1. 后端加两行：`app.add_middleware(GZipMiddleware, minimum_size=1024)`；
2. Nginx `http`/`server` 块加 `gzip on; gzip_types application/json; gzip_min_length 1024;`。

**成本**：一行代码。**收益**：全站 API 传输量降 ~70%+。

### P0-2 ｜ 限流阈值误伤真实用户浏览

**证据**：`PUBLIC_PROJECT_LIST = 60/minute` 同时套在 **列表 + 详情 + 成交案例** 三个读接口上（`routers/public/projects.py`）。用户正常刷 10 分钟首页即可触顶：首页每次挂载拉 1 次列表 + 详情页每次拉 detail（还会另触发 visit 埋点 POST）。实测连发 70 次全 429，且窗口内持续被拒。

**影响**：移动 4G（基站级共享出口 IP）、公司/家庭共享宽带下多个真实用户会互相顶掉；一旦触发，之后整分钟浏览全挂，表现为"网页突然刷不出来"。同时 429 处理本身也消耗后端资源（ab 30s 内 2813 个 429）。

**修复建议**：读接口（列表/详情/成交/搜索/统计）上调至 **300/minute** 或改 `default_limits` 兜底；写/敏感接口维持现状（`10/hour` 注册、`10/hour` 留资等合理保留）。

### P1-1 ｜ 详情页前端存在一次冗余请求

**证据**：`GET /public/projects/{id}` 响应已内嵌 `consultant` 字段（nickname + 脱敏手机号，`routers/public/projects.py` 详情 handler 组装 `PublicConsultantInfo`）；但 `frontend/src/app/(c)/projects/[id]/page.tsx` 仍单独发起 `useSWR(.../consultant)` 第二次请求（实测多 ~72ms RTT + 一次后端 User 查询）。

**修复**：删除详情页独立的 consultant 请求，直接读 `data.consultant`。**成本**：删几行。**收益**：详情页少一次往返。

### P1-2 ｜ 详情接口全量返回 media（含未用字段）

**证据**：`/public/projects/298` 返回 66 个 media items（24.4KB），前端轮播只消费 `photo_category === "marketing"` 的部分；`description` 恒为 `None` 仍占 schema 传输。

**修复**（可分期）：
- 快速：详情接口裁剪 media（只返回 marketing 分类 + 视频海报缩略图），预计响应降至 ~6–8KB；
- 或在压缩（P0-1）落地后暂缓——gzip 后 24KB→~5KB，紧迫性大降。

### P1-3 ｜ C端列表/详情页为纯客户端渲染（CSR），首屏 = HTML骨架 + JS + 再请求 API

**证据**：`(c)/page.tsx`、`(c)/projects/[id]/page.tsx` 均为 `"use client"` + SWR；首页 HTML 42.6KB 中无房源数据，实际内容需等 18 个 chunk（gzip 共 ~277KB）加载 + 水合后再发 API。桌面宽带实测总时延尚可（<0.5s 可见内容），但移动端弱网下 LCP 会显著劣化（估 2–4s）。

**修复建议**（收益大、改造中等，建议列入迭代规划而非立即执行）：
- 列表页首页与详情页改 Server Component 预取首屏数据（`Promise.all` 并行取列表+统计），分页/筛选仍走客户端 SWR；
- 好处：首屏 API 由"浏览器→Nginx→后端"变为"Node 内网 127.0.0.1:8000 直连"（`lib/config.ts` 已具备该链路），省一次公网 RTT；HTML 直出内容利于 SEO/分享卡片。

### P2-1 ｜ 列表查询 `count(*)` + 状态分组排序在数据量增长后的隐患

**证据**：`get_published_projects` 先 `query.count()` 再 `offset/limit` 取页（两次往返）；默认排序用 `case()` 状态分组（在售→在途→已售）无法走普通索引。当前房源量（<数百）无感；万级数据后列表 p95 会明显抬升。

**建议**：现阶段不动（符合"最简代码"）；数据量过万时再考虑：状态列冗余成可索引的 `status_priority` 字段 + `count` 缓存或 `estimated count`。

### P2-2 ｜ OSS 未挂 CDN

**证据**：图片直连 `profo.oss-cn-shanghai.aliyuncs.com`，上海节点外用户 RTT 更高且无边缘缓存。当前缩略图策略（webp ~30KB）已把单图成本控制得很好，全国性访问加速后才需要 CDN。

**建议**：流量上来后给 OSS 绑自定义域名 + 开 CDN（阿里云控制台操作，无代码改动）。注意 `.next/image` 已 `unoptimized: true`（配置注释说明了 2 核服务器跑不动图片转换，该决策合理，保留）。

### 做得好的（保持）

- `/_next/static` 长缓存 + immutable + gzip；字体 preload；HTTP/2 + TLS1.3；
- 列表封面 `resolve_cover_images_batch` 批量解析（无 N+1），缩略图 `thumbs/*.webp`（~30KB）策略有效；
- 轮播优先缩略图、视频 `preload="metadata"` + 缩略图海报；
- 限流有 Redis 后端 + 内存降级（`in_memory_fallback_enabled`），多 worker 一致；
- 房源导出专用 Nginx location（放宽超时 + 关 buffering）思路清晰；
- `images.unoptimized` 关闭 next/image 优化的取舍有注释、有理由。

## 六、⚠️ 未覆盖与不确定项（Fail Loud）

1. **服务器侧指标未观测**：无生产 SSH/监控数据，CPU/内存/慢查询均为推断（依据 Dockerfile 注释"服务器 CPU 弱（2核）"+ 并发延迟放大曲线）。
2. **真实弱网/移动端未模拟**：全部数据来自本机宽带（低 RTT），移动 4G/弱网绝对值会更差，但相对结论（压缩收益、请求数）不变。
3. **需登录态的 C端接口未测**：`/public/leads/mine`、`/public/users/profile`、预约/留资写接口。避免向生产库写入测试数据，仅验证了 401 拒绝路径（56ms，正常）。
4. **容量上限未探测**：受生产限流与"不对生产做破坏性压测"约束，50 并发 × 30s 的 ab 结果中 94.2% 为 429，**不能**作为吞吐结论引用；§三容量判断为保守推断。
5. **`/valuation`、`/leads` 页面**：线上 `/valuation` 返回 307（本地路由表中为 `/valuation` 目录），本次仅测网络层，未追业务重定向链是否预期。⚠️ 不确定，建议后续人工确认一次。
6. **限流 key 口径**：`_get_client_ip` 具体取 `X-Real-IP` 还是 `X-Forwarded-For` 首段未逐行核验（Nginx 已传两头）；若取了代理链外层 IP，存在全站共享限流桶的理论风险，建议代码复核一眼。

## 七、结论

C端链路整体健康：页面 TTFB <100ms、接口 p50 <150ms、静态资源缓存策略正确、图片缩略图策略有效。**最需要立即处理的是两件低成本高收益的事：API gzip 压缩与公开读接口限流阈值**——前者直接改善所有移动端用户的传输耗时，后者消除真实用户被 429 误伤的风险。其余项（CSR 改造、media 裁剪、CDN）按 ROI 列入迭代即可，无需紧急处理。
