# 小程序微信授权体系调研报告

- **日期**：2026-10-06
- **范围**：`miniapp/`（登录、手机号授权、头像昵称、订阅消息、隐私协议）+ `backend/`（微信服务层、令牌体系、受众校验）
- **调研问题**：
  1. 是否最大化利用微信公众平台的规则获取登录用户的权限？
  2. 当前的微信用户权限管理方案是否是最佳实践？
- **方法**：通读 miniapp 全部鉴权/授权相关代码与后端对应实现，逐条比对微信官方文档（登录、code2Session、手机号组件、头像昵称组件、订阅消息、隐私协议指南、UnionID 机制）。

## 一、现状架构盘点（代码事实）

### 1.1 登录链路（wx.login 静默登录 → 自建 JWT）

```
用户点击「手机号快捷登录」（需先勾选自绘协议 checkbox）
→ wx.login 取 code（utils/wechat-auth.ts:52）
→ POST /auth/wechat/login {code}（backend/routers/system/auth.py:423）
→ 服务端 jscode2session 换 openid/unionid/session_key（backend/services/system/wechat.py:170）
→ login_or_register_wechat_user：openid 命中 → 复用；unionid 兜底；未命中 → 建临时账号（is_temporary=True）
→ 签发 JWT：内部员工双令牌（aud=admin + aud=c），纯 C 端单令牌（aud=c）
→ 前端写入 4 个 storage key（access_token / refresh_token / c_access_token / c_refresh_token）
```

- JWT：access 30 分钟、refresh 7 天轮换 + 按 jti 撤销 + `token_version` 吊销（`backend/settings.py:151`）。
- 前端 401 自动刷新：按请求路径推断受众（`/public/*`、`/keys/*` → C 端令牌，其余 → admin 令牌），并发刷新复用同一 Promise（`miniapp/utils/request.ts`）；后端有对应的 `_infer_audience_from_path` 严格校验 aud（`backend/dependencies/auth.py:38-50`）。
- 前端同步解析 JWT payload（手写 base64url 解码，`utils/token.ts`），用于 onShareAppMessage 等同步回调取 sub/aud 做分享归因——这是合理的官方文档没有替代方案的场景。
- code 一次性消费；并发首登 IntegrityError 兜底；已合并（status='merged'）账号经 merged_to_user_id 重定向（`wechat.py:203` 起）。

### 1.2 手机号（手机号快速验证组件，付费 0.03 元/次）

三个入口，全部由用户主动点击 `button open-type="getPhoneNumber"` 触发，无任何强制/自动拉起：

| 场景 | 触发点 | 后端端点 | 说明 |
|---|---|---|---|
| 绑定手机号弹窗 | profile 页 onShow 自动弹（仅临时账号、仅弹一次，`c_phone_prompted` 标记）/「完善手机号」主动点 | `/public/users/phone/wechat` | 40901 冲突 → 切合并视图引导去 bind-account（`components/phone-bind-modal/index.ts`） |
| 估价提交页 | 未绑手机号展示 banner「完善手机号，加速评估速度」，不阻断提交 | 同上 | 引导而非强制 |
| 招募留资 | 报名按钮本身即 getPhoneNumber 按钮 | `/public/recruit/leads` | code → getuserphonenumber 解密手机号 → 归因落库 |

- 后端统一走 `phonenumber.getPhoneNumber` 新方式（动态令牌 code，5 分钟有效、一次性），**未使用已废弃的 encryptedData/iv 解密方式**（`wechat.py:269`、官方文档明确建议新方式）。
- 手机号 Fernet 加密存储 + `phone_hash` 唯一索引保唯一性（`models/user/user.py:117-119`）。
- 绑定端点限流 10 次/小时（`utils/common.py:198`）。

### 1.3 头像昵称（官方「头像昵称填写能力」）

- 头像：`button open-type="chooseAvatar"` → 临时路径上传 `/public/files/upload` → `PUT /public/users/wechat-profile`（`pages/profile/index/index.ts:595`）。
- 昵称：`input type="nickname"`（微信键盘上方展示昵称，onBlur 微信侧自动内容安全检测）（`pages/profile/index/index.wxml:27`）。
- **未使用已回收的 `wx.getUserProfile` / `wx.getUserInfo`** —— 与官方推荐一致（官方隐私指引文档明确标注这两个 API 已回收）。

### 1.4 订阅消息（一次性订阅）

- 3 类模板：估价结果通知（`utils/valuation-notify.ts`）、房源上新/调价（`utils/marketing-notify.ts`）、招募线索（`utils/recruit-employee.ts`）。
- 模板 ID 由后端配置下发（未配置 = 功能关闭）；授权严格在用户 tap 手势回调内同步发起（符合微信限制）。
- 细节完整：`getSetting(withSubscriptions)` 区分单次拒绝 vs 总是拒绝（总是拒绝引导 `wx.openSetting`）；accept 结果上报后端累计额度；后端发送区分 43101（未订阅）/40003（openid 无效）为预期业务态按额度扣减（`wechat.py:403`）。

### 1.5 隐私协议

- `app.json` 配置了 `__usePrivacyCheck__: true`；内置《用户协议》《隐私政策》子包页面；登录按钮前置自绘 checkbox 勾选校验。
- 隐私政策文案声明了 openid/unionid/session_key/手机号/头像昵称的收集目的（`pages/agreement/privacy/index/index.ts`）。
- **未接入 `wx.getPrivacySetting` / `wx.onNeedPrivacyAuthorization` / `agreePrivacyAuthorization` 按钮**——完全依赖官方默认弹窗兜底。

### 1.6 其他开放能力

- 分享：`onShareAppMessage` / `onShareTimeline` + referrer 归因、招募小程序码（`getwxacodeunlimit`）、`showShareMenu` 启用朋友圈。
- UnionID：openid 未命中时以 unionid 兜底查询复用已有用户（`wechat.py:246`），为 Web 端 OAuth（`/auth/wechat/authorize`，snsapi_userinfo）与小程序跨端身份打通预留了机制。

## 二、问题一：是否最大化利用微信公众平台规则获取权限？

**结论：身份类权限已基本用满（约 85-90 分），但有 1 项未兑现的规则红利和 3 项可选扩展；"最大化"应止步于此——微信明确警告不合理索权会被处罚，当前克制的设计是正确方向。**

### 2.1 逐项对照表

| 微信平台能力 | 状态 | 证据/说明 |
|---|---|---|
| wx.login 静默登录（openid） | ✅ 已用 | 登录页主入口 + key-share 页未登录自动补登（`pages/key-share/index.ts:299`） |
| UnionID 跨端身份打通 | ✅ 机制已用，⚠️ 依赖运营配置 | 代码已做 unionid 兜底；但 unionid 仅在小程序绑定到微信开放平台账号后才返回（官方 UnionID 机制文档），**未绑定则恒为 null**，Web OAuth 用户与小程序用户将产生两个账号。需在 mp 后台确认绑定状态 |
| 手机号快速验证组件（付费） | ✅ 已用，方式正确 | 新 code 方式；三入口全部用户主动点击；免费/付费规则不受影响（企业主体） |
| 头像昵称填写能力 | ✅ 已用，方式正确 | chooseAvatar + input type=nickname，getUserProfile 已弃用而未使用 |
| 订阅消息 | ✅ 已用（一次性 × 3 类） | 额度上报、拒收处理、总是拒绝引导均完整 |
| 朋友圈分享/小程序码 | ✅ 已用 | onShareTimeline + getwxacodeunlimit |
| **冷启动静默续登** | ⚠️ **未实现（规则红利缺口）** | 见 2.2 |
| 位置类（getFuzzyLocation 等） | ❌ 未用（可选） | 「附近房源」是潜在产品能力；使用需在隐私指引声明 scope，当前未声明则调用会被平台直接禁用 |
| 客服会话（button open-type=contact） | ❌ 未用（可选） | 免费的用户触达通道，about 页目前是 400 电话占位（`settings.py:163` 值本身还是占位符） |
| 手机号实时验证组件 | ❌ 未用（合理） | 账号唯一性场景快速验证足够，实时验证更重更贵 |
| 长期订阅消息 | ❌ 不可用（合理） | 仅政务/医疗等特定类目可申请 |
| session_key 解密能力 | ⚠️ 存而未用 | 见问题二缺陷 2 |

### 2.2 唯一的"规则红利"缺口：冷启动静默续登

官方推荐的小程序登录形态是：启动时静默 `wx.login`（**不弹任何窗、不属于隐私接口**）换取登录态，用户全程无感。当前实现里：

- refresh_token 7 天轮换可以覆盖 7 天内的续期（体验尚可）；
- 但超过 7 天（或用户清缓存/换设备）后，用户必须重新找到「我的」→ 点登录 → 勾协议 → 点按钮，四步才能恢复登录态；
- `wx.login` 本身无弹窗、无需授权，属于平台鼓励的静默能力，未被利用。

**可最大化点**：`App.onLaunch` 检测本地令牌失效 → 静默调 `wechatLogin()` 补登。唯一约束：若用户从未同意过协议（首次使用），不应在未告知的情况下静默收集 openid——用 `getPhonePrompted()` 同款思路加一个「已同意过协议」标记即可区分。详见建议 P1-1。

### 2.3 "不最大化"的部分恰恰是合规优势

微信官方文档（手机号快速验证组件）明确警告：*不合理地要求用户提供手机号、中断正常使用流程，将依据《微信小程序平台运营管理规范》处罚*。当前实现中估价提交不强制手机号（banner 引导）、绑定弹窗可「暂不绑定」且记录不重复打扰——这是**正确的克制**，不应为了"多拿手机号"改成强制索权。

## 三、问题二：当前微信用户权限管理方案是否是最佳实践？

**结论：架构层面高度接近最佳实践（双受众 JWT、服务端 code2session、令牌轮换撤销、新式手机号组件、官方推荐的头像昵称组件均达标），存在 2 个中危缺陷、若干低危改进点；无高危问题。**

### 3.1 已达最佳实践的项目（对照官方文档逐条验证）

| 官方要求 | 现状 | 判定 |
|---|---|---|
| session_key 不得下发到前端 | 存后端 `wechat_session_key` 列，EncryptedString 加密，无任何下发路径 | ✅ |
| code 只能使用一次 / 服务端调用 jscode2session | secret 仅在后端；code 换取后即弃 | ✅ |
| 手机号用新 code 动态令牌方式 | `phonenumber.getPhoneNumber` + code，未用废弃解密方式 | ✅ |
| getPhoneNumber 必须用户点击触发 | 全部经 button open-type，代码注释也明确此约束 | ✅ |
| 头像昵称用官方填写能力（getUserProfile 已回收） | chooseAvatar + type=nickname | ✅ |
| 隐私接口需用户先同意隐私指引 | `__usePrivacyCheck__: true` + 自绘协议 + 官方默认弹窗兜底 | ✅（体验可优化，见 3.3） |
| 订阅消息在 tap 手势内同步发起 | 各 notify 工具均如此，且处理了"总是拒绝"分支 | ✅ |
| 令牌安全（轮换/撤销/短期） | refresh 轮换防重放 + jti 撤销 + token_version + 并发刷新单飞 | ✅ |
| 双端身份隔离 | aud 路径推断 + 前端同规则注入，前后端口径一致 | ✅ |

### 3.2 缺陷清单（按严重度）

#### 🔴 P0-1 非鉴权失败也会清空登录态（真实可用性缺陷）

`pages/profile/index/index.ts` `loadUser()`：

```
const ok = await this.loadPublicUser(authHeader);
if (!ok) { this.clearTokensAndReset(); }
```

`loadPublicUser` 的 catch 对**一切**异常返回 false——包括网络超时、500、DNS 失败。`utils/request.ts` 已对 401 做了自动刷新重试，所以能走到 catch 的 401 已经是刷新失败（该清）；但**一次网络抖动就会把有效登录态误清**，用户被迫重新登录。401 链路已被 request.ts 覆盖，此处应只在确认服务端判定身份失效（401/403 且刷新失败）时清令牌，网络类异常保留登录态、提示重试。

- 验证点：断网打开 profile → 恢复网络后不应要求重新登录。
- 附带：登录页 `index.ts` 对 `from=valuation/recruit/booking/subscribe` 用 navigateBack，若来源页栈不存在（分享直接进入）navigateBack 会失败，属边缘路径，建议 fallback switchTab。

#### 🔴 P0-2 session_key 收集了但从未使用（隐私最小化问题）

全后端仅三处写 `wechat_session_key`（登录/合并/复用用户），**没有任何读取方**：手机号走新 code 方式无需 session_key 解密，群信息等解密场景不存在。按 PIPL 最小必要原则与微信审核口径，"收集了不用的个人信息"属于冗余声明——隐私政策 2.1 明确写了"获取 openid、unionid 与 session_key"。

- 处理选项（二选一）：① 停止写入并清空存量列（保留字段一版过渡，符合项目迁移惯例）；② 保留但确认为未来解密场景预留，且 checkSession 逻辑补齐。
- 注意：若选 ①，需同步修订隐私政策文案与微信后台《用户隐私保护指引》声明（平台以代码实际调用为准，jscode2session 返回 session_key 本身不构成隐私接口调用，但声明与行为一致更稳妥）。

#### 🟡 P1 隐私授权体验分裂（合规达标，体验非最优）

登录页自绘 checkbox 勾选协议，之后调用 getPhoneNumber 等隐私接口时微信还会弹**官方隐私弹窗**（因为代码未接 `onNeedPrivacyAuthorization`，也未用 `agreePrivacyAuthorization` 耦合按钮）→ 用户点两次确认。官方 PrivacyAuthorize 指南推荐两种做法：

1. 登录按钮改为 `open-type="getPhoneNumber|agreePrivacyAuthorization"`（2.32.3+ 支持耦合）；
2. 或 `wx.getPrivacySetting` 判定 needAuthorization 后才展示自绘协议区，用户勾选时用 `agreePrivacyAuthorization` 按钮同步微信侧。

另外 `app.json` 的 `__usePrivacyCheck__: true` 在 2023-10-17 之后已无条件强制启用，该配置现在是无害的冗余，可留可删。

#### 🟡 P1-3 unionid 绑定状态需确认（配置问题，非代码问题）

`login_or_register_wechat_user` 的 unionid 兜底逻辑正确，但 unionid 生效前提是小程序已绑定到微信开放平台账号（官方 UnionID 机制文档）。若未绑定：小程序用户与 Web OAuth 用户（`/auth/wechat/callback` 拿到的 unionid 同样为空时）无法自动识别为同一人，产生双账号。**代码无法自证，需要运营在 mp.weixin.qq.com / open 平台确认绑定关系。**

#### 🔵 P2 清单

| # | 事项 | 位置 | 说明 |
|---|---|---|---|
| 1 | 内部身份判定靠 permissions 差集 | `profile/index.ts:39` | 代码已自注 ⚠️ TODO；权限模板调整（给 customer 加权限）会静默把 C 端用户判成内部员工。建议后端 `/public/auth/me` 下发显式 `is_internal` |
| 2 | getPhoneNumber 欠费 errno 1400001 未显式处理 | phone-bind-modal / recruit detail | 平台默认半屏提示足够；若要自定义可设 `phone-number-no-quota-toast=false`，当前可不改 |
| 3 | `c_phone_prompted` 仅存本地 | `utils/token.ts` | 换设备/清缓存后弹窗重现一次，低危 |
| 4 | 隐私政策联系邮箱为占位符 | privacy/index/index.ts | `privacy@example.com` 会影响审核观感，需替换真实联系方式 |
| 5 | wx.checkSession 未使用 | app.ts | 当前无解密场景、自建 JWT 不依赖微信侧 session 有效期，**暂不需要**；若启用 session_key 能力则必须在 wx.login 前先 checkSession（官方登录时序） |
| 6 | 登录页按钮文案与实际行为不一致 | `login/index/index.wxml:11` | 主按钮叫「手机号快捷登录」但实际是纯 wx.login 静默登录（不取手机号）；叫「微信一键登录」更准确，避免用户误以为会弹出手机号授权 |
| 7 | refresh 端点限流 10/min 偏紧 | `utils/common.py:103` | access 30min 过期 + 双令牌体系下，重度使用页面可能逼近限额；401 刷新失败链路已有静默兜底，观察日志再定 |

## 四、改进建议（按优先级）

| 优先级 | 建议 | 对应缺陷 | 验收标准 |
|---|---|---|---|
| P0 | loadUser 仅在 401/403 且刷新失败时清令牌，网络异常保留登录态 | P0-1 | 断网→恢复网络，无需重新登录；单测覆盖 catch 分支分类 |
| P0 | 决策 session_key 去留并执行（清存储或补 checkSession+用途） | P0-2 | 后端无死字段或 checkSession 就位；隐私指引与行为一致 |
| P1 | 登录按钮耦合 agreePrivacyAuthorization 或接入 getPrivacySetting | P1 | 首次登录全程只出现一次协议确认（自绘与官方弹窗二合一） |
| P1 | 确认小程序已绑定微信开放平台（运营动作） | P1-3 | mp 后台可见绑定关系；联调环境验证 unionid 非 null |
| P1 | App.onLaunch 静默续登（仅对已同意协议用户） | 2.2 红利缺口 | 7 天未使用用户冷启动自动恢复登录态，且无未同意先收集的合规风险 |
| P2 | 后端下发显式 is_internal 字段 | P2-1 | profile 判定不再依赖 permissions 差集 |
| P2 | 登录主按钮文案改「微信一键登录」 | P2-6 | 文案与行为一致 |
| P2 | 替换隐私政策占位邮箱 | P2-4 | 审核可用的真实联系方式 |
