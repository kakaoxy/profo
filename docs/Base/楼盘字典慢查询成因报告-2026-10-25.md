# 楼盘字典慢查询成因报告（2026-10-25）

> 现象：生产导入 735 万户上海楼盘字典后，`/admin/building-dictionary` 总览页的小区搜索与翻页都变得非常慢。
> 结论先行：**主因是算法/查询设计问题（KPI 接口每次页面加载实时 `COUNT(*)` 730 万行，单次 6.3~9 秒并阻塞整页渲染），服务器配置（1.6G 小内存机）是放大因子**。小区搜索与分页 SQL 本身并不慢（1~15ms）。
> 业务口径核验（迭代二）：搜索只按小区名、对象 ~2.17 万小区，户室级不参与检索——据此逐项判定，**过度查数仅 KPI 两处，其余读路径全部健康**（详见 §4.4）；修复优先级已按此修订（§6）。

1. 代码走查：定位页面加载链路与每条 SQL 的生成位置（见 §2）。
2. SSH 登录生产（139.224.162.134）：采集服务器资源、容器内存、数据库规模与统计信息。

## 2. 页面加载链路（代码依据）

[page.tsx](frontend/src/app/(main)/admin/building-dictionary/page.tsx#L53-L74) 为 Server Component（`force-dynamic`），**每次搜索关键词、点击翻页都会重新触发服务端渲染**，并 `Promise.all` 并行请求 3 个接口：

| 接口 | 后端实现 | 关键 SQL |
| --- | --- | --- |
| `/kpi` | [dict_read_service.py get_kpi](backend/services/property/dict_read_service.py#L271-L297) | `SELECT count(*) FROM bd_rooms`（730 万行）<br>`SELECT count(*) FROM bd_buildings`（53 万行）等 5 条 |
| `/communities` | [dict_read_service.py query_communities](backend/services/property/dict_read_service.py#L299-L404) | `count` + `LIKE '%kw%'` 过滤 + `ORDER BY name OFFSET/LIMIT` + 每页 3 个聚合 |
| `/filter-options` | [dict_read_service.py get_filter_options](backend/services/property/dict_read_service.py#L234-L269) | 两条 `GROUP BY` 聚合 |

由于 `Promise.all` 等最慢者，**整页耗时 ≈ `/kpi` 耗时**。

## 4. 成因定位

### 4.1 主因：算法/查询设计 —— KPI 实时全表计数阻塞整页（⚠️已实锤）

- `/kpi` 每次调用执行 `SELECT count(*) FROM bd_rooms`。PG 的 `COUNT(*)` 必须逐行扫描（MVCC 无行数计数器），730 万行 × 1GB 表在 2 核 + 128MB shared_buffers + `effective_io_concurrency=1` 的环境下单次 **6.3~9 秒**，且暖缓存无改善（表装不进内存，每次都从磁盘/OS 缓存读约 446MB）。
- 该接口被并行进每次页面渲染（`Promise.all`），而搜索、翻页、筛选的每一次操作都是一次新的服务端渲染 → **每次操作都重新付出 6~9 秒**。这正是「搜索慢、翻页慢」的直接原因。
- 用户浏览器实测的 **16.5s 文档请求**（`GET /admin/building-dictionary`）即这条 SSR 链路的端到端呈现：SSR 同步等待 KPI（容器内实测 5.9~6.3s，内存压力下可劣化至 ~9s+），叠加 swap 换页/冷缓存/移动网络后即为现场观测值（详见 §3.4）。
- 用户感知的「小区搜索慢」是错觉锚定：搜索 SQL 本身 1~9ms，慢的是同屏必须等待的 KPI。

### 4.2 放大因子：服务器配置（⚠️不是根因，但决定了慢的量级）

- **1.6G 物理内存**：bd_rooms 一张表 1GB，`shared_buffers=128MB` 不可能缓存；OS page cache 也只有约 583Mi 且要供 4 个容器共用 → 每次 COUNT 都大量读盘（实测 57120 blocks/query）。
- **Swap 已用 1.2Gi**：系统已处于内存超卖状态，backend 容器 85.8% 接近 512m 上限，偶发换页进一步拖慢所有查询。
- **2 核 CPU**：`COUNT(*)` 即便并行（2 worker）也受限于单核聚合能力与 IO。
- 同样的算法放到 4 核 16G、shared_buffers≥2G 的机器上，单次 COUNT 会降到约 0.5~1.5s（仍是每次翻页 1 秒+，仍不合格）；反之只修算法不动服务器即可把页面从 7s+ 拉回百毫秒级。

### 4.3 已排除项

| 排除项 | 依据 |
| --- | --- |
| 统计信息过期（导入后未 ANALYZE） | `pg_stat_user_tables.last_autoanalyze` 显示导入后已完成（2026-10-25 08:34~08:37 UTC），且第 6/7 项计划选择了正确索引 |
| 小区搜索缺索引 / LIKE 无法优化 | communities 仅 2.2 万行，`pg_trgm` 扩展与 3 个 trgm 索引均已就位；实测 1~9ms |
| 分页 OFFSET 深翻页问题 | ORDER BY name 走 `communities_name_key`，页 1~N 均在毫秒级 |
| 别名表拖慢搜索 | community_aliases 仅 18 行 |
| 导入任务残留占用资源 | bd_import_tasks 仅 1 条已完成任务，排查时 load 0.14 |
| 抽屉/楼栋户室查询 | 均走 building_id/community_id 索引，毫秒级 |

### 4.4 过度查数清单（按业务口径逐项判定）

业务口径：搜索只按小区名、对象 ~2.17 万小区；户室/楼栋级数据只作展示与绑定，不参与检索。据此把总览页每次加载的全部查询分为三类：

| 查询 | 频次 | 耗时 | 判定 |
| --- | --- | --- | --- |
| `count(*) FROM bd_rooms`（KPI hero 数字） | **每次页面加载** | 5.6~6.3 s | **过度查数 ★主犯**：纯展示数字却实时全表扫 730 万行，业务根本不需要对户室级做精确计数，更不需要每次加载都算 |
| `count(*) FROM bd_buildings`（KPI hero 数字） | **每次页面加载** | 0.35~0.9 s | **过度**：同上，53 万行同样只是展示数字 |
| `count(*) FROM communities WHERE is_active`（KPI + 列表 total） | 每次页面加载 ×2 | 2.5~3 ms | 合理：分页必需，2.2 万行量级成本低 |
| 列表页查询 + 每页 4 个聚合（IN 20） | 每次页面加载 | <20 ms | 合理 |
| keyword 三列 LIKE（name/address/别名） | 搜索时 | 1.7~19 ms | 合理：2.2 万行下扫全表也快；业务口径可收敛为仅小区名，属契约精简项而非性能项（见 §6.3） |
| filter-options 两条 GROUP BY | 每次页面加载 | 8~15 ms | 边际：区县/板块仅在导入/新增小区时变化，每次全量聚合略浪费，可缓存（低优先级） |
| 抽屉小区/楼栋/户室各查询 | 点击时 | 毫秒级 | 合理：全部走索引 |
| 楼栋列表 floor_counts（20 栋 distinct floor） | 点击抽屉时 | 毫秒级（索引扫描） | 合理 |

**结论：过度查数只有一处——KPI 的两个全表 COUNT。其余读路径在「2.2 万小区」业务口径下全部健康，无需改造。** 问题本质是把「展示用统计数字」当成了「实时精确检索」来做：户室总数在导入对账时就已算过一次（bd_import_tasks 对账数据），却选择在每次页面加载时对 730 万行重算。

## 5. 结论

> **「算法优化问题还是服务器配置问题？」—— 主要是算法（查询设计）问题，服务器配置是放大因子。**

- 每次页面加载对 730 万行做实时 `COUNT(*)`（KPI room_count/building_count）是错误的算法选择：数据量从 0 → 735 万后，该查询成本从几 ms 退化为 6~9s，并因 `Promise.all` 阻塞整页。
- 按「只搜 2.2 万小区名、户室不参与检索」的业务口径判定：**过度查数仅 KPI 两处，其余读路径全部健康**——把展示用统计数字当成了实时精确检索来做，而户室总数在导入对账时本就算过一次。
- 服务器 1.6G 内存 + `shared_buffers=128MB` 无法缓存 1GB 热表，把本可缓解的重复计数放大为每次都读盘的 6~9s；同时 Swap 1.2Gi 说明整机内存已超卖。
- 若只升配不修算法：页面从 ~7s 降到 ~1s，仍随数据量增长继续劣化；只修算法不升配：页面即可回到百毫秒级。优先级一目了然。

## 6. 修复建议（迭代二：按业务口径修订优先级）

### 6.1 止血（后端，改动小、见效确定）

1. **KPI 计数去实时化**（⚠️迭代二修订：原首选 reltuples 估算经实测否决——bd_rooms 估算偏差 7.5%（679.99 万 vs 735.06 万），autoanalyze 采样时导入未完全结束所致，展示可感知。修订后优先级如下）：
   - a. **首选：Redis 缓存精确计数**（后端已有 Redis）：`bd:kpi:counts` 缓存 room/building 两个精确值，TTL 10~30min；导入任务完成、小区/楼栋/户室增删时主动失效。首次 miss 用 stale-while-revalidate（先回旧值、后台重算），避免冷启动 6s。
   - b. **次选：导入对账冗余计数**：bd_import_tasks 对账阶段已算过精确户数，导入完成时将精确计数写入 kv 表/配置，KPI 直读。精度 100%，但需处理补录/删除路径的计数维护，改动面比缓存大。
   - c. **不推荐：`pg_class.reltuples` 估算**——实测偏差 7.5%；若坚持使用必须在每次导入完成后手动 `ANALYZE bd_rooms, bd_buildings`，且仍存在分析窗口期漂移。
2. **前端解耦**：KPI 与列表渲染解耦（KPI 数字用 Suspense 流式/懒加载），列表与筛选不再等 KPI——即使 KPI 首次 miss 慢，搜索与翻页也秒开。此条与 1 互相独立，可并行实施。

### 6.2 短期（服务器）

3. 提升 `shared_buffers` 至 256MB、`effective_cache_size` 下调至 1GB（贴合真实内存），并 `pg_prewarm` bd_rooms 的 PK 索引。
4. 升配到 4G+ 内存（当前 Swap 1.2Gi 已实质超卖；backend 512m 也已 85%）。

### 6.3 中长期

5. **搜索口径收窄（业务确认后实施）**：keyword 从 name/address/别名三列 OR 收敛为仅小区名单列。当前 2.2 万行下无性能收益（18.8ms vs 1.7ms，均在毫秒级），收益在于：语义更符合用户预期、避免 address 命中带来的结果噪声；且未来小区数增长到数十万时，单列可稳定走 trgm GIN 索引。
6. **filter-options 缓存**：区县/板块值域变化频率极低，加 Redis 缓存（导入/新增小区时失效），省掉每次加载的 8~15ms GROUP BY。低优先级。
7. **口径护栏**：业务明确户室/楼栋级不做检索——后续任何需求若要在 730 万户室上做关键词搜索，必须走独立方案（全文索引/搜索引擎），禁止在 PG 实时模糊扫。
8. 大表趋势监控：对 KPI 查询耗时/缓存命中加观测（呼应 SPEC-iteration3-observability）。
