# 房源数据结构报告

> 版本：v1.0 | 日期：2026-07-19 | 用途：数据团队设计数据报表模块的核心依据

---

## 一、报告概述

### 1.1 报告目标

本报告对 Profo 项目中所有与"房源"相关的数据结构进行全面、深入的调研与分析,包括但不限于:

- **房源基础信息**:市场层房源(Property)与小区(Community)的核心数据
- **业务层房源信息**:项目管理(Project)及其全生命周期业务数据
- **属性特征**:户型、面积、楼层、价格、装修、媒体资源等
- **状态分类**:房源状态、项目状态、改造阶段、合同状态、销售状态等枚举体系
- **关联数据**:业主、跟进、合同、装修、销售、财务、互动、文书、营销等
- **数据来源**:贝壳/链家/网签数据导入、手工录入、C端线索提交
- **历史快照**:房源价格/状态变更的历史记录

本报告为数据团队设计数据报表模块提供核心依据,确保字段定义、类型、取值范围、业务含义与关联关系的准确性、完整性与规范性。

### 1.2 数据架构总览

项目采用分层的数据架构,自下而上分为四层:

```
┌─────────────────────────────────────────────────────────────┐
│  L4 营销层 (Marketing)                                       │
│  L4MarketingProject / L4MarketingMedia                       │
│  - 营销展示、案例作品集                                         │
├─────────────────────────────────────────────────────────────┤
│  L3 业务层 (Project)                                          │
│  Project / ProjectOwner / ProjectContract / ProjectSale      │
│  ProjectRenovation / ProjectFollowUp / ProjectEvaluation     │
│  ProjectInteraction / FinanceRecord / ProjectStatusLog       │
│  ProjectDocument / RenovationPhoto / Investment / Investor   │
├─────────────────────────────────────────────────────────────┤
│  L2 线索层 (Lead)                                             │
│  Lead / LeadFollowUp / LeadPriceHistory                      │
│  - C端用户提交的房源线索                                        │
├─────────────────────────────────────────────────────────────┤
│  L1 市场层 (Market)                                           │
│  PropertyCurrent / PropertyHistory / PropertyMedia           │
│  Community / CommunityAlias / CommunityCompetitor             │
│  - 外部房源数据(贝壳/链家等)与小区基础数据                       │
└─────────────────────────────────────────────────────────────┘
```

| 层级 | 业务定位 | 主要数据来源 | 数据规模(参考) |
|------|---------|------------|---------------|
| L1 市场层 | 外部房源原始数据 | 贝壳/链家/网签数据导入 | ~25,000 条 |
| L2 线索层 | C端用户提交的待评估房源 | C端用户提交、手工录入 | ~10 条 |
| L3 业务层 | 公司签约后管理的房源(项目) | 后台手工创建 | ~10 条 |
| L4 营销层 | 房源营销展示与案例作品集 | 后台手工创建 | ~10 条 |

### 1.3 数据库与技术栈

- **数据库**:PostgreSQL(主)+ Redis(OAuth state、临时缓存)
- **ORM**:SQLAlchemy 2.0(同步 Session)
- **数据验证**:Pydantic v2
- **Schema 变更**:`backend/migrations/__init__.py` 启动迁移脚本(幂等)
- **关联策略**:逻辑外键(`project_id`/`community_id` 等 String 列),级联由 Service 层处理;PostgreSQL 物理外键由数据库强制
- **加密策略**:`EncryptedString` 自定义类型基于 Fernet 自动加解密,用于业主电话、身份证号、银行卡号等敏感字段

## 七、数据来源与数据流

### 7.1 房源数据来源

  3. 字段映射 → `PropertyIngestionModel` 校验
  4. 小区查找或创建(`Community` + `CommunityAlias`)

- **入口**:C端 `/valuation` 路由 → `Lead` 表

## 八、状态流转与业务流程

### 8.1 房源状态流转(L1 市场层)

```
┌────────┐  上架   ┌────────┐  成交   ┌────────┐
│ 未导入  │ ────→  │ 在售   │ ────→  │ 成交   │
└────────┘        └────────┘        └────────┘
                     │
                     │ 30天未更新
                     ▼
                  ┌────────┐
                  │ 过期   │ (派生状态,不入库)
                  └────────┘
```

**说明**:
- `PropertyStatus` 枚举仅含 `在售`/`成交` 两种
- `过期` 为派生状态,由响应层 `_compute_display_status` 根据 `updated_at` 计算(30天阈值)
- 历史快照通过 `PropertyHistory.change_type` 记录变更类型

### 8.2 线索状态流转(L2 线索层)

```
┌──────────────────┐  评估通过   ┌──────────────┐  看房完成   ┌──────────┐  签约   ┌────────┐
│ pending_assessment │ ────────→ │ pending_visit │ ────────→ │ visited  │ ─────→ │ signed │
└──────────────────┘            └──────────────┘            └──────────┘        └────────┘
         │                            │
         │ 评估驳回                    │ 看房后驳回
         ▼                            ▼
    ┌──────────┐                ┌──────────┐
    │ rejected │                │ rejected │
    └──────────┘                └──────────┘
```

### 8.3 项目状态流转(L3 业务层)

```
┌─────────┐  签约完成  ┌──────────────┐  装修完成  ┌─────────┐  确认成交  ┌──────┐  软删除  ┌─────────┐
│ signing │ ────────→ │ renovating   │ ────────→ │ selling │ ────────→ │ sold │ ───────→ │ deleted │
└─────────┘          └──────────────┘          └─────────┘          └──────┘          └─────────┘
                          │
                          │ 子阶段流转(renovation_stage)
                          ▼
                  ┌──────────────────────────────────────┐
                  │ 拆除 → 设计 → 水电 → 木瓦 → 油漆 → 交付 → 已完成 │
                  └──────────────────────────────────────┘
```

**状态流转日志**:每次状态变更生成 `ProjectStatusLog` 记录,含 `old_status`/`new_status`/`trigger_event`/`operator_id`

### 8.4 资金账本结算状态

```
┌────────────┐  结算(含日期+说明)  ┌───────┐  反结算(需原因)  ┌────────────┐
│ unsettled │ ─────────────────→ │ settled │ ←───────────── │ unsettled │
└────────────┘                    └───────┘                  └────────────┘
```

## 十、敏感数据与安全约束

### 10.1 加密字段

使用 `EncryptedString` 类型([backend/models/common/encrypted.py](file:///Users/bugco/Desktop/profo/backend/models/common/encrypted.py))基于 Fernet 自动加解密:

| 表 | 字段 | 业务含义 |
|----|------|---------|
| `project_owners` | `owner_phone` | 业主联系方式 |
| `project_owners` | `owner_id_card` | 业主身份证号 |
| `project_owners` | `bank_card_number` | 银行卡号 |

**特点**:写入时自动加密,读取时自动解密,对 Service 层透明。底层存储为 Text,Fernet 密文为 base64 编码。

### 10.2 软删除策略

所有业务表使用 `is_deleted` 字段(Boolean,默认 False)进行逻辑删除,查询时统一过滤 `is_deleted = false`。`Investment` 表使用 `deleted_at`(DateTime,可空)标记软删除时间。

### 10.3 软引用(逻辑外键)

所有跨表关联使用 String 类型字段存储 ID,无数据库物理外键约束。级联操作由 Service 层处理。例如:
- `Project.community_id` → `Community.id`
- `ProjectOwner.project_id` → `Project.id`
- `Lead.source_property_id` → `PropertyCurrent.id`(注意类型为 Integer)
- `FinanceRecord.operator_id` → `User.id`

### 10.4 时间字段统一规范

- 时间戳字段统一使用 `DateTime(timezone=True)`,避免时区 stripping
- 日期字段(如 `commission_start_date`)使用 `Date` 类型
- 业务日期字符串(如 `archive_date`)使用 `String(10)` 存储 `YYYY-MM-DD` 格式

### 12.3 数据质量注意事项

报表设计时需注意以下数据质量约束:

1. **软删除过滤**:所有业务表查询需过滤 `is_deleted = false` 或 `is_active = true`
2. **NULL 处理**:`Numeric` 字段大量为 NULL,聚合时需使用 `COALESCE` 或过滤
3. **时区统一**:时间戳字段为 `DateTime(timezone=True)`,报表需统一时区(UTC 或 Asia/Shanghai)
4. **派生字段**:`unit_price`、`display_status` 等派生字段不入库,需在 SQL 或应用层计算
5. **金额单位差异**:
   - `property_current.listed_price_wan` / `sold_price_wan`:万
   - `finance_records.amount`:元
   - `contract.signing_price`:万
   - 报表需统一单位(推荐统一为元)
6. **加密字段**:`owner_phone`/`owner_id_card`/`bank_card_number` 等敏感字段在数据库为密文,报表场景应避免直接展示或仅展示脱敏数据
7. **逻辑外键完整性**:由于使用逻辑外键,可能出现孤立记录(子表存在但主表已删除),报表需用 LEFT JOIN 并处理 NULL
8. **数据规模差异**:L1 市场层数据量约 25,000 条,L2/L3 层数据量 < 100 条,报表设计需考虑数据稀疏性

### 12.4 推荐数据接入方式

1. **只读副本**:建议报表查询使用 PostgreSQL 只读副本,避免影响业务
2. **物化视图**:对高频查询(如小区均价、区域分布)可创建物化视图定期刷新
3. **预聚合**:对大数据量分析(如价格趋势)可按月/区域预聚合
4. **API 复用**:复用 [backend/routers/market/properties.py](file:///Users/bugco/Desktop/profo/backend/routers/market/properties.py) 已有的筛选/导出能力
5. **CSV 导出**:已有 `/properties/export` 接口,可直接复用其字段格式
