### 2.2 逐条需求明细

#### REQ-IT1-01 「新增公司」入口必须在搜索之后才出现

**来源原文**：所属公司必须搜索后再出现新增公司按钮，避免操作者图方便全部新建增加审核工作量。

**现状与根因**
- `miniapp/pages/merchant/store/create/index.wxml:29-31`：`＋ 新增公司` 链接**常显**，与是否搜索过无关；`companySearched` 仅用于第 28 行的「未找到，可新增公司」空态提示。
- 后端已按「必须搜索」设计：`backend/services/merchant/company.py:43-45` 空关键词直接返回空列表（不发起全量查询），因此未搜索时列表本就为空，但用户仍能直接点开新增表单——与「避免全量新建」的初衷相悖。

**期望行为（可判定）**
1. `companySearched === false`（本次进入页面后尚未成功搜索）时，不渲染 `＋ 新增公司` 入口，也不渲染新增公司表单。
2. 搜索成功返回**任意结果数**（含 0 条）后，入口出现；0 条时同时显示「未找到，可新增公司」。
3. 重新搜索时重置：`showCompanyCreate` 收起、表单输入清空（避免旧输入被带进新关键词场景）。
4. 已选中公司（`selectedCompany` 非空）或编辑模式（`mode === 'edit'`）时不显示搜索区与新增入口（现状已是 `selected-row`，保持）。
5. 点「更换」清空已选公司后，回到「未搜索」初态（入口再次隐藏）。

**落点文件**
- `miniapp/pages/merchant/store/create/index.wxml`（公司区块 8-39 行）
- `miniapp/pages/merchant/store/create/index.ts`（`onSearchCompany` 231-246、`onSelectCompany` 248-255、`onClearCompany` 257-259、`onToggleCompanyCreate` 261-263）

**不在本期范围**：`miniapp/pages/merchant/broker/store-create/index.wxml:27-30` 经纪人自建店页**没有**新增公司入口（只有选择），行为已符合本需求意图，不改。

**验收标准**
- 首次进入页面：公司区块只有搜索框 + 「搜索」按钮，无「新增公司」。
- 搜索「绝对不存在的公司名」→ 出现「未找到，可新增公司」且「新增公司」可点。
- 搜索有结果 → 出现「新增公司」；选中某公司后入口消失；点「更换」后入口消失直到再次搜索。

**验证方式**：微信开发者工具 + 三步操作截图（未搜索 / 搜索无结果 / 搜索有结果）+ 选中与更换后各一张。

#### REQ-IT1-02 新增公司时「创建并选择」按钮超出屏幕宽度

**来源原文**：新增公司时，创建并选择按钮超出屏幕宽度。

**现状与根因（样式计算，已核对源码）**
- `miniapp/pages/merchant/store/create/index.wxss:81-95`：`.mini-btn { padding: 0 32rpx }` 未声明 `box-sizing`（WXSS 默认 `content-box`），`.mini-btn--full { width: 100% }`。
  → 实际占宽 = 容器宽 + 64rpx，横向溢出 64rpx。
- 同类隐患：`.section`（`index.wxss:26-33`）同样未声明 `box-sizing`，而 `.page` 设了 `padding: 32rpx 32rpx`（`index.wxss:1-5`、`box-sizing: border-box`）。
  → 卡片自身已吃掉页面左右各 32rpx 内边距，卡片内的 100% 宽度按钮进一步顶到屏幕边缘，视觉即「超出屏幕」。
- 附带小缺陷：`.company-create` 用 `gap: 16rpx`（`index.wxss:143-147`），按钮又带 `margin-top: 16rpx`，间距被叠加成 32rpx。

**期望行为（可判定）**
1. 按钮左右边界不超出所在的白色卡片内边距；页面右侧不出现横向滚动/裁切。
2. 375pt（iPhone SE）与 393pt（iPhone 14 Pro）两种宽度均满足第 1 条。
3. 修复方式限定为 `box-sizing: border-box` 补齐 + 去除重复 `margin-top`，**不引入魔法数值**。

**落点文件**：`miniapp/pages/merchant/store/create/index.wxss`（`.mini-btn` 81-91、`.mini-btn--full` 92-95、`.section` 26-33、`.company-create` 143-147）

**验收标准**：新增公司表单展开后，按钮右侧留白 ≥ 卡片内边距（32rpx）；两种机型截图右侧无裁切。

**验证方式**：修复前后同机型截图对比（iPhone SE / iPhone 14 Pro 各一组），并在截图旁标注实测按钮宽度与容器宽度（开发者工具 Wxml 面板）。

#### REQ-IT1-03 门店信息去掉省/市字段（小程序 + 后台一致）

**来源原文**：门店信息不需要省市字段（admin 管理后台同理）。

**现状**
- 小程序表单：`index.wxml:48-61` 省/市/区县三个并列输入框；默认值 `上海市 / 上海市 / 浦东新区`（`index.ts:119-133`）；提交前强校验 `index.ts:409-411`；编辑回填 `index.ts:194-208`；创建/编辑请求体 `index.ts:481-490`、`513-521` 均发送 `province`/`city`。
- 后台表单：`frontend/src/app/(main)/admin/merchant/stores/new/page.tsx:339-347` 「省份」「城市」两个必填 Input；`FormState` 含 `province`/`city`，默认值同小程序（47-62）。
- 后端契约与存储：`backend/schemas/merchant/__init__.py:72-73` 必填；`backend/models/merchant/store.py:34-35` 为 `NOT NULL` 列；服务层写入 `backend/services/merchant/store.py:228-229`，列表筛选 344-347，审计快照与「省份/城市」变更留痕 507-508、608-609、872-873，CSV 导出 1303-1304。
- 经纪人自建店页也有省/市/区县自由输入：`miniapp/pages/merchant/broker/store-create/index.wxml:29-32`。

**期望行为（可判定）**
1. 小程序门店建档/编辑表单不再出现省、市输入项；校验提示不再要求省市区。
2. 后台上建/编辑门店表单不再出现「省份」「城市」输入项。
3. 提交给后端的 `province`/`city` 要么不再发送，要么由后端按统一规则补齐——**两端行为必须一致**，不允许前端硬编码默认值散落多处。
4. 历史数据、列表筛选、导出、审计留痕不得因字段隐藏而报错或丢失。

**方案决策（2026-11-01，Q1=A）**：采用方案 A——DB 列保留、接口改可选、后端统一补齐，前端两端隐藏字段。
- 方案 A（已采用）：DB 列保留，`MerchantStoreCreate/Update` 的 `province/city` 改为可选，由后端按统一常量（如系统所在城市）补齐；前端完全不再出现该字段。
- 方案 B（未采用）：彻底下线省市（含模型/迁移/报表/导出），成本高、风险大。
- 方案 C（未采用）：省市由「区域→省市」映射表自动推导。**现状不支持**：`backend/models/property/community.py:35-36` 只有 `city_id`(int) 与 `district`，无省市名称；未找到 City 模型，需新增主数据，超出本期范围。

#### REQ-IT1-04 地图选点上移 + 自动回填区域 + 区域/商圈改为系统列表选择

**来源原文**：地图选点放到门店名称和区域-商圈之间，选择后自动填入区域字段，而商圈由用户手动选择，另外区域商圈直接从系统的区域-商圈列表中选择而不是填写，避免手填错误。

**现状**
- 字段顺序（`index.wxml`）：门店名称 44-47 → 省/市/区县 48-61 → 商圈 62-71 → 详细地址 72-75 → 地图选点 76-85 → 联系人 86-95。
- 选点逻辑 `index.ts:306-320`：仅回填 `address`（`res.address + res.name`）、`lng`、`lat`，**不回填区域**。
- 区域/商圈均为自由文本输入；商圈另有「加载建议」按钮拉取候选 chip（`index.wxml:62-71`、`index.ts:322-337`），但输入框依然手填。
- 候选来源：`MerchantStoreService.business_circles`（`backend/services/merchant/store.py:1199-1213`）= 小区表 `Community.business_circle`（按 district 过滤）+ 已建门店商圈兜底，去重排序取前 30。
- **缺失能力**：商户端没有「区域（district）字典」接口，只有 `GET /public/merchant/business-circles`（`backend/routers/merchant/public.py:224-233`）与 `GET /admin/merchant/business-circles`（`backend/routers/merchant/admin.py:711-721`）。系统级字典接口 `GET /market/communities/dictionaries?dict_type=district|business_circle`（`backend/routers/market/communities.py:62-73`）需 `property:read` 权限，商户员工/经纪人不可用。

**期望行为（可判定）**
1. 字段顺序调整为：**门店名称 → 地图选点 → 区域 → 商圈 → 详细地址 → 联系人/电话 → 合作状态**（小程序与后后台一致）。
2. 地图选点成功后：自动回填区域（命中时）；`lng/lat` 与详细地址仍回填；区域命中失败时**不阻断**，提示用户手动选择区域。
3. 区域只能从系统区域列表中选择（picker/Select），不可手填；商圈在区域选定后才能选择，选项来自该区域的系统商圈列表。
4. 切换区域时清空已选商圈（避免跨区域错配）。
5. 商圈必填校验保持；「商圈必须来自列表」按 §4-Q3 默认口径执行：**仅前端约束**，后端保留自由值以兼容历史数据与经纪人流程（如评审改为后端强校验，需同步评估历史脏数据 422 风险）。
6. 加载中/空列表/接口失败三态：区域列表为空或接口失败时给出可理解的提示与重试，不得让用户卡死（DESIGN.md 空/载/错状态要求）。

**实现方案（区域回填）决策（2026-11-01，Q2=A）**：采用方案 A——地址文本匹配系统区域字典，失败降级手动选择。
- 方案 A（已采用）：**地址文本匹配系统区域字典**。新增 `GET /public/merchant/districts`（`MerchantCReadDep`）与 `GET /admin/merchant/districts`，返回系统区域字典（`Community.district` 去重）；选点后用 `res.address` 匹配字典项中最长的区县名，命中即回填。零新依赖、零新 Key，失败降级为手动选择。
- 方案 B（未采用）：后端新增逆地理代理 `GET /public/merchant/regeo?lng&lat` 调高德 Web 服务。**现状不满足**：系统只配置了 JS API Key（`backend/services/system/amap_config.py:14-15` 的 `amap_js_key` / `amap_security_js_code`），Web 服务 Key 需另行开通并新增系统配置项与配额管理。
- 方案 C（未采用）：小程序直连高德 Web 服务。不推荐：需在小程序后台配置 request 合法域名，且会把 Web 服务 Key 暴露到客户端。

#### REQ-IT1-BUG-01 门店建档页「地图选点」未弹出地图，直接提示失败

**状态**：待验收（代码已改，等待真机/开发者工具复测 errMsg 定因）
**来源原文（2026-11-01）**：`miniapp/pages/merchant/store/create/index` 的地图选点并没有弹出地图而显示「地图选点失败请重试」，小程序已经开通了 wx.chooseLocation 权限。

**症状**：点击「地图选点」后地图选点页未打开，立刻出现 toast「地图选点失败，请重试或检查定位权限」。说明 `wx.chooseLocation` 的 `fail` 回调被立即触发，而非用户取消。

**现状与根因**
- 原实现 `miniapp/pages/merchant/store/create/index.ts:306-320` 的 `fail` 回调**完全丢弃 `errMsg`**，统一 toast 固定文案 → 现场无法判断属于哪一类失败。这是本次首先要消除的「不可观测」问题。
- 隐私侧：`miniapp/app.json` 已配 `"requiredPrivateInfos": ["getLocation","chooseLocation"]`、`"permission":{"scope.userLocation":...}`、`"__usePrivacyCheck__": true`；`miniapp/pages/login/index/index.wxml:18-33` 用 `<button open-type="agreePrivacyAuthorization">` 收集同意。**但《用户隐私保护指引》中的「位置信息」声明属于小程序后台配置，代码内不可见/不可验证** —— 本项目既有调研结论（`docs/Done/2026-10-06-小程序微信授权体系调研报告.md:85`）已记录「位置类…使用需在隐私指引声明 scope，**当前未声明则调用会被平台直接禁用**」，因此这是当前第一优先怀疑项：指引未声明「位置信息」→ 平台直接禁用 `chooseLocation`，表现为「不弹地图、立即失败」。
- 授权侧：全仓无 `wx.openSetting` 引导，用户曾拒绝 `scope.userLocation` 后无法在页内恢复（`auth deny` 只会得到同一句文案）。
- 平台侧：小程序后台「开发管理-接口设置」的位置接口是否开通、开发者工具是否支持地图选点，均需实测确认（工具端不支持属已知限制，应以真机为准）。

**本次改进（诊断 + 恢复，不猜具体故障）**
1. 新增 `miniapp/utils/location.ts`：`chooseMapLocation(): Promise<ChosenLocation | null>`
   - 预检 1：`wx.getPrivacySetting().needAuthorization === true` → 弹窗「需先同意隐私保护指引」，确认后 `wx.openPrivacyContract()`；
   - 预检 2：`wx.getSetting().authSetting["scope.userLocation"] === false` → 弹窗引导「去设置」，确认后 `wx.openSetting()` 并复查；
   - `wx.chooseLocation` 的 fail 按 `errMsg` 分流：`cancel` 静默不提示；`privacy` → 隐私指引弹窗；`auth deny/authorize` → 授权设置弹窗；`requiredPrivateInfos/not declared/not support/system permission/invalid scope` → 明确列出三项配置检查；其余 → 把原始 `errMsg` **复制到剪贴板**并弹窗展示（可截图反馈）；
   - 所有 fail 均 `console.error("[chooseLocation] 失败", errMsg, err)` 留痕；开发者工具下附加「模拟器可能不支持，请真机复测」提示。
2. 两个调用点改为复用该封装（同语义、两处消费，符合抽取条件）：`miniapp/pages/merchant/store/create/index.ts`（`onChooseLocation`）与 `miniapp/pages/merchant/broker/store-create/index.ts`（`onChooseLocation`，原「未选择位置」吞错同样被替换）。
3. 地址拼接口径统一为 util 内的「`res.address` + 空格 + `res.name`」（原建档页口径），经纪人建店页随之统一（原为 `res.address || res.name`，会丢兴趣点名）。

**验收标准**
1. 正常授权且指引已声明位置信息时：点击即打开地图选点页，选中后地址/经纬度回填。
2. 用户取消选点：无任何错误提示。
3. 位置权限被拒：出现「位置权限未开启 + 去设置」弹窗，开启后再次点击可选点。
4. 隐私未通过：出现隐私指引弹窗，可打开协议页。
5. 其他失败：弹窗展示**真实 errMsg** 并已复制到剪贴板（据此可定位是配置还是平台限制）。

**验证方式**
- 静态：`pnpm --prefix miniapp tsc`（`tsc --noEmit`）零错 —— 已通过。
- 动态（待人工执行，真机优先）：真机 + 开发者工具各点一次选点，记录 §「期望得到的 errMsg 对照」结果，工件放 `docs/商户管理模块需求/verification/2026-11-01-迭代1/`。
- **errMsg 对照（用于定因，实施方不必二次猜）**：

| errMsg 关键词 | 含义 | 处置方 |
|---|---|---|
| `privacy permission is not authorized` / 含 `privacy` | 隐私指引未同意，或指引未声明「位置信息」 | 小程序后台《用户隐私保护指引》勾选「位置信息」并提交审核通过 |

- **现状与根因**：`.btn-primary`/`.btn-secondary` 是 `display: inline-flex` + 固定左右 padding 且**未声明 `box-sizing`**；页面用 `.footer__btn { width: 100% }` 拉满宽度时，实际宽度 = 容器宽度 + 左右 padding，右侧被裁掉，文字在超宽盒子里居中即表现为「偏左」。与迭代 1 的 `.mini-btn`（REQ-IT1-02）是同一类缺陷。`.footer` 本身是块级容器，未做 flex 居中。
- **期望行为**：按钮类统一 `box-sizing: border-box`；footer 容器 `display:flex; justify-content:center`，按钮 `flex:1` 撑满并保持居中；覆盖 `miniapp/pages/merchant/{home,agreement/list,visit/create,store/create}` 四个带底部主按钮的页面。
- **落点文件**：`miniapp/app.wxss`、`miniapp/pages/merchant/{home,agreement/list,visit/create,store/create}/index.wxss`
- **验收标准**：按钮在底部占满安全区且文字水平居中；小屏（375pt）不出现右侧裁切；无横向滚动。

#### REQ-IT4-02 门店列表按距离由近到远 + 进入/刷新重新定位

- **来源原文**：「门店列表排序应该按照距离从近到远，第一次打开页面或者点击刷新后会更新设备位置来刷新列表」
- **现状与根因**：首页 `loadStores()` 只传 `page/page_size/keyword`，后端 `MerchantStoreService.search` 固定 `order_by(updated_at.desc())`；`MerchantStoreListItem` 无 `lng/lat/distance_m`，前端无从排序；页面也从未调用 `wx.getLocation`。
- **期望行为**：
  1. 后端 `GET /public/merchant/stores` 新增可选 `origin_lng`/`origin_lat`，传入时用 SQL 侧 Haversine 表达式 `ORDER BY distance ASC NULLS LAST, updated_at DESC`（只在当前页内存排序会让翻页顺序错乱），列表项回填 `distance_m`；
  2. 小程序首次进入、下拉刷新、点「刷新」时先 `wx.getLocation({type:"gcj02"})` 再带原点请求；定位被拒/隐私未同意时不打断用户，回退默认排序；
  3. 卡片展示距离（`<1000m` 显示 `xxxm`，否则 `x.xkm`）。
- **落点文件**：`backend/schemas/merchant/__init__.py`、`backend/services/merchant/{store,serializers}.py`、`backend/routers/merchant/public.py`、`miniapp/utils/location.ts`、`miniapp/pages/merchant/home/index.{ts,wxml,wxss}`
- **验收标准**：带原点查询返回的距离严格升序（无坐标门店排最后且 `distance_m` 为空）；不带原点时 `distance_m` 全为 `null` 且保持 `updated_at` 倒序；小程序定位失败时列表仍可用。

#### REQ-IT4-03 补录照片「加载失败」

- **来源原文**：「补录照片时，显示加载失败」
- **现状与根因**：本地 `.env` 为 `STORAGE_BACKEND=oss` + `OSS_ENDPOINT=oss-cn-shanghai-internal.aliyuncs.com`（阿里云**内网**端点）。实测 `POST /api/v1/public/files/upload` → `400 {"code":400,"message":"文件上传失败，请稍后重试"}`；直接调存储层 `OSSStorage.upload_file` → `ServerError {'status': 502, ...}`。小程序端上传失败后取 `errMessage()` 兜底文案，即用户看到的「加载失败」。
- **期望行为**：本地开发改用本地存储（`STORAGE_BACKEND=local`，`UPLOAD_DIR` 指向仓库内 `backend/static/uploads`），返回相对 URL `/static/uploads/...` 并可由 `/static` 静态挂载访问；生产环境的 OSS 配置不动。
- **落点文件**：根 `.env`（gitignore，不入库）
- **验收标准**：上传返回 `url` 以 `/static/uploads/` 开头且 `curl` 该地址 200；门店详情补录照片成功并回显。

#### REQ-IT4-04 拜访时间线实时刷新

- **来源原文**：「登记拜访后，拜访时间线中的记录没有实时刷新」
- **现状与根因**：`miniapp/pages/merchant/store/detail/index.ts` 只在 `onLoad` 里 `loadAll()`，从拜访登记页返回时页面重新可见但不会重新拉数据（无 `onShow`）。
- **期望行为**：详情页改为 `onLoad` 只解析参数，`onShow` 负责加载：首次进入加载一次，之后每次重新可见都**静默刷新**（不清空内容、不闪「加载中」，失败只 toast 不整页报错）。
- **落点文件**：`miniapp/pages/merchant/store/detail/index.ts`
- **验收标准**：登记拜访返回后时间线立即出现新记录；返回时页面不闪 loading；接口失败时保留旧内容并提示。

#### REQ-IT4-05 合作状态可选项由后端裁决

- **来源原文**：「合作状态变更时，没有状态可选」
- **现状与根因**：前端用 `me?.role?.code` / `me?.additional_roles` 判断是否为管理员，但 `/public/auth/me` 返回的 `PublicUserInfo` 只有 `permissions/is_internal`，**没有 role 字段** → `privileged` 恒为 false → 只保留 `negotiating`；若门店当前状态已是「洽谈中」又被「排除当前状态」过滤掉 ⇒ 弹层里一个选项都没有。同时前端还在复制后端的权限规则（已合作需已签协议等），规则漂移风险高。
- **期望行为**：后端新增 `GET /public/merchant/stores/{store_id}/status-options`，返回 `current_status`、`current_status_label`、`items[{code,label}]`、`reason`；由后端按角色范围（`ensure_scope_role`）、当前状态、是否已签协议裁决；小程序改为消费该端点，无选项时打开弹层前直接 toast 展示 `reason`。
- **落点文件**：`backend/schemas/merchant/__init__.py`、`backend/services/merchant/store.py`、`backend/routers/merchant/public.py`、`miniapp/pages/merchant/store/detail/index.{ts,wxml}`
- **验收标准**：任意当前状态下的门店，弹层至少有一个可选项（除非后端明确给出 `reason`）；可选项与字典一致且不含当前状态；员工角色只出现「洽谈中」；已合作需已签协议才出现。

#### REQ-IT4-06 表单主操作按钮不贴左（「提交审核」偏左）

- **来源原文**：「pages/merchant/agreement/create/index 提交审核按钮还是偏左」（m02429）
- **现状与根因**：`<button class="btn-primary submit-btn">` 所在页面的 `.submit-btn` 只声明了 `margin-top`，**没有 width，也没有居中**。`.btn-primary` 是 `display: inline-flex`（行内级），在块级父容器（`.card`）里按内容收缩成胶囊后贴着左侧基线排布 —— 这与 REQ-IT4-01 的「width:100% + 缺 box-sizing 导致溢出裁切」不是同一个成因，REQ-IT4-01 的全局 box-sizing 修不到它。
- **同模式受影响页面**（全仓扫描确认共 4 个，均为商户端表单页）：`miniapp/pages/merchant/agreement/create/index.wxss`、`miniapp/pages/merchant/agreement/sign/index.wxss`、`miniapp/pages/merchant/broker/index.wxss`、`miniapp/pages/merchant/broker/store-create/index.wxss`。
- **不受影响但同名的页面**（已确认无需改动）：`pages/bind-account/index`（`margin: 12rpx auto 0` 居中）、`pages/profile/index`（`margin: 32rpx auto 0`）、`pages/login/password`（父级 `align-items: center`）、`pages/valuation/submit`（`.submit-wrap { justify-content: center }`）、`pages/about/index`（hero 内左对齐是设计意图）。
- **期望行为**：4 个商户端表单页的 `.submit-btn` 显式声明 `display: flex; width: 100%`，按钮铺满父容器、文字在整行内居中。
- **落点文件**：上述 4 个 `index.wxss`；回归守卫 `frontend/e2e/merchant-iteration4.spec.ts`（新增全仓扫描用例）。
- **验收标准**：`.submit-btn` 宽度 = 父容器内容宽度、按钮四角不越界；全仓自动扫描不再出现「`btn-primary submit-btn` 且既无 `width: 100%`/`margin auto`、外层容器也未居中」的页面。

### 11.2 需求明细

#### REQ-IT5-01 合作状态与协议解耦

- **来源原文**：「合作状态没有包含 admin/settings/dicts 中的所有状态，这个不应该和协议签署之类的耦合在一起」
- **现状与根因**：`MerchantStoreService.change_cooperation_status` 对 `target == cooperated` 强制校验 `_has_signed_agreement(store.id)`，失败即 `ValidationError("改为已合作前必须先签署电子合作协议")`；`cooperation_status_options` 同样把「已合作」从候选中剔除。结果是：运营手工确认线下已签约门店无法标记「已合作」，且门店状态候选随协议数据波动（曾出现「没有状态可选」）。
- **期望行为**：候选＝字典 `merchant_cooperation_status` 的启用项（排除当前状态）；「已合作」不再要求已签协议；员工角色仍只可改为「洽谈中」（权限规则，不属于协议耦合）。
- **落点文件**：`backend/services/merchant/store.py`
- **验收标准**：①运营把「未合作」门店改为「已合作」返回 200 且状态落库；②`status-options` 在门店为「已合作」时仍返回其他字典状态；③员工（user 角色）改非「洽谈中」仍被拒绝。
- **验证方式**：`e2e/merchant-iteration5.spec.ts`（REQ-IT5-01 用例）+ `pytest tests/test_merchant_store_visit.py::test_employee_status_permission_and_decoupled_from_agreement`。

#### REQ-IT5-02 协议「全部」包含新发起的待签署

- **来源原文**：「pages/merchant/agreement/list/index 门店协议全部协议没有包含待签署的协议」
- **现状与根因**：列表页只在 `onLoad` 调 `load()`，没有 `onShow`；员工在发起页提交后 `navigateBack` 回列表，页面实例复用、不重新请求，新发起的 `pending_sign` 记录不出现。后端筛选实测正常（不带 `status` 时 `total=2`，含 `pending_sign`）。
- **期望行为**：从发起页返回列表即刷新，新协议出现在「全部」。
- **落点文件**：`miniapp/pages/merchant/agreement/list/index.ts`
- **验收标准**：①`onShow` 存在且会重新拉取；②首帧不与 `onLoad` 重复请求；③静默刷新不闪 loading。
- **验证方式**：`e2e/merchant-iteration5.spec.ts`（源码断言）+ 真机复测（见工件 §4）。

#### REQ-IT5-03 取消审核，商户凭分享码自助签署

- **来源原文**：「签署流程太复杂需要简化，原则上协议是格式条款，所以签署不需要审核，只要员工发起，填入商户信息，然后分享给商户，商户打开小程序链接进入后核对信息然后签署提交，员工侧看到已完成签署即可」
- **现状与根因**：发起后 `status=not_initiated` + `review_status=pending`，必须运营在后台「通过」后才变 `pending_sign`；签署依赖 `merchant:agreement` 权限（商户无）；详情页只展示审核状态，没有面向商户的签署入口。
- **期望行为**：①员工发起即 `pending_sign` 并生成 `sign_code`；②后台/小程序不再有审核入口与文案；③详情页可「分享给商户签署」（微信分享 + 复制路径）；④商户微信登录后打开链接，核对协议正文/主体后勾选确认并手写签名提交；⑤签署成功即 `signed`，并自动把门店改为「已合作」（Q13）；⑥重复签署/错误分享码被拒绝。
- **落点文件**：`backend/models/merchant/agreement.py`、`backend/schemas/merchant/agreement.py`、`backend/services/merchant/agreement.py`、`backend/routers/merchant/agreement_sign.py`（新增）、`backend/routers/merchant/agreement_admin.py`、`backend/dependencies/auth.py`、`backend/services/notification/events.py`、`backend/migrations/_merchant_agreement_no_review.py`（新增 v116）、`frontend/src/app/(main)/admin/merchant/agreements/{page.tsx,[id]/page.tsx}`、`miniapp/pages/merchant/agreement/{create,detail,list,sign}/**`、`miniapp/pages/merchant/agreement/merchant-sign/**`（新增）、`miniapp/app.json`

#### REQ-IT5-04 发起协议签署人从门店经纪人中选择

- **来源原文**：「pages/merchant/agreement/create/index 的签署人也应该是从门店的经纪人中选择，而不是手动填写」（m03051）
- **现状与根因**：发起页 `signerName` 是自由输入框，默认取门店 `contact_name`（门店联系人，不一定是经纪人）；员工可填任意姓名，签约主体与门店实际经纪人无关，且与拜访登记页（REQ-IT2-03 已改经纪人选择）口径不一致。
- **期望行为**：①选中门店后拉该门店经纪人列表，用 picker 选择签署人并回填姓名；②经纪人手机号在接口侧只有脱敏值（`phone_masked`），因此手机号仍由员工手填，默认沿用门店联系电话并给出提示；③门店暂无经纪人（或接口失败）时退回手填，不阻断发起；④顺带清掉该页残留的审核口径（副标题「提交后由运营审核」与按钮「提交审核」）。

#### REQ-IT5-05 发起页支持直接补录门店经纪人

- **来源原文**：「门店如果没有签署人，应该支持在这个页面直接添加经纪人，以便流程继续推进」（m03196）
- **现状与根因**：REQ-IT5-04 让签署人来自门店经纪人，但门店没有经纪人时只能手填姓名——签署人无法进入经纪人台账，后续绑店、二维码、`BrokerResponse` 关联都缺失；而给门店补经纪人的既有入口只有「后台新建经纪人」（`POST /admin/merchant/brokers`，需 `merchant:broker` 权限）与「二维码扫码自注册」，员工在发起页无法补齐，流程中断。
- **期望行为**：①门店无经纪人时，签署人区块下方出现「＋ 新增门店经纪人」，点击弹出补录表单（姓名 + 手机号）；②提交后立即绑定到当前门店并成为本次签署人，picker 自动选中、签署人手机号回填为刚录入的真实号码；③手机号唯一（哈希）：已在本店 → 409「该经纪人已在本门店」，已绑定他店 → 409「该手机号已绑定其他门店，请走换绑流程」，档案已停用 → 400「该经纪人档案已停用，请联系运营」，未绑定的存量档案直接绑到本店；④员工只能给可见门店补录（`ensure_store_visible`），写操作落审计 `merchant_broker`。
- **落点文件**：`backend/schemas/merchant/broker.py`（`BrokerStoreCreate`）、`backend/services/merchant/broker.py`（`create_for_store`）、`backend/routers/merchant/public.py`（`POST /public/merchant/stores/{store_id}/brokers`）、`miniapp/pages/merchant/agreement/create/index.{ts,wxml,wxss}`
- **验收标准**：①`POST /public/merchant/stores/{id}/brokers` 返回 201 且 `store_id` 为当前门店、`bind_status=bound`、`phone_masked` 脱敏（无明文 `phone`）；②补录后 `GET /public/merchant/stores/{id}/brokers` 立即包含该经纪人；③重复手机号同店 409、跨店 409 且提示换绑；④无经纪人时页面渲染「＋ 新增门店经纪人」入口与弹层，保存成功后签署人下拉自动选中新经纪人；⑤手机号非法（非 11 位）时不发请求并提示。
- **验证方式**：`e2e/merchant-iteration5.spec.ts`「REQ-IT5-05 门店无经纪人时可在发起页直接补录经纪人（接口 + 源码断言）」（含反向验证：改掉入口文案即失败）。

#### REQ-IT5-06 建店联系人自动建档为门店经纪人

- **来源原文**：「新建门店的时候pages/merchant/store/create/index，填写的联系人自动创建门店经纪人，对应手机号码扫码后自动关联上」
- **现状与根因**：建店只写 `merchant_stores.contact_name/contact_phone`，不产生 `merchant_brokers` 记录。结果是新门店「一个经纪人都没有」：协议签署人要另走补录（REQ-IT5-05）、线索无法归属到该联系人、门店二维码邀请也没有可对应的档案；而扫码认证走 `POST /public/merchant/brokers/register` 时按手机号哈希查档案，查不到就新建一条 `source=self_apply` 的孤立档案，与门店联系人彻底脱节。
- **期望行为**：①新建门店成功后，按联系人姓名与手机号自动建档 **并立即绑定该门店**（`bind_status=bound`、`source=store_contact`）；②同一手机号后续扫码认证时，命中该档案并回填 `user_id`（即「自动关联上」），不新增重复档案；③联系人手机号若已是他人经纪人档案（已绑他店/已被认领/已停用），**跳过自动建档并留审计**，建店必须照常成功；④小程序建店页与管理后台建店表单共用同一逻辑，仅提示文案不同。
- **落点文件**：`backend/services/merchant/broker.py`、`backend/services/merchant/store.py`、`miniapp/pages/merchant/store/create/index.{wxml,wxss}`、`frontend/src/app/(main)/admin/merchant/stores/new/page.tsx`
- **验收标准**：①建店返回 201，且 `GET /public/merchant/stores/{id}/brokers` 立即返回该联系人（姓名一致、`phone_masked` 脱敏、`store_id` 为本人门店）；②同手机号用户扫码认证后 `merchant_brokers.user_id` 被回填且档案总数不变、`GET /public/merchant/brokers/me` 指向该门店；③联系人手机号已被占用时建店仍 201、该门店经纪人列表为空、`operation_logs` 出现 `resource_type=merchant_broker` 且 `action=skip_existing`；④门店删除（软删）不因这条占位绑定而被拒绝。
- **验证方式**：`pytest tests/test_merchant_broker.py`（3 条新用例）与 `e2e/merchant-iteration5.spec.ts`（REQ-IT5-06 用例：自动建档 API + 冲突跳过 + 源码断言），并做反向验证（禁用自动建档钩子 → 用例必须失败）。

#### REQ-IT7-08 经纪人绑定门店：扫码 + 搜索两条路径

- **来源原文（m05520）**：「流程上有问题，逻辑上是从现有门店中搜索自己的店，如果店不存在再创建，而不是只有创建门店和暂不绑定，绑定门店应该分两种操作一种是扫内部员工提供的二维码，一种是搜索门店找不到再创建」。

- **期望行为**：①未绑定卡内直接给出「搜索绑定门店」（主按钮）与「扫码绑定门店」两条路径；②搜索弹层展示「门店搜索中…」，无结果时提供「找不到？创建新门店」直接跳建店页；③认证页提供「搜索门店（认证后绑定）」与「扫码识别门店」，认证成功自动绑定；④扫码内容兼容小程序码 `scene` 短码、`?code=` 链接与纯短码；⑤已认证经纪人扫码后立即绑定（`POST /public/merchant/brokers/me/bind`），未认证则写入 `qrCode/qrStoreName`，提交认证时自动绑定。
- **落点文件**：`miniapp/pages/merchant/broker/index.ts`（`onScanBind`/`bindByQrCode`/`onCreateStoreFromPanel`/`extractStoreQrCode`、`storeSearching/storeSearched`）、`index.wxml`（未绑定卡、认证页扫码卡、搜索弹层空态、页脚 CTA 文案）。
- **验收标准**：页面源码包含两条绑定路径与搜索空态创建入口；`onScanBind` 能解析 `scene`/`code`；`POST /public/merchant/brokers/me/bind` 仍为首次绑定入口；`tsc --noEmit` 零错。
- **验证方式**：`e2e/merchant-iteration7.spec.ts` 用例 9「REQ-IT7-08 经纪人绑定门店：扫码 + 搜索两条路径，搜索无结果可创建」（源码断言）+ 既有后端 `tests/test_merchant_broker.py` 绑定用例。
