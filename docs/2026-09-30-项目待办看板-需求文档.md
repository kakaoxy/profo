# 项目待办看板 · 需求文档（讨论稿 v0.1）

> 整理日期：2026-09-30 ｜ 状态：**思考阶段讨论稿**，供多轮反馈迭代
> 依据代码现状：`backend/models/project/*`、`backend/services/projects/*`、`frontend/src/app/(main)/admin/projects/*`
> 范围：admin 后台新增「项目待办看板」，覆盖**签约 + 装修**两个阶段的事项推进检测

---

## 一、背景与问题

项目在售之前的推进事项（签约资料完善、文书签署回收、装修进度）目前**分散在各个项目详情页里**，点开才能看到，不直观、易遗忘。典型失控场景：

| 场景 | 现状问题 |
|---|---|
| 项目签约了，但基础信息还缺几项没填 | 不阻塞流程，但很容易遗忘，一直缺着 |
| 合同签署了但没有回收归档 | 文书状态停在 signed，没人催归档 |
| 重要文档压根没签署 | 只有进详情页逐份看文书清单才能发现 |
| 装修没有及时安排施工方 | 项目进了装修阶段却迟迟没进场 |
| 施工方进场 30 天了水电还没结束 | 工序停滞没有滞后信号 |

**目标**：新建一个看板页，以**项目卡片**为单位聚合展示每个项目的待办清单（每卡最多 6 条、按重要紧急度排序），让相关人员一眼看到"哪些项目卡在哪些事上"，及时处理。

**一句话定位**：这不是任务管理系统（不人工建任务、不勾选完成），而是一个**规则驱动的体检报告**——后端按规则实时计算每个项目的"未完成事项"，看板只读展示。

---

## 二、目标与非目标

### 2.1 目标（v1）

1. 新增 admin 看板页：项目卡片流，仅展示 `签约`、`装修` 两个阶段的项目。
2. 每张卡片展示该项目最多 **6 条**待办，按 **P0 > P1 > P2** 优先级排序，溢出折叠为"+N 件"。
3. 待办由后端**规则引擎实时计算**（不落库），规则可枚举、可单测。
4. 每条待办可点击跳转到对应项目详情页的对应分区（锚点直达）。
5. 提供阶段 / 优先级 / 负责人筛选。

### 2.2 非目标（v1 明确不做）

- ❌ 通知推送（订阅消息/短信/站内信）
- ❌ 人工自定义待办、待办勾选/忽略状态（需要落库，v2 再议）
- ❌ 在售、已售、已下架阶段的事项检测
- ❌ 修改现有项目详情页
- ❌ 自动指派责任人（v1 只展示项目负责人，不做提醒触达）

## 三、现状盘点（代码事实）

写规则前先摆清数据基础。以下均为当前代码事实，**规则设计只能建立在已有字段上**。

### 3.1 项目主表与阶段

- `Project.status`：`signing / renovating / selling / sold / ended / deleted`（`backend/models/common/base.py:46-54`），默认 signing。
- `Project.renovation_stage`：改造子阶段，**枚举值为中文**：`拆除 / 设计 / 水电 / 木瓦 / 油漆 / 交付 / 已完成`（`base.py:57-66`）。进入装修时自动置"拆除"（`services/projects/internal/state.py:126-127`）。
- `Project.project_manager_id`：项目负责人。
- 状态流转日志 `project_status_logs`：`old_status / new_status / operate_at`（`models/project/_project_status_log.py`）——**"进入装修阶段多久了"可由此计算**（取最新一条 `new_status=renovating` 的 `operate_at`）。

### 3.2 签约阶段数据（分散在三张子表）

| 数据 | 位置 | 可空性 / 备注 |
|---|---|---|
| 合同编号 | `Project.contract_no` | 创建时必填 |
| 签约日期 / 合同周期 / 顺延期 / 业主交房时间 | `ProjectContract.signing_date / signing_period / extension_period / planned_handover_date`（`_project_contract.py`） | 全可空 |
| 合同状态 | `ProjectContract.contract_status` | `生效 / 未生效 / reserved`，`signing_date` 为空时自动"未生效"（`creator.py:134`） |
| 房源信息 | `Project.area / layout / orientation / floor_info` | 全可空 |
| 水电煤户号 | `Project.electricity_account / water_account / gas_account` | 全可空 |
| 业主信息 | `ProjectOwner.owner_name / owner_phone / owner_id_card / bank_*`（`_project_owner.py`） | 全可空；手机/证件/卡号**加密存储** |
| 业务形式 | `Project.business_form` | `agent / wholesale`，可空 |

**关键事实**：创建项目时除 `community_name / address / contract_no` 外全部可空（`schemas/project/core.py:57-103`），**全后端没有任何"信息完善度"校验**——这正是"基础信息缺几项很容易遗忘"的根源，看板是第一道完善度检测。

### 3.3 文书签收清单

- 模型 `ProjectDocument`：`document_name / signoff_status(unsigend→signed→archived) / archive_date(字符串 YYYY-MM-DD) / category`（`models/project/_project_document.py`），**无附件字段**，只记录状态。
- 模板按业务形式：代理 12 项 / 收购 18 项（`backend/constants/documents.py:33-67`）。
- **关键事实**：`business_form=None` 时文书清单为空列表（`documents.py:80-81`）——这类项目产不出"文书未签署"待办，规则需单独兜底（提示先初始化文书清单）。
- 归档联动：状态回 unsigned 清空归档日期；变 archived 未传日期自动填今天（`services/projects/internal/documents.py:148-151`）。

### 3.4 装修阶段数据

| 数据 | 位置 | 备注 |
|---|---|---|
| 施工方 | `ProjectRenovation.renovation_company` | **自由字符串，无施工队表** |
| 合同约定进场 / 竣工时间 | `contract_start_date / contract_end_date` | 可空 |
| 实际开工 / 竣工时间 | `actual_start_date / actual_end_date` | 可空；标记"拆除"完成时自动填开工（`services/projects/renovation.py:249-250`） |
| 工序完成记录 | `stage_completed_dates` JSON，格式 `{工序: 日期}` | 7 个中文枚举键；全部实际工序完成 → 自动置竣工+主阶段"已完成"（`renovation.py:237-241`） |
| 工序照片 | `RenovationPhoto.stage` | 辅证，可佐证工序真实性 |

**关键缺口**：❶ 无**工序级计划时间**（只有完成日期），"水电 30 天没结束"只能靠**每道工序的标准工期阈值**来判断；❷ 无验收字段；❸ 延期只能由 `contract_end_date vs actual_end_date` 推导，两者均可空。

### 3.5 既有可复用机制

- **无任何 todo/reminder 基础设施**（全后端无 todo/task/reminder 模型）。
- 到期公式先例：`签约日期 + (合同周期 + 顺延期) 天`（`services/projects/internal/query.py:216-218`），且已处理字段缺失兜底——"委托期临近"待办直接复用。
- 看板类聚合 API 先例：`GET /api/v1/projects/stats`（状态计数）、`monitor_sort=true`（工作台重点监控排序）。
- 权限：`ProjectReadPermDep`（读）+ 业务身份双通道（详情页）；前端 `PATH_PERMISSION_MAP` 中 `/admin/projects` 为 `exact: true`（仅匹配列表页）。
- 前端卡片先例：工作台 `ProjectCardClient`（Steep 白卡 `rounded-cards shadow-steep`）。

## 四、核心设计决策：待办如何生成

**方案 A（推荐）：实时规则计算，不落库**

- 每次打开看板，后端拉取签约+装修阶段的项目及关联子表，在内存中跑规则引擎，即时返回。
- 优点：零状态同步问题（数据改了待办立刻消失）、实现简单、天然无"待办与事实不一致"的 bug；符合"检测/体检"定位。
- 缺点：无法记录"已忽略/已读"、无法做"本周解决数"等历史统计（v1 不需要）。
- 性能：项目量级为几十个（现网签约+装修阶段项目数有限），一次聚合查询 + 内存计算完全可行；需批量预载子表避免 N+1。

**方案 B（备选）：规则定时跑批 + 待办落库**

- 仅当未来需要"忽略某条待办 7 天""解决率统计""推送提醒"时才有必要，届时可将规则引擎产出物持久化为 `project_todos` 表。v1 不做，但规则引擎应输出稳定的 `rule_code`，为将来落库留好主键。

> **决策点 D1**：采用方案 A。是否同意？

## 五、待办规则清单 v1（核心）

规则编号 `R*` 是前后端契约的一部分（`rule_code` 稳定不变），新增规则追加编号。每条规则：触发条件 → 优先级 → 详情文案 → 跳转位置。

### 5.1 优先级定义

| 级别 | 定义 | 典型情形 | 徽章视觉（Steep 体系） |
|---|---|---|---|
| **P0 阻塞/逾期** | 已逾期或流程卡死，有违约/停滞风险 | 竣工逾期、核心文书未签、施工方未安排 | `bg-rust text-white`（Rust 强调） |
| **P1 重要滞后** | 核心流程未推进且已有滞后信号 | 合同未生效、委托期临近、工序停滞 | `bg-apricot-wash text-rust` |
| **P2 易遗忘项** | 不阻塞但要收尾 | 基础信息缺项、已签未归档 | `bg-fog text-ash` |

### 5.2 签约阶段规则（status = signing）

| 编号 | 待办名称 | 触发条件（字段级） | 优先级 | 跳转 |
|---|---|---|---|---|
| **R1** | 合同未生效 | `contract.contract_status == "未生效"`（即 `signing_date` 为空） | P1 | 详情页 · 合同要件 |
| **R2** | 基础信息缺 N 项 | 见下方 5.2.1 字段集，任一为空即触发；详情聚合展示缺失项清单 | 核心字段缺 → P1；仅次要字段缺 → **P2** | 详情页 · 概览 |
| **R3** | 文书未签署 | `documents` 中 `signoff_status == unsigned` 计数 > 0 | **签约合同/装修合同**未签 → P0；其余未签 → P1 | 详情页 · 文书签收清单 |
| **R3a** | 文书清单未初始化 | `business_form == None`（文书模板为空的根因） | P1 | 详情页 · 概览（先完善业务形式） |
| **R4** | 已签署未归档 | `signoff_status == signed` 且 `archive_date` 为空，计数 > 0 | P2；签署后超 **30 天**未归档 → 升 P1 | 详情页 · 文书签收清单 |
| **R5** | 交房逾期未确认 | `planned_handover_date < today` 且项目仍在签约阶段 | P0 | 详情页 · 合同要件 |

#### 5.2.1 R2「基础信息完善」字段集（草案，待业务确认）

| 分级 | 字段 | 来源 |
|---|---|---|
| 核心字段（缺任一 → 整条升 P1） | `signing_date`、`signing_price`、`business_form`、`planned_handover_date`、业主 `owner_name` + `owner_phone`（至少一位业主联系方式） | `ProjectContract` / `Project` / `ProjectOwner` |
| 次要字段（仅计数） | `area`、`layout`、`orientation`、`floor_info`、`electricity_account`、`water_account`、`gas_account` | `Project` |

展示形态：**聚合为一条**待办（"基础信息缺 4 项：签约日期、签约价、水电户号…"），避免刷屏；点击跳详情页补录。业主手机号在明细中**不展示明文**（加密字段，看板不下发）。

### 5.3 装修阶段规则（status = renovating）

| 编号 | 待办名称 | 触发条件 | 优先级 | 跳转 |
|---|---|---|---|---|
| **R6** | 未安排施工方 | `renovation_company` 为空 且 进入装修状态 > **7 天**（取自 `project_status_logs` 最新 `new_status=renovating` 的 `operate_at`） | P0 | 详情页 · 装修合同 |
| **R7** | 未实际开工 | `renovation_company` 已填 且 `actual_start_date` 为空 且 进入装修 > **15 天**；若 `contract_start_date` 已过仍无开工记录 → P0 | P1 | 详情页 · 装修进度 |
| **R8** | 当前工序停滞 | 工序已进行天数 > 该工序标准工期阈值（见 5.3.1）。进行天数 = `today − max(已完成工序的最新完成日期, actual_start_date)` | P1；超阈值 2 倍 → P0 | 详情页 · 装修进度 |
| **R9** | 竣工逾期 | `contract_end_date < today` 且 `actual_end_date` 为空 | P0（展示逾期天数） | 详情页 · 装修进度 |

#### 5.3.1 工序标准工期阈值（草案，待业务确认，建议做成可配置）

| 工序 | 设计 | 拆除 | 水电 | 木瓦 | 油漆 | 交付 |
|---|---|---|---|---|---|---|
| 标准工期（天） | 14 | 7 | 20 | 25 | 15 | 7 |

> 用户场景"施工方 30 天了水电还没结束"即由 R8 捕获（水电阈值 20 天）。
> 数据缺口说明：装修表只有**完成日期**、没有工序级计划时间，因此停滞判断 = 实际已耗天数 vs 标准工期阈值。阈值 v1 先放后端常量模块，后续可迁 `system_configs` 做成运营可调。

### 5.4 通用规则（签约 + 装修都可能出现）

| 编号 | 待办名称 | 触发条件 | 优先级 | 跳转 |
|---|---|---|---|---|
| **R10** | 委托期临近/已超 | `today > signing_date + (signing_period + extension_period) 天 − 30` 触发临近；已超过当天 → P0（复用 `query.py:216-218` 既有到期公式；字段缺失则静默跳过，与重点监控排序同一兜底逻辑） | 临近 P1 / 已超 P0 | 详情页 · 合同要件 |

### 5.5 排序规则

1. 卡片内待办：P0 → P1 → P2；同级按**逾期/滞后天数降序**，无天数的按规则编号。
2. 每卡截取前 **6 条**，其余折叠为"+N 件"（展开抽屉或仅提示，v1 只提示 + 跳详情）。
3. 卡片间排序：P0 数量多 → P1 数量多 → 最深滞后天数长。也可按负责人分组（v1 不做分组，先平铺）。

## 六、页面设计

### 6.1 入口与路由

- **路由**：`/admin/projects/todo-board`（归属"项目管理"家族，与列表/详情同族）。
  - 权限说明：`PATH_PERMISSION_MAP` 中 `/admin/projects` 是 `exact: true` 只匹配列表页本身，`/admin/projects/todo-board` 不会命中该条目——需**新增一条** `{ prefix: "/admin/projects/todo-board", permission: PROJECT_READ }`（注意按 prefix 长度降序插入的硬约束）。
- **菜单**：`admin-nav-data.ts` 的 `navMain` 「业务」分组新增「项目待办」入口（挂「项目管理」之后）；移动端「更多」弹层同步。
- **备选**：独立路由 `/admin/todo-board`。决策点 D2。

### 6.2 页面结构（自上而下）

```
PageHeader「项目待办」        ── 副标题：签约与装修阶段事项推进一览
统计条（StatCardGrid 4 张）    ── 待办项目数 / P0 事项数 / 待办总数 / 最深逾期天数
筛选行（ListView 工具行）      ── 阶段 Tabs（签约/装修，带计数）· 优先级 Select · 负责人 Select
项目卡片流（响应式网格）       ── 2~3 列桌面端 / 1 列移动端
空状态（EmptyState）          ── "全部事项已推进完毕 🎉"（无待办项目时不出现卡片）
```

顶部统计条与筛选均可选做（v1 建议：统计条做，负责人筛选缓一缓——`project_manager_id` 已有，实现不难，但先验证看板本身价值）。

### 6.3 项目卡片结构

模板参照工作台 `ProjectCardClient`（Steep 白卡）：

```
┌─────────────────────────────────────────────┐
│ 小区名 + 地址缩略            [签约] [P0×2]   │  ← 状态徽章 + P0 计数徽章
│ SH0028-DL · 负责人：张三                     │
│ ──────────────────────────────────────────  │
│ ● P0  交房逾期未确认                         │
│       约定 09-10 交房，已逾期 20 天           │
│ ● P1  文书未签署                             │
│       3 份未签：装修合同、产证、房屋交接书      │
│ ○ P2  基础信息缺 4 项                        │
│       签约日期、水电户号…                     │
│ ○ P2  已签署未归档                           │
│       2 份签署后未回收                       │
│ ──────────────────────────────────────────  │
│ 共 5 件待办 · 还有 1 件 →            去处理 → │  ← text link，非填充按钮
└─────────────────────────────────────────────┘
```

- 每条待办：优先级标识（P0 实心 Rust 点 / P1 空心 / P2 灰点）+ 标题（`font-[480]`）+ 灰色详情行（`font-[430]`）；整条可点，跳详情页对应锚点。
- 卡片 hover 上浮（对齐 `ProjectCardClient` 的 `-translate-y-[3px]`）。
- 金额/天数用 `tabular-nums`；逾期天数是"滞后的程度"，用文字而非金额红绿色语义。
- 全卡仅一个可点主行动（"去处理 →"跳详情页），遵循 Steep"每屏一个填充 CTA"纪律（本页可以零填充按钮）。
- 视觉纪律：画布 `bg-fog`、白卡 `rounded-cards shadow-steep` 无边框、彩色只允许 Rust（P0）与 Apricot/Sky wash 卡底；字重 430/450/480，从不 bold。

## 七、API 与实现草案

### 7.1 聚合端点

```
GET /api/v1/projects/todo-board?stage=signing|renovating&priority=p0|p1|p2
```

```ts
ProjectTodoBoardResponse {
  generated_at: string          // 服务端时间
  summary: {
    project_count: number       // 有待办的项目数
    todo_count: number          // 待办总条数（截断前）
    p0_count: number            // P0 总条数
    max_overdue_days: number | null
  }
  projects: ProjectTodoCard[]
}

ProjectTodoCard {
  project_id: string
  community_name: string
  address: string
  contract_no: string
  status: "signing" | "renovating"
  renovation_stage: string | null   // 装修中的当前工序
  business_form: "agent" | "wholesale" | null
  manager: { id: string; name: string } | null
  todo_count: number            // 规则命中总条数（截断前）
  p0_count: number
  todos: ProjectTodoItem[]      // 已排序，≤6
  todo_overflow: number         // 被折叠条数
}

ProjectTodoItem {
  rule_code: string             // "R1".."R10"，稳定契约
  priority: "p0" | "p1" | "p2"
  title: string                 // "文书未签署"
  detail: string | null         // "3 份未签：装修合同、产证…"
  overdue_days: number | null   // 逾期/滞后/临近天数
  anchor: string | null         // 详情页分区锚点（对齐现有 SECTION_IDS）
}
```

### 7.2 实现要点

- **后端**：新增 `routers/projects/todo_board.py` + `services/projects/todo_board.py`（规则引擎独立成模块，纯函数化：输入项目聚合数据 → 输出待办列表，便于逐规则单测）；schema 放 `schemas/project/`。权限 `ProjectReadPermDep`。预载 `contract / owners / documents / renovation / status_logs` 各项目一次性批量查询（`selectinload` 或按 ID 集合 in 查询），避免 N+1。
- **前端**：Server Component 首屏 `fetchClient().GET("/api/v1/projects/todo-board")`（注意 `isRedirectError` 放行惯例）；筛选走 nuqs URL 同步（对齐列表页 `useQueryStates` 模式）；api-types 生成后开发（`pnpm gen-api`，两份 d.ts 字节一致）。
- **测试**：规则引擎单测覆盖每条规则的触发/不触发/边界（阈值当天、字段缺失兜底）；R10 复用既有到期公式需与 `query.py` 共享实现避免两处漂移。

## 九、数据缺口与风险提示

这些是**现有数据做不到**的事，设计上已绕开，但需要知晓：

1. **无工序级计划时间**——"水电 30 天没结束"依赖人工校准的工序标准工期阈值（5.3.1），阈值不准会误报/漏报。
2. **无验收字段**——装修"验收"环节无数据支撑，v1 规则不含验收。
3. **`business_form=None` 的项目文书清单为空**——此类项目只能提示"初始化文书清单"（R3a），无法逐文书催办。
4. **`archive_date` 是字符串非日期类型**——判空没问题；若未来要按归档日期排序/统计需注意。
5. **进入阶段时间依赖状态日志**——`project_status_logs` 若历史数据缺失（早期项目），"进入装修 N 天"无法计算，R6/R7 静默跳过。
6. **规则是只读快照**——没有"已处理/忽略"记忆，同一待办处理完前会一直挂着（这是体检式设计的取舍，见 D1）。
