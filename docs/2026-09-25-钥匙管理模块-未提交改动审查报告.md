## 三、确认并已修复

### 1. 【高】`miniapp/utils/config.ts` develop 基址被改成内网 IP（已还原）

- 原改动：`develop` 由 `https://fangmengchina.com/api/v1` 改为 `http://192.168.110.82:8000/api/v1`（本地联调开关被留在改动里）。
- **客观证据**：修复前小程序 vitest 为 6 failed，其中 2 个正是
  `test-utils/utils/url.test.ts` 断言 `develop` 应解析为 `https://fangmengchina.com`，实际得到 `http://192.168.110.82:8000`。
- 风险：破坏既有单测；私网 IP 入库；他人 develop 环境静默指向个人机器。
- 处理：还原到 HEAD（文件已与 HEAD 字节一致）。本地联调仍按该文件顶部注释的方式临时切换，或使用开发者工具的本地覆盖，勿入库。修复后 `url.test.ts` 13/13 通过。

### 2. 【中】前端 4 个文件未过 `prettier --check`（已格式化）

`batch-entry-dialog.tsx`、`manager-key-card.tsx`、`normal-keys-card.tsx`、`side-column.tsx`。
其中 `side-column.tsx` 的 **HEAD 版本是格式干净的** → 属本轮引入。已仅对这 4 个文件 `--write`，`side-column.tsx` 的实际改动经 diff 确认只落在新增区域。

### 3. 【中】`key_audit_logs.detail ->> 'share_id'` 查询无索引可用（已补表达式索引）

- 问题：`KeyShareService.get_share_detail` 的分享时间线、`KeyService.get_logs` 的分享级事件合并，都以 `detail ->> 'share_id'` 过滤；该表原有索引仅为 `project_id` / `(project_id, created_at)` / `action`，**无法覆盖该条件 → 每次请求全表扫描 + 排序**。而经纪人每次查看明文都会写入一行 `agent_view`，表持续增长。
- 关键复核（易误判点）：SQLAlchemy 会把 JSON key 也作为**绑定参数**下发（`detail ->> $1`），而驱动是 **psycopg3（服务端绑定）**，本可能因 `Param ≠ Const` 导致表达式索引失效、修复落空。已在真实 PG16 上按真实绑定路径 `EXPLAIN` 验证：**字面量与绑定参数两种写法均命中 `Bitmap Index Scan`**，索引有效。
- 处理：新增 `migrations/_keys.py::add_key_audit_share_id_index`（仅 PostgreSQL、`_index_exists` 幂等、`CREATE INDEX IF NOT EXISTS`），并接入 `_run_all_migrations`。真库执行 2 次验证幂等、数据无损。

### 4. 【中】`miniapp/utils/request.ts` 的 PATCH 支持为无用代码且注释与事实不符（已移除）

- 全量小程序代码无任何调用使用 PATCH（`update_normal` 走 POST 别名）；`wx.request` 官方类型不含 PATCH，为此引入的 `method as "GET" | "POST" | "PUT" | "DELETE"` 断言纯为死代码服务。
- 原注释「后端仅暴露 PATCH 端点」与后端实际（同时暴露 PATCH + POST 双通道）矛盾。
- 处理：`method` 恢复 4 方法联合类型、去掉类型断言、修正注释为「后端统一提供 POST 别名，调用方一律用 POST」。
- 保留：`isCAudiencePath`（`/keys/* → aud=c` 是真实需要的改动）。

### 5. 【低】`schemas/keys/shares.py::KeyShareViewEvent` 死代码（已删除）

定义后无任何引用、未导出、未进入 OpenAPI。
