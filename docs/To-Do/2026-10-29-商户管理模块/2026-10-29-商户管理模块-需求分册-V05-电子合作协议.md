## 2. 模块概述与目标

本册负责电子合作协议的模板维护、协议发起、手写签名、PDF 生成、归档、状态管理与到期提醒触发。本期按 D4-C 采用“小程序手写签名 + 生成 PDF”，不接第三方电子签平台；签署过程保留签名图片与 PDF，不记录设备信息，不使用第三方时间戳（N03）。

协议可挂在门店或公司主体上：连锁品牌签公司、单店签门店（Q14）；运营维护多套模板（Q15）；到期前 30 天站内通知（Q16）；支持附件上传与补充协议关联，盖章在线下完成（Q17）。

## 4. 功能需求

### 4.1 协议模板

#### REQ-M04-001 协议模板维护

| 项目 | 内容 |
|---|---|
| 功能描述 | 运营维护多套协议模板，按合作类型区分，供员工发起协议时选择。 |
| 触发条件 | 运营进入后台“商户管理 → 协议模板”。 |
| 主流程 | 1. 查看模板列表；2. 新建模板；3. 填写模板名称、适用合作类型、正文内容、状态；4. 保存；5. 员工发起协议时按合作类型加载可用模板。 |
| 分支与异常 | 1. 模板名称为空：拒绝；2. 正文为空：拒绝；3. 模板停用：不可新选，历史协议仍可查看；4. 模板被协议引用：不允许物理删除，只能停用。 |
| 输入字段 | 模板名称、适用合作类型、正文、状态 |
| 输出字段 | `template_id`、模板版本、状态 |
| 业务规则 | BR-M04-001：运营维护多套模板，按合作类型区分（Q15）；BR-M04-002：模板停用不影响已发起协议；BR-M04-003：模板修改是否影响已发起协议见 R-V05-04。 |
| 权限与角色 | admin/operator；`merchant:agreement`。 |

### 4.2 协议发起与签署

#### REQ-M04-002 发起协议

| 项目 | 内容 |
|---|---|
| 功能描述 | 员工在门店详情选择模板，确定签约主体与签署人，生成待签协议记录。 |
| 触发条件 | 员工在门店详情点击“发起协议”，或拜访完成后选择“需要签协议”。 |
| 主流程 | 1. 选择签约主体：门店或公司；2. 系统按 Q14 推荐默认主体；3. 选择协议模板；4. 填写协议编号（可空）、签署人姓名、签署人手机号、到期时间（可空）、备注；5. 生成协议记录，状态“未发起”、`review_status=待审核`；6. 运营审核通过后协议状态变为“待签署”；7. 展示协议正文与签署入口。 |
| 分支与异常 | 1. 公司不存在/已停用：拒绝发起；D1-A 要求门店必须归属公司；2. 公司下多门店：默认签公司，运营可调整；3. 模板为空：拒绝发起；4. 签署人姓名或手机号为空：拒绝；5. 协议编号重复：提示，具体唯一性见 R-V05-03；6. 门店已停用/合并：拒绝发起；7. 签署人不是门店/公司联系人：默认拒绝，运营可授权代签并留痕。 |
| 输入字段 | 门店 `id`、公司 `id`、签约主体类型、模板 `id`、协议编号、签署人姓名、签署人手机号、到期时间、备注 |
| 输出字段 | 协议 `id`、协议状态、协议正文、签署链接/页面 |
| 业务规则 | BR-M04-004：连锁签公司、单店签门店（Q14）；BR-M04-005：`store_id` 与 `company_id` 按签约主体二选一必填，另一个为空；BR-M04-006：协议发起后状态保持“未发起”、`review_status=待审核`；运营审核通过后进入“待签署”；BR-M04-007：签署人必须为门店联系人（公司主体为公司联系人），手机号与档案一致；不匹配时仅 admin/operator 可授权代签并记录原因；签署人手机号属于个人信息，展示按权限脱敏。 |
| 权限与角色 | 员工 `merchant:agreement` 且门店在本人范围；admin/operator 可发起/代发起。 |
| 状态流转 | 未发起/待审核 → 待签署（审核通过）→ 已签署；未发起/待审核 → 未发起（审核驳回）。 |

#### REQ-M04-003 手写签名与 PDF 生成

| 项目 | 内容 |
|---|---|
| 功能描述 | 签署人在小程序查看协议正文，手写签名并确认，系统生成含签名图片的协议 PDF。 |
| 触发条件 | 协议状态为“待签署”，签署人打开签署页。 |
| 主流程 | 1. 展示协议正文、签署人信息；2. 签署人阅读并确认；3. 在签名画布手写签名；4. 提交签名；5. 系统校验签名非空；6. 生成签名图片；7. 将协议正文、签署人信息、签名图片、签署时间合成 PDF；8. 保存 `file_url`；9. 更新 `signed_at`、状态“已签署”；10. 联动门店合作状态为“已合作”（见 V02 REQ-M01B-004）。 |
| 分支与异常 | 1. 签名空白：拒绝提交；2. PDF 生成失败：协议保持“待签署”，允许重试；3. 文件上传失败：保持“待签署”，保留签名草稿；4. 签署人手机号与记录不一致：提示并拒绝；5. 协议已作废/已过期：禁止签署；6. 重复提交：幂等，不生成多份有效 PDF。 |
| 输入字段 | 协议 `id`、签名图片、签署人确认 |
| 输出字段 | `signer_name`、`signer_phone`、`signed_at`、`file_url`、协议状态 |
| 业务规则 | BR-M04-008：D4-C 手写签名 + PDF；BR-M04-009：存证保留签名图片与 PDF，不记录设备信息，不使用第三方时间戳（N03）；BR-M04-010：`external_sign_id` 字段保留但本期不使用（D4-C）；BR-M04-011：门店主体协议签署完成后，通过 V02 门店状态内部服务联动该门店合作状态为“已合作”（S05）；该内部调用以系统操作者执行，不受员工手动改状态权限限制；公司主体协议不自动回写各门店，见 R-V05-08；BR-M04-012：协议 PDF 必须可下载、可归档，文件名含协议编号或协议 `id`。 |
| 权限与角色 | 签署人本人；员工可协助打开签署页，但不能代替签名。 |

#### REQ-M04-004 线下盖章扫描件上传

| 项目 | 内容 |
|---|---|
| 功能描述 | 对需要线下盖章的协议，员工上传已签署/盖章的扫描件，系统记录为已签署协议。 |
| 触发条件 | 员工在协议详情点击“上传扫描件”；或运营补录历史协议。 |
| 主流程 | 1. 选择协议记录；2. 上传扫描件；3. 填写签署人、签署时间；4. 系统校验文件格式；5. 保存 `file_url`；6. 状态改为“已签署”；7. 联动门店合作状态。 |
| 分支与异常 | 1. 文件格式不支持：拒绝；2. 文件过大：拒绝；3. 协议已存在有效 PDF：提示是否替换，替换需留痕；4. 上传失败：保持原状态。 |
| 输入字段 | 协议 `id`、扫描件、签署人、签署时间 |
| 输出字段 | `file_url`、`signed_at`、协议状态 |
| 业务规则 | BR-M04-013：线下盖章件作为协议文件归档，盖章动作在线下完成（Q17）；BR-M04-014：扫描件上传不产生手写签名图片；BR-M04-015：替换文件必须记录操作日志与前后文件地址。 |
| 权限与角色 | 员工本人门店；admin/operator 可补录。 |

### 4.3 协议状态与归档

#### REQ-M04-005 协议状态流转

| 项目 | 内容 |
|---|---|
| 功能描述 | 管理协议从发起到签署、过期、作废的完整状态。 |
| 触发条件 | 发起、签署、到期、作废操作。 |
| 主流程 | 1. 发起后进入待签署；2. 签署完成进入已签署；3. 到达 `expire_at` 后进入已过期；4. 运营作废后进入已作废；5. 每次变更记录操作人、时间、原因。 |
| 分支与异常 | 1. 未发起直接签署：拒绝；2. 已作废协议再签署：拒绝；3. 已过期协议续签：新建协议，不复活原协议；4. 到期时间早于签署时间：拒绝发起；5. 作废未填原因：拒绝。 |
| 输入字段 | 协议 `id`、目标状态、原因 |
| 输出字段 | 新状态、变更时间、操作人 |
| 业务规则 | BR-M04-016：协议状态为未发起、待签署、已签署、已过期、已作废（8.5、Q51）；BR-M04-017：状态变更写审计日志；BR-M04-018：已过期由到期时间触发，允许运营手动作废；BR-M04-019：已作废协议保留文件与历史，不物理删除。 |
| 权限与角色 | 员工可发起、签署本人门店协议；admin/operator 可作废、补录、查看全量。 |
| 状态流转 | 未发起 → 待签署 → 已签署 → 已过期；未发起/待签署/已签署 → 已作废。 |

#### REQ-M04-006 协议归档与查询

| 项目 | 内容 |
|---|---|

| 分支与异常 | 1. 无协议：空状态；2. 文件不存在：展示“文件缺失”，运营可补传；3. 无权限：不展示签署人手机号等敏感字段；4. 已过期：列表标记并可按到期时间排序。 |
| 输入字段 | 门店 `id`、公司 `id`、协议编号、状态、到期时间范围 |
| 输出字段 | 协议列表、协议详情、文件地址 |
| 业务规则 | BR-M04-020：协议按门店或公司主体归档（Q14）；BR-M04-021：协议文件下载需鉴权，禁止公开直链；BR-M04-022：协议列表默认按签署时间倒序。 |
| 权限与角色 | 员工本人门店/公司；admin/operator 全量。 |

#### REQ-M04-007 补充协议与附件

| 项目 | 内容 |
|---|---|
| 功能描述 | 为原协议关联补充协议与附件，保留完整合同链路。 |
| 触发条件 | 员工或运营在协议详情点击“新增补充协议/附件”。 |
| 主流程 | 1. 选择原协议；2. 新建补充协议记录或上传附件；3. 填写说明；4. 关联原协议 `id`；5. 保存；6. 在原协议详情展示关联列表。 |

#### REQ-M04-008 到期时间与提醒触发

| 项目 | 内容 |
|---|---|
| 功能描述 | 记录协议到期时间，每日扫描并在到期前 ≤30 天窗口为 V09 提供提醒事件。 |
| 触发条件 | 协议发起或编辑时填写 `expire_at`；每日到期扫描。 |
| 主流程 | 1. 保存协议到期时间；2. 每日扫描已签署协议；3. 距到期 ≤30 天且本到期周期未发送时触发提醒事件；4. 事件携带 `agreement_id`、`store_id` 或 `company_id`、主体名称、到期日；5. 到期后状态置为已过期。 |
| 分支与异常 | 1. `expire_at` 为空：不提醒、不自动过期；2. 已作废：不提醒；3. 已过期：不重复提醒；4. 任务漏跑：后续扫描仍在 30 天窗口内补发一次；5. 通知失败：记录失败并重试，具体重试策略见 V09。 |
| 输入字段 | 协议 `id`、`store_id`/`company_id`、主体名称、`expire_at`、状态 |
| 输出字段 | 提醒事件、协议状态 |
| 业务规则 | BR-M04-026：到期前 30 天窗口站内通知（Q16）；BR-M04-027：提醒接收人由 V09 定义；BR-M04-028：到期状态变更写审计日志；BR-M04-029：V05 只生产到期事件，不直接发送通知。 |
| 权限与角色 | 系统任务；运营可查看提醒记录。 |

#### REQ-M04-009 协议审核

| 项目 | 内容 |
|---|---|
| 功能描述 | 员工发起协议后提交运营审核；运营审核通过后协议进入待签署，驳回则退回发起人并记录原因。 |
| 触发条件 | 员工提交协议发起；或运营打开待审核协议。 |
| 主流程 | 1. 员工填写主体、模板、签署人、到期时间并提交；2. 系统置 `review_status=待审核`，协议状态保持“未发起”；3. 运营审核；4. 通过：`review_status=审核通过`，协议状态“待签署”；5. 驳回：`review_status=审核驳回`，记录 `review_remark`，通知发起人；6. 全过程写审计日志。 |
| 分支与异常 | 1. 非 admin/operator 审核：拒绝；2. 同一协议重复审核：幂等，以首次结果为准；3. 协议已作废/已签署：不可审核；4. 审核驳回后重新发起：生成新的审核记录，保留历史。 |
| 输入字段 | 协议 `id`、审核结果、审核意见 |
| 输出字段 | `review_status`、`reviewed_at`、`reviewed_by`、`review_remark`、协议状态 |
| 业务规则 | BR-M04-030：S05 明确员工发起、运营审核；审核通过前不得进入签署；BR-M04-031：审核操作仅 admin/operator，审核人与发起人可为同一人但需二次确认；BR-M04-032：审核记录不可覆盖，追加历史。 |
| 权限与角色 | 员工 `merchant:agreement` 发起；admin/operator 审核。 |
| 状态流转 | 未发起/待审核 → 待签署（审核通过）；未发起/待审核 → 未发起（审核驳回，允许修改后重提）。 |

## 6. 接口与数据

### 6.1 数据对象

#### 6.1.1 `merchant_agreements`

| 字段 | 类型 | 必填 | 说明 | 来源 |

## 7. 依赖与影响说明

1. 本册依赖 V02 的公司与门店主数据；签约主体按 Q14 选择公司或门店。
2. 协议签署完成联动 V02 的合作状态为“已合作”，因此 V02 的“已合作”前置校验以本册已签署协议为准。
3. 协议文件复用现有文件上传服务；文件访问必须鉴权。
4. D4-C 不使用第三方电子签，`external_sign_id` 保留为空；法律效力风险按第十三章记录。
5. V09 只负责通知发送，到期扫描与提醒事件由本册产生。
6. V07 后台协议列表、门店详情协议区复用本册数据与状态。
