## 一、背景与问题

### 1.1 业务背景

公司通过员工线下拓展获取房产经纪门店资源。当前「找门店 → 拜访 → 谈合作 → 签协议 → 门店推荐客户」整条链路全部在线下和微信里完成：

- 门店信息记在员工个人微信、备忘录或表格里；
- 门店合作到哪一步、协议签没签，只有当事人知道；
- 门店下有多少经纪人、谁是店长、谁在帮忙推荐客户，没有档案；
- 线索虽然有「分享归属员工」，但无法回答「这个客户是哪家门店的哪个经纪人推荐的」。

| 现状 | 结论 | 证据 |

### 1.3 问题清单

| 典型场景 | 现状问题 | 业务影响 |
|---|---|---|
| 员工跑了一天，拜访了 8 家门店 | 信息散落在微信、纸质名片、个人表格里，回公司后才补记 | 数据滞后、遗漏、无法沉淀为公司资产 |
| 两个员工先后拜访同一家门店 | 互相不知道，重复建档或重复谈 | 撞单、重复投入、对外口径不一致 |
| 领导问「这个区有多少家合作门店」 | 没有台账，只能人工汇总 | 无法做区域规划和拓展目标管理 |
| 想知道「这家店有几个经纪人」 | 无经纪人档案 | 无法评估门店产出能力，也无法做门店激励 |
| 客户问「是谁推荐来的」 | 只有分享员工，没有门店 / 经纪人 | 门店贡献无法统计，合作门店没有获得感 |
| 员工说「今天去了 A、B、C 三家店」 | 无拜访留痕 | 无法验证真实性，无法复盘路线和频次 |
| 合作协议签完 | 纸质协议归档散乱，到期无人提醒 | 合作到期裸奔，续签靠记忆 |

### 1.4 一句话定位

把线下「扫街拓店」变成系统内**可建档、可留痕、可归属、可复盘**的一条数据链，并在后台形成一张可查、可管、可看的门店与经纪人地图。

## 二、目标与非目标

### 2.1 目标（v1）

1. 建立「商户（公司）→ 门店 → 经纪人」的主数据模型（层级见决策 D1）。
2. 员工可在小程序完成拜访登记与门店建档：门店不存在当场新增，门店存在则记录拜访。
3. 门店可维护合作状态、联系人与电子合作协议。
4. 经纪人可登录小程序并绑定门店，形成可追溯的归属关系。
5. 线索可记录「推荐门店 + 推荐经纪人」；员工分享的估价页支持经纪人代填并正确归属。
6. Admin 提供：区域门店地图、门店详情、拜访时间线 / 轨迹、门店与经纪人的简单增删查改。
7. 全链路操作留痕（操作人、时间、变更前后），关键动作可审计。

### 2.2 非目标（v1 明确不做）

- ❌ 门店经营业绩统计、成交分佣、佣金结算（属于财务域，另行立项）。
- ❌ 经纪人佣金、提成、等级体系。
- ❌ 门店选址分析、热力图、竞品分析。
- ❌ 连续 GPS 轨迹采集（若决策 D6 选择「打卡点」模式）。
- ❌ 完整电子签平台能力（若决策 D4 选择「上传扫描件」方案）。
- ❌ 多租户 SaaS、跨公司数据隔离。
- ❌ 改造现有线索跟进流程本身（只在归属维度做扩展）。
- ❌ C 端公开展示门店列表 / 门店详情页（本期不做，后续再议）。

## 三、名词定义与实体关系

> 这三个概念是全新的，且「经纪人」与系统现有 `AGENT`（C 端看房人）撞名，**必须先在团队内统一口径**，否则后续数据模型无法落地。

| 名词 | 定义 | 与现状的关系 |
|---|---|---|
| **商户（公司）** | 门店所属的经营主体 / 品牌公司，如「XX 房地产经纪有限公司」 | 系统当前无此实体；是否独立建表见 D1 |
| **门店** | 线下实体经营门店，是拜访、合作、经纪人归属的最小单元 | 新增实体；地址包含区域 / 商圈 / 经纬度 |
| **经纪人** | 门店内的从业人员，可登录小程序、可绑定门店、可推荐客户 | 新增实体；建议代码命名 `merchant_broker`，**严禁复用 `AGENT`** |
| **员工** | 公司内部人员，即现有 `users` 中具备后台身份者（admin / operator / user） | `backend/services/system/identity.py:17` `is_internal_user` 已可判定 |
| **拜访** | 员工对某门店的一次线下到访记录 | 新增实体；含拍照、联系人、时间、定位 |
| **合作状态** | 门店与公司的合作阶段（如：未合作 / 洽谈中 / 已合作 / 暂停 / 终止） | 建议走业务字典，不硬编码 |
| **电子合作协议** | 门店 / 商户与公司签署的合作协议电子件 | 系统当前无电子签能力，见 D4 |

### 3.1 实体关系

```
商户（公司） 1 ── N 门店 1 ── N 经纪人（当前绑定）
                      │
                      ├── N 拜访记录（员工 N ── 1）
                      ├── N 电子合作协议
                      └── N 线索（推荐门店）
经纪人 1 ── N 线索（推荐经纪人）
员工   1 ── N 拜访记录 / N 分享归因线索
```

### 3.2 关键边界说明

1. **门店是主实体**：所有拜访、协议、经纪人都挂在门店上；「商户（公司）」是可选的组织层。
2. **经纪人不是内部员工**：经纪人不能登录 admin 后台，只能在小程序中使用经纪人相关功能。
3. **门店 ≠ 小区**：`communities` 是房源小区（用于房源、估价、楼盘字典），门店是中介经营场所，两者不能混用同一张表。
4. **一个门店可以有多个经纪人，一个经纪人同一时间只属于一个门店**（建议值，见 Q23）。

| 角色 | 身份来源 | 主用端 | 核心操作 | 现状支持 |

### 6.2 场景明细

#### S01 员工拜访新门店并建立档案

- **场景**：员工线下拓展到访一家系统内不存在的门店，需要现场建立门店档案，并留下本次拜访记录。
- **角色 / 端**：员工 / 小程序
- **触发**：员工进入「商户拓展 → 拜访登记」，搜索门店（名称 / 地址 / 电话）无结果，点击「新增门店」。
- **主流程**：
  1. 员工填写公司名称、门店名称；
  2. 选择区域（省 / 市 / 区县）、商圈，填写详细地址，并通过地图选点获取经纬度；
  3. 填写联系人、联系电话、合作状态；
  4. 现场拍照（门头照必拍、店内照选拍）；
  5. 提交；
  6. 系统创建门店档案，同时自动生成该门店的第一条拜访记录；
  7. 若当场达成合作，可继续发起电子协议（转入 S05）。
- **涉及功能模块**：**M01 门店档案、M02 地址与地图选点、M03 拜访记录、M04 电子合作协议、M12 权限与审计、M13 业务字典**
- **规则与边界**：
  - 「新增门店」必须与一次拜访绑定，禁止无拜访凭空建档（避免刷门店数）；
  - 门店名称、详细地址、经纬度为必填；区域必填、商圈必填（门店场景建议比小区更严格）；
  - 门头照至少 1 张；
  - 同一员工短时间内重复提交同名 / 同址门店，系统提示「疑似重复」（见 S03）。
- **现状与差距**：无门店实体、无拜访实体、无地图选点能力、无现场拍照上传入口。
- **待确认**：Q01（公司是否独立实体）、Q02（必填字段）、Q03（商圈来源）、Q04（是否需要审核）。

#### S02 员工拜访已有门店并留痕

- **场景**：员工再次拜访一家已录入的门店，记录本次到访情况（拍照、联系人、洽谈结果），并可更新合作状态。
- **角色 / 端**：员工 / 小程序
- **触发**：员工在「拜访登记」中搜索并选中已有门店，或从「附近门店」列表选择。
- **主流程**：
  1. 选择门店；
  2. 现场拍照；
  3. 填写本次联系人、拜访结果 / 洽谈进展、备注；
  4. 提交；
  5. 系统生成拜访记录，并更新门店的「最近拜访时间」；
  6. 若合作状态有变化，同步更新门店合作状态（转入 S06）。
- **涉及功能模块**：**M03 拜访记录、M01 门店档案、M02 地址与地图选点、M12 权限与审计**
- **规则与边界**：
  - 允许同一员工一天内多次拜访同一门店（记录多条）；
  - 拜访时间默认当前时间，是否允许补录历史拜访见 Q08；

  - 拍照张数、是否强制见 Q06。
- **现状与差距**：无拜访记录表；上传能力可复用，但小程序侧没有统一的拍照上传封装。
- **待确认**：Q05（是否强制定位）、Q06（拍照要求）、Q07（拜访结果是否结构化）、Q08（补录限制）。

#### S03 门店查重与重复门店合并

- **场景**：员工新建门店时，系统提示疑似已存在；运营在后台发现重复门店后进行合并。
- **角色 / 端**：员工（提交时提示） / 运营（后台合并）
- **主流程**：
  1. 员工填写门店名称 / 地址 / 地图选点；
  2. 系统按「名称相似 + 地址相似 + 坐标半径」计算疑似重复，展示候选门店；
  3. 员工可选择「就是这家」（转为 S02 拜访）或「确认新建」（需填写理由）；
  4. 运营在后台门店列表中发起「合并」，选择保留门店与被合并门店；
  5. 系统迁移拜访记录、经纪人绑定、线索归属、协议，原门店置为「已合并」并保留追溯。

  - 合并必须二次确认并记录操作日志；
  - 被合并门店的历史数据全部迁移，原门店号保留为「曾用门店」。
- **现状与差距**：无门店实体，无查重能力；小区合并已有先例可参考（`docs/Done/2026-10-26-楼盘字典-小区合并信息合集-SPEC.md`）。

- **待确认**：Q48（数据范围，见 D9）、Q49（权限点划分粒度）、Q50（审计范围）。

#### S18 业务字典与配置维护

## 十、关键决策点（需业务 / 技术共同确认）

> 以下决策会显著改变数据模型或实现成本，**建议先定这些，再进入方案设计**。

### D1 商户（公司）是否独立实体？

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| A. 两层：公司 1:N 门店 | 公司独立建表，门店必属公司 | 支持连锁品牌；可按公司聚合；协议可签在公司层 | 建模与维护成本高；单店客户录入更繁琐 |
| B. 单层：门店即商户 | 公司名称仅作为门店的文本字段 | 简单，贴合「拜访门店」的实际动作 | 连锁门店无法聚合；公司级协议无处挂 |

**建议**：先按 B 落地（v1 简单优先），数据模型预留 `company_id` 可空字段；若连锁客户占比高再升级为 A。

### D2 经纪人身份模型

| 方案 | 说明 | 风险 |
|---|---|---|
| A. 独立 `merchant_brokers` 表 + 可选 `users.id` | 经纪人档案独立，登录时关联 C 端账号 | 需要扩展 `resolve_valid_referrer`，但不动角色体系（**推荐**） |
| B. 复用 `users` + 新增 `broker` 角色 | 经纪人也成为系统用户 | 会触发 `is_internal_user`（非 customer 即内部员工），需全面排查内部能力，风险高 |
| C. 经纪人不登录，仅员工代录 | 最轻 | 不满足「经纪人登录小程序绑定门店」的原始需求 |

**建议**：A。

### D3 经纪人绑定门店是否需要审核？

| 方案 | 说明 |
|---|---|
| A. 免审直接绑定 | 体验最好，但存在抢绑、错绑风险 |
| B. 申请 + 门店归属员工 / 运营审核 | 数据质量高（**推荐**） |
| C. 门店二维码 / 邀请码绑定 | 效率高，可与 B 组合 |

### D4 电子合作协议采用哪种形式？

| 方案 | 说明 | 法律效力 | 成本 |
|---|---|---|---|
| A. 线下签署 + 扫描件上传 + 系统记录状态 | v1 最轻 | 取决于纸质原件 | 低（**v1 推荐**） |
| B. 第三方电子签平台（e签宝 / 法大大等） | 实名认证、意愿认证、存证 | 高 | 高（资质、费用、回调对接） |
| C. 小程序内手写签名 + 生成 PDF | 体验好 | 中 / 取决于实现与存证 | 中 |

### D5 地图供应商与坐标系

- 候选：高德 / 腾讯 / 百度。
- 现状：`communities.lng/lat` 为 **BD-09**；微信 `wx.chooseLocation` 返回 **GCJ-02**；三者混用会产生 50–500 米偏移。
- **建议**：门店模块统一存 **GCJ-02**，表中增加 `coordinate_system` 字段；后台地图优先选高德或腾讯（与 GCJ-02 一致）；存量 BD-09 数据如要复用需转换。

### D6 拜访轨迹口径

| 方案 | 说明 | 风险 |
|---|---|---|
| A. 到店打卡点 + 顺序连线 | 只记录每次拜访的定位点（**推荐**） | 轨迹不是连续路径，但满足「去了哪些店」的复盘需求 |
| B. 连续 GPS 轨迹 | 后台持续定位 | 耗电、隐私合规、微信后台定位权限审核严格 |

### D7 线索归属模型

| 方案 | 说明 |
|---|---|
| A. 三字段并存：`referrer_id`（分享员工）+ `store_id`（推荐门店）+ `broker_id`（推荐经纪人） | 表达最完整，支持多维统计（**推荐**） |
| B. 单一「归属对象」字段 + 类型枚举 | 简单，但无法同时表达员工、门店、经纪人贡献 |

### D8 门店查重规则

- 建议组合：名称相似度 + 地址相似度 + 经纬度半径（如 500 米）+ 联系电话。命中后**只提示不阻断**，员工可强制新建并填写理由。

### D9 数据可见范围

- 员工是否只能看自己拓展 / 拜访的门店？运营是否按区域划分？系统当前无部门 / 区域负责人字段，按区域隔离需要额外建模。
- **建议 v1**：员工仅看自己拓展 / 拜访的门店；admin / operator 看全量。

### D10 与「区域伙伴招募计划」的关系

- 项目已有《区域伙伴招募计划》（`docs/Done/区域伙伴招募计划.md`）与 `recruit_*` 数据模型，其中「区域伙伴」也是外部合作角色。
- **必须确认**：门店经纪人与「区域伙伴」是否为同一角色？
  - 若是 → 复用招募活动的归因链路与用户体系，避免两套外部角色；
  - 若否 → 独立建模，并在文档中明确两者边界。

## 十三、风险与依赖

| 风险 / 依赖 | 说明 | 应对建议 |
|---|---|---|
| 地图 SDK 资质与费用 | 高德 / 腾讯 / 百度均需企业 Key、域名白名单、配额与可能的商用授权 | 立项时同步申请，避免开发到一半卡住 |
| 微信定位接口权限 | `wx.getLocation` / `wx.chooseLocation` 需在 `app.json` 声明 `requiredPrivateInfos`，部分接口需小程序类目审核 | 提前确认小程序类目与接口权限，真机验证 |
| 电子签法律效力 | 「手写签名 + PDF」不一定构成可靠电子签名 | 若业务要求法律效力，直接走第三方电子签（D4-B） |
| 个人信息保护 | 经纪人手机号、员工位置轨迹属于个人信息 | 最小必要采集；隐私政策与员工告知；手机号加密存储 |
| 坐标系不一致 | BD-09 / GCJ-02 / WGS-84 混用导致点位偏移 | 统一坐标系并在表内记录 `coordinate_system` |
| 门店数据质量 | 重复建档、地址不准、坐标缺失 | 查重提示 + 后台合并 + 地图只展示有坐标门店 |
| 组织架构缺失 | 系统无部门 / 区域负责人字段，区域数据权限难落地 | v1 先按「本人拓展」隔离，后续再引入组织架构 |
| 存量线索兼容 | 现有线索没有门店 / 经纪人 | 新字段可空，历史展示「—」，不做强制回填 |
| 角色体系污染 | 新增经纪人角色可能被判定为内部员工 | 优先采用 D2-A（独立档案 + 可选 users 关联），不改角色码 |
