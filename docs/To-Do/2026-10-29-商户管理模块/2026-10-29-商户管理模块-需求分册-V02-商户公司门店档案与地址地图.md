## 2. 模块概述与目标

本册负责商户（公司）与门店主数据，以及门店地址、商圈、地图选点和合作状态。目标是让员工在小程序现场完成“公司—门店”建档，让运营在后台维护同一套主数据，并为拜访、经纪人、协议、线索和地图提供稳定的门店主键与归属。

本期按 D1-A 建立“公司 1:N 门店”两层模型，门店必须归属一家公司；门店地址统一使用 GCJ-02 坐标系；门店查重只提示不阻断；员工可维护本人拓展（`owner_employee_id`）或本人拜访过的门店，关键字段变更留痕。

## 3. 名词与术语

| 术语 | 定义 | 本册使用说明 |
|---|---|---|
| 商户（公司） | 门店所属的经营主体或品牌公司 | 独立实体，代码称 `merchant_companies` |
| 门店 | 线下实体经营门店，是拜访、合作、经纪人归属的最小单元 | 代码称 `merchant_stores` |
| 门店档案 | 门店主数据及其联系人、地址、合作状态等字段的集合 | 本册核心对象 |
| 商圈 | 门店所在商业区域，优先从已有小区商圈聚合，允许手工新增 | 字段 `business_circle` |
| 坐标系 | 经纬度所采用的大地坐标系统 | 本期统一 GCJ-02，字段 `coordinate_system` |
| 查重 | 新建门店时按名称、地址、距离、电话识别疑似重复门店 | 只提示，不阻断 |
| 合并 | 将重复门店的历史数据迁移到保留门店 | 后台操作，见 V07 |
| 搬迁 | 原门店地址发生迁移，保留原门店历史并新建门店 | Q12 确认口径 |
| 合作状态 | 门店与公司的合作阶段 | 字典 `merchant_cooperation_status` |

## 4. 功能需求

### 4.1 商户（公司）主数据

#### REQ-M01A-001 公司创建

| 项目 | 内容 |
|---|---|
| 功能描述 | 在门店建档过程中创建公司主数据，或在后台单独创建公司；公司是门店的必填归属。 |
| 触发条件 | 员工新建门店时选择“新增公司”；经纪人注册创建门店时选择“新增公司”；或 admin/operator 在后台公司管理入口点击“新建公司”。 |
| 主流程 | 1. 输入公司名称并查询是否已存在；2. 未存在时填写公司名称、状态、联系人、联系电话、备注；3. 提交；4. 系统生成公司 `id`；5. 返回公司 `id` 与公司名称，供门店建档使用。 |
| 分支与异常 | 1. 公司名称为空：拒绝提交并提示必填；2. 公司名称已存在：提示“可能已存在”，允许选择已有公司或继续创建，具体策略见 R-V02-02；3. 状态为空：默认“正常”；4. 保存失败：整笔失败并提示，不产生半条公司记录。 |
| 输入字段 | 公司名称、状态、联系人、联系电话、备注 |
| 输出字段 | 公司 `id`、公司名称、状态、创建结果 |
| 业务规则 | BR-M01A-001：公司名称为必填；BR-M01A-002：公司状态至少包含“正常”“停用”，具体枚举见 R-V02-01；BR-M01A-003：公司停用后不可再被新建门店选择，已有门店仍可展示；BR-M01A-004：公司不物理删除。 |
| 权限与角色 | 员工可在门店建档流程内创建公司；经纪人在注册建店流程内可创建/选择公司；admin/operator 可在后台创建；user 仅可创建自己发起的门店所需公司。经纪人创建的公司随门店进入后台审核（R-V02-13）。 |
| 状态流转 | 正常 → 停用；停用后是否可恢复为正常见 R-V02-01。 |

#### REQ-M01A-002 公司查询与选择

| 项目 | 内容 |
|---|---|
| 功能描述 | 按公司名称搜索并选择已有公司，避免重复创建。 |
| 触发条件 | 新建门店、编辑门店、后台门店筛选需要选择公司时。 |
| 主流程 | 1. 输入公司名称关键词；2. 系统返回匹配的公司列表；3. 选择公司；4. 回填 `company_id` 与 `company_name`。 |
| 分支与异常 | 1. 无匹配结果：提示“未找到，可新增公司”；2. 公司已停用：列表可见但不可选，提示状态；3. 输入为空：返回空列表，不发起全量查询。 |
| 输入字段 | 公司名称关键词、状态筛选 |
| 输出字段 | 公司 `id`、公司名称、状态、联系人、联系电话 |
| 业务规则 | BR-M01A-005：门店保存时 `company_id` 必填；BR-M01A-006：门店上的 `company_name` 为冗余展示字段，公司改名后应同步或按公司主数据展示，具体同步方式见 R-V02-02。 |
| 权限与角色 | 员工、admin、operator 均可查询；停用公司仅 admin/operator 可选择用于历史修正。 |

### 4.2 门店档案

#### REQ-M01B-001 小程序新建门店

| 项目 | 内容 |
|---|---|
| 功能描述 | 员工在小程序现场创建门店档案，填写公司、门店、地址、联系人、合作状态并提交。 |
| 触发条件 | 员工进入“商户拓展 → 拜访登记”，搜索门店无结果，点击“新增门店”。 |
| 主流程 | 1. 选择或新增公司；2. 填写门店名称；3. 选择省/市/区县；4. 选择或输入商圈；5. 填写详细地址；6. 地图选点获取经纬度；7. 现场拍照（门头照、店内照均选拍）；8. 填写联系人、联系电话；9. 选择合作状态（新建默认“未合作”，不得直接选“已合作/暂停/终止”）；10. 提交前执行查重提示；11. 确认新建后保存门店档案；12. 自动生成首条拜访记录（见 V03 REQ-M03-001）。 |
| 分支与异常 | 1. 必填字段缺失：逐项提示，不允许提交；2. 地图选点失败：允许重试或手工选择地图位置，不允许无坐标保存；3. 查重命中：展示候选门店，员工选择“就是这家”转 S02，选择“确认新建”须填写理由；4. 员工无门店写权限：拒绝进入新建入口；5. 重复提交：前端幂等处理，避免生成两条门店；6. 新建时选择“已合作/暂停/终止”：拒绝，合作状态变更统一走 REQ-M01B-004。 |
| 输入字段 | 见 4.2.1 门店字段表；门店照片为可选附件，见 REQ-M01B-006 |
| 输出字段 | 门店 `id`、门店名称、公司 `id`、创建时间、首条拜访记录 `id` |
| 业务规则 | BR-M01B-001：门店名称、省、市、区县、商圈、详细地址、经纬度、联系人、联系电话、合作状态、公司为必填（Q02、D1-A）；BR-M01B-002：门头照与店内照均为选拍，不强制（Q06）；BR-M01B-003：员工新建门店免审核，但必须写操作日志（Q04）；BR-M01B-004：员工端创建时 `source=员工拓展`、`owner_employee_id=当前员工`；admin/operator 后台代建时 `source=后台新增`、`owner_employee_id` 由代建人选择，可空；BR-M01B-005：门店状态新建时为“正常”；除经纪人自建门店外 `review_status=已转正`，经纪人自建门店按 `REQ-M01B-007` 置“未审核”；合作状态新建时默认“未合作”；BR-M01B-006：员工小程序现场新建门店必须与一次拜访绑定，禁止无拜访建档（S01）；后台补录/导入是否生成补录首访见 R-V07-11【待确认】；BR-M01B-026：新建门店不得绕过 Q19，禁止直接选择“已合作/暂停/终止”。 |
| 权限与角色 | 员工需 `merchant:write` + `merchant:visit`；admin/operator 后台代建走 V07 REQ-M11-002，仅需 `merchant:write`，不创建首访；user 仅可建自己拓展的门店。 |
| 状态流转 | 新建后为“正常”；后续可转“停用”“已合并”“已搬迁”。 |

#### REQ-M01B-002 门店查重提示

| 项目 | 内容 |
|---|---|
| 功能描述 | 新建门店提交前，按名称、地址、距离、电话识别疑似重复门店，向员工展示候选并允许强制新建。 |
| 触发条件 | 员工填写门店名称、地址、经纬度、联系电话后点击提交。 |
| 主流程 | 1. 系统以名称相似、地址相似、500 米半径、联系电话为信号召回候选门店；2. 按综合相似度排序展示；3. 展示候选门店名称、地址、距离、联系人、合作状态；4. 员工选择“就是这家”转已有门店拜访；5. 或选择“确认新建”并填写理由；6. 系统记录查重结果与理由。 |
| 分支与异常 | 1. 无候选：直接进入保存；2. 候选较多：分页展示，最多展示数量待技术方案；3. 员工不填写强制新建理由：不允许提交；4. 查重服务超时：允许继续保存，但记录“查重未完成”并在后台可复核。 |
| 输入字段 | 门店名称、详细地址、经纬度、联系电话、强制新建理由 |
| 输出字段 | 候选门店列表、匹配信号、员工选择结果 |
| 业务规则 | BR-M01B-007：查重只提示，不阻断（D8、Q09）；BR-M01B-008：强制新建必须填写理由并写操作日志；BR-M01B-009：名称、地址、500 米、电话的具体相似度算法与权重见 R-V02-03，不在本册臆造。 |
| 权限与角色 | 员工在新建门店时触发；admin/operator 后台新建时同样触发。 |

#### REQ-M01B-003 门店信息维护

| 项目 | 内容 |
|---|---|
| 功能描述 | 员工在小程序、运营在后台修改门店档案字段，关键字段变更留痕。 |
| 触发条件 | 员工打开本人拓展（`owner_employee_id`）或本人拜访过的门店详情点击“编辑”；或 admin/operator 在后台门店详情点击“编辑”。 |
| 主流程 | 1. 展示当前门店字段；2. 修改字段；3. 提交前校验必填与格式；4. 关键字段变更记录变更前后值；5. 保存成功并刷新详情。 |
| 分支与异常 | 1. 员工编辑非本人门店：拒绝；2. 必填字段被清空：拒绝；3. 修改地址/经纬度：进入搬迁或纠错选择（见 BR-M01B-012）；4. 修改合作状态：按 REQ-M01B-004 处理；5. 并发修改：以最后提交为准并记录前后值，冲突提示见 R-V02-05。 |
| 输入字段 | 门店字段表全部业务字段 |
| 输出字段 | 更新后的门店档案、变更日志 |
| 业务规则 | BR-M01B-010：员工可编辑本人拓展（`owner_employee_id`）或本人拜访过门店的全部业务字段（Q11 确认，覆盖原文“部分字段”建议）；BR-M01B-011：名称、地址、经纬度、合作状态为关键字段，变更必须记录变更前后值；BR-M01B-012：地址发生跨区域或坐标变化时，员工须选择“地址纠错”或“门店搬迁”；选择搬迁时原门店置为“已搬迁”，新建门店承接后续拜访，原门店历史保留（Q12）；BR-M01B-013：公司名称变更时同步更新门店冗余 `company_name`，同步方式见 R-V02-02。 |
| 权限与角色 | 员工仅本人拓展（`owner_employee_id`）/本人拜访门店；admin/operator 全量；均需 `merchant:write`。 |

#### REQ-M01B-004 合作状态变更

| 项目 | 内容 |
|---|---|
| 功能描述 | 按字典维护门店合作状态，记录变更人、时间、原因，并形成门店时间线。 |
| 触发条件 | 员工或运营在门店详情修改合作状态；或拜访提交时同步变更（V03）。 |
| 主流程 | 1. 展示当前状态与可选目标状态；2. 选择目标状态；3. 填写变更原因；4. 校验权限与前置条件；5. 保存并写操作日志；6. 在门店详情时间线展示。 |
| 分支与异常 | 1. 员工尝试修改为“已合作/暂停/终止”：无论是否有已签协议，均无权限，拒绝；已合作由 operator/admin 修改（Q19）；2. 目标状态与当前相同：不产生变更记录；3. 原因未填：拒绝；4. 字典项停用：不允许新选择，历史值仍可展示。 |
| 输入字段 | 当前状态、目标状态、变更原因 |
| 输出字段 | 新状态、操作人、操作时间、变更前后值 |
| 业务规则 | BR-M01B-014：合作状态枚举为未合作、洽谈中、已合作、暂停、终止（Q18）；BR-M01B-015：员工仅可将状态改为“洽谈中”；operator/admin 可改全部状态（Q19）；BR-M01B-016：“已合作”必须以已签署协议为前提（Q19、V05）；BR-M01B-017：所有状态变更必须记录原因并写审计日志。 |
| 权限与角色 | 员工 `merchant:write` 且仅本人门店；admin/operator 全量。 |
| 状态流转 | 未合作 → 洽谈中 → 已合作 → 暂停 / 终止；暂停 → 洽谈中（operator/admin）；终止后的重开规则见 R-V02-05。 |

#### REQ-M01B-005 门店搜索与详情

| 项目 | 内容 |
|---|---|

## 7. 依赖与影响说明

1. 本册依赖 V01 的权限点、字典组与审计能力；V01 未完成时，本册接口不得上线。
2. V03 的首访创建必须与本册门店创建处于同一业务事务；门店创建成功但首访失败时，整笔回滚。
3. V04 的经纪人必须挂在门店上，门店停用或合并后，经纪人绑定关系按 V04 规则处理。
4. V05 的“已签署协议”是合作状态改为“已合作”的前置条件。
5. V06 的线索 `store_id` 引用本册门店主键；门店合并时线索迁移由 V07 执行。
6. V07 的后台门店 CRUD、合并、导出均复用本册字段与校验规则，不另建一套门店模型。
7. V08 地图只展示有坐标的门店；坐标缺失门店在列表展示并提示补全。
8. 小程序定位与地图选点依赖 `wx.getLocation`/`wx.chooseLocation`，必须在 `app.json` 声明 `requiredPrivateInfos` 并完成微信类目审核；后台地图按 N05 接入高德地图，统一 GCJ-02。
9. 门店联系电话、联系人属于个人信息，展示与导出必须受权限控制。
