**SPEC §4.1 的一处断言不成立（必须纠偏）**：SPEC 写「DDL 必须与 ORM 逐列一致（迭代一 `test_migration_model_parity` 强制）」。实测该测试 `_TABLES = (SchemaMigration, MigrationCompensation)`（`backend/tests/test_migration_model_parity.py:13`），**只覆盖版本账本两张表**，对 `notifications` 等新表**没有任何校验**。→ 新表 DDL/ORM 一致性只能靠人工 + 自建断言保证，不能引用该测试。

**其它数据层约束（已核对，实施时按此写）**：
- 时间列一律 `DateTime(timezone=True)`（`models/common/base.py:282` 的 `BaseModel` 范式；总纲 C8）。
- JSONB 有先例：`models/key/_key_share.py:9`、`models/project/_project_finance.py:159`（`from sqlalchemy.dialects.postgresql import JSONB`）。
- `BigInteger` 自增主键有先例：`models/property/building_dict.py:68`。
- 部分索引有先例：`models/project/_project_sale.py:55`（`postgresql_where=text("is_deleted = false")`）→ 未读索引可用同法。
- `ON CONFLICT DO NOTHING` 有先例：`services/property/dict_import_loader.py:484`、`migrations/_finance.py:195`。
- `dedupe_key` 为可空唯一列：PostgreSQL 允许多个 NULL，与 SPEC K4「空 dedupe 不去重」语义天然一致，**无需额外改造**。

### 3.4 `todo-board?scope=mine`（`my_todos` 的前置条件）

| 事实 | 证据 |
|------|------|
| 路由**零查询参数** | `routers/projects/core.py:196-207`（docstring 明写「无查询参数，全量返回（数据量小），筛选由前端完成」） |
| Service 无 scope | `services/projects/todo_board.py:49 get_board(self)`；`:94 _load_projects()` 固定 `status IN (SIGNING, RENOVATING)` |
| facade 无 scope | `services/projects/facade.py:83-85` |
| 复用的业务身份谓词已存在 | `services/projects/internal/query.py:271 get_by_business_identity`（装修对接人 + 销售 3 字段，UNION 去重） |
| **`user` 角色默认无 `project:read`** | `migrations/_seeds.py:444-455`（user 权限集：`property:read/lead:read/lead:create/lead:upload_photo/ledger:read/investment:read/l4_marketing:read`） |

**两个必须解决的语义问题**：
1. **权限**：`my_todos` 是 `user` 角色的 core widget，而 `user` 无 `project:read`。若沿用 `ProjectReadPermDep` → 直接 403。SPEC 的「`scope=all` 需 `project:read`，`scope=mine` 仅登录」方向正确。
2. **覆盖面**：`_load_projects()` 只取 `SIGNING + RENOVATING`；而业务身份中的「销售团队 3 字段」命中项目通常是 `SELLING/SOLD`。→ 纯销售身份的 `user`，`scope=mine` 会返回**空看板**，与 hifi 样例（客户复看、价格复核）完全不符。需产品决策：是扩 `mine` 到销售阶段（需新增规则），还是接受空态。
