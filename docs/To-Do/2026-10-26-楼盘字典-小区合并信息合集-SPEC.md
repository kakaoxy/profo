# SPEC · 楼盘字典 · 小区合并「信息取最大合集」

> **状态**：**已实施并验证**（T1-T11 完成，后端 1518 单测 + 新 E2E 67 断言 + 前端 460 用例全绿，见 §14）｜撰写 2026-10-26｜module id：`community-merge-union`
> **报障原文**：「a 小区信息不完整但是名字是正确的，b 小区信息完整但是名字不正确，合并后 b 的完整信息全没了。理想中的合并是取两个小区信息的最大合集，保留正确名称（b 并入 a 则保留 a 的名称）」
> **结论**：**现状已复现，属实**。合并只做「归属搬迁 + 软归档」，**完全没有画像字段与户型图的合并步骤**；且链式合并、待审条目、竞品关系三处还有同类「子档数据留在归档行、主档看不见」的缺陷（§1.3）。
> **口径来源**：`docs/Done/2026-10-12-楼盘字典-需求规格说明书.md` FR-14（合并弹层「影响预览」含**图片归属**）、FR-20（「合并小区时图片随主档收敛」）；`DESIGN.md`（前端视觉，冲突时以设计稿为准）
> **仓库约束**：`AGENTS.md` —— 迁移只能追加（`NEXT_VERSION=98`）+ 幂等 + 登记 `registry.py` 与 `__init__.py` 同序；错误响应 `{"code":≠0,"message":"…"}`；前端类型必须 `pnpm gen-api`；修复必须附可复跑验证证据。

## 0. 一页速览

### 0.1 一句话定位

**把「小区合并」从「搬数据 + 归档」升级为「画像取并集 + 资产随迁 + 关系改指 + 全链可逆」**，主档名称永不被覆盖。

### 0.2 用户场景的目标态

| | 合并前 | 合并后（目标） |
|---|---|---|
| 名称 | a =「金杨十街坊」（正确） | **「金杨十街坊」**（保留 a） |
| 环线/物业类型/年代/开发商/物业公司/地址/坐标 | a 全空；b 全有 | **a 全部有值**（来自 b） |
| 户型图 | a 0 张；b 2 张 | **a 2 张**；b 0 张 |
| b | 独立小区（名字错） | 软归档 + b 的名字成为 a 的别名（可搜索、可解除合并） |

### 0.3 改动落点

| # | 改动 | 落点 | 优先级 |
|---|------|------|-------|
| ① | 画像并集（9 字段 + `city_id`） | `services/market/merger.py` 新增 `_merge_community_profile` | **P0** |
| ② | 户型图随迁（含 URL 撞唯一索引处理） | 同上 `_migrate_community_images` + `community_images.origin_community_id` | **P1** |
| ③ | 待审条目 / 竞品关系改指 | 同上 `_migrate_pending_entries` / `_migrate_competitors` | P2 |
| ④ | 链式合并压缩层级 + `origin` 不被覆盖 | `_archive_communities` / `_migrate_dict_buildings` | P2 |
| ⑤ | 存量归档子档画像回填 | 迁移 v99 | **P1** |
| ⑥ | 合并前「将补入什么」预览 + 合并结果回执 | 新端点 `POST /admin/communities/merge/preview` + `merge-dialog.tsx` | **P1** |

### 1.4 同类相邻缺陷（本次一并修，理由：同一个「子档数据看不见」根因）

| # | 缺陷 | 证据 |
|---|------|------|
| A | **户型图不随迁**：`CommunityImage.community_id` 无人改指；弹层却承诺「户型图片随主档收敛」（[merge-dialog.tsx#L185](frontend/src/app/(main)/admin/building-dictionary/_components/merge-dialog.tsx#L185)、SRS FR-20 [L153](docs/Done/2026-10-12-楼盘字典-需求规格说明书.md#L153)） | S3 实测 |
| B | **待审条目（`bd_pending_entries`）不随迁**：`community_id`/`community_scope` 仍指归档子档，审核转正后楼栋落进归档小区（字典树不可见） | S4 实测 |
| C | **竞品关系（`community_competitors`）不随迁**：主档竞品雷达丢数据 | S5 实测 |
| D | **链式合并不压缩层级**：B→A 后再 A→C，B 的 `merged_into_id` 仍指已归档的 A → C 的 `merged_children` 看不到 B；`origin_community_id` 被覆盖成 A（丢失最初归属 B）；且无法从 C 直接解除 B | S6 实测 |
| E | **合并归档后仍可写子档**：`create_buildings` / `dict_import_loader` 不校验 `is_active`，导入同名小区会把楼栋/户室继续落进归档行（实测 `POST /admin/building-dictionary/buildings` 对归档小区返回 201） | 见 §11.2 |

> E 的处置口径见 §3 D7：**只加写入守卫，不做数据搬迁**（避免把「导入落错地方」的历史数据静默改挂）。

### 1.5 现状可绕行方案（已实测，供评审参考——**不满足「最大合集」，且不可接受**）

| 步骤 | 结果 |
|---|---|
| ① 反向合并（把「名字对但不全」的 a 并入「名字错但完整」的 b） | 200，b 保住完整画像，a 变别名 |
| ② 把 b 改名为 a 的原名 | **409**「小区名已被占用（已归档/已合并）」——a 的名字被归档行占用 |
| ③ 先解除合并 → a 改名腾位 → b 改成正确名 → 反向合并 | 全 200，但**需要 4 步人工操作、每次产生一条审计**，且中途任何一步失败都会留下两个错名小区 |

结论：**绕行不可接受**，必须修。

## 2. 目标与验收标准

### 2.1 成功标准（可测）

| ID | 标准 | 验证方式 |
|---|---|---|
| AC-1 | b（完整/错名）并入 a（不全/对名）后，a 的 9 个画像字段全部有值，且值等于 b 的原值 | E2E 逐字段断言 |
| AC-2 | a 的名称不变；b 的名称成为 a 的 `merge_operation` 别名（搜索 b 名命中 a） | E2E + 列表搜索 |
| AC-3 | a 已有非空值**永不被 b 覆盖**（人工修正优先） | E2E：a 有 developer，b 有不同 developer → a 保留 |
| AC-4 | b 的户型图全部出现在 a 的图库；b 图库为空 | E2E 计数 |
| AC-5 | 解除合并后，b 的画像**原样还在**（不被合并污染）；b 的图片按 `origin` 回迁 | E2E |
| AC-6 | 合并前预览接口准确列出「将补入的字段 + 来源子档 + 将迁移的图片/待审/竞品数量」 | 契约测试 |
| AC-7 | 合并响应回执包含补入字段与迁移计数；审计日志 `after` 含同口径明细 | 响应体 + `operation_logs` 查询 |
| AC-8 | 存量归档子档（`merged_into_id` 非空）的画像被回填到主档，且迁移可重复执行 | 迁移幂等测试（跑两次结果一致） |
| AC-9 | 链式合并后主档 `merged_children` 包含全部后代；`origin_community_id` 保留最初归属 | E2E |
| AC-10 | 全部既有 E2E 不回归（`test_bd_merge_conflict.py` / `test_bd_unmerge.py` / `test_bd_perf_security_fixes.py` 等） | `bash backend/tests/e2e/run_all.sh` |

### 2.2 非目标（Out of Scope）

- ❌ 不提供「合并后撤销画像补入」——解除合并**不回退**主档已补入的画像（无法区分「合并补入」与「人工修正」，见 §3 D5）

- ❌ 不修 `community_aliases` 的「`(alias_name, data_source)` 全库唯一」历史怪癖（登记为已知问题，见 §9）
- ❌ 不做「合并影响预览」的房源级明细（只给计数）

## 3. 已裁决口径（实施不得偏离）

| # | 问题 | 结论 | 理由 |
|---|------|------|------|
| **D1** | 画像冲突策略 | **主档非空值永不覆盖；只填主档的空**（逐字段 `COALESCE(primary, child)`） | 「最大合集」的自然语义；同时保护运营对主档的人工修正不被机器覆盖 |
| **D2** | 名称 | 保留主档名；子档名进 `community_aliases(merge_operation)`（**现有行为不变**） | 用户明确要求；别名保证旧名可搜索 |
| **D3** | 「空」的判定 | `NULL` / `strip()` 后空串 / 空数组（`NULL` 或 `{}`）均视为空 | 现网存在 `business_circle=''` 121 行，不能只判 `NULL` |
| **D4** | `property_types` | **并集**（主档在前，去重保序），而非 COALESCE | 数组天然可合并；主档有值时子档的类型也不该丢 |
| **D5** | 解除合并是否回退画像 | **不回退**。子档行从未被改写，故子档画像天然完好；主档补入值保留 | 无法区分补入值与人工值；回退会误删运营修正 |
| **D6** | 图片「迁移」还是「复制」 | **迁移**（改挂主档 + `origin_community_id` 记录原归属），不复制 | 复制会产生双份占位与双份清理成本；`origin` 保证可逆（与 `bd_buildings` 既有模式一致） |
| **D7** | 归档子档的写入守卫 | **加**（补录楼栋/户室、导入 upsert 命中归档行 → 409/跳过并告警），**不搬迁历史数据** | 与 `patch_community` 已有的 409 守卫（[dict_write_service.py#L699-L719](backend/services/property/dict_write_service.py#L699-L719)）、`rename_community` 守卫（[dict_rename_mixin.py#L259](backend/services/property/dict_rename_mixin.py#L259)）同口径 |
| **D8** | 迁移编号 | v98（3 个 `origin` 列）/ v99（存量画像回填）；`NEXT_VERSION` 从 98 起 | [registry.py#L1227](backend/migrations/registry.py#L1227) |
| **D9** | 合并/解除的 `origin` 模式 | 统一用「逐表 `origin_community_id`」列，**不引入通用 ledger 表** | `bd_buildings` 已是此模式（[building_dict.py#L70](backend/models/property/building_dict.py#L70)）；两套机制混用违反 `AGENTS.md` §5「禁止混合」 |

### 3.1 待裁决（评审时确认，默认按推荐执行）

| # | 歧义点 | 推荐 | 备选 | 影响 |
|---|---|---|---|---|
| **Q1** | `address` 两边都非空且不同：拼接还是保留主档？ | **按 `,` 切分去重合并**（主档在前）；合并后 > 500 字符则**保留主档地址**并把子档地址写进回执 `warnings`（不静默丢） | 只保留主档（更保守，但丢子档地址） | 现网 1,845 行地址是多弄拼接（最长 388），拼接语义更贴合数据形态；但可能超列宽 |
| **Q2** | `era_from/era_to` 只补一侧会产生「跨小区年代区间」 | **成对优先**：主档整对为空 → 整对取子档；主档只有一侧 → 补另一侧（需满足 `from<=to`，否则整对保留主档并告警） | 严格成对（主档缺一侧就不补） | 现网 11,099 行只有单侧年代，严格成对会大量放弃可补数据 |
| **Q3** | 合并前预览是新增端点还是复用 merge 的 dry-run | **新增只读 `POST /admin/communities/merge/preview`**（同请求体，零副作用） | merge 加 `dry_run` 字段 | 新增端点语义清晰、不污染写端点；但需多一个权限点/限流配置 |

> **⚠️ 未覆盖/不确定**：Q1 的 500 字符上限是按 `String(500)` 列宽推的（[community.py#L61](backend/models/property/community.py#L61)）。若要彻底避免截断，需评估是否把列宽提到 1000 —— 本 SPEC 选择「不扩列 + 告警」，因为扩列属 schema 变更且收益有限。

## 4. 后端方案设计

### 4.1 主流程（新顺序）

```python
# backend/services/market/merger.py::merge_communities
primary = self._validate_communities(primary_id, merge_ids, db)
children = db.query(Community).filter(Community.id.in_(merge_ids)).all()
affected = self._count_affected_properties(merge_ids, db)

profile_result = self._merge_community_profile(primary, children)      # ① P0 新增
self._process_aliases(primary, children, db)
self._migrate_properties(primary_id, merge_ids, db)
dict_stats = self._migrate_dict_buildings(primary_id, merge_ids, db)
doc_count = self._migrate_business_docs(primary_id, merge_ids, db)
pending_stats = self._migrate_pending_entries(primary, children, db)    # ② P2 新增
image_stats = self._migrate_community_images(primary, children, db)     # ③ P1 新增
competitor_stats = self._migrate_competitors(primary, children, db)     # ④ P2 新增
self._archive_communities(primary, children)                           # ⑤ 压缩层级
self._refresh_primary_stats(primary, db)
db.commit()
```

- 全部步骤**同一事务**（既有 `db.commit()` 单点，异常回滚语义不变）
- 行锁沿用 `_validate_communities` 的 `with_for_update`（[L172-L205](backend/services/market/merger.py#L172-L205)）
- 新增步骤**不得**自行 commit

### 4.2 ① 画像并集（P0，核心）

**纯函数**（可单测、无 DB 依赖）：

```python
# backend/services/market/community_profile_merge.py（新文件，≤200 行）
@dataclass(frozen=True)
class ProfileUnion:
    values: dict[str, Any]          # 合并后的字段值
    filled: list[str]               # 本次由子档补入的字段名（回执/审计用）
    warnings: list[str]             # 超长地址、年代交叉、坐标越界等

def merge_community_profile(
    primary: Mapping[str, Any],     # 主档现有值
    children: Sequence[Mapping[str, Any]],  # 子档现有值（按 merge_ids 顺序）
) -> ProfileUnion: ...
```

| `business_circle` | 空则取子档 | |
| `ring` | 空则取子档 | |

| `era_from` / `era_to` | 成对规则见 Q2 | |
| `developer` | 空则取子档 | |
| `property_mgmt` | 空则取子档 | |
| `address` | 规则见 Q1 | |
| `lng` / `lat` | **成对**：任一为空 → 整对取子档；取值需在 `lng∈[73,136]`、`lat∈[3,54]` 内，越界丢弃并告警 | 与 `BdCommunityPatchRequest` 值域一致（[schemas/building_dict.py#L223-L224](backend/schemas/building_dict.py#L223-L224)） |

| `source` | **保留主档**，不取子档 | 子档 `source` 代表其录入端，混用会误标 |
| `avg_price_wan` | **不参与** | 现网全 NULL，Out of Scope |
| `total_properties` | 由 `_refresh_primary_stats` 重算（现有逻辑） | |

**多子档合并顺序**：按请求 `merge_ids` 顺序依次叠加（先到先得，主档优先）。即 `result = fold(primary, children)`，保证确定性。

**写回**：只 `setattr` `filled` 里的字段 + `primary.updated_at`。**子档行一个字节都不改**（AC-5 的前提）。

### 4.3 ② 待审条目改指（P2）

```
对 bd_pending_entries(kind IN (building, room), status=pending, community_id ∈ merge_ids)：
  1. 尝试 community_id = primary, community_scope = primary, origin_community_id = 原子档
  2. 若撞 uq_pending_open（同 kind/scope/parent_is_pending/parent_id/normalized_name）：
     - 把本条 bd_pending_references 逐条改挂到已存在条目（撞 uq_bd_pending_ref_biz 的重复引用直接删除）
     - 本条置 status=merged、resolved_target_id=已存在条目 id、resolved_by=操作人、resolved_at=now
     - 审计记一条 bd_pending_merge_by_community_merge
  3. 否则直接改指并落 origin
```

- **不改** `kind=community` 的 pending（其 `community_id` 为 NULL，与小区档案合并无关）
- **不改** `parent_is_pending=true` 的条目（父级本身在审核池，拓扑由审核链路管）

### 4.4 ③ 户型图随迁（P1）

```
对 community_images(community_id ∈ merge_ids, is_deleted=false)：
  base = 主档当前 max(sort_order) + 1
  逐张：
    if 主档已存在同 url 的未删行：
        image.community_id = primary
        image.is_deleted   = true        # 去重软删（解除合并时复活）
        image.origin_community_id = 原子档
    else:

```

- 已软删的图片不动（不占主档图库）。
- 公开端点 `GET /public/communities/{id}/images` 目前不校验 `is_active`；迁移后归档子档图片为 0，残留仅可能来自历史数据 → 本 SPEC 顺手在**两个图片读端点**加「小区必须 active」的守卫（P1，见 §5.3）。

### 4.5 ④ 竞品关系改指（P2）

```
1. owner 侧：community_id ∈ merge_ids → primary（origin=原子档）
2. 引用侧：competitor_community_id ∈ merge_ids → primary
3. 结果去重：撞 uq_community_competitor 的重复边直接删除

### 14.8 S13 的顺序不变量（实施中发现并修掉的一个自己引入的缺陷）

- 验证：新增 E2E **S13**（两个子档各持不同的 ring/developer，分别以甲/乙在前跑两轮，
  断言「预览值 == 实际值 == 请求序第一个子档的值」）。
- **变异测试**（证明该断言真的有判别力，不是恒真）：临时把合并侧还原成
  `db.query(...).in_(...)` 原样序后重跑，S13 立刻失败并给出真实漂移证据 ——

```

   — 预览 ring=外环外/dev=乙开发商  实际 ring=内环内/dev=甲开发商  预期 外环外

还原修复后 60/60 复绿。另注：S13 起初内含一次 `cleanup()`，会把 S11 留给 S12 的
造数一起删掉，使 S12 的 400 变成「主档不存在」而非「子档已归档」而**假绿**；
已移除该 cleanup 并在注释中钉住原因。

### 14.9 竞品边迁移的两个实施期自找缺陷（都由新增 E2E 抓出）

§4.5 原本只写了「改指 + 撞唯一约束则删除」，实施时踩到两个坑，都是**自己引入**的：

**缺陷 A：先用 ORM 改 `community_id`，再跑去重 SQL。**
SQLAlchemy 的 autoflush 会在去重语句之前就把重复边写进库里，直接撞
`uq_community_competitor` → 整笔合并 **400「数据库操作失败」**（E2E S7-b 实测）。
修法：**整个竞品迁移改为纯 SQL，且先按「改指后的最终 (owner, competitor)」预清理冲突**
（`WITH projected ... ROW_NUMBER()`），之后两条 UPDATE 必然不撞约束。

**缺陷 B：去重时按 `id` 任意取舍。**
`community_competitors.id` 是随机 UUID，`a.id > b.id` 等于抛硬币。一旦留下的是
**迁移来的那条**（带 `origin`）、删掉主档原本那条，解除合并就会把这唯一一条边
搬回子档 → **主档平白丢掉它本来就有的竞品关系**，正是本 SPEC 要消除的那类丢失。
修法：排序键改为 `ORDER BY (origin_community_id IS NULL) DESC, id ASC`
（优先保留主档原行），并在 §9 记为 L7（子档重复边不随解除合并恢复）。

§5.1 契约补充（§14.10）：预览端点**不加行锁**。

两次都做了**变异测试**证明断言有判别力：

| 变异 | S7-b 结果 |
|---|---|
| `will_move DESC`（优先保留迁移来的边） | ❌ 合并后剩 `origin=e4bea4b5`（应是 NULL）；❌ **解除合并后主档竞品关系=0 条** |
| 还原为 `ASC` | ✅ 62/62 |

> 第一轮变异用 `ORDER BY id DESC` 时**没有**触发失败——因为 UUID 随机，那是概率性
> 反例。教训：变异测试的「错误版本」必须是**确定性**的，否则「断言没红」说明不了
> 断言无效，反而会给出假的安心。


### 14.10 预览端点偷加行锁（实施期自找缺陷，第三个）

`preview_merge` 复用了写路径的 `_validate_communities`，而后者带
`with_for_update()` —— 于是「只读、零副作用」的预览实际会**锁住主档 + 全部子档行**。
预览在弹层里每次勾选都触发（防抖 300ms），意味着运营一边点勾选、一边就可能有
同事的真实合并被行锁挡住。这既违反本文档 §5.1 的契约，也是我自己引入的。

修法：`_validate_communities(..., for_update: bool = True)`，**写路径保持加锁**
（并发合并保护一点没削弱），预览显式传 `for_update=False`（校验规则完全一致，只是不锁行）。

验证（E2E **S14**，不靠「应该没锁」的推断，而是 `before_cursor_execute` 钩子
捕获真实发出的 SQL）：

| 断言 | 结果 |
|---|---|
| 预览全程 SQL 不含 `FOR UPDATE` | ✅ 「无锁语句」 |
| 合并仍对 `communities` 加行锁 | ✅ 命中 `SELECT communities.id … FOR UPDATE` |

双向变异测试（证明两个方向都不是空断言）：

| 变异 | 结果 |
|---|---|
| 预览改回 `for_update=True` | ❌ 「预览全程 SQL 不含 FOR UPDATE」失败（捕获到 offenders） |
| 默认值改成 `for_update=False`（写路径也失去锁） | ❌ 「合并仍对 communities 加行锁」失败（未观察到行锁） |


### 14.11 审计留痕失真（实施期自找缺陷，第四个）

§5.4 要求审计记 `profile_before / profile_after`。我最初在 `merge_communities` 里这样取：

```python
profile = self._merge_community_profile(primary_community, merge_communities)  # 已就地改写主档
...
profile_before={name: getattr(primary_community, name, None) for name in profile.filled},  # ❌
```

`_merge_community_profile` 是**就地修改 ORM 对象**的，等调用方再去 `getattr` 读到的
已经是「改之后」的值 → 审计里 `before` 与 `after` **完全相同**，等于没留痕：
无法核对「补入了什么」、也无法支撑 L1「按快照人工回退」。实测留档：

```
profile_before: {"ring": "外环外", "property_types": [], "developer": "乙开发商"}
profile_after : {"ring": "外环外", "property_types": [], "developer": "乙开发商"}
→ 两者相同（before 是假的）
```

修法：快照改由 `_merge_community_profile` **在改写之前**捕获，随 `ProfileUnion`
返回（`ProfileUnion` 是 frozen dataclass，用 `dataclasses.replace` 产出新实例——
直接赋值会抛 `FrozenInstanceError`，这也是我先试出来的）。调用方只读 `profile.before/after`，
**没有机会再取错**。修复后实测：

```
before: {"ring": null, "developer": null, ...}
after : {"ring": "外环外", "developer": "乙开发商", ...}   ← 真实区分
```

新增 E2E 断言两条把它钉住（`profile_before != profile_after` 且 `before` 为 None、
快照键集合 == `profile_filled`）。**这两条断言在修复前直接失败、修复后转绿**，
判别力由缺陷本身证明，无需额外变异。

> 过程教训（如实记录）：这条断言之所以此前没被发现，是因为原 §8.2 只断言了
> 「审计里有 `profile_filled` 这个键」——**存在性断言挡不住内容失真**。
> 另外，本轮一次补丁因 shell `cd` 失败而**静默未应用**（我误以为已修好），
> 是重跑 E2E 才暴露的。结论：改完必须重跑断言，不能只看补丁命令退出码。
