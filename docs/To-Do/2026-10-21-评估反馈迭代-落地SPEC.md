## 3. 关键口径收口（K1–K14，全部为实施决策，不再二次讨论）

| # | 决策 | 口径 |
|---|------|------|
| **K1** | 评分粒度 | **单一综合分** 1–5（不拆户型/楼层）。锚点表见 §4.1，锚点只进前端文案，**不入库** |
| **K2** | 评分可空性 | **DB 可空 / Pydantic 新写入必填**。DB 可空是为存量；新写入路径由 `LeadEvalHistoryCreate` 的必填校验兜住 |
| **K3** | 天数可空性 | 同上。范围 `1–365`（整数天），DB 加 `CHECK` |
| **K4** | 档位是否入库 | **不入库**。档位（快/正常/偏慢/慢）由纯函数派生 —— 阈值会调，改阈值不该刷全表 |
| **K5** | 档位阈值 | `≤30 快` / `31–60 正常` / `61–90 偏慢` / `>90 慢`。**该阈值沿用本项目既有「带看时效」分档语感，非市场校准结果**；后续拿到真实成交周期分布后只改 `lead-verdict` 一处（两端同改） |
| **K6** | 天数展示翻译 | 恒附带「约 N 个月」：`Math.round(days/30*10)/10`，整数去小数点（`45 → 约 1.5 个月`，`30 → 约 1 个月`） |
| **K7** | 真实号可见性 | **员工与客户均可见真实号**。列表/详情只给脱敏号（`mask_phone`）；真实号走**独立端点**按需拉取 |
| **K8** | 真实号归属校验 | 客户：`lead.creator_id == user_id`；员工：`_has_internal_role(user)`。二者其一即放行，否则 403 |
| **K9** | 留痕时机 | **先拨号、后异步上报**。`wx.makePhoneCall` 有系统确认、可能被取消；上报失败静默，绝不因记不上日志而让人打不出电话 |
| **K10** | 留痕内容 | `method='phone'`，`content='客户致电评估人 {nickname}'` / `'员工致电评估人 {nickname}'`（按调用者身份区分），≤500 字 |
| **K11** | 终态线索是否允许留痕 | **允许**。跟进记录是事实记录，`rejected`/`lost_to_competitor` 已关闭线索仍应能记录「为何关闭后再联系」；但**员工侧既有 `create_followup` 会 409**，故客户侧新端点走独立路径，不复用该守卫（见 §5.4 K11 说明） |
| **K12** | 评估人取值 | 取**最新一条** `LeadEvalHistory` 的 `evaluator`。历史行不各自挂拨号入口 —— 避免「该打给谁」变选择题 |
| **K13** | 存量降级文案 | `condition_score IS NULL` → 「未评分」；`expected_sale_days IS NULL` → 「周期待补」。**灰底 chip，不隐藏、不补默认值** |
| **K14** | 职称徽标 | **本期不做**。`users` 无职称字段；只显示昵称 + 角色码映射（`admin`→管理员、`operator`→运营）。设计稿的「评估师」徽标标注为待补 |

## 4. 设计细节

### 4.1 评分锚点表（写入前端常量，不入库）

| 分 | 短标签 | 锚点（员工自我对照） |
|---|-------|-------------------|
| 5 | 优质 | 户型方正通透、当前楼层段在小区里最好卖，几乎无硬伤 |
| 4 | 良好 | 主流户型，楼层可接受，有 1 项需在带看时说清的短板 |
| 3 | 一般 | 户型或楼层有一项明显折价，需要靠价格补 |
| 2 | 偏弱 | 户型与楼层同时偏弱，或存在硬伤需重装化解 |
| 1 | 难售 | 结构性难卖，通常伴随长周期或需要显著让价 |

> 锚点用于保证「4 分」跨员工指同一件事。无锚点的一致性，跨人评分等于噪声。

### 4.2 派生函数契约（`lead-verdict`）

```ts
// 前端 frontend/src/lib/lead-verdict.ts
// 小程序 miniapp/utils/lead-verdict.ts —— 两处必须同值（V5 断言）

export type ScoreLevel = 1 | 2 | 3 | 4 | 5;
export type CycleTier = "rush" | "normal" | "slowish" | "slow";

/** 评分短标签；score 为空返回 null（调用方渲染降级态）。 */
export function scoreLabel(score: number | null | undefined): string | null;

/** 天数档位；days 为空/非正返回 null。 */
export function daysTier(days: number | null | undefined): CycleTier | null;

/** 天数档位短词（快/正常/偏慢/慢）；null 入参返回 null。 */
export function daysTierLabel(days: number | null | undefined): string | null;

/** 「约 N 个月」；null 入参返回空串（调用方自行决定是否渲染）。 */
export function daysSay(days: number | null | undefined): string;

/** 卡片一行摘要：「45 天 · 约 1.5 月」；null 返回 "周期待补"。 */
export function daysSummary(days: number | null | undefined): string;
```

**边界口径（写进单测）**

| 输入 | `daysTier` | `daysSay` | `daysSummary` |
|------|-----------|-----------|--------------|
| `null` / `undefined` / `0` / `-1` / `NaN` | `null` | `""` | `"周期待补"` |
| `1` | `rush` | `约 0.1 个月` | `1 天 · 约 0.1 月` |
| `30` | `rush` | `约 1 个月` | `30 天 · 约 1 月` |
| `31` | `normal` | `约 1 个月` | `31 天 · 约 1 月` |
| `45` | `normal` | `约 1.5 个月` | `45 天 · 约 1.5 月` |
| `60` | `normal` | `约 2 个月` | `60 天 · 约 2 月` |
| `61` | `slowish` | `约 2 个月` | `61 天 · 约 2 月` |
| `90` | `slowish` | `约 3 个月` | `90 天 · 约 3 月` |
| `91` | `slow` | `约 3 个月` | `91 天 · 约 3 月` |
| `365` | `slow` | `约 12.2 个月` | `365 天 · 约 12.2 月` |

> 注意 `31` 与 `30` 分属不同档位但 `daysSay` 同为「约 1 个月」—— 这是**刻意**的：
> 档位是机器判断，月份是人话翻译，两者不必对齐。

```python
"""为 lead_eval_histories 增加评分与可售周期两列及 CHECK 约束（幂等）."""

import logging

from sqlalchemy import text
from sqlalchemy.engine import Engine

logger = logging.getLogger(__name__)


def _constraint_exists(engine: Engine, table: str, conname: str) -> bool:
    """检查某表上是否已有指定名称的 CHECK 约束.

    ⚠️ 必须同时按 ``conrelid`` 过滤：PG 的约束名只在**表内**唯一，
    全局按 ``conname`` 查会把别的表上的同名约束误判为本表已有。
    """
    with engine.connect() as conn:
        return bool(
            conn.execute(
                text(
                    "SELECT 1 FROM pg_constraint "
                    "WHERE conrelid = :tbl::regclass AND conname = :name AND contype = 'c' LIMIT 1"
                ),
                {"tbl": f"public.{table}", "name": conname},
            ).first()
        )


def add_lead_eval_verdict_fields(engine: Engine) -> None:
    """幂等为 lead_eval_histories 增加评分与可售周期两列及其 CHECK 约束."""
    # 延迟导入避免循环依赖（与 add_lead_eval_history_and_expected_price 一致）
    from migrations import _column_exists

    table = "lead_eval_histories"

    # 1. 加列（幂等）
    if not _column_exists(engine, table, "condition_score"):
        logger.info("迁移：%s 增加 condition_score", table)
        with engine.begin() as conn:
            conn.execute(text(f"ALTER TABLE {table} ADD COLUMN condition_score SMALLINT"))

    if not _column_exists(engine, table, "expected_sale_days"):
        logger.info("迁移：%s 增加 expected_sale_days", table)
        with engine.begin() as conn:
            conn.execute(text(f"ALTER TABLE {table} ADD COLUMN expected_sale_days SMALLINT"))

    # 2. 加 CHECK 约束（幂等：ADD CONSTRAINT 不支持 IF NOT EXISTS，必须先查 pg_constraint）
    if not _constraint_exists(engine, table, "ck_lead_eval_condition_score"):
        logger.info("迁移：%s 增加 ck_lead_eval_condition_score", table)
        with engine.begin() as conn:
            conn.execute(
                text(
                    f"ALTER TABLE {table} ADD CONSTRAINT ck_lead_eval_condition_score "
                    "CHECK (condition_score IS NULL OR (condition_score BETWEEN 1 AND 5))"
                )
            )

    if not _constraint_exists(engine, table, "ck_lead_eval_expected_sale_days"):
        logger.info("迁移：%s 增加 ck_lead_eval_expected_sale_days", table)
        with engine.begin() as conn:
            conn.execute(
                text(
                    f"ALTER TABLE {table} ADD CONSTRAINT ck_lead_eval_expected_sale_days "
                    "CHECK (expected_sale_days IS NULL OR (expected_sale_days BETWEEN 1 AND 365))"
                )
            )
```

> **为何不用 `ADD CONSTRAINT ... NOT VALID` + `VALIDATE` 两步**：
> 该手法是为大表避免长时间持锁；`lead_eval_histories` 当前量级远小于此阈值，
> 一次性 `ADD CONSTRAINT` 更快且少一个中间态。**若上线前实测表行数 > 百万级**，
> 再改用两步法（`NOT VALID` → 单独 `VALIDATE CONSTRAINT`）。

```python
def get_evaluator_contact(self, lead_id: str, user: User) -> PublicEvaluatorContact:
    """获取评估人真实联系方式.

    权限：线索创建人 或 内部员工（admin/operator）。
    取最新一条 LeadEvalHistory 的 evaluator；评估人或其手机号缺失 → 409。

    Raises:
        ResourceNotFoundError: 线索不存在/已软删除/无任何评估记录
        PermissionDeniedError: 既非创建人也非内部员工
        BusinessLogicError: 评估人未登记手机号
    """
    lead = self.query_service.get_by_id(lead_id, load_creator=False)
    if lead is None:
        raise ResourceNotFoundError("线索不存在")
    if lead.creator_id != user.id and not self._has_internal_role(user):
        raise PermissionDeniedError("无权查看该线索的评估人联系方式")

    rec = (
        self.db.query(LeadEvalHistory)
        .options(joinedload(LeadEvalHistory.evaluator))
        .filter(LeadEvalHistory.lead_id == lead_id)
        .order_by(desc(LeadEvalHistory.evaluated_at))
        .first()
    )
    if rec is None:
        raise ResourceNotFoundError("该线索尚无评估记录")
    evaluator = rec.evaluator
    if evaluator is None or not evaluator.phone:
        raise BusinessLogicError("评估人未登记手机号")

    return PublicEvaluatorContact(
        phone=evaluator.phone,
        nickname=evaluator.nickname or "",
        lead_id=lead_id,
        evaluation_id=str(rec.id),
    )
```

> 因此**不用** `text("SELECT DISTINCT ON ...")`（DISTINCT ON 是 PG 专属，且破坏 ORM 一致性），
> 改用仓库已有的 `func.row_number().over(partition_by=..., order_by=...)` 子查询范式
> —— 先例：`backend/services/marketing/subscription.py:186` 的「取每人最新一条日志」。

```python
# services/leads/internal/query.py
from models.lead import Lead, LeadEvalHistory, LeadFollowUp   # 追加 LeadEvalHistory

def get_latest_eval_verdicts(self, lead_ids: list[str]) -> dict[str, dict[str, Any]]:
    """批量取每条线索最新评估记录的条件分与可售周期（单次查询，避免 N+1）.

    口径：每条线索取 ``evaluated_at`` 最新的一条；同刻并发写入时以 ``id`` 倒序作确定性
    tiebreaker（对齐 get_handled 的 tiebreaker 习惯）。

    Args:
        lead_ids: 线索ID列表（空列表直接返回空字典，不发查询）

    Returns:
        dict[lead_id] -> {"condition_score": int|None, "expected_sale_days": int|None}；
        无评估记录的线索不出现在结果中（调用方用 ``.get(id, {})`` 回退）

    """
    if not lead_ids:
        return {}
    latest = self.db.query(
        LeadEvalHistory.lead_id,
        LeadEvalHistory.condition_score,
        LeadEvalHistory.expected_sale_days,
        func.row_number()
        .over(
            partition_by=LeadEvalHistory.lead_id,
            order_by=(desc(LeadEvalHistory.evaluated_at), desc(LeadEvalHistory.id)),
        )
        .label("rn"),
    ).filter(LeadEvalHistory.lead_id.in_(lead_ids)).subquery()

    rows = (
        self.db.query(
            latest.c.lead_id,
            latest.c.condition_score,
            latest.c.expected_sale_days,
        )
        .filter(latest.c.rn == 1)
        .all()
    )
    return {
        r.lead_id: {
            "condition_score": r.condition_score,
            "expected_sale_days": r.expected_sale_days,
        }
        for r in rows
    }
```

在 **`services/leads/core.py::get_handled_leads`** 里与 `followup_stats` **同一处**追加
（现成的批量聚合就在 `:645`，与 `get_followup_stats` 并列；**不是**在 Router 里）：

```python
# services/leads/core.py — get_handled_leads（现有 :643-646）

items: list[Lead] = result["items"]

```

Router 侧（`routers/public/leads.py::get_handled_assessment`）只需在构造 `HandledItem` 时取值：

```python
for lead in result["items"]:
    ...
    verdict = eval_verdicts.get(lead.id, {})   # 无评估记录的线索 → 空 dict → 两字段 None

        ...,

```

> `eval_histories = self.eval_service.get_evaluations(lead_id)`（按 `evaluated_at DESC` 排序，`evaluation.py:66`），
> 因此 Router 侧直接取 **`eval_histories[0]`** 即可得到最新一条的 `condition_score` /
> `expected_sale_days` / `evaluator`（该记录的 `evaluator` 已 `joinedload`）。
> **不要**再调 `get_latest_eval_verdicts([lead_id])` 多打一次库。

> ⚠️ **同类还有两处需要同样处理**（容易只改一处）：
> - `routers/leads/core.py::_to_list_item`（admin 列表）— 其数据源 `get_list` 不带 verdicts，
>   需在 Router 层构造前统一批量取：`verdicts = service.get_latest_eval_verdicts([i.id for i in items])`；
> - `routers/leads/core.py::get_lead`（admin 详情，走 `LeadResponse.model_validate(lead)`）—
>   **`Lead` 没有这两列**，`model_validate` 取不到值，必须在 validate 后手动 `setattr`，
>   与现有 `_dict_names_update` 补字典名称的写法完全同构：
>   ```python
>   verdict = service.get_latest_eval_verdicts([lead.id]).get(lead.id, {})
>   resp.condition_score = verdict.get("condition_score")
>   resp.expected_sale_days = verdict.get("expected_sale_days")
>   ```

> **性能边界**：`(lead_id)` 已有索引 `idx_lead_eval_history_lead`（建表时声明），
> `IN (当前页 ≤ page_size 个 id)` + 窗口函数不引入新索引需求；
> `page_size` 上限受 `settings.max_page_size` 约束，单页行数可控。
> **若后续 page_size 上调到千级**，再评估是否需要 `(lead_id, evaluated_at DESC)` 复合索引。

**方案 B（不推荐）**：`Lead` 加冗余列 —— 需额外维护「评估写入时同步刷新」，
且与 `Lead.eval_price` 的既有冗余重复，成本高于收益。**仅在方案 A 的窗口函数查询有明显性能问题时再考虑**。

## 7. 边界与降级

### 7.1 无评估记录（`pending_assessment` 线索）

- `LeadEvalHistory` 不存在 → `condition_score` / `expected_sale_days` 全 `None`
- admin KPI 两格显示「—」；小程序卡不渲染结论条（待评估卡本来就没有）
- E4 `evaluator-contact` 返回 **404**「该线索尚无评估记录」

### 7.2 评估人无手机号

- `PublicEvaluatorBrief.phone_masked = None`
- C 端 `SystemEstimateCard` 评估人条：「暂未登记手机号」+ **不渲染拨号按钮**（不留死链）
- 小程序评估人卡：按钮降级为「登记跟进」（跳既有跟进面板）

### 7.3 存量记录（`condition_score IS NULL`）

- admin 历史行：不渲染星级与天数 chip
- 小程序已处理卡：灰底 chip「未评分」「周期待补」
- C 端详情：**不渲染**双指标区（存量线索客户看不到该区块，属预期）
- **绝不**用默认分补齐（K13）

### 7.4 职称徽标

- 本期**不显示**「评估师」徽标（`users` 无职称字段，K14）
- 若产品坚持要显示，降级方案：用角色码映射（`admin`→「管理员」、`operator`→「运营」）。
  **不得**硬编码「评估师」字符串伪装成数据

### 7.5 基线对比（「快于小区平均 N 天」）

- **本期不实现**。无数据源（`services/reports/aggregations.py` 的 `absorption_months` 是商圈级、按月、非单套）
- WXML / TSX 中**不写**该区块，避免留空壳
- 后续接入时：有基线才渲染，无基线整行消失（不显示「暂无对比数据」）

## 10. 明确不做（Out of Scope）

| 项 | 原因 |
|----|------|
| 户型分 / 楼层分**拆分**打分 | 员工打两次分、客户读两个数字再自综合，与「对数据不敏感」直接冲突（K1） |
| 评分**趋势图** | 员工关心最新结论，历史只需可追溯；抽屉内塞可视化是负担 |
| 档位**入库** | 阈值会调，入库意味着改阈值要刷全表（K4） |
| 「评估准不准」回写校准 | 需在 `signed` 时回写实际售出天数，属**下一轮**（§11） |
| 评估人**职称/岗位** | `users` 无该字段（K14 / R6） |
| 小区**平均售出天数**基线 | 无数据源（§7.5） |
| Web admin 拨号**留痕写 lead_followups** | admin 侧写 `operation_logs`（`sensitive_data_access`）即可；写跟进会污染客户可见时间线 |
| 手机号**审计**在 Service 层 | 仓库惯例是 Router 层插桩（三处先例），Service 保持不写审计 |
| OpenAPI **版本化 / 兼容层** | 单团队单仓，同版本发布（R1 缓解已说明） |

## 11. 后续建议（下一轮，需要单独排期）

### 11.1 让「预计 45 天」可被校准

**问题**：`expected_sale_days` 是员工主观预估，永远无法验证准确性。两三年后它仍是一句猜测。

**建议**：线索转到 `signed` 且项目最终售出时，回写实际售出天数（项目侧已有
`days_on_market` 字段，见 `admin/projects/[projectId]/_components/page-shell/hero-section.tsx:143`），
与 `expected_sale_days` 做差。

**验收**：`SELECT avg(actual_days - expected_sale_days) FROM ...` 可得偏差分布；
偏差 > ±30 天的员工进入校准提示名单。

### 11.2 档位阈值重新校准

`30 / 60 / 90` 来自本项目既有「带看时效」分档语感，**不是市场数据**（K5）。
拿到真实成交周期分布后，只需改 `lead-verdict.ts` 一处（两端镜像，见 V5）。

### 11.3 评分与成交转化率的相关性

有了 `condition_score` 后，可算「4 分以上的线索签约率 vs 3 分以下」。
若两者无相关性，说明评分锚点没被员工真正使用 —— 这会是最有价值的反馈信号。
