## 2. 模块概述与目标

本册负责门店经纪人的独立档案、微信登录认证、门店绑定、换绑、解绑与绑定历史，以及经纪人在小程序查看“我的门店”和本人推荐记录。经纪人不是内部员工，不新增系统角色码，不进入 admin 后台；经纪人身份由独立 `merchant_brokers` 表承载，可选关联 `users.id`。D3-A/Q22 的免审仅适用于**首次绑定**；S08 原文明确换绑/解绑由“运营审核”，本册对换绑/解绑按审核流程落地。

本期按 D2-A 独立经纪人表 + 可选 `users.id` 落地；按 D3-A 绑定免审直接生效；同一经纪人同一时间只能绑定一个门店；换店不迁移历史线索；经纪人可查看本人推荐线索的完整跟进记录（Q26）；手机号必填并上线短信验证（N06）；与招募域按 N02 只读引用招募线索 ID、手机号哈希匹配。

## 3. 名词与术语

| 术语 | 定义 | 本册使用说明 |
|---|---|---|
| 经纪人 | 门店内的从业人员，可登录小程序、绑定门店、推荐客户 | 代码称 `merchant_broker`，严禁复用 `AGENT` |
| 经纪人档案 | 经纪人姓名、手机号、当前门店、绑定状态等主数据 | `merchant_brokers` |
| 绑定关系 | 经纪人与门店的当前及历史关系 | `merchant_broker_bindings` |
| 免审绑定 | 提交绑定申请后立即生效，无需门店员工或运营审核 | D3-A |
| 换绑 | 解绑原门店并绑定新门店 | 历史线索不迁移 |
| 招募域 | 现有 `recruit_*` 区域伙伴招募数据域 | N02 只读关联 |
| 手机号哈希 | 手机号规范化后的不可逆哈希，用于唯一性与匹配 | `phone_hash` |

## 4. 功能需求

### 4.1 经纪人档案

#### REQ-M05-001 经纪人认证与建档

| 项目 | 内容 |
|---|---|
| 功能描述 | 经纪人通过微信授权登录小程序，填写姓名、手机号并完成短信验证，系统创建或关联经纪人档案。 |
| 触发条件 | 经纪人首次进入“我的 → 经纪人认证”。 |
| 主流程 | 1. 微信授权登录，复用现有 C 端登录流程；2. 进入经纪人认证；3. 填写姓名、手机号；4. 发送短信验证码；5. 输入验证码校验；6. 系统按 `phone_hash` 查询是否已有经纪人档案；7. 无档案则创建，来源为“自主申请”；8. 有档案且 `user_id` 为空则关联当前 C 端用户；9. 返回经纪人档案。 |
| 分支与异常 | 1. 手机号格式错误：拒绝；2. 验证码错误/过期：提示重试；3. 手机号已被其他 `user_id` 占用：拒绝并提示联系运营；4. 微信授权失败：返回登录页；5. 姓名或手机号为空：拒绝；6. 档案已停用：禁止认证并提示联系运营。 |
| 输入字段 | 微信身份、姓名、手机号、短信验证码 |
| 输出字段 | 经纪人 `id`、`user_id`、姓名、手机号、`bind_status`、当前 `store_id` |
| 业务规则 | BR-M05-001：手机号必填并短信验证（Q21、Q24、N06）；BR-M05-002：一个手机号只能对应一个经纪人档案，`phone_hash` 唯一（Q47、8.2），认证时同时校验 `merchant_brokers.phone_hash` 与 `users` 手机号哈希，跨表重复即拒绝；BR-M05-003：手机号加密存储，匹配使用 `phone_hash`（Q47）；BR-M05-004：经纪人不新增系统角色码，不进入 admin，`is_internal_user` 判定不变（D2-A、S07）；BR-M05-005：自主申请来源记为“自主申请”；BR-M05-006：档案创建不自动绑定门店，绑定走 REQ-M06-001；BR-M05-020：经纪人小程序登录态不得展示评估工作台、钥匙管理、内部员工入口等内部功能，菜单按经纪人权限集渲染。 |
| 权限与角色 | 经纪人本人；admin/operator 可后台创建，见 V07。 |
| 状态流转 | 未绑定 → 已绑定 / 已停用；已解绑后可再次绑定。 |

#### REQ-M05-002 经纪人档案维护

| 项目 | 内容 |
|---|---|
| 功能描述 | 维护经纪人姓名、手机号、备注等档案字段；手机号变更需重新验证并更新唯一哈希。 |
| 触发条件 | 经纪人本人在小程序编辑资料；或 admin/operator 在后台编辑（后台入口见 V07）。 |
| 主流程 | 1. 展示当前档案；2. 修改姓名、手机号、备注；3. 手机号变更时发送并校验短信验证码；4. 校验新手机号未被占用；5. 保存并写审计日志。 |
| 分支与异常 | 1. 新手机号已存在：拒绝；2. 验证码失败：拒绝；3. 姓名清空：拒绝；4. 已停用档案：本人不可编辑，运营可修正；5. 并发修改：以最后提交为准并记录前后值。 |
| 输入字段 | 姓名、手机号、短信验证码、备注 |
| 输出字段 | 更新后的档案 |
| 业务规则 | BR-M05-007：手机号变更必须重新验证并同步 `phone`、`phone_hash`；BR-M05-008：`id`、`user_id`、`source` 不允许本人修改；BR-M05-009：姓名、手机号、备注变更写审计日志。 |
| 权限与角色 | 经纪人本人仅可改姓名、手机号、备注；admin/operator 可改全部业务字段。 |

#### REQ-M05-003 经纪人状态管理

| 项目 | 内容 |
|---|---|
| 功能描述 | 管理经纪人档案状态，包括未绑定、已绑定、已解绑、已停用；停用后禁止登录经纪人功能。 |
| 触发条件 | 运营在后台停用/启用；或绑定关系变化导致状态更新。 |
| 主流程 | 1. 选择经纪人；2. 选择目标状态；3. 填写原因（停用/解绑时）；4. 校验当前绑定关系；5. 保存并写日志。 |
| 分支与异常 | 1. 仍有有效绑定时停用：先解绑或同步解绑，具体规则见 R-V04-02；2. 已停用经纪人重新启用：恢复为未绑定；3. 状态相同：不产生变更；4. 无权限：拒绝。 |
| 输入字段 | 经纪人 `id`、目标状态、原因 |
| 输出字段 | 新状态、变更时间、操作人 |
| 业务规则 | BR-M05-010：`bind_status` 取值为未绑定、已绑定、已解绑、已停用；8.2 的“待审核”作为历史兼容值保留，D3-A 新流程不产生；BR-M05-011：停用经纪人不可登录经纪人功能、不可被新绑定；BR-M05-012：状态变更写审计日志。 |
| 权限与角色 | admin/operator；经纪人本人不可自行停用。 |
| 状态流转 | 未绑定 → 已绑定 → 已解绑；任意状态 → 已停用；已停用 → 未绑定（启用）。 |

#### REQ-M05-004 招募域只读关联

| 项目 | 内容 |
|---|---|
| 功能描述 | 建立经纪人档案与现有招募域线索的只读关联，用于复用招募归因关系；不复制招募域字段。 |
| 触发条件 | 经纪人认证建档或手机号变更时，按 `phone_hash` 匹配招募域线索。 |
| 主流程 | 1. 规范化手机号并计算 `phone_hash`；2. 查询招募域是否存在匹配线索；3. 存在则记录 `recruit_lead_id`；4. 不存在则留空；5. 展示时按需回查招募域。 |
| 分支与异常 | 1. 招募域不可用：不影响经纪人建档，`recruit_lead_id` 留空；2. 多条匹配：取最近一条并记录匹配依据，具体规则见 R-V04-03；3. 手机号变更：重新匹配并更新关联。 |
| 输入字段 | `phone_hash`、招募域线索 |
| 输出字段 | `recruit_lead_id`（可空） |
| 业务规则 | BR-M05-013：只读引用招募线索 ID，不复制招募域字段（N02）；BR-M05-014：`recruit_lead_id` 不改变经纪人主数据归属；BR-M05-015：招募域关联失败不阻断经纪人认证。 |
| 权限与角色 | 系统内部处理；admin/operator 可查看关联结果。 |

### 4.2 门店绑定

#### REQ-M06-001 绑定门店

| 项目 | 内容 |
|---|---|
| 功能描述 | 经纪人搜索并选择门店，提交绑定；按 D3-A 免审直接生效。 |
| 触发条件 | 经纪人在“我的 → 经纪人认证/我的门店”点击“绑定门店”。 |
| 主流程 | 1. 搜索门店（名称/地址）；2. 选择门店；3. 展示门店名称、地址、合作状态；4. 提交绑定；5. 校验经纪人当前无其他有效绑定；6. 创建绑定历史记录，状态“已生效”；7. 更新经纪人 `store_id`、`bind_status=已绑定`、`bound_at`；8. 返回“我的门店”。 |
| 分支与异常 | 1. 经纪人已有有效绑定：拒绝并提示先解绑/换绑；2. 门店已停用/已合并：拒绝；3. 门店不存在：拒绝；4. 经纪人已停用：拒绝；5. 重复提交：幂等，不产生重复有效绑定。 |
| 输入字段 | 经纪人 `id`、门店 `id` |
| 输出字段 | 绑定记录 `id`、`store_id`、`bind_status`、`bound_at` |
| 业务规则 | BR-M06-001：首次绑定按 D3-A 免审，提交即生效，不产生“待审核”状态；换绑/解绑不适用本条；BR-M06-002：一个经纪人同一时间只能绑定一个门店（Q23）；BR-M06-003：绑定关系保留历史，解绑不删除记录；BR-M06-004：绑定成功后经纪人可见“我的门店”；BR-M06-004A：每次创建绑定记录必须写入 `store_name_snapshot`。 |
| 权限与角色 | 经纪人本人；admin/operator 可代绑（V07）。 |
| 状态流转 | 未绑定 → 已绑定；已解绑 → 已绑定（新记录）。 |

#### REQ-M06-002 我的门店

| 项目 | 内容 |
|---|---|
| 功能描述 | 经纪人查看当前绑定门店信息与本人推荐记录入口。 |
| 触发条件 | 经纪人进入“我的 → 我的门店”。 |
| 主流程 | 1. 查询当前有效绑定；2. 展示门店名称、公司、地址、合作状态、门店照片（若有）；3. 展示“推荐记录”入口；4. 只读展示，不提供门店编辑。 |
| 分支与异常 | 1. 无有效绑定：展示空状态与“绑定门店”入口；2. 门店已停用/已合并：展示状态，禁止推荐；3. 多绑定历史：只展示当前有效绑定。 |
| 输入字段 | 经纪人 `id` |
| 输出字段 | 当前门店信息、推荐记录入口 |
| 业务规则 | BR-M06-005：经纪人只读查看门店，不允许修改门店档案（S09）；BR-M06-006：仅展示当前有效绑定门店；BR-M06-007：不展示门店联系人、联系电话、最近拜访时间等内部跟进信息；门店照片按 V02 门店照片数据展示。 |
| 权限与角色 | 经纪人本人。 |

#### REQ-M06-003 换绑门店

| 项目 | 内容 |
|---|---|
| 功能描述 | 经纪人从原门店换到新门店，提交后由运营审核；审核通过后生效，保留原绑定历史，历史线索不迁移。 |
| 触发条件 | 经纪人在“我的门店”点击“换绑”。 |
| 主流程 | 1. 展示当前门店；2. 搜索并选择新门店；3. 填写换绑原因并提交换绑申请；4. 创建绑定历史记录，状态“待审核”，记录 `applied_at`；5. 运营审核；6. 审核通过：原绑定置为“已解绑”并记录 `unbound_at`，新绑定置为“已生效”；7. 更新经纪人 `store_id`、`bound_at`；8. 保留原绑定历史。 |
| 分支与异常 | 1. 新门店与原门店相同：拒绝；2. 新门店停用/合并：拒绝；3. 原绑定不存在：按新绑定处理；4. 审核拒绝：原绑定保持有效，申请记录置“已拒绝”并记录原因；5. 换绑失败：原绑定保持有效，整笔回滚。 |
| 输入字段 | 经纪人 `id`、新门店 `id`、换绑原因、审核意见 |
| 输出字段 | 申请状态、原绑定状态、新绑定 `id`、新 `store_id` |
| 业务规则 | BR-M06-008：换店后新产生的线索归属新门店，历史线索不追溯迁移（Q25）；BR-M06-009：原绑定记录永久保留；BR-M06-010：换绑不改变经纪人 `id` 与 `user_id`；BR-M06-016：换绑须运营审核，审核通过前原绑定持续有效（S08）；BR-M06-017：审核通过或拒绝均写审计日志，记录审核人、时间、意见。 |
| 权限与角色 | 经纪人本人发起；admin/operator 审核；admin/operator 后台强制换绑可跳过审核但必须留痕（V07）。 |

#### REQ-M06-004 解绑门店

| 项目 | 内容 |
|---|---|
| 功能描述 | 经纪人申请解绑当前门店，提交后由运营审核；审核通过后生效，保留解绑原因与起止时间。 |
| 触发条件 | 经纪人在“我的门店”点击“解绑”；或运营后台强制解绑。 |
| 主流程 | 1. 展示当前绑定；2. 填写解绑原因；3. 提交解绑申请，绑定历史记录状态“待审核”；4. 运营审核；5. 审核通过：绑定历史置为“已解绑”并记录 `unbound_at`；6. 经纪人 `store_id` 清空、`bind_status=已解绑`。 |
| 分支与异常 | 1. 无有效绑定：提示无绑定；2. 原因未填：拒绝；3. 审核拒绝：原绑定保持有效，记录拒绝原因；4. 解绑后经纪人仍可登录并查看历史推荐记录，具体见 R-V04-05；5. 门店已合并：按合并后门店处理。 |
| 输入字段 | 经纪人 `id`、解绑原因、审核意见 |
| 输出字段 | 申请状态、绑定状态、`unbound_at` |
| 业务规则 | BR-M06-011：解绑必须保留起止时间与原因（S08）；BR-M06-012：解绑不删除历史绑定记录；BR-M06-013：解绑不影响历史线索的门店/经纪人字段；BR-M06-018：解绑须运营审核，审核通过前绑定持续有效；BR-M06-019：审核通过或拒绝均写审计日志。 |
| 权限与角色 | 经纪人本人发起；admin/operator 审核；admin/operator 后台强制解绑可跳过审核但必须留痕。 |

#### REQ-M06-005 绑定历史

| 项目 | 内容 |
|---|---|
| 功能描述 | 查询经纪人历次绑定门店、起止时间、状态与原因。 |
| 触发条件 | 经纪人在“我的门店 → 绑定历史”；或后台经纪人详情。 |
| 主流程 | 1. 按经纪人 `id` 查询绑定记录；2. 按 `applied_at` 倒序；3. 展示门店、状态、申请时间、生效时间、解绑时间、原因。 |
| 分支与异常 | 1. 无历史：空状态；2. 历史门店已删除：展示门店名称快照与“已停用/已合并”状态；3. 无权限：拒绝。 |
| 输入字段 | 经纪人 `id`、分页 |
| 输出字段 | 绑定历史列表 |
| 业务规则 | BR-M06-014：绑定历史只读，不允许修改；BR-M06-015：历史记录保留门店名称快照，避免门店改名后无法追溯。 |
| 权限与角色 | 经纪人本人；admin/operator 全量。 |

### 4.3 经纪人推荐记录

#### REQ-M05-005 我的推荐记录

| 项目 | 内容 |
|---|---|
| 功能描述 | 经纪人查看本人推荐过的线索及完整跟进记录。 |
| 触发条件 | 经纪人进入“我的 → 推荐记录”。 |
| 主流程 | 1. 按 `broker_id` 查询线索；2. 展示线索基本信息；3. 展示跟进记录时间线；4. 支持分页。 |
| 分支与异常 | 1. 无推荐记录：空状态；2. 线索已关闭：仍可查看历史；3. 线索涉及敏感客户信息：按 Q26 与隐私规则展示，具体字段见 R-V04-04；4. 经纪人已解绑：仍可查看历史推荐记录。 |

## 7. 依赖与影响说明

1. 本册依赖 V02 门店主数据；门店停用或合并后，绑定关系按 V02/V07 规则处理。
2. 经纪人不是内部员工，不新增 `broker` 角色码，避免 `is_internal_user` 将经纪人判为内部员工（S07、D2-A、第十三章风险）。
3. V06 的 `broker_id` 引用本册经纪人主键；换绑不迁移历史线索（Q25）。
4. V07 后台经纪人 CRUD 复用本册字段、手机号加密与绑定规则。
5. V09 不实现“绑定待审核通知”，因为 D3-A 已取消审核；协议到期与拜访提醒由 V09 负责。
6. 短信验证依赖现有短信服务，成本和配额由项目统一确认（N06）。
