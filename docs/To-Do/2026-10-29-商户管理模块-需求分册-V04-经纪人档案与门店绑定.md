## 2. 模块概述与目标

本册负责门店经纪人的独立档案、微信登录认证、门店绑定、换绑、解绑与绑定历史，以及经纪人在小程序查看“我的门店”和本人推荐记录。经纪人不是内部员工，不新增系统角色码，不进入 admin 后台；经纪人身份由独立 `merchant_brokers` 表承载，可选关联 `users.id`。

本期按 D2-A 独立经纪人表 + 可选 `users.id` 落地；首次绑定按 D3-A 免审直接生效，换绑/解绑按 S08 运营审核。按 2026-10-30 业务场景（m02721）：经纪人**不强制绑定门店，可以是独立经纪人**；员工可通过门店二维码邀请经纪人注册，扫码注册后自动绑定到该门店；经纪人注册时可创建门店或选择已有门店；经纪人绑定门店前必须先完成手机号绑定，手机号走现有“完善手机号码”流程，不新建短信验证流程。换店不迁移历史线索；经纪人可查看本人推荐线索的完整跟进记录（Q26）；与招募域按 N02 只读引用招募线索 ID、手机号哈希匹配。

## 3. 名词与术语

| 术语 | 定义 | 本册使用说明 |
|---|---|---|
| 经纪人 | 可登录小程序、推荐客户的从业人员；可不绑定门店成为独立经纪人 | 代码称 `merchant_broker`，严禁复用 `AGENT` |
| 独立经纪人 | 未绑定任何门店、但仍可提交推荐线索的经纪人 | `bind_status=未绑定`，m02721 |
| 经纪人档案 | 经纪人姓名、手机号、当前门店、绑定状态等主数据 | `merchant_brokers` |
| 绑定关系 | 经纪人与门店的当前及历史关系 | `merchant_broker_bindings` |
| 免审绑定 | 提交绑定申请后立即生效，无需门店员工或运营审核 | D3-A |
| 换绑 | 解绑原门店并绑定新门店 | 历史线索不迁移 |

| 手机号哈希 | 手机号规范化后的不可逆哈希，用于唯一性与匹配 | `phone_hash` |

## 4. 功能需求

### 4.1 经纪人档案

#### REQ-M05-001 经纪人认证与建档

| 项目 | 内容 |
|---|---|
| 功能描述 | 经纪人通过微信授权登录小程序，完成现有手机号绑定后填写姓名，系统创建或关联经纪人档案；支持从员工门店二维码进入并记录邀请员工。 |
| 触发条件 | 经纪人首次进入“我的 → 经纪人认证”，或通过员工分享的小程序卡片/链接、门店二维码进入注册。 |
| 主流程 | 1. 微信授权登录，复用现有 C 端登录流程；2. 查询当前用户是否已绑定手机号；3. 未绑定则引导进入现有“完善手机号码”流程（`POST /api/v1/public/users/phone` 或 `POST /api/v1/public/users/phone/wechat`），绑定成功后返回本流程；4. 填写姓名；5. 按 `phone_hash` 查询是否已有经纪人档案；6. 无档案则创建，来源记为“自主申请”；7. 有档案且 `user_id` 为空则关联当前 C 端用户；8. 解析进入参数：来自门店二维码则记录 `store_id`、`inviter_employee_id`、`bind_source=二维码邀请`；来自员工分享卡片/链接则记录分享员工 `referrer_id` 为 `inviter_employee_id`、`bind_source=员工分享`；9. 若为门店二维码路径，调用 `REQ-M06-006` 完成自动绑定；10. 若为普通路径或仅员工分享路径，进入 `REQ-M05-006` 选择创建门店、选择已有门店或暂不绑定；11. 返回经纪人档案。 |
| 分支与异常 | 1. 手机号未绑定：不得跳过，必须完成现有手机号流程；2. 手机号格式错误：拒绝；3. 手机号已被其他主账号占用：沿用现有合并/冲突处理，不新建流程；4. 微信授权失败：返回登录页；5. 姓名为空：拒绝；6. 档案已停用：禁止认证并提示联系运营；7. 二维码失效/门店停用/门店已合并：提示原因，允许转入普通注册但不自动绑定；8. 二维码对应的邀请员工无效：仍允许注册，`inviter_employee_id` 置空并记录异常。 |
| 输入字段 | 微信身份、当前用户手机号、姓名、二维码场景参数（`store_id`、`inviter_employee_id`）、员工分享参数（`referrer_id`） |
| 输出字段 | 经纪人 `id`、`user_id`、姓名、手机号（脱敏展示）、`bind_status`、当前 `store_id`、`inviter_employee_id`、`bind_source` |
| 业务规则 | BR-M05-001：手机号必须来自现有 `users` 绑定；未绑定必须走现有“完善手机号码”流程，不新建短信验证流程（m02721、N14）；BR-M05-002：一个手机号只能对应一个经纪人档案，`phone_hash` 唯一（Q47、8.2），认证时同时校验 `merchant_brokers.phone_hash` 与 `users` 手机号哈希，跨表重复即拒绝；BR-M05-003：手机号加密存储，匹配使用 `phone_hash`（Q47）；BR-M05-004：经纪人不新增系统角色码，不进入 admin，`is_internal_user` 判定不变（D2-A、S07）；BR-M05-005：自主申请来源仍记为“自主申请”，二维码邀请通过 `bind_source=二维码邀请` 与 `inviter_employee_id` 表达；BR-M05-006：档案创建不强制绑定门店，未绑定状态合法（m02721）；BR-M05-007：员工分享小程序路径必须把分享员工写入 `inviter_employee_id` 与 `bind_source=员工分享`，分享员工无效则置空并记录异常（m02721）；BR-M05-020：经纪人小程序登录态不得展示评估工作台、钥匙管理、内部员工入口等内部功能，菜单按经纪人权限集渲染。 |
| 权限与角色 | 经纪人本人；admin/operator 可后台创建，见 V07。 |
| 状态流转 | 未绑定（独立经纪人）→ 已绑定；已解绑 → 未绑定 / 已绑定；已停用仅后台恢复。 |

#### REQ-M05-002 经纪人档案维护

| 项目 | 内容 |
|---|---|
| 功能描述 | 维护经纪人姓名、手机号、备注等档案字段；手机号变更复用现有用户手机号修改流程并更新唯一哈希。 |
| 触发条件 | 经纪人本人在小程序编辑资料；或 admin/operator 在后台编辑（后台入口见 V07）。 |
| 主流程 | 1. 展示当前档案；2. 修改姓名、手机号、备注；3. 手机号变更时调用现有 `PUT /api/v1/public/users/phone` 完成验证与变更；4. 校验新手机号未被占用；5. 同步 `merchant_brokers.phone`、`phone_hash`；6. 保存并写审计日志。 |
| 分支与异常 | 1. 新手机号已存在：拒绝；2. 现有手机号修改流程校验失败：拒绝并保留原手机号；3. 姓名清空：拒绝；4. 已停用档案：本人不可编辑，运营可修正；5. 并发修改：以最后提交为准并记录前后值。 |
| 输入字段 | 姓名、新手机号、现有手机号修改流程所需凭证、备注 |
| 输出字段 | 更新后的档案 |
| 业务规则 | BR-M05-007：手机号变更必须复用现有手机号修改流程并同步 `phone`、`phone_hash`，不新建验证流程（m02721）；BR-M05-008：`id`、`user_id`、`source` 不允许本人修改；BR-M05-009：姓名、手机号、备注变更写审计日志。 |
| 权限与角色 | 经纪人本人仅可改姓名、手机号、备注；admin/operator 可改全部业务字段。 |

#### REQ-M05-003 经纪人状态管理

| 项目 | 内容 |
|---|---|
| 功能描述 | 管理经纪人档案状态，包括未绑定、已绑定、已解绑、已停用；停用后禁止登录经纪人功能。 |
| 触发条件 | 运营在后台停用/启用；或绑定关系变化导致状态更新。 |
| 主流程 | 1. 选择经纪人；2. 选择目标状态；3. 填写原因（停用/解绑时）；4. 校验当前绑定关系；5. 保存并写日志。 |
| 分支与异常 | 1. 仍有有效绑定时停用：先解绑或同步解绑，具体规则见 R-V04-02；2. 已停用经纪人重新启用：恢复为未绑定；3. 状态相同：不产生变更；4. 无权限：拒绝。 |
| 输入字段 | 经纪人 `id`、目标状态、原因 |
| 输出字段 | 新状态、变更时间、操作人 |
| 业务规则 | BR-M05-010：`bind_status` 取值为未绑定、已绑定、已解绑、已停用；8.2 的“待审核”作为历史兼容值保留，D3-A 新流程不产生；BR-M05-011：停用经纪人不可登录经纪人功能、不可被新绑定；BR-M05-012：状态变更写审计日志。 |
| 权限与角色 | admin/operator；经纪人本人不可自行停用。 |
| 状态流转 | 未绑定 → 已绑定 → 已解绑；任意状态 → 已停用；已停用 → 未绑定（启用）。 |

#### REQ-M05-004 招募域只读关联

| 项目 | 内容 |
|---|---|
| 功能描述 | 建立经纪人档案与现有招募域线索的只读关联，用于复用招募归因关系；不复制招募域字段。 |
| 触发条件 | 经纪人认证建档或手机号变更时，按 `phone_hash` 匹配招募域线索。 |
| 主流程 | 1. 规范化手机号并计算 `phone_hash`；2. 查询招募域是否存在匹配线索；3. 存在则记录 `recruit_lead_id`；4. 不存在则留空；5. 展示时按需回查招募域。 |
| 分支与异常 | 1. 招募域不可用：不影响经纪人建档，`recruit_lead_id` 留空；2. 多条匹配：取最近一条并记录匹配依据，具体规则见 R-V04-03；3. 手机号变更：重新匹配并更新关联。 |
| 输入字段 | `phone_hash`、招募域线索 |
| 输出字段 | `recruit_lead_id`（可空） |
| 业务规则 | BR-M05-013：只读引用招募线索 ID，不复制招募域字段（N02）；BR-M05-014：`recruit_lead_id` 不改变经纪人主数据归属；BR-M05-015：招募域关联失败不阻断经纪人认证。 |
| 权限与角色 | 系统内部处理；admin/operator 可查看关联结果。 |

#### REQ-M05-006 经纪人注册门店选择与创建

| 项目 | 内容 |
|---|---|
| 功能描述 | 非二维码路径的经纪人在完成手机号绑定和姓名填写后，可选择“创建新门店”“选择已有门店”或“暂不绑定”成为独立经纪人。 |
| 触发条件 | 经纪人完成 `REQ-M05-001` 第 1–7 步且未从门店二维码进入。 |
| 主流程 | 1. 展示三个选项；2. 选择“创建新门店”：跳转 V02 `REQ-M01B-007`，创建结果返回 `store_id`，按 SCN-06 决定是否自动绑定；3. 选择“选择已有门店”：调用门店搜索接口，仅返回 `status=正常` 且 `review_status=已转正` 的门店，选择后调用 `REQ-M06-001` 绑定；4. 选择“暂不绑定”：档案保持 `bind_status=未绑定`，作为独立经纪人进入小程序；5. 返回注册结果。 |
| 分支与异常 | 1. 无可用门店：提示可创建门店或暂不绑定；2. 门店在提交前被停用/合并：拒绝绑定，回到选择；3. 创建门店审核未通过：门店仍为未审核，经纪人可保留独立状态，待后台处理；4. 经纪人已有有效绑定：不再展示“选择已有门店”，改走换绑；5. 用户取消：保留已创建档案，不强制绑定。 |
| 输入字段 | 经纪人 `id`、选择类型、门店 `id`、新建门店字段（创建时） |
| 输出字段 | `store_id`（可空）、`bind_status`、`bind_source`、创建门店 `id`（创建时） |
| 业务规则 | BR-M05-021：经纪人可不绑定门店，独立经纪人身份合法（m02721）；BR-M05-022：选择已有门店只能选择正常且已转正门店；BR-M05-023：创建门店按 V02 `REQ-M01B-007` 生成 `review_status=未审核` 门店，不能伪装为已转正；BR-M05-024：创建门店与绑定门店均要求手机号已绑定。 |
| 权限与角色 | 已认证经纪人本人。 |
| 状态流转 | 未绑定 → 已绑定（选择已有或创建后自动绑定，SCN-06）；未绑定保持独立经纪人。 |

### 4.2 门店绑定

#### REQ-M06-001 绑定门店

| 项目 | 内容 |
|---|---|
| 功能描述 | 经纪人可主动搜索并选择门店绑定，或通过门店二维码自动绑定；首次绑定按 D3-A 免审直接生效。经纪人也可以不绑定门店。 |
| 触发条件 | 经纪人在注册流程选择已有门店、在“我的门店”点击“绑定门店”，或扫描门店二维码注册。 |
| 主流程 | 1. 搜索门店（名称/地址）；2. 选择门店；3. 展示门店名称、地址、合作状态；4. 提交绑定；5. 校验经纪人当前无其他有效绑定；6. 创建绑定历史记录，`bind_source` 记为 `手动选择` 或 `二维码邀请`，状态“已生效”；7. 更新经纪人 `store_id`、`bind_status=已绑定`、`bound_at`；8. 返回“我的门店”。 |
| 分支与异常 | 1. 经纪人已有有效绑定：拒绝并提示先解绑/换绑；2. 门店已停用/已合并：拒绝；3. 门店不存在：拒绝；4. 经纪人已停用：拒绝；5. 重复提交：幂等，不产生重复有效绑定；6. 经纪人选择不绑定：允许，保持 `bind_status=未绑定`，作为独立经纪人；7. 二维码对应的经纪人已绑定其他门店：按 SCN-01 处理。 |
| 输入字段 | 经纪人 `id`、门店 `id`、绑定来源（手动/二维码/后台）、邀请员工 `id`（二维码时） |
| 输出字段 | 绑定记录 `id`、`store_id`、`bind_status`、`bound_at`、`bind_source` |
| 业务规则 | BR-M06-001：首次绑定按 D3-A 免审，提交即生效，不产生“待审核”状态；换绑/解绑不适用本条；BR-M06-002：经纪人可以不绑定门店；若绑定，同一时间最多绑定一个门店（Q23 按 m02721 修订）；BR-M06-003：绑定关系保留历史，解绑不删除记录；BR-M06-004：绑定成功后经纪人可见“我的门店”；BR-M06-020：每次创建绑定记录必须写入 `store_name_snapshot`；BR-M06-021：二维码自动绑定必须写入 `inviter_employee_id` 与 `bind_source=二维码邀请`，见 `REQ-M06-006`。 |
| 权限与角色 | 经纪人本人；admin/operator 可代绑（V07）；二维码绑定由系统服务完成。 |
| 状态流转 | 未绑定 → 已绑定；已解绑 → 已绑定（新记录）；未绑定可长期保持独立经纪人状态。 |

#### REQ-M06-002 我的门店

| 项目 | 内容 |
|---|---|
| 功能描述 | 经纪人查看当前绑定门店信息与本人推荐记录入口。 |
| 触发条件 | 经纪人进入“我的 → 我的门店”。 |
| 主流程 | 1. 查询当前有效绑定；2. 展示门店名称、公司、地址、合作状态、门店照片（若有）；3. 展示“推荐记录”入口；4. 只读展示，不提供门店编辑。 |
| 分支与异常 | 1. 无有效绑定：展示空状态与“绑定门店”入口；2. 门店已停用/已合并：展示状态，禁止推荐；3. 多绑定历史：只展示当前有效绑定。 |
| 输入字段 | 经纪人 `id` |
| 输出字段 | 当前门店信息、推荐记录入口 |
| 业务规则 | BR-M06-005：经纪人只读查看门店，不允许修改门店档案（S09）；BR-M06-006：仅展示当前有效绑定门店；BR-M06-007：不展示门店联系人、联系电话、最近拜访时间等内部跟进信息；门店照片按 V02 门店照片数据展示。 |
| 权限与角色 | 经纪人本人。 |

#### REQ-M06-003 换绑门店

| 项目 | 内容 |
|---|---|
| 功能描述 | 经纪人从原门店换到新门店，提交后由运营审核；审核通过后生效，保留原绑定历史，历史线索不迁移。 |
| 触发条件 | 经纪人在“我的门店”点击“换绑”。 |

## 7. 依赖与影响说明

1. 本册依赖 V02 门店主数据；门店停用或合并后，绑定关系按 V02/V07 规则处理；经纪人注册建店调用 V02 `REQ-M01B-007`。
2. 经纪人不是内部员工，不新增 `broker` 角色码，避免 `is_internal_user` 将经纪人判为内部员工（S07、D2-A、第十三章风险）。
3. V06 的 `broker_id` 引用本册经纪人主键；V04 与 V06 通过只读查询对接（V04 读线索统计、V06 读经纪人/绑定），不互相调用写接口，不形成服务循环；换绑不迁移历史线索（Q25）。
4. V07 后台经纪人 CRUD 复用本册字段、手机号加密与绑定规则。
5. 首次绑定与二维码自动绑定按 D3-A 免审、无绑定审核通知；换绑/解绑按 S08 运营审核，审核结果是否通知经纪人见 V09 R-V09-07【待确认】；协议到期与拜访提醒由 V09 负责。
6. 手机号绑定复用现有 `POST /api/v1/public/users/phone` 与 `/phone/wechat`，不新建短信验证流程（m02721、N14）；现有流程的频控、合并冲突与成本沿用平台口径。
