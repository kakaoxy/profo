# 微信小程序“招募计划”拉新归因方案（完整最终版）

> **落地依据**：第九节《落地实施方案》已对照 `miniapp/`（原生微信小程序 + TypeScript）与 `backend/`（FastAPI + SQLAlchemy）现有代码完成现状盘点，含数据模型、接口清单、页面设计与分阶段实施计划，**全部复用既有基础设施，可直接进入开发**。


## 一、项目概述与核心目标

**业务背景**：利用现有员工的人脉资源，通过社交分享为“招募计划”引流。

**核心目标**：
1. **精准归因**：客户通过员工分享进入小程序并完成留资后，后台自动将该条客户记录**准确、唯一地归属**到该员工名下，作为后续业绩核算与跟进的依据。
2. **高效拉新**：简化客户操作流程（一键授权），最大化降低留资门槛，减少脏数据。
3. **实时响应**：客户留资后，系统需实时通知分享员工，以便及时跟进。


## 二、核心业务规则（最终确认版）

以下规则已在讨论中全部敲定，是开发与运营的硬性基准：

| 业务要素 | 最终决策与细则 |
| :--- | :--- |
| **分享渠道** | 支持两种方式：①小程序卡片分享至**好友/群聊**；②生成**海报**分享至**朋友圈**。后台**不区分**渠道来源，统一归入总数据。 |
| **分享素材** | 所有分享的标题、配图、文案由运营**统一配置**，员工**不可自定义**。确保品牌输出一致性，无需人工审核。 |
| **分享资格** | **全员皆可分享**，后台不设权限开关，无需管理员单独开启。 |
| **客户留资方式（核心亮点）** | 摒弃传统的“手动输入姓名+手机号”。客户需先**填写主营商圈**（必填，填写），再点击“立即报名”按钮，通过微信原生 **“一键授权获取手机号”** 组件完成授权。**授权即视为留资**，拒绝授权则流程终止。此举可彻底规避假号、格式错误等脏数据。 |
| **归属判定锚点（最重要规则）** | **只看“首次留资”，不算“打开”**。客户多次点击不同员工的链接不会建立归属，只有在**首次成功完成手机号授权**的那一刻，后台才将当前这条留资记录归属给“本次分享的员工”。 |
| **多员工分享冲突处理** | 以**首次留资**的时间戳为准（后端解密手机号成功的时间）。例：客户先点A链接（未留资），后点B链接（留资）→ 归B；若客户点A留资后，再点B链接 → 归A（首次留资不变）。 |
| **老客户/内部员工误点** | 计入**PV（打开次数）+1**，但**不计入UV（新增独立访客）**。若其本人完成手机号授权，系统按正常逻辑记录留资（业务上后续可由人工筛选剔除）。 |
| **留资后通知** | **必须实时触发**。系统需通过微信模板消息/服务号通知/企业微信等方式，向**分享了该链接的员工**推送新线索提醒。 |
| **防刷与作弊机制** | **技术侧不做硬性拦截**（如限制IP/设备）。业务上认为留资仅为销售过程的起点，后续销售跟进建联、转化成交才是终点，刷来的无效数据会在跟进环节自然淘汰。 |
| **合规底线** | 必须严格符合《微信公众平台运营规范》及《个人信息保护法》。在调起手机号授权前，页面必须提供**用户主动勾选**的“我已阅读并同意《隐私协议》”复选框，**不可默认打勾**。报名按钮**始终可点击**（与微信一键登录交互一致），未勾选协议时点击提交仅提示“请先阅读并同意隐私协议”、不触发授权，而非置灰禁用。 |


## 三、用户端全流程操作示意（C端视角）

1. **客户收到分享**：在微信聊天框看到卡片，或在朋友圈看到海报。
2. **客户打开页面**：点击进入小程序“招募计划”详情页。
3. **客户浏览内容**：上下滑动阅读招募权益、要求、福利等信息。
4. **客户填写主营商圈**：在报名区填写其**主营商圈**（必填，未选择时点击报名提示“请先填写主营商圈”）。
5. **客户点击报名**：点击页面底部的 **“立即报名 / 一键授权”** 按钮（按钮始终可点；若未勾选隐私协议，点击时提示“请先阅读并同意隐私协议”，不触发授权）。
6. **系统弹出授权**：微信弹出手机号快速验证组件（非手动输入框）。
   - 若点击**“拒绝”**：提示“授权失败，无法报名”，流程结束。
   - 若点击**“允许”**：授权成功，页面提示“报名成功，我们将尽快联系您”。
7. **员工收到通知**：此时，分享该链接的员工手机收到微信/企业微信的**新线索实时提醒**。


## 四、前后端功能职责划分（无代码描述）

### 前端（小程序端）负责：
1. **双渠道分享入口**：提供“分享好友”和“生成海报”两个显性按钮。
2. **携带身份标识**：点击分享时，自动将当前登录员工的唯一身份ID装载进卡片/海报（用户无感知）。
3. **主营商圈收集**：报名表单必填项为“主营商圈”（填写），未选择时点击报名提示“请先填写主营商圈”。
4. **合规前置校验**：报名按钮**始终可点击**（与微信一键登录交互一致）；点击提交时校验**隐私协议勾选状态**，未勾选则提示“请先阅读并同意隐私协议”并中止授权流程。
5. **原生授权调用**：调用微信原生 `getPhoneNumber` 组件，获取用户授权。
6. **捆绑上报数据**：向后台传输数据时，必须同时包含 `{主营商圈, 加密手机号数据, 分享员工ID, 页面来源标记}`。
7. **用户与员工反馈**：客户侧显示“报名成功”；员工侧在分享操作后显示“已分享”状态反馈。

### 后端（服务器端）负责：
1. **员工身份安全管理**：维护员工唯一标识，确保分享出去的标识不可篡改。
2. **手机号解密与存储**：接收前端传来的加密数据（含主营商圈），调用微信接口解密出真实手机号，连同主营商圈一并存入客户线索表。
3. **核心归因引擎**：
   - 收到留资请求时，以**手机号**为唯一键查库。
   - 若该手机号**首次出现**，则将当前请求中的 `员工ID` 写入该记录的 `归属员工` 字段。
   - 若该手机号**已存在**，则忽略本次请求中的 `员工ID`，保持原有归属不变（确保首次归因）。
4. **消息通知中心**：留资成功落库后，立即异步调用消息接口，向归属员工推送新线索提醒。
5. **数据统计看板**：为运营/管理层提供基于漏斗模型的多维度数据汇总查询接口。


## 五、精细化数据漏斗模型（最终完整版）

经过深度讨论，我们确定了以下 **6级核心业务漏斗**。特别注意：由于采用“一键授权”，传统的手动“表单填写完成率”断层已不存在，被替换为“授权点击率”。

| 层级 | 指标名称 | 业务定义/衡量标准 | 数据反映的核心业务问题 |
| :--- | :--- | :--- | :--- |
| **1** | **分享次数** | 员工点击“分享”或“生成海报”按钮的总次数（含同一人多次）。 | 衡量**员工端的推广积极性**及触达频次。 |
| **2** | **打开次数(PV) / 人数(UV)** | 客户点击卡片/海报进入小程序的累计次数(PV)与去重人数(UV)。老客户/内部员工计入PV，不计入UV。 | 衡量**分享素材（标题/图片）的点击吸引力**。UV越高，覆盖新面孔越多。 |
| **↓ 断层①** | **3. 深度浏览人数** | **（关键补全指标）** 进入页面后，真正认真阅读了核心内容的客户。判定标准：**页面停留时长≥3秒**（唯一判定条件）。 | **判断落地页内容吸引力**。若UV高但深度低，说明首屏标题/头图失败；若深度高但下一步点击低，说明福利权益不够诱人。 |
| **↓ 断层②** | **4. 点击授权按钮人数** | 浏览页面并**填写主营商圈**后，点击“立即报名”按钮并成功触发微信授权弹窗的人数（未勾选隐私协议被拦截的点击不计入）。 | 衡量**客户的意向转化意向**。此处流失高，说明“诱饵”价值感不足。 |
| **5** | **授权成功数（原始留资）** | 用户在授权弹窗点击“允许”，后台成功解密手机号并落库的总条数。 | 核心中间指标（**原始线索池**）。 |
| **↓ 断层③** | **6. 有效新客留资数（北极星指标）** | 在原始留资基础上，经后台自动/人工判定：非内部员工、非重复手机号后，最终确认为纯净新线索的数量。 | **业务最终认可的拉新成果**，直接挂钩员工业绩考核。 |


## 六、特殊场景与异常处理机制

| 场景 | 系统处理逻辑（业务规则） |
| :--- | :--- |
| **客户拒绝手机号授权** | 前端弹窗提示“授权失败，无法完成报名”，流程终止，后台**不记录**任何客户数据，员工**不收到**通知。 |
| **客户未勾选隐私协议** | “立即报名”按钮**保持可点击**（与微信一键登录交互一致），点击提交时校验未勾选则提示“请先阅读并同意隐私协议”，不触发授权弹窗、不提交数据。 |
| **客户未选择主营商圈** | 点击报名时提示“请先选择主营商圈”，不触发授权弹窗；主营商圈为必填项。 |
| **同一客户短时间重复留资** | 后台根据手机号去重，忽略后续重复提交，归属关系与首次留资保持一致（不覆盖、不更新）。 |
| **分享员工已离职** | 因其分享链接中的员工ID仍有效，若后续产生留资，系统依然正常记录并归属该离职员工名下（数据留痕，用于历史业绩核算）。 |
| **获取手机号接口失败/超时** | 前端提示“网络异常，请稍后重试”，记录失败日志供运维排查，不影响员工分享链接的有效性。 |


## 七、合规与数据安全专项说明

1. **隐私协议展示**：小程序必须配置《用户隐私协议》，且在授权流程中明确告知用户“我们将收集您的手机号及主营商圈信息用于XXX招募活动联系”，并获取用户**主动勾选同意**。报名按钮保持可点击，但未勾选协议时点击提交不生效（与微信一键登录交互一致）。
2. **权限最小化**：仅申请 `getPhoneNumber` 权限，不额外索取用户头像、昵称等其他无关权限，符合微信审核要求。
3. **数据传输加密**：前端传输员工ID及加密数据需走 HTTPS 协议，后端解密流程需符合微信官方安全指引。


## 八、后续运营衔接建议（超出拉新范畴但建议预留）

1. **员工跟进状态回传**：建议在后台为“有效留资”开辟跟进状态字段（如：待联系、已联系、意向高、已转化、已淘汰）。这能将数据从“拉新漏斗”延伸到“销售转化漏斗”，完整衡量 ROI。
2. **通知模板内容**：建议包含信息——`【新线索提醒】您推荐的客户 {客户手机号后四位} 已完成报名，请登录小程序后台查看详情并尽快跟进。`（避免明文显示完整手机号，保护客户隐私）。

> 本方案已对照 `miniapp/`（原生微信小程序，TypeScript）与 `backend/`（FastAPI + SQLAlchemy）现状盘点，全部设计均复用既有基础设施，**无需引入新框架**。以下为可直接进入开发的设计依据。

### 9.1 现状盘点：可直接复用的资产

| 能力 | 现有实现 | 本方案复用点 |
| :--- | :--- | :--- |
| **微信登录** | `utils/wechat-auth.ts` → `POST /auth/wechat/login`，支持临时账号/内部员工双令牌（JWT `aud` 区分 admin / c） | 客户进入招募页自动登录；员工分享时从令牌识别员工身份 |

| **分享能力** | `about` / `projects/detail` 页已有 `onShareAppMessage` + `showShareMenu`（含分享朋友圈） | 招募页分享直接套用同款实现，路径追加活动与员工参数 |
| **幂等迁移** | `backend/migrations/__init__.py`（`_column_exists` / `_index_exists` 幂等建表/加列） | 新增 4 张表全部通过迁移脚本落地 |
| **后台权限** | 角色体系 `admin/operator/user/customer`，附加角色可让后台员工同时具备 C 端身份（`ADDITIONAL_ROLE_CODES=customer`） | 后台员工登录小程序后可直接打开招募页分享，身份由 JWT 解析 |
| **协议页** | `pages/agreement/privacy` 已有《隐私协议》页面 | 勾选文案直接链接复用 |
| ⚠️ **订阅消息** | **当前无任何模板消息/订阅消息实现** | 员工通知一期采用“后台待办+角标”，二期接微信订阅消息（详见 9.7） |
| ⚠️ **隐私检查** | `app.json` 当前 `"__usePrivacyCheck__": false` | 需改为 `true`，并同步微信后台配置《用户隐私保护指引》 |

### 9.2 总体技术架构

```
小程序 C 端（miniapp/pages/recruit/detail）
  │  onShow 上报访问（埋点） / 停留≥3s 判定 / 主营商圈选择 / 协议勾选 / getPhoneNumber 授权
  ▼
后端 FastAPI
  ├─ /public/recruit/*      C 端：活动详情、商圈选项、访问埋点、留资提交（含归因引擎）
  ├─ /admin/recruit/*       后台：活动配置、线索管理、漏斗统计、小程序码生成
  └─ 归因引擎 Service       手机号 phone_hash 查重 → 首次留资写归属 → 异步通知
  ▼
PostgreSQL
  ├─ recruit_campaigns   招募活动/分享素材配置
  ├─ recruit_leads       招募客户线索（核心归因表）
  ├─ recruit_visits      访问埋点（漏斗 2/3/4 级）
  └─ recruit_share_events  分享事件（漏斗 1 级）
```

### 9.3 数据模型设计（新增 4 张表）

**① `recruit_campaigns` — 招募活动配置表（运营统一配置分享素材，员工不可自定义）**

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| id | String(36) UUID | 主键 |
| name | String(100) | 活动名称 |
| title | String(200) | 分享卡片标题（运营配置，员工不可自定义） |
| image_url | String(500) | 分享配图 URL（微信官方规范长宽比 **5:4**，建议 500×400，PNG/JPG） |
| content | JSON | 详情页内容（权益/要求/福利；**一期使用运营默认模板**，二期支持可视化编辑） |
| poster_bg_url | String(500) | 海报背景图 URL（**二期**海报生成启用，一期预留） |
| status | Enum 启用/停用 | 活动开关 |
| created_at / updated_at | DateTime(tz) | 时间戳 |

**② `recruit_leads` — 招募客户线索表（核心归因表，手机号为主键语义）**

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| id | String(36) UUID | 主键 |
| phone | EncryptedString(20) | 手机号（Fernet 加密，复用 User.phone 方案） |
| phone_hash | String(64) | 手机号 HMAC 哈希，**普通索引**（归因查重用） |
| main_business_area | String(50) | **主营商圈（必填）** |
| campaign_id | String(36) | 所属活动（逻辑外键） |
| source | Enum card/poster | 渠道标记（后台不区分统计，仅留痕） |
| referrer_employee_id | String(36) | **归属员工 ID（首次留资写入，此后永不更新）** |
| status | Enum 新线索/已联系/意向高/已转化/已淘汰 | 跟进状态（预留第八节字段） |
| is_internal | Boolean | 是否内部员工误点（人工/自动标记） |
| created_at / updated_at | DateTime(tz) | 首次留资时间 = created_at |

索引：`idx_recruit_lead_phone_hash`（归因查重）、`idx_recruit_lead_referrer`（员工业绩）、`idx_recruit_lead_status`。

**③ `recruit_visits` — 访问埋点表（漏斗第 2/3/4 级数据源）**

### 9.5 小程序端落地设计

**新增页面：`pages/recruit/detail/index`（招募详情页，单页承载全部报名能力）**

页面结构（自上而下）：
1. 招募详情内容区（**一期使用运营默认模板**渲染：权益/要求/福利）
2. 报名区：
   - **主营商圈**：`picker` 下拉，选项来自 `GET /public/recruit/business-areas`（必填，未选提示“请先选择主营商圈”）
   - **隐私协议**：`checkbox` 勾选“我已阅读并同意《隐私协议》”，**默认不勾选**，文案可点跳转 `pages/agreement/privacy`
   - **立即报名 / 一键授权** 按钮：**始终可点**（对齐微信一键登录交互）；点击时依次校验：主营商圈 → 协议勾选 → `button[open-type=getPhoneNumber]` 调起授权
3. 成功态：授权成功后页面提示“报名成功，我们将尽快联系您”

**分享与归因（员工侧）**
- 员工（登录态，调 `GET /auth/me` 获取员工 ID，等价且更安全；2026-08-15 更新）在页面看到“分享给客户”入口；
- 卡片分享：`onShareAppMessage` 返回 `path: "/pages/recruit/detail/index?campaign_id=xx&referrer=员工ID&source=card"`，`showShareMenu` 同时开放朋友圈；
- 客户点击进入 → `onLoad` 读取 `referrer` 参数 → 写入 `recruit_visits.referrer_employee_id` → 留资时透传 → 归因引擎落库；
- 分享计数：员工点击“分享”按钮时上报 `recruit_share_events`（漏斗第 1 级）；未登录用户亦可分享（referrer 为空，可传播但不归因，符合“不设权限开关”）。

**深度浏览判定（唯一标准：停留 ≥3s）**
- 前端：`onShow` 记录 `enterTime = Date.now()` 并 `POST /visits` 创建访问；`onHide` / `onUnload` 计算 `stayedMs`，`is_deep_view = stayedMs >= 3000`，随 `PUT /visits` 上报；
- 后端兜底：收到 `PUT` 时按 `exited_at - entered_at` 复核 `is_deep_view`，二者取“或”（防前端漏报）；
- 点击授权埋点：报名按钮通过校验、调起授权弹窗时置 `clicked_auth=true`（未勾协议被拦截的点击不计入，与第五节口径一致）。

**海报生成（二期已实施，2026-08-15 更新）**
- 员工在招募详情页点击“生成海报”→ 调 `GET /public/recruit/campaigns/{id}/qrcode` 取绑定自身身份的小程序码；
- `canvas 2d` 绘制：背景 = 活动 `poster_bg_url`（未配置/加载失败时用品牌渐变兜底）+ 标题 + 引导文案 + 白卡内嵌小程序码；
- `canvasToTempFilePath` → 预览/保存相册（授权拒绝时引导 `openSetting`）；
- 生成成功后上报 `share_type=poster` 分享事件。

### 9.6 关键流程细节

**报名提交（POST /public/recruit/leads）后端处理顺序（归因引擎）**
1. 校验主营商圈非空、活动启用中（`limiter` 限流防刷，按方案不设硬拦截）；
2. 调微信接口用 `code` 解密手机号（复用 `/public/users/phone/wechat` 同款解密能力）；
3. `phone_hash` 查 `recruit_leads`：
   - **不存在（首次）** → 创建记录，`referrer_employee_id` 写入本次 `referrer`，`first_lead_at = now`，返回 `{lead_id, is_new: true}`；
   - **已存在** → 返回原记录 `{lead_id, is_new: false}`，**不更新归属**（多员工冲突以首次留资为准）；
4. 更新对应 `recruit_visits.authed = true`；
5. 异步触发员工通知（见 9.7），不阻塞响应。

**隐私合规落地**
- `app.json`：`"__usePrivacyCheck__": true`（当前为 false，需改）；
- 微信公众平台后台：配置《用户隐私保护指引》，声明收集**手机号、主营商圈**，用途为“招募活动报名联系”；
- 页面内协议 checkbox 不可默认打勾；未勾选时点击报名仅 toast 提示，不调起 `getPhoneNumber`（满足《微信公众平台运营规范》与《个人信息保护法》）。
