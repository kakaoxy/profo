## 2. 模块概述与目标

### 2.1 模块定位

商户管理模块把公司线下「扫街拓店」的过程，转化为系统内可建档、可留痕、可归属、可复盘的一条数据链：员工在小程序完成门店建档与拜访，经纪人通过小程序绑定门店并参与估价代填，运营在后台查看门店地图、拜访轨迹并维护门店与经纪人档案。

V01 不实现具体门店、拜访、经纪人、协议、线索业务，只负责三件平台基础能力：**权限与数据范围**、**操作审计**、**业务字典与配置**。这三项能力是 V02–V09 所有业务分册的共同前置条件。

### 2.2 业务背景

公司通过员工线下拓展获取房产经纪门店资源。当前「找门店 → 拜访 → 谈合作 → 签协议 → 门店推荐客户」整条链路全部在线下和微信里完成，存在以下典型问题：

| 编号 | 典型场景 | 现状问题 | 业务影响 |
|---|---|---|---|
| BP-01 | 员工跑了一天，拜访了 8 家门店 | 信息散落在微信、纸质名片、个人表格里，回公司后才补记 | 数据滞后、遗漏、无法沉淀为公司资产 |
| BP-02 | 两个员工先后拜访同一家门店 | 互相不知道，重复建档或重复谈 | 撞单、重复投入、对外口径不一致 |
| BP-03 | 领导问「这个区有多少家合作门店」 | 没有台账，只能人工汇总 | 无法做区域规划和拓展目标管理 |
| BP-04 | 想知道「这家店有几个经纪人」 | 无经纪人档案 | 无法评估门店产出能力，也无法做门店激励 |
| BP-05 | 客户问「是谁推荐来的」 | 只有分享员工，没有门店 / 经纪人 | 门店贡献无法统计，合作门店没有获得感 |
| BP-06 | 员工说「今天去了 A、B、C 三家店」 | 无拜访留痕 | 无法验证真实性，无法复盘路线和频次 |
| BP-07 | 合作协议签完 | 纸质协议归档散乱，到期无人提醒 | 合作到期裸奔，续签靠记忆 |

## 3. 名词与术语

### 3.1 名词定义

| 名词 | 定义 | 与现状的关系 |
|---|---|---|
| 商户（公司） | 门店所属的经营主体 / 品牌公司，如「XX 房地产经纪有限公司」 | 系统当前无此实体；D1-A 已确认独立建表，公司 1:N 门店 |
| 门店 | 线下实体经营门店，是拜访、合作、经纪人归属的最小单元 | 新增实体；地址包含区域 / 商圈 / 经纬度 |
| 经纪人 | 门店内的从业人员，可登录小程序、可绑定门店、可推荐客户 | 新增实体；代码命名统一为 `merchant_broker`，严禁复用 `AGENT` |
| 员工 | 公司内部人员，即现有 `users` 中具备后台身份者（admin / operator / user） | `backend/services/system/identity.py:17` `is_internal_user` 已可判定 |
| 拜访 | 员工对某门店的一次线下到访记录 | 新增实体；含拍照、联系人、时间、定位 |
| 合作状态 | 门店与公司的合作阶段（未合作 / 洽谈中 / 已合作 / 暂停 / 终止） | 走业务字典，不硬编码 |
| 电子合作协议 | 门店 / 商户与公司签署的合作协议电子件 | D4-C 已确认小程序手写签名 + 生成 PDF |

### 3.2 实体关系

```text
商户（公司） 1 ── N 门店 1 ── N 经纪人（当前绑定）
                      │
                      ├── N 拜访记录（员工 N ── 1）
                      ├── N 电子合作协议
                      └── N 线索（推荐门店）
经纪人 1 ── N 线索（推荐经纪人）
员工   1 ── N 拜访记录 / N 分享归因线索
```

### 3.3 关键边界说明

| 编号 | 边界规则 |
|---|---|
| BD-01 | 门店是主实体：所有拜访、协议、经纪人都挂在门店上；商户（公司）是组织层，门店必须归属公司（D1-A） |
| BD-02 | 经纪人不是内部员工：经纪人不能登录 admin 后台，只能在小程序中使用经纪人相关功能；不得新增 `broker` 角色码，避免被 `is_internal_user` 判定为内部员工 |
| BD-03 | 门店 ≠ 小区：`communities` 是房源小区（用于房源、估价、楼盘字典），门店是中介经营场所，两者不能混用同一张表 |
| BD-04 | 一个门店可以有多个经纪人，一个经纪人同一时间只属于一个门店（Q23 已确认） |

## 4. 功能需求

### 4.1 角色与使用端

| 角色 | 身份来源 | 主用端 | 核心操作 | 现状支持 |
|---|---|---|---|---|
| 员工（拓展） | 现有 `users`，角色 admin / operator / user | 小程序（约 99%）+ admin（少量补录） | 门店建档、拜访登记、协议发起、分享估价页 | 小程序已支持工号 + 密码绑定内部账号（`miniapp/pages/bind-account/index/index`） |
| 经纪人 | 新增独立档案，可选关联 `users.id`（D2-A） | 小程序 | 绑定门店、查看我的门店、代填估价、查看自己的推荐 | 无 |
| 运营 / 管理员 | 现有 admin 角色 | admin 后台 | 门店地图、门店 / 经纪人维护、协议审核、数据查看 | 有 |
| 客户（C 端） | 现有 customer 角色 | 小程序 | 浏览房源、提交估价、留资 | 有 |

> 端的分工原则：员工与经纪人的「产生数据」动作（建档、拜访、绑定、代填）全部在小程序完成；admin 只做「看数据 + 修数据」。

### 4.2 M12 权限与审计

M12 为全端平台能力，包含权限点、角色默认权限、后台导航、数据范围和操作审计。本节定义的权限点与数据范围规则，V02–V09 只能引用，不得另起一套。

#### REQ-M12-001 商户域权限点注册

| 项目 | 内容 |
|---|---|
| 功能描述 | 在后台权限种子与前端权限常量中注册商户域 6 个权限点，供路由、菜单和接口鉴权使用 |
| 触发条件 | 系统初始化、权限种子执行、前端构建时 |
| 主流程 | 1. 在后端 `_PERMISSIONS_SEED` 注册 6 个权限点；2. 在前端 `PERMISSION_CODES` 镜像同一组编码；3. 在 `_ROLE_PERMISSIONS_SEED` 为 admin 默认授予全部 6 个权限点；4. 启动时校验前后端权限编码集合一致；5. 接口鉴权中间件按编码校验 |
| 分支与异常 | 1. 权限编码已存在：按幂等处理，不重复插入；2. 前后端编码不一致：启动自检失败并报错；3. 请求未携带权限：返回 403 统一错误体；4. 未知权限编码：视为无权限 |
| 输入字段 | `code`（权限编码）、`name`（权限名称）、`module`（所属模块）、`description`（说明） |
| 输出字段 | 权限记录；前端 `PERMISSION_CODES` 常量；角色权限关联记录 |
| 业务规则 | BR-M12-001 至 BR-M12-006 |
| 权限与角色 | 仅系统初始化 / admin 可维护权限种子；普通用户不可修改权限定义 |
| 状态流转 | 不涉及 |

| 编号 | 业务规则 |
|---|---|
| BR-M12-001 | 权限点固定为 6 个：`merchant:read`、`merchant:write`、`merchant:visit`、`merchant:broker`、`merchant:agreement`、`merchant:map` |
| BR-M12-002 | `merchant:read` 控制门店、经纪人、协议、线索等商户域数据的查看；写操作接口必须同时校验对应写权限，不得仅依赖读权限 |
| BR-M12-003 | `merchant:write` 控制门店与公司主数据的新增、编辑、停用、软删；门店合并除 `merchant:write` 外还必须校验当前角色为 admin/operator（Q10、V07 BR-M11-017） |
| BR-M12-004 | `merchant:visit` 控制拜访登记、补录、拜访记录查看 |
