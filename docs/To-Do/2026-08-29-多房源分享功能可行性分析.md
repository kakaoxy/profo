# 多房源分享功能可行性分析（"房源单分享"）

- 日期：2026-08-29
- 范围：miniapp（微信小程序，原生框架）+ backend（FastAPI + PostgreSQL）
- 性质：可行性分析文档，仅作方案论证，不涉及代码改动
- 说明：文中引用代码均为相对项目根目录的路径；不确定处显式标注"⚠️待确认"；路由命名、字段命名等最终以后续实现 spec 为准

---

## 1. 背景与目标

### 1.1 背景

miniapp 现有"分享获客"体系（入口见 `miniapp/pages/profile/index/index.ts` 的 `SHARE_ENTRIES` 常量，仅内部员工可见）只支持**单房源卡片分享**：员工推广多套在售房源时，需要为每套房源各发一条朋友圈。多条内容高度雷同的营销类朋友圈会被微信判定为营销内容并**折叠**（仅显示一条一行摘要），曝光大幅缩水，推广效果差。

招募模块已沉淀了"海报 + 小程序码 + 短码落地解析"的完整先例，具备直接复用的技术土壤。

### 1.2 目标

1. **解决朋友圈折叠**：员工将多条房源朋友圈合并为一条——一张含多套在售房源的综合海报，降低被判定为刷屏营销内容的概率。
2. **单条分享多房源**：一张海报承载 1~N 套在售房源（建议上限 10 套），客户扫码一次进入即可浏览全部。
3. **保持归因闭环**：客户扫码进入房源单聚合页后，访问埋点、留资线索仍能归属到分享员工，与现有单房源分享归因口径一致。

### 1.3 成功标准（建议，业务指标 ⚠️待确认）

- 功能成功标准：员工可选多套在售房源生成一张可保存相册的综合海报；海报小程序码扫码可打开聚合页并正确归因到分享人；非在售/未发布房源不出现在海报与聚合页（或明确标注）。
- 业务成功标准（⚠️待确认，建议后续 spec 定义）：海报扫码进入 UV、聚合页留资转化率、朋友圈折叠率对比（后者依赖人工观察，无法程序化统计）。

## 2. 现状与差距

### 2.1 现状盘点（基于代码调研，均已核实）

- **分享获客入口**：`miniapp/pages/profile/index/index.ts` 中 `SHARE_ENTRIES` 常量（第 45 行起）定义了三项入口：房源分享（switch-tab-projects）、评估分享（switch-tab-valuation）、招募分享（recruit），仅内部用户可见。
  > 注：调研材料中写作 `SHARE_MENU`，经核实代码中实际常量名为 `SHARE_ENTRIES`，本文按实际代码引用。
- **单房源分享**：`miniapp/pages/projects/detail/index.ts` 仅有 `onShareAppMessage` / `onShareTimeline` 卡片分享，`buildSharePath` 在 path 中携带 `referrer=<员工UUID>` 明文透传；`onLoad` 解析 `referrer` 后经 `reportVisit` 上报 `POST /public/projects/{id}/visit-events`（免登录，body 含 `visitor_id` / `referrer` / `source`）；分享行为上报 `POST /public/projects/{id}/share-events`；分享统计走 `GET /public/projects/my/share-stats`（见 `backend/routers/public/projects.py:197`）。
- **留资归因**：`backend/services/leads/core.py:107` 的 `LeadService._resolve_referrer_id` 校验员工存在 + active + 有后台身份，无效则静默置 `None`，不阻断留资。
- **顾问联系方式**：`GET /public/projects/{marketing_project_id}/consultant?referrer={userId}`（`backend/routers/public/projects.py:322`，免登录 + 限流），分享人优先（`is_referrer=True`，前端展示"分享人"角标），回退房源顾问。
- **招募海报先例（可复用）**：
  - `miniapp/utils/recruit-poster.ts`：布局纯函数，600×960 竖版（`POSTER_WIDTH=600` / `POSTER_HEIGHT=960`），提供 `estimateTextWidth` / `wrapTitleLines` / `computeCoverSourceRect` / `toQrcodeDataUri` / `buildPosterLayout`。
  - `miniapp/utils/recruit-poster-render.ts`：canvas 2d 绘制编排 `drawPoster` / `createPosterTempFile` / `savePosterToAlbum`，含相册授权拒绝 → 引导去设置 → 重试的完整流程；canvas 节点使用 `<canvas type="2d">`。
- **小程序码**：`backend/services/system/wechat.py:432` 的 `WeChatAuthService.fetch_miniapp_unlimited_qrcode(scene, page)` → `POST https://api.weixin.qq.com/wxa/getwxacodeunlimit`，`scene ≤ 32` 字符、`check_path=False`，返回图片 bytes，**无缓存、每次实时调微信**。当前仅招募模块使用：`GET /public/recruit/campaigns/{campaign_id}/qrcode`（需 `aud=c` 登录态）→ `{code, image_base64}`；短码映射表 `recruit_qr_scenes`（`backend/models/recruit/recruit.py:224`，8 位 `secrets.token_hex` 短码唯一索引 + `(campaign_id, employee_id)` 复合唯一复用已有短码，`IntegrityError` 并发兜底，见 `backend/services/recruit/qrcode.py`）；scene 格式 `code=<短码>`，page 固定 `pages/recruit/detail/index`；落地解析 `GET /public/recruit/qr/{code}`（`backend/routers/recruit/public.py:271`，游客可访问 + 限流）→ `{campaign_id, referrer}`。
- **在售房源数据**：`GET /public/projects`（免登录）返回 `PublicProjectListItem`（`backend/schemas/public/__init__.py:189`）：`id/title/cover_image/cover_thumbnail_url/community_name/layout/orientation/floor_info/area/total_price/unit_price/tags/project_status` 等；在售 = `project_status == "在售"`（`MarketingProjectStatus` 枚举中文值：在途/在售/已售，见 `backend/models/marketing/l4_marketing.py:39`）且 `publish_status == "发布"`；缩略图规则 `thumbs/{stem}.webp`（800px 宽 WebP，见 `backend/utils/image_processing.py`）。
- **数据库与分层约束**：PostgreSQL；Schema 变更通过 `backend/migrations/__init__.py` 幂等启动迁移脚本管理（不使用 Alembic，参照 `backend/migrations/_recruit.py` 的建表/补索引模式）；模型用 `Mapped[]`；Pydantic Schema 按 `*Create/*Update/*Response/*Filter` 划分、触发动作用 `*Request`；Router 禁 SQLAlchemy 查询，严格 Router→Service→Model 分层。
- **miniapp 请求封装**：`miniapp/utils/request.ts` 自动携带 token、401 自动刷新（admin 与 c 双令牌，并发刷新复用 Promise）、`/public/*` 优先 `c_access_token`；员工判定用 `getUserIdFromAccessToken()` 同步解析 JWT sub 作 employeeId，`/auth/me` 校验。

## 3. 推荐技术方案

### 3.0 总体架构

```
员工端（miniapp）                          服务端（backend）                        客户端（微信）
────────────────                        ─────────────────                        ──────────────
选多套在售房源
   │ POST /public/property-sheets ──────▶ 创建房源单（主表+明细，生成8位短码）
   ▼                                              │
海报预览页（canvas 2d）                            │
   │ GET .../{id}/qrcode ──────────────▶ 调微信 getwxacodeunlimit ─▶ 返回 base64（建议 Redis 缓存）
   │ 封面图下载（cover_thumbnail_url）                │
   ▼ 绘制 600×960 综合海报                           ▼
保存相册 ── 用户手动发朋友圈 ─────────────────────────────────────▶ 客户扫码
                                                                  │ scene=code=xxxx
                                                                  ▼
                                          GET /public/property-sheets/qr/{code}
                                          （游客可访问+限流）→ {sheet_id, referrer}
                                                                  │
                                                                  ▼
                                              聚合页渲染在售房源列表 + 分享人联系卡片
                                              visit 埋点（visitor_id/referrer/source）
                                                                  │
                                                                  ▼
                                              客户留资 → LeadService._resolve_referrer_id
                                              归因到分享员工（与单房源口径一致）
```

架构原则：

- **前端做表现，后端做数据**：海报为纯前端 canvas 绘制（服务端零图片合成压力）；后端只负责房源单 CRUD、短码解析、小程序码生成与归因数据。
- **最大化复用**：短码模式复用 `recruit_qr_scenes` 思路，海报绘制复用 `miniapp/utils/recruit-poster*.ts` 的纯函数 + 编排分层模式，归因复用单房源既有链路。
- **分层约束**：后端严格 Router→Service→Model；新表迁移走 `backend/migrations/__init__.py` 幂等启动脚本。

### 3.1 模块A：房源单 CRUD

#### 表设计建议

```
property_share_sheets（房源单主表）
  id              BIGSERIAL PK
  employee_id     VARCHAR(36) NOT NULL        -- 创建员工（逻辑外键，关联 users.id）
  code            VARCHAR(8) NOT NULL UNIQUE  -- 8位短码（secrets.token_hex(4)），同招募模式
  status          VARCHAR(16) NOT NULL DEFAULT 'active'   -- active/archived（⚠️待确认状态集）
  title           VARCHAR(64) NULL            -- 房源单名称（⚠️待确认是否需要）
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
  updated_at      TIMESTAMPTZ NULL

property_share_sheet_items（房源单明细表）
  id                   BIGSERIAL PK
  sheet_id             BIGINT NOT NULL          -- 逻辑外键 → property_share_sheets.id
  marketing_project_id BIGINT NOT NULL          -- 逻辑外键 → l4_marketing_project.id
  sort_order           INT NOT NULL DEFAULT 0   -- 海报展示顺序
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now()
  -- (sheet_id, marketing_project_id) 复合唯一，防重复添加
```

设计要点：

- 短码直接放主表 `code` 唯一列（一张房源单即一个码，无需独立映射表），与 `recruit_qr_scenes` 的"短码唯一索引 + 复用"模式同构；房源单不存在"多员工共用一张单"的场景，故比招募少一层映射。
- 明细不加指向营销项目的数据库外键（项目逻辑外键惯例），房源是否在售/发布由查询时 join 实时判断；级联删除（删主表明细随之失效）由 Service 处理。
- 明细数量上限建议 **≤10**（Service 层强校验，见第 5 节性能分析）。

#### 幂等迁移要点

- 在 `backend/migrations/__init__.py` 中新增迁移步骤（或按现有组织方式新增 `_property_sheet.py` 子模块，参照 `backend/migrations/_recruit.py`）：
  - 建表前用 `_get_table_names` 类似的表存在性检查，已存在则跳过；
  - 唯一索引（`code`、`(sheet_id, marketing_project_id)`）用 `_index_exists` 类似检查幂等补建；
  - 时间列统一 `DateTime(timezone=True)`；
  - 确保语句 PostgreSQL 兼容（ BIGSERIAL / TIMESTAMPTZ / 部分索引如需）。
- 迁移脚本必须可重复执行无副作用（幂等），已有部署升级时只补缺失对象。

#### 接口草案（路由命名最终以后续实现 spec 为准）

| 方法 | 路径 | 登录态 | 说明 |
| --- | --- | --- | --- |
| POST | `/public/property-sheets` | 需登录（员工） | 创建房源单：body 为 `PropertySheetCreateRequest`（含 `project_ids` 有序列表，≤10）；Service 校验所选房源均为在售+发布；返回 `PropertySheetResponse`（含 `code`） |
| GET | `/public/property-sheets/mine` | 需登录（员工） | 我的房源单列表（供分享页复选/管理），含各明细当前在售状态摘要 |
| GET | `/public/property-sheets/{id}` | 需登录（员工） | 房源单详情（本人创建才可见；管理场景 ⚠️待确认） |
| DELETE | `/public/property-sheets/{id}` | 需登录（员工） | 归档/删除本人房源单（建议软删 `status=archived`，码失效由落地解析接口按 status 拦截） |
| GET | `/public/property-sheets/qr/{code}` | 游客可访问 + 限流 | 短码落地解析：返回 `{sheet_id, referrer}`（同 `GET /public/recruit/qr/{code}` 契约），referrer 取创建员工 |
| GET | `/public/property-sheets/{id}/qrcode` | 需登录（员工，`aud=c`） | 生成/获取小程序码：`scene=code=<短码>`，page 指向聚合页；返回 `{code, image_base64}`（同招募 qrcode 接口契约） |

约束遵循：请求 Schema 用 `*Request` / 响应用 `*Response`；Router 不写 SQLAlchemy 查询，逻辑下沉 Service；错误响应统一 `{"code": ≠0, "message": "..."}`。

### 3.2 模块B：综合海报生成（前端 canvas 2d）

复用 `miniapp/utils/recruit-poster.ts`（布局纯函数）+ `miniapp/utils/recruit-poster-render.ts`（绘制编排）的分层模式，新建房源单海报的布局与渲染模块（如 `miniapp/utils/property-sheet-poster.ts` / `property-sheet-poster-render.ts`，命名以后续 spec 为准）。

海报规格与版式：

- 尺寸：**600×960 竖版**（与招募海报一致，`<canvas type="2d">`）。
- 标题：固定文案 **"美房宝品质二手房"**（`wrapTitleLines` / `estimateTextWidth` 可直接复用）。
- 房源封面拼接规则（`computeCoverSourceRect` 做 cover 裁剪，避免拉伸变形）：
  - 1 套：单图通栏；
  - 2 套：双图并排；
  - 3 套：上 1 下 2（或类似网格规则，最终以视觉稿为准 ⚠️待确认视觉稿）；
  - 超过 3 套：展示前 3 套封面 + 角标文案 **"更多扫码"**（引导扫码看全部）。
- 封面图来源：优先 `cover_thumbnail_url`（800px WebP，体积小、canvas `createImage` 加载快），缺失时降级 `cover_image`。
- 每套房源可附小区名/价格等简要文字（是否展示见第 8 节决策项 4），文字绘制复用招募海报的宽度估算与截断函数。
- 小程序码：**右下角**，`toQrcodeDataUri(base64)` 转为可绘制 data URI。
- 保存流程：直接复用 `savePosterToAlbum` 的"保存 → 授权拒绝 → 引导去设置 → 返回重试"完整流程（`miniapp/utils/recruit-poster-render.ts` 已实现，含 `scope.writePhotosAlbum` 状态检查）。
- 兜底：绘制过程 loading 态 + 失败提示重试（封面图加载失败时跳过该图或整图重试，策略 ⚠️待确认，建议跳过并占位，不阻断海报生成）。

### 3.3 模块C：小程序码与短码

- **scene 32 字符限制 → 8 位短码映射**：`scene=code=<8位短码>`（共 13 字符，远小于 32 上限），page 指向新落地页（如 `pages/property-sheet/detail/index`）。短码用 `secrets.token_hex(4)` 生成 8 位十六进制（与 `backend/services/recruit/qrcode.py` 同法），主表 `code` 唯一索引保证全局唯一，冲突时重试。
- **复用 `fetch_miniapp_unlimited_qrcode`**：`backend/services/system/wechat.py:432` 直接调用，无需改动；`check_path=False` 语义下 page 参数按微信要求为已发布版本中存在的路径（⚠️待确认：聚合页首次提审发布前，开发版/体验版扫码行为与线上不同，上线顺序需在 spec 中明确）。
- **短码复用策略**：同 `(sheet_id, employee_id)` 维度天然一对一（房源单创建即定），无需额外映射表；重复请求二维码直接返回主表 `code` 对应的码，避免重复占用微信 getwxacodeunlimit 调用次数。
- **缓存建议**：现状 `fetch_miniapp_unlimited_qrcode` 每次实时调微信、无缓存；建议对**码图片 base64 加 Redis 缓存**（key 含短码，TTL 建议天级——小程序码内容不随房源状态变化，仅当房源单归档/短码失效时主动清除）。招募模块 `GET /public/recruit/campaigns/{campaign_id}/qrcode` 同样存在此改进点，可一并在实施时统一处理（属公共优化，非本功能阻塞项）。
- **失效控制**：房源单归档（status=archived）后，落地解析接口应返回业务错误码，客户端提示"房源单已失效"；小程序码图片本身无需吊销（扫码后解析阶段拦截）。

### 3.4 模块D：扫码落地聚合页

- **新页面**：如 `pages/property-sheet/detail/index`（路径以后续 spec 为准），在 `miniapp/app.json`（或分包配置）注册。
- **onLoad 解析 scene**：从二维码 scene 中取出 `code=<短码>` → 调 `GET /public/property-sheets/qr/{code}`（游客可访问 + 限流）换取 `{sheet_id, referrer}`。解析失败（码无效/房源单归档）展示占位错误页。
- **房源卡片列表**：按 `sort_order` 渲染 `GET /public/property-sheets/{id}`（或专用游客可访问的聚合详情接口 ⚠️待确认：若复用 `{id}` 接口需登录态，游客扫码场景应提供免登录聚合查询，建议落地解析接口直接附带房源单渲染数据或新增免登录接口）数据；**实时过滤**非在售/未发布房源；已售房源建议保留卡片并标注"已售"（见第 6 节风险对策）。卡片字段沿用 `PublicProjectListItem`（title / community_name / layout / orientation / floor_info / area / total_price / unit_price / tags / cover_thumbnail_url）。
- **分享人联系卡片**：复用 consultant 接口思路——按 `referrer` 返回分享人联系方式（现有 `GET /public/projects/{id}/consultant?referrer=` 绑定了单房源 project_id，房源单场景需要**按 sheet_id（或 referrer 直查）的新接口**，内部实现复用"`_resolve_referrer_id` 同口径的员工有效性校验 + 分享人优先、回退房源顾问"的思路 ⚠️待确认接口形态，建议 `GET /public/property-sheets/{id}/consultant?referrer=`，免登录 + 限流）。
- **visit 埋点**：复用 `visitor_id/referrer/source` 机制，进入页面即上报（`source=scan_qrcode` 或沿用 `share`，⚠️待确认 source 取值口径）；若需按房源单维度统计访问，需新增 `POST /public/property-sheets/{id}/visit-events`（免登录），与单房源 `visit-events` 结构一致。
- **单房源跳转**：卡片点击是否跳转房源详情页见第 8 节决策项 5；若跳转，path 携带 `referrer` 延续既有归因参数。

### 3.5 模块E：归因

与单房源分享**完全同口径**，不新增归因机制：

1. **referrer 明文透传**：员工创建房源单时 `employee_id` 即归因主体；客户扫码经短码解析获得 `referrer`（创建员工 UUID），后续页面内所有上报携带该值。
2. **visit / share 埋点**：聚合页上报 visit（`visitor_id` 匿名去重 + `referrer` + `source`）；客户从聚合页再转发单房源卡片时，进入既有单房源 `visit-events` / `share-events` 链路。
3. **留资归因**：客户在聚合页或跳转后的房源详情留资，`LeadService._resolve_referrer_id` 校验员工有效性（存在 + active + 有后台身份）后归属，无效静默置 `None`——该逻辑无需任何改动。
4. **短码的定位**：仅用于绕过 `getwxacodeunlimit` 的 scene 32 字符限制（无法直接塞完整 referrer UUID + 房源 id 列表），**不改变归因字段语义**；`_resolve_referrer_id` 校验失败的场景（员工离职/停用）归因自然落空为游客，与现状一致。

## 4. 微信平台限制分析

| 限制点 | 说明 | 影响 | 结论 |
| --- | --- | --- | --- |
| `getwxacodeunlimit` scene ≤32 字符 | scene 参数上限 32 可见字符 | 无法直接携带 referrer UUID + 多房源 id 列表 | 用 8 位短码映射绕过（`scene=code=xxxx`，13 字符），方案成立 |
| `getwxacodeunlimit` 调用频率限制 | 微信官方文档对该接口有频率配额（具体数值以官方文档为准 ⚠️待实测确认） | 每次生成实时调微信，无缓存时高频请求可能触顶 | ① (sheet_id, employee_id) 维度短码复用，避免重复生成；② Redis 缓存码图片 base64；③ 建议实施前实测配额并压测 |
| canvas 2d `createImage` 加载网络图片 | 受小程序 downloadFile 合法域名白名单约束 | 海报封面图必须来自已配置域名 | 本项目图片域名与 API 同域 fangmengchina.com（招募海报已验证可行）；需检查 OSS 域名是否已在 downloadFile 白名单（`cover_thumbnail_url`/`cover_image` 实际指向的域名清单）⚠️待确认，不在则需在小程序后台补配 |
| `scope.writePhotosAlbum` 保存相册授权 | 用户拒绝后再次保存会直接 fail | 需处理授权拒绝分支 | 已有现成处理模式（`miniapp/utils/recruit-poster-render.ts` 的 `savePosterToAlbum`：拒绝 → openSetting 引导 → 返回重试），直接复用 |
| 朋友圈代发能力 | 小程序**无法**直接代用户发布朋友圈，无相关开放 API | "一键分享朋友圈"**不可行** | 交互定为"生成海报 → 保存相册 → 引导用户手动发朋友圈"（保存成功后 toast + 文案引导），需在产品预期中对齐 |
| 分享卡片与海报双通道 | 卡片（onShareAppMessage/onShareTimeline）与海报是两条独立链路 | 好友会话与朋友圈场景习惯不同 | 保留：转发好友仍用现有房源卡片（会话内卡片体验更直接）；朋友圈用综合海报。两条通道归因字段口径一致 |

## 5. 性能影响分析

| 环节 | 评估 | 结论 |
| --- | --- | --- |
| 封面图下载 | 海报最多加载 3 张 `cover_thumbnail_url`（800px 宽 WebP，单张体积小），且与招募海报同量级 | 下载量小，移动网络可接受；失败重试/占位兜底 |
| canvas 绘制耗时 | 600×960 纯 2D 绘制（图片 + 文字 + 码），招募海报同规格已在线上验证 | 耗时可控；绘制期间 loading 态，失败提供重试 |
| 服务端压力 | 海报为纯前端绘制，服务端**无图片合成**；新增接口均为轻量 CRUD/解析查询 | 无新增图片处理压力；`GET /public/property-sheets/qr/{code}` 高频扫码走限流 + 单表索引查询 |
| 小程序码生成 | `fetch_miniapp_unlimited_qrcode` 实时调微信（一次 HTTPS RT），现状无缓存 | 首次生成有微信接口 RT 开销（秒级），前端 loading 承接；建议 Redis 缓存 base64 后，二次生成毫秒级返回（招募模块同款改进点） |
| 落地页列表查询 | 聚合页需按明细 join 房源实时状态 | 明细数量上限 **≤10**（Service 层创建时强校验），单次查询可控；列表页避免 N+1（Service 一次性批量查询房源） |
| 数据库 | 新增 2 张表，量级 = 员工数 × 人均房源单数，远小于房源/线索表 | 无容量顾虑；`code` 唯一索引 + 明细复合索引覆盖全部查询路径 |

## 6. 潜在风险与对策

| 风险 | 等级 | 对策 |
| --- | --- | --- |
| 诱导分享审核风险（微信审核判定海报为诱导/营销内容） | 中 | 海报不出现"分享得奖励/转发有礼"等诱导文案；标题固定"美房宝品质二手房" + 房源事实信息（小区/户型/价格），保持内容属性；上线前可走一次体验版自审 |
| 短码遍历/滥用（8 位短码被脚本枚举批量请求解析接口） | 中 | 落地解析接口 `GET /public/property-sheets/qr/{code}` 参照 `GET /public/recruit/qr/{code}` 做游客限流（IP/visitor 维度）；短码空间 16^8 ≈ 43 亿，配合限流枚举成本高；解析失败不回显存在性细节 |
| 房源状态过期（生成海报后房源已售/下架，海报与落地页不一致） | 中 | ① 生成海报时 Service 校验所选房源均为在售+发布，不合格直接拒绝创建；② 落地页**实时过滤**非在售/未发布房源，已售房源保留卡片并标注"已售"（避免客户扫码后内容空洞，也维护信息真实性） |
| 低端机 canvas 兼容（老基础库/低端安卓绘制失败或字体异常） | 低 | 使用 `<canvas type="2d">`（官方推荐接口，招募海报已在线上验证同一套绘制路径）；保留失败重试；文字宽度用 `estimateTextWidth` 自行估算而非依赖 measureText 的机型差异 ⚠️待确认：实施时在低端真机回归一遍海报绘制 |
| 图片合规/版权（海报拼接第三方图片引发投诉） | 低 | 封面仅使用项目已上传至自家图床/OSS 的房源封面（`cover_thumbnail_url` 降级 `cover_image`），不引入任何外部图源；不缓存到本地相册之外的路径 |
| 朋友圈折叠不能 100% 保证（合并为一条仍可能被判营销折叠，属平台黑盒策略） | 中 | 明确产品预期：本方案**降低**折叠概率（条数减少 + 内容差异化），不承诺完全消除；使用说明建议员工配合"多套房源 + 生活化/科普文案"发布（文案建议由运营提供，不在本功能代码范围） |

## 7. 工作量评估

难度评级：**低** = 有现成模式照搬；**中** = 需新开发但路径清晰；**高** = 存在不确定依赖（仅评难度，不给时间估计）。

| 模块 | 难度 | 主要工作项 |
| --- | --- | --- |
| 模块A 房源单 CRUD | 中 | ① 2 张新表 Model（`Mapped[]`）+ Pydantic Schema（`*Create/*Response/*Request`）；② 幂等迁移脚本（`backend/migrations/__init__.py`，参照 `_recruit.py`）；③ Service（创建校验在售+发布、明细≤10、短码生成与冲突重试）；④ 6 个 REST 接口 Router；⑤ `pytest` 单测（创建校验/短码复用/解析限流） |
| 模块B 综合海报 | 中 | ① 房源单海报布局纯函数（600×960、标题、1/2/3 套封面网格、"更多扫码"角标，复用 recruit-poster 工具函数）；② 绘制编排模块（多图 `createImage` 加载 Promise 化 + loading/失败重试）；③ 保存相册流程直接复用 `savePosterToAlbum`；④ 海报预览页（`<canvas type="2d">`）接线到房源单选择交互；⑤ 低端真机回归 |
| 模块C 小程序码与短码 | 低 | ① qrcode 接口（复用 `fetch_miniapp_unlimited_qrcode`，契约对齐招募 qrcode 接口）；② scene/page 参数定版；③（可选公共优化）Redis 缓存 base64 |
| 模块D 落地聚合页 | 中 | ① 新页面注册与 scene 解析；② 落地解析接口联调 + 错误占位页；③ 房源卡片列表（实时过滤 + 已售标注，批量查询避免 N+1）；④ 分享人联系卡片（新 consultant 形态接口或扩展）；⑤ visit 埋点接入（visitor_id/referrer/source） |
| 模块E 归因 | 低 | ① 短码解析返回 referrer 与既有字段对齐；② 跳转单房源详情时 path 透传 referrer；③ 验证 `_resolve_referrer_id` 归因落库正确性（单测 + 手工留资验证）；④ 分享统计口径确认（是否需要房源单维度 share/visit 统计 ⚠️待确认） |
| 类型同步与收尾 | 低 | ① 后端启动后 `pnpm gen-api` 同步前端类型；② `pytest` / `tsc --noEmit` / `ruff check` / `pnpm lint` 全过；③ 真机走通"选房 → 海报 → 相册 → 扫码 → 归因"全链路 |

**无"高"难度模块**：核心不确定性集中在模块C的微信接口配额实测（第 4 节）与模块B的视觉稿定版，均不影响技术路径成立。

## 8. 待确认业务决策清单

1. **房源可选范围**：员工可从**全部在售房源**中挑选，还是仅限**自己负责/关联**的房源？（影响创建接口的房源查询过滤与数据权限口径；建议"全部在售 + 默认勾选自己负责"以最大化推广灵活性。）
2. **单次上限**：一张房源单最多包含几套房源？（建议 **10** 套：海报仅展示 3 套封面 + 扫码看全部，10 套以内落地页滚动体验良好且查询可控。）
3. **房源单是否需要命名/有效期**：是否允许员工给房源单命名（如"XX学区三房合集"）？房源单是否有有效期/自动归档策略，还是长期有效 + 手动归档？（影响主表 `title` 字段与 status 流转设计。）
4. **海报是否展示价格与小区名**：封面下方是否标注小区名、总价/单价？（展示价格更促转化但信息更"营销化"；建议至少展示小区名 + 总价，最终由视觉稿定版。）
5. **落地页是否开放单房源跳转**：客户点击房源卡片是否可跳转房源详情页？（跳转可复用详情页完整能力且延续 referrer 归因，但多一层页面跳转；建议开放。）
6. **员工离职后房源单与码的处理**：员工停用/离职后，其历史房源单如何处理？（建议：落地解析时复用 `_resolve_referrer_id` 同口径校验——员工无效则归因置空、联系卡片回退房源顾问，房源单内容仍可访问；是否直接失效房源单 ⚠️待确认业务取舍。）
7. （补充）**房源单维度统计需求**：是否需要按房源单维度统计扫码访问/留资（供 `share-stats` 类报表扩展），还是仅复用现有单房源统计口径？（影响是否新增统计表与接口。）

---

> 结论：方案在现有代码体系（招募海报先例、单房源归因链路、小程序码短码模式）上均为增量复用，无技术障碍；主要前置事项为微信 getwxacodeunlimit 配额实测、OSS 域名白名单核查与第 8 节业务决策定版。
