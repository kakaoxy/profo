## 1. 场景一：审核通过新增时，允许修正提交内容名称

### 1.1 现状（已核对）

**后端**

- `backend/services/property/building_review_service.py:503-571`
  - `_create_community_from_pending` / `_create_building_from_pending` / `_create_room_from_pending`
    三处 `db.add(...=entry.name)` —— **名称完全取自 pending 原文，无覆盖参数**。
  - 查重键也直接用 `entry.name`（如 building 用 `(community_id, entry.name)`）→ 名称一改，
    查重键必须同步改，否则会插出重复行或被 `uq` 打成 500。
  - `entry.normalized_name` 只用于 `uq_pending_open`（同名并发唯一），**落库后不参与业务**。
- `backend/schemas/building_dict.py:311-319` `BdReviewResolveRequest` 只有 `action` / `target_id`，
  **无名称字段**。
- `backend/routers/property/building_dict.py:450-463` `resolve` 端点直接透传 body，无 name 处理。

**前端「自动加号」的真实来源（重点，运营描述的「系统自动加号」）**

后端 `bd_buildings.building_no` **原样存储**（BR-03 不做数字化抽取），**不加号**。
「号」是**展示层**拼上去的，共 5 处硬编码：

| 位置 | 代码 | 后果 |
|------|------|------|
| `frontend/src/components/dict-address-picker/index.tsx:99` | `buildingNo && \`${buildingNo}号\`` | 拼装门牌：`金杨路660弄21号` → `金杨路660弄21号号` |
| 同上 `:584`、`:592` | 级联 chip 文案 | 展示「21号号」 |
| `…/review/review-resolve-modal.tsx:95` | `` `${target.building.building_no}号` `` | 合并目标预览「21号号」 |
| 同上 `:97` | 同上 + `plate_no` | 「21号号401」 |
| `…/_components/community-drawer.tsx:701`、`:757` | `{picked.buildingNo}号` | 抽屉底部回显「21号号」 |

→ 运营看到「金杨路660弄21号号」这类拼接错误时会想把楼栋号里的「号」删掉，但**审核弹层没有任何输入框**。

**决策点（必须拍板）**

- **D-A**：修的是「**审核落库时的名称**」（后端改 `entry.name` 的落库值），还是「**只修展示拼装**」？
  - 只修展示（只改 `${no}号` 为后缀感知）→ 楼栋号仍是 `金杨路660弄21号`，
    单据/房源/报表里到处是「号」；数据口径不干净。
  - 只改落库（不动展示）→ 落库 `金杨路660弄21`，展示变成 `金杨路660弄21号`，**恰好正确**。
  - 两者都做 → 落库干净 + 展示对任意历史数据（含 4477 条以「号」结尾）都正确。**推荐两者都做**。

### 1.2 方案（推荐：后端落库 + 前端拼装同口径）

#### A. 后端：`resolve` 增加可选 `name`

**Schema** `backend/schemas/building_dict.py`

```python
class BdReviewResolveRequest(BaseModel):
    action: str = Field(pattern="^(create|merge|reject)$")
    target_id: str | None = Field(None, description="目标ID(...)")
    # ↓ 新增：仅 create 生效；merge/reject 传了忽略（改名属于「确认新增」语义）
    name: str | None = Field(
        None, min_length=1, max_length=200,
        description="修正后的提交内容名称（仅 create 生效；不传=沿用原文）",
    )
```

**Service** `backend/services/property/building_review_service.py`

新增一个纯函数式归一方法（放在模块级，便于复用与单测）：

```python
# 修正名称归一：去首尾/内部多余空白（与 normalize_community_name 的空白口径对齐，
# 但不做全半角/小写改写——楼栋号「201乙」「122乙」的大小写与全半角要保留原文）
def normalize_pending_display_name(raw: str) -> str:
    """审核修正名称归一（仅折叠空白，不改写业务字符）."""
    return " ".join(raw.split())
```

`resolve()` 入口新增（在 action 分支前）：

```python
override_name: str | None = None
if action == "create" and body.name is not None:
    override_name = normalize_pending_display_name(body.name)
    if not override_name:
        raise ValidationError("修正名称不能为空")
    if override_name == normalize_pending_display_name(entry.name):
        override_name = None   # 无实际变化，走原路径（避免无谓审计噪声）
```

三个 `_create_*_from_pending` 增加 `name: str | None` 参数，内部统一：

```python
target_name = name or entry.name
existing = db.query(...).filter(..., ...==target_name).first()
if existing:
    return existing.id          # BR-26 幂等：修正后撞已有 → 直接并入，不报错
... BdBuilding(building_no=target_name ...)
```

**必须同时处理的三件事**（否则会产生脏数据或 500）：

1. **`entry.name` 是否回写？**
   建议**回写**（`entry.name = target_name`、`entry.normalized_name = normalize_community_name(target_name)`），
   理由：
   - 审核池历史列表要展示「审核员最终落库的名称」，否则运营回看时对不上字典；
   - `resolved_target_id` 已指向新行，entry 与字典必须一致；
   - ⚠️ 回写 `normalized_name` 会触碰 `uq_pending_open`（partial unique，`status='pending'`）——
     **因为同一事务内该行 `status` 已被置为 `CREATED`，不满足部分索引条件，不会冲突**；
     但仍需在 `db.flush()` 顺序上先置 `status` 再改 `normalized_name`（或直接同语句 flush，PG 在**语句结束时**判定唯一性，不会命中）。
2. **审计**：`_audit(...)` 的 `after` 增加 `name_from` / `name_to`，`action` 保持 `bd_review_create`
   （不新增 action 值，避免报表口径分叉）；另在 `message` 里带上「名称已修正：A → B」。
3. **响应回显**：`BdReviewResolveResponse` 增加 `resolved_name: str | None`，
   前端 toast 用它提示最终落库名（运营要看到「实际写进去的是哪个名字」）。

**边界规则（写进 docstring + E2E）**

| 场景 | 行为 |
|------|------|
| `create` + `name` 为空/纯空白 | 400 `修正名称不能为空` |
| `create` + 修正后与**同小区已有楼栋**同名 | **幂等并入已有行**（`existing.id`），响应 `message` 提示「修正后与已有楼栋重合，已并入」 |
| `create` + 修正后与**同小区另一条 pending** 名字相同 | 允许（pending 之间不校验 dict uq），落库时谁先谁建；后到的走 `existing` 分支并入 |
| `merge` / `reject` + 传 `name` | 忽略（不报错，保持向后兼容）；**不落审计** |
| `name` 长度 > 200 | 422（Pydantic） |
| `name` == 原文（仅空白差异） | 视为未修正，走原路径 |
| 拓扑约束（父级未转正） | 不变，先于名称处理（`_check_topology` 在入口） |

#### C. 前端：统一门牌拼装（消除 5 处硬编码「号」）

新增 `frontend/src/lib/dict-display.ts`：

```ts
/** 楼栋号后缀是否已自带量词（号/号楼/栋/幢/单元/弄）——避免拼成「21号号」「2号楼号」 */
export function hasBuildingSuffix(buildingNo: string): boolean {
  return /(号|号楼|栋|幢|单元|弄)$/.test(buildingNo.trim());
}

/** 楼栋展示：自带后缀则原样，否则补「号」（与后端 BR-03 原样存储口径对齐） */
export function formatBuildingLabel(buildingNo: string): string {
  const s = buildingNo.trim();
  if (!s) return "";
  return hasBuildingSuffix(s) ? s : `${s}号`;
}

/** 门牌预览：小区 + 楼栋展示 + 户号映射（0401→401） */
export function formatPlate(communityName: string, buildingNo: string, plateNo?: string): string {
  return [communityName, formatBuildingLabel(buildingNo), plateNo].filter(Boolean).join(" ");
}
```

替换点（5 处硬编码 + `buildPlate`）：

| 文件 | 现状 | 改后 |
|------|------|------|
| `dict-address-picker/index.tsx:98-101` `buildPlate` | 内部 `${buildingNo}号` | 改调 `formatPlate` |
| `dict-address-picker/index.tsx:584,592` | `${v.buildingNo}号` | `formatBuildingLabel(v.buildingNo)` |
| `review-resolve-modal.tsx:95,97` | `${...building_no}号` | `formatBuildingLabel(...)` |
| `community-drawer.tsx:701,757` | `{picked.buildingNo}号` | `formatBuildingLabel(picked.buildingNo)` |
| `review-target-picker.tsx:298` | `{b.building_no}栋` | **保持不变**（chip 是「栋」前缀语义，见 §3 决策点 D-C） |

> ⚠️ `formatBuildingLabel` 只在**楼栋号**场景使用；项目/营销列表的 `${building_no}栋`
> 是另一套口径（后缀为「栋」），本次**不动**，避免扩大改动面。

## 2. 场景二：默认「用已有的」但楼盘无数据时「推荐」标还在且提交不了

### 2.1 现状（已核对）

**前端（三处硬编码）**

| 位置 | 代码 | 问题 |
|------|------|------|
| `review-resolve-modal.tsx:84` | `useState<ActionKind>("merge")` | 不论有无可合并目标，**默认永远 merge** |
| `review-resolve-modal.tsx:165` | `tag: "推荐"` | 推荐标**无条件渲染** |
| `review-target-picker.tsx:133` | `.filter((b) => !b.pending)` | 楼栋 chips **剔除 pending 行** |
| `review-target-picker.tsx:167` | `.filter((r) => !r.pending)` | 户室网格**剔除 pending 行** |
| `review-target-picker.tsx:300/352` | 「本小区暂无实表楼栋」「该楼栋暂无实表户室」 | 只提示，无出口 |
| `review-resolve-modal.tsx:101` | `canSubmit = create \|\| ... \|\| !!targetSummary` | 无目标 → **提交按钮永久 disabled** |

**触发链路（运营可见的死路）**

```
小区无楼栋（实测 2066 个小区）
  → 楼栋条目 merge：buildings 空 → 无 chips → target.building=null
  → targetSummary=null → canSubmit=false
  → 提交按钮置灰 + 卡片写着「推荐」   ← 运营既不能提交也被告知这是推荐项
```

户室条目同构（246 栋无户室）；另有 **30/41 条** pending room 的父楼栋已被删除，
`communityId` 为空时 `ReviewTargetPicker` 直接 `return`（`useEffect: if (isCommunityKind || !communityId) return`）
→ 面板空白，**连提示都没有**。

**后端可复用能力（无需新接口）**

- `list_buildings` 已把 pending 楼栋以 `pending=true, pending_id` 叠加返回
  （`dict_read_service.py:515-562`），**前端主动 filter 掉了**。
- `get_building_detail` 已把 pending 户室以 `pending=true` 叠加返回（`:662-680`）。
- 故「合并到待审兄弟条目」在数据层已可呈现，**只差前端放行 + 后端接受**。

**后端现状缺口**：`_resolve_merge` 只查 `BdBuilding` / `BdRoom` 实表
（`building_review_service.py:401,420`），传入 pending_id 会 404「目标楼栋不存在」。
→ 需要新增「合并到待审兄弟」分支：先把它转正（或要求先审核它）。

### 2.2 方案

#### A. 默认动作与推荐标「按数据可用性派发」

`review-resolve-modal.tsx` 新增纯函数（可单测）：

```ts
type MergeAvailability = "available" | "empty" | "unknown";

/**
 * 判断「用已有的」是否可提交：
 * - community 条目：全库搜索，恒 available（总是可以搜一个出来，搜不到是运营操作问题）
 * - building 条目：所属小区楼栋 chip 数（含 pending 兄弟）> 0
 * - room 条目：所属楼栋户室数（含 pending 兄弟）> 0；父楼栋缺失 → empty
 */
```

落地要点：

1. `ReviewTargetPicker` 通过新 prop `onAvailabilityChange?: (v: MergeAvailability) => void`
   把「本小区可合并目标数」上报（`buildings.length + pendingBuildings.length` 等）。
2. `ReviewResolveModal` 收到 availability：
   - `empty` → `action` 初值 **`"create"`**，merge 卡片**去掉「推荐」标**，
     卡片文案改为「本小区/本楼栋暂无任何实表或待审数据可合并」+ **disabled**；
   - `available` → 保持现状（默认 merge + 推荐标，与设计稿 v2.0 一致）；
   - `unknown`（尚未加载完）→ 保持 merge 但不显示推荐标，加载完成后纠正。
3. 默认值用 `useEffect` 在 availability 首次确定时**只纠正一次**（用户手动点过卡片就不再覆盖：
   `userTouchedRef`），避免「加载完把用户选择冲掉」。

> 为什么不是「永远默认 create」？设计稿 v2.0 ARTBOARD 04 明确楼栋/户室以 merge 为推荐项
> （「已有这栋/这户」是绝大多数情况）；只在**数据为空**时降级，改动最小且符合运营直觉。

#### B. 目标选择器放行 pending 兄弟条目（BR-23 对齐）

`review-target-picker.tsx`

- 删除 `:133` / `:167` 的 `!b.pending` / `!r.pending` 过滤；
- pending 项**可见但默认不可选**？—— 这里需要决策（见 D-B）：

或者更干净的做法（**推荐**）：新增 `target_kind` 字段而不是字符串前缀 hack：

```python
class BdReviewResolveRequest(BaseModel):
    action: str
    target_id: str | None = None
    target_kind: str | None = Field(
        None, pattern="^(dict|pending)$",
        description="目标来源：dict=字典实表(默认) / pending=审核池待审条目",
```

`_resolve_merge` 分支：

- `target_kind == "pending"`：
  1. 校验目标 pending 存在、`status == pending`、`kind` 与本条目**同 kind**；
  2. 校验 `community_scope` 一致（拓扑/归属）；
  3. **同一事务内先转正该目标**（复用 `_resolve_create` 的落库方法，但**不改它的 status**
     —— 由本方法显式置 `CREATED` 并记 `resolved_by=当前审核员`？⚠️ 决策点 D-B2）；
  4. 本条目落 `MERGED`，`resolved_target_id = 目标转正后的实表 id`；
  5. 两侧引用账本合并回填（目标 pending 的 open 引用 + 本条目的 open 引用都指向同一实表 id）；
  6. `_rewire_child_buildings` / 子户室改指（与既有 create 分支一致）。
- 冲突拦截：目标 pending 已非 pending → 409（与行锁口径一致，**先 `with_for_update` 锁目标行**，
  避免并发双审创建两行）。
- 审计：`action="bd_review_merge"`, `after={"target_kind":"pending","promoted_target":<id>}`。

> ⚠️ **决策点 D-B2（必须拍板）**：合并到「待审兄弟」时，那个兄弟条目算谁的审核结果？
> - 方案 i（推荐）：**顺手转正它并记在当前审核员名下**（`resolved_by`），审计写「A 合并至 B 并转正 B」。
>   运营一次操作解决两条待审，符合「同一栋楼重复提交」的真实场景。
> - 方案 ii：拒绝合并到待审（只允许 create/驳回），把边界留在运营侧处理。实现最小，
>   但「两条待审同楼栋」仍需两次操作。
> - 方案 iii：允许选但**要求先审兄弟**，本次仅提示（不改后端）。

### 3.2 方案：新增「字典楼栋/户室重命名」写端点（P0）+ 抽屉内联编辑

#### A. Schema（`backend/schemas/building_dict.py`）

```python
class BdBuildingRenameRequest(BaseModel):
    """修正楼栋号（admin 即时生效 + 审计；BR-29 扩展）."""

    building_no: str = Field(min_length=1, max_length=100, description="修正后的楼栋号（原样存储，不自动补「号」）")


class BdRoomRenameRequest(BaseModel):
    """修正户室号（admin 即时生效 + 审计）."""

    room_no: str = Field(min_length=1, max_length=100, description="修正后的户室号（如 0401 / 0233-1）")
```

#### B. Router（`backend/routers/property/building_dict.py`）

```python
@router.patch("/buildings/{building_id}")
@limiter.limit(RateLimits.COMMUNITY_UPDATE)

@router.patch("/buildings/{building_id}/rooms/{room_id}")
```

权限：`CurrentAdminUserDep`（与既有补录/删除同口径），限流复用 `COMMUNITY_UPDATE`（1000/h）。

#### C. Service（`dict_write_service.py`）

```python
def rename_building(self, db, building_id, body, *, operator_id, request=None) -> ...:
    """修正楼栋号（uq 冲突 409 / 待审同名条目同步修正 / 审计）."""
```

**必须处理的 5 个约束**（逐条给实现口径）：

| # | 约束 | 口径 |
|---|------|------|
| 1 | `uq_bd_building_no (community_id, building_no)` | 改名撞同小区已有楼栋 → **409** `小区内已存在楼栋「X」，如需合并请走治理合并` |
| 2 | 名称归一 | `" ".join(name.split())`；空 → 400；与原名相同 → 直接返回（不写审计） |
| 3 | **待审同名条目**（改名后与某 pending building 同名） | 复用既有 `_promote_matching_pendings` 语义：视为 admin 确认，**自动转正**该 pending + 回填引用 + 通知提交人（与 BR-26 一致）<br>⚠️ **实现坑**：该方法内部自带 `db.commit()`（`dict_write_service.py:138` 区域内）且在 commit 后继续循环后续 pending —— rename 若同事务调用它，会出现「楼栋改名未提交但 pending 已提交」的半提交。**本次实现须**：把 rename 写序改为「先 `db.flush()` 提交改名 → 再调 `_promote_matching_pendings` → 最后 `_audit`」，并在该方法 docstring 注明「调用方必须先 flush 自身写入」。 |
| 4 | **业务单据冗余**（projects/leads/marketing 的 `building_id` 指针） | `building_id` 未变 → **无需改单据**；但 `projects.address` 里的旧门牌文本是冻结原文（FR-12 口径「原手填 address 原值保留」），**不改写**，仅提示 |
| 5 | **待审子级户室条目** | `parent_id` 指向本楼栋的 pending room 无需改（id 未变）；但 `payload` 里若存了旧楼栋号，**不改**（payload 是提交快照，FR-11 口径保留原文） |

```python
def rename_room(self, db, building_id, room_id, body, *, operator_id, request=None) -> ...:
    """修正户室号（uq 409 / floor 重算 / room_count 不变 / 审计）."""
```

**户室改名额外 3 条**：

| # | 约束 | 口径 |
|---|------|------|
| 1 | `floor` 是派生列 | 改名后 **必须重算** `parse_room_floor(new_no)`，否则楼层分组错乱（改名 `0401`→`0501` 必须移到 5 层） |
| 2 | `uq_bd_room_no (building_id, room_no)` | 撞同楼栋已有户室 → 409 |
| 3 | 户室改名的**楼层变动**是否允许？ | 允许（同楼栋内移动），但要 `room_count` 不变、`floor` 重算；审计记录 `floor_from/floor_to` |

审计：`action="bd_building_rename"` / `"bd_room_rename"`，`before={old}`、`after={new}`。

#### E. 小区名（`communities.name`）修正 —— **建议单独立项，本次不做**

理由（都需要拍板 **D-D**）：

1. `communities.name` 是 **UNIQUE 全库**（实测 `communities_name_key`），改名撞名需 409；
2. 冗余面广：`projects.community_name`（38 条，实测 0 条不一致）、`leads.community_name`（124 条，0 不一致）、
   `l4_marketing_projects.community_name`（315 条，1 条不一致）、`community_aliases`（43 条）、
   机器链路 `property_current.community_name`；
3. 已有 `CommunityUpdateRequest.name`（市场情报端点）**不做上述补偿**，若字典里再接一条
   会形成两套改名口径（事故风险）；
4. 更稳的替代：**「改名」= 新增别名 + 主档名保持**，或走既有「合并 + 解除合并」治理链路。

若确认要做，最小闭环是：
`PATCH /admin/building-dictionaries/communities/{id}/rename`：
事务内 ① 更新 `name`；② 把旧名写入 `community_aliases(alias_name=old, data_source='rename_operation')`；
③ **不回写**单据冗余（FR-12 明确保留原文）；④ 全库唯一冲突 409；⑤ 审计 `bd_community_rename`。
⚠️ 仍需确认「不影响 C 端/小程序展示」的验收口径。

```sql
-- ① 存量待审条目带尾部「号」（确认归一策略对未审核条目的影响）
--    结论：无需处理 —— 审核 create 时统一归一，pending 原文保留作为提交证据。
SELECT count(*) FROM bd_pending_entries WHERE status = 'pending' AND name ~ '号$';

-- ② 存量楼栋号带「号」（预期无需清洗）
--    实测 2026-10-20：4477 行；其中 100 行去掉「号」会与同小区另一楼栋同名
--    （0 行有业务单据引用），故清洗必须逐条确认，本轮按决策不清洗。
SELECT count(*) FROM bd_buildings WHERE building_no ~ '号$';

-- ③ 展示层不冲突验证：归一后展示恒等于原展示（无需清洗的依据）
--    「21号」原样展示为「21号」；「21」拼装为「21号」 —— 两者视觉一致。
SELECT count(*) FROM bd_buildings
 WHERE building_no ~ '号$' AND regexp_replace(building_no, '号$', '') = '';
-- 预期 0（不存在剥完为空的脏值；归一函数另有回退保护兜底）
```
