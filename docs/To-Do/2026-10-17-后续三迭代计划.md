## 0. 执行摘要

三个迭代按「**先保命、再提效、后可观测**」排序：

| 顺序 | 主题 | 解决的问题 | 核心交付 | 建议周期 |
|------|------|-----------|---------|---------|
| **迭代一** | 迁移版本化与可回滚 | 77 个启动迁移无版本表、无补偿脚本；数据修复事故只能靠人工记忆 | `schema_migrations` 版本表、迁移注册表/校验和、强制备份、补偿 CLI、高风险迁移矩阵 | 2 周 |
| **迭代二** | 统一消息中心 + 角色化工作台 | 通知散落在 4 条微信订阅链路、无站内信/已读/偏好；所有角色共用一套工作台 | `notifications` 三表 + `user_preferences`、统一事件/收件人/渠道、消息中心 UI、角色默认布局与个人定制 | 2–3 周 |
| **迭代三** | Prometheus 指标 + 慢查询告警 | 仅有 `/health` 与文本日志；274 个 API、2 个 worker，线上故障发现靠用户反馈 | `/metrics`、HTTP/DB/连接池/业务指标、慢查询日志与计数器、Prometheus 告警规则、可观测性部署 profile | 2 周 |

**关键依赖**：

- 迭代三的「告警送达」优先复用迭代二的 `NotificationService`（系统告警 → 站内信 + 微信）；若迭代二延期，降级为 Alertmanager 直接 webhook 到群机器人。
- 迭代二的消息表需要走迭代一的「新迁移必须登记版本 + 备份策略」，因此迭代一必须先落地。
- 迭代三的迁移指标（`profo_migrations_total`）直接消费迭代一的注册表/执行结果。

**不做的事**（全阶段）：

- 不引入 Alembic 重写现有迁移（成本高、收益低；见决策 D1）。
- 不做全量 APM/Tracing、日志平台（Loki/ELK）、SLO 平台；本期只做 Prometheus + 慢查询 + 告警。
- 不做邮件/短信/Web Push；消息渠道本期为「站内信 + 微信订阅消息」。
- 不做小程序消息中心页；本期消息中心以 B 端后台为主（小程序已有「我的客户」角标与订阅消息）。

## 3. 迭代一：迁移版本化与可回滚

### 3.1 问题陈述

当前启动迁移是「**代码即清单**」：77 个函数按硬编码顺序执行，幂等但无执行记录、无备份、无回滚。一次数据修复迁移（加密手机号、清空微信 session_key、楼盘字典多表修正）如果逻辑有误，只能靠人工回忆和事后备份恢复，**无法回答**：

- 这个环境执行到第几版？什么时候执行的？耗时多久？
- 某次迁移失败停在哪一步？是否已部分提交？
- 这次数据修复改了多少行？改动前的值是什么？
- 如果上线后发现错误，如何在不丢新数据的前提下回退？

### 3.2 目标与成功指标

**目标**：让每一次迁移都具备「**可追溯、可校验、可备份、可补偿/恢复**」四要素；未来新增数据修复迁移必须声明备份与补偿策略，否则不允许执行。

**成功指标**：

| 指标 | 目标 |
|------|------|
| 迁移记录覆盖率 | 100%（77 个既有迁移 + 后续新增全部登记） |
| 启动可解释性 | 启动日志能输出「pending N / applied N / failed N」，失败行含 `version/name/error/backup_path` |
| 校验和 | 已执行迁移源码变更时启动**阻断**并给出修复指令；误报可通过 `rebaseline` 显式处理 |
| 备份 | 所有 `backup_required` 迁移执行前备份成功；备份失败则迁移不执行 |
| 回滚演练 | 在 staging 对 1 个数据修复迁移完成「备份 → 补偿 → 验证」全流程，≤30 分钟 |
| 启动耗时 | 增量启动（无 pending）额外耗时 ≤ 2 秒；基线首跑允许较长，需在维护窗口执行 |

### 3.3 范围

#### In Scope

1. `schema_migrations` / `migration_compensations` 两张表及幂等建表。
2. 迁移注册表：版本、名称、函数、类型、备份策略、可逆性、补偿脚本、描述。
3. 迁移执行器重构：advisory lock、版本校验、pending 执行、状态记录、失败阻断。
4. 首次基线：既有 77 个迁移的 `baseline` 流程（执行一次并登记）。
5. 迁移前备份：`pg_dump` custom format + 校验和 + 保留策略。
6. 补偿脚本框架 + CLI：`status` / `baseline` / `up` / `verify` / `retry` / `compensate`。
7. 高风险迁移逐项分类：自动补偿 / 脚本补偿 / 备份恢复 / 不可回滚。
8. 运行手册与演练记录。

#### Out of Scope

- 迁移到 Alembic 或独立迁移服务。
- 自动为 77 个迁移全部生成 down SQL（不可逆的仍以备份恢复为主）。
- 零停机在线 DDL（本期不处理锁表优化）。
- 迁移审批流/工单系统。

### 3.4 方案设计

#### 3.4.1 版本表

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    version        INTEGER PRIMARY KEY,
    name           VARCHAR(200) NOT NULL UNIQUE,
    checksum       VARCHAR(64) NOT NULL,
    kind           VARCHAR(20) NOT NULL,          -- schema / data / seed
    status         VARCHAR(20) NOT NULL,          -- applied / failed
    started_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    applied_at     TIMESTAMPTZ,                  -- 仅成功时写入
    duration_ms    INTEGER,
    app_version    VARCHAR(32),
    worker         VARCHAR(100),
    backup_path    TEXT,
    backup_sha256  VARCHAR(64),
    error          TEXT,
    notes          TEXT
);

CREATE TABLE IF NOT EXISTS migration_compensations (
    id           BIGSERIAL PRIMARY KEY,
    version      INTEGER NOT NULL,                -- 逻辑外键，不建 DB FK（项目约定）
    action       VARCHAR(30) NOT NULL,            -- compensate / restore / rebaseline
    operator     VARCHAR(100),
    started_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at  TIMESTAMPTZ,
    duration_ms  INTEGER,
    result       VARCHAR(20) NOT NULL,            -- success / failed / dry_run
    notes        TEXT
);
```

> 遵循项目「逻辑外键、不建 DB FK」约定；版本表只做记录与审计，不参与业务查询。

#### 3.4.2 迁移注册表

新增 `backend/migrations/registry.py`：

```python
@dataclass(frozen=True)
class Migration:
    version: int                 # 既有 1..77，新增从 78 开始
    name: str                    # 唯一，稳定，不随函数重命名变化
    fn: Callable[[Engine], None]
    kind: Literal["schema", "data", "seed"]
    backup: Literal["none", "table", "full"]
    reversible: bool
    backup_tables: tuple[str, ...]  # backup=table 时备份的表
    compensation: str | None     # compensations/<version>_<name>.py
    description: str
```

- `MIGRATIONS: tuple[Migration, ...]` 按 `version` 升序排列。
- `_run_all_migrations` 不再硬编码 77 行调用，改为遍历注册表。
- 既有 77 个迁移按当前执行顺序赋 `version=1..77`；新增迁移从 `78` 开始，**禁止插入历史版本中间**。
- 校验和：`sha256(inspect.getsource(fn))`。已执行迁移源码变化 → 启动阻断：
  - 正确做法：新增一条迁移，而不是修改已执行迁移。
  - 纯重构/移动函数：执行 `manage rebaseline <version> --reason "..."`，写 `migration_compensations` 审计。

#### 3.4.3 启动流程

```text
run_startup_migrations(engine)
  ├─ 获取 pg_advisory_lock（复用现有 key）
  ├─ CREATE TABLE IF NOT EXISTS schema_migrations / migration_compensations
  ├─ 读取 applied/failed
  ├─ 校验 applied 的 checksum
  ├─ 若存在 failed → 记录错误并 raise（阻断启动，给出 manage retry 指令）
  ├─ 若 schema_migrations 为空且核心业务表（users/projects/leads）有数据 → 拒绝自动执行，提示先 baseline
  ├─ 若 schema_migrations 为空且核心业务表均为空（全新库）→ 按注册表全量执行并记录
  └─ 否则只执行 pending：
       ├─ 如 backup != none → 备份 + 记录 backup_path/sha256
       ├─ 执行 fn(engine)，计时
       ├─ 成功 → INSERT/UPDATE status=applied
       └─ 失败 → 写 status=failed/error，raise（启动失败）
```

**首次基线**（既有环境）：

```bash
# 在维护窗口、后端停止或仅单 worker 时执行
docker compose exec backend python -m migrations.manage baseline --confirm
docker compose exec backend python -m migrations.manage status
```

- `baseline` 会先做**全库备份**，再按注册表执行全部迁移（幂等 no-op 为主），逐条登记。
- 不在启动时自动 baseline 既有库：避免误判/长时间启动；全新库可自动全量执行。
- **注意**：`lifespan` 先 `init_db()` 建表再跑迁移，不能用「users 表是否存在」区分新旧库；应检查核心表是否有数据（`users/projects/leads` 任一非空即视为既有库）。
- 开发/测试库可显式 `MIGRATION_AUTO_BASELINE=true` 简化。

#### 3.4.4 迁移前备份

| 项 | 设计 |
|----|------|
| 工具 | `pg_dump --format=custom`（需在 backend 镜像安装 `postgresql-client`，约 +20MB） |
| 范围 | `backup=table` → `--data-only --table=<backup_tables 逐个>`；`backup=full` → 全库 |
| 路径 | `MIGRATION_BACKUP_DIR`，Docker 挂载 `./backups:/app/backups`，默认 `backups/migrations/` |
| 文件名 | `YYYYMMDD-HHMMSS_v{version}_{name}.dump` |
| 校验 | 记录 `backup_sha256`、文件大小；失败/0 字节 → 中止迁移 |
| 保留 | `MIGRATION_BACKUP_RETENTION_DAYS=30`、`MIGRATION_BACKUP_MAX_COUNT=20`，启动后清理，保留最新 |
| 失败策略 | 备份失败 = 迁移不执行（Fail Loud），不允许 `--skip-backup` 在生产使用 |
| 安全 | 备份可能含手机号/身份证等 PII：目录 `700`、文件 `600`，禁止提交 Git；生产建议加密归档并限制下载 |
| 本地开发 | 无 `pg_dump` 时明确报错；允许 `MIGRATION_BACKUP_MODE=off` **仅限开发**并在日志高亮 |

> 数据修复迁移优先 `table` 级备份（体积小、恢复快）；涉及删列/删表/多表修正用 `full`。

#### 3.4.5 补偿脚本

目录：`backend/migrations/compensations/`

```text
compensations/
├── __init__.py
├── registry.py                 # version -> compensate(engine, ctx)
├── 00xx_encrypt_existing_phones.py
├── 00xx_backfill_lead_unit_price.py
└── ...
```

每个脚本暴露：

```python
def compensate(engine: Engine, ctx: CompensationContext) -> CompensationResult:
    """执行补偿；必须幂等、可 dry-run、返回影响行数。"""
```

CLI：

```bash
python -m migrations.manage status
python -m migrations.manage baseline --confirm
python -m migrations.manage up
python -m migrations.manage verify
python -m migrations.manage retry <version> --reason "..."
python -m migrations.manage compensate <version> --dry-run
python -m migrations.manage compensate <version> --yes --reason "..."
```

安全约束：

- `--dry-run` 必须只统计/打印，不写库；输出预计影响行数。
- 默认拒绝影响行数 > `MIGRATION_COMPENSATION_MAX_ROWS`（默认 10000），需 `--force`。
- 生产环境需 `--yes` + `MIGRATION_PRODUCTION_CONFIRM=<环境名>` 双确认。
- 补偿在事务中执行；失败回滚并记录 `migration_compensations.result=failed`。
- 不可逆迁移不提供 `compensate`，只提供 `restore` 运行手册（见 3.4.6）。

#### 3.4.6 高风险迁移分类

| 等级 | 定义 | 处理 | 示例 |
|------|------|------|------|
| **A 自动补偿** | 纯新增、可安全 `DROP` | 脚本自动 `DROP COLUMN/INDEX/TABLE`（仅当该表无业务数据依赖） | `add_*_column`、`create_*_table` |
| **B 脚本补偿** | 数据回填，有确定性逆操作 | 补偿脚本按条件反向更新（如 `SET NULL`），带行数守卫 | `backfill_lead_unit_price`、`backfill_bd_room_floor`、`recover_stale_bd_import_tasks` |
| **C 备份恢复** | 加密/删除/多表修正/列重命名 | 迁移前 `table/full` 备份；补偿 = 按 runbook 从备份恢复，不承诺一键 | `encrypt_existing_phones`、`clear_wechat_session_key`、`run_bd_audit_*`、`rename_return_adjustment_columns` |
| **D 不可回滚** | 外部副作用/已删除源数据 | 禁止自动执行；需 `--allow-irreversible` + 变更评审 | 本地文件上传 OSS 后删除源文件的带外脚本（若有） |

**初始矩阵（发布前必须补全 77 项）**：

| 迁移 | 等级 | 备份 | 补偿策略 |
|------|------|------|---------|
| `encrypt_existing_phones` | C | table `users` | 从备份恢复 `users.phone`；不提供“解密回明文”默认脚本（安全风险） |
| `populate_phone_hash` | B | table `users` | `UPDATE users SET phone_hash=NULL`（可按 `notes` 限定本次迁移范围） |

#### 3.4.7 执行器与现有迁移的兼容

- 现有迁移函数内部自行 `engine.begin()` 提交；执行器**不包裹外层大事务**（否则与内部 commit 冲突），而是：
  - 迁移前备份；
  - 迁移函数执行；
  - 成功/失败单独写 `schema_migrations`（独立连接）；
  - 部分提交无法自动回滚 → 这正是备份 + 补偿存在的原因。
- 新迁移建议：单一事务、可重复执行、显式 `backup/reversible/compensation` 元数据。
- 迁移函数签名保持 `fn(engine: Engine) -> None`，避免大改 77 个函数。

## 4. 迭代二：统一消息中心 + 角色化工作台

### 4.1 问题陈述

**消息侧**：当前通知是 4 条独立的微信订阅消息链路，各自解析 openid、拼模板、best-effort 发送；没有站内收件箱、已读状态、用户偏好、统一失败重试。用户没看到微信消息就没有兜底；运营也无法在一个地方查看「今天有哪些线索/待办/系统异常需要处理」。

**工作台侧**：`/admin` 是单套仪表盘，所有角色看到同一组卡片，仅靠权限码隐藏。admin 需要全局经营视角，operator 需要获客/线索/审核视角，user 需要「我的项目/我的待办」执行视角，但当前没有角色默认布局，也没有个人定制。

### 4.2 目标与成功指标

**目标**：

1. 建统一消息中心：**一个事件 → 统一收件人解析 → 站内信（持久化）+ 微信（best-effort）→ 已读/偏好/审计**。
2. 建角色化工作台：**角色默认布局 + 用户个人定制 + 权限硬门控**，不改变现有业务 API 的权限边界。

**成功指标**：

| 指标 | 目标 |
|------|------|
| 站内信可见时延 | 事件成功后 ≤ 2s（同库插入） |
| 未读数一致性 | 列表/角标/已读操作后 100% 一致（以 DB 为准） |
| 跨用户隔离 | 0 泄漏；A 用户无法读取/标记 B 用户消息 |
| 通知去重 | 同一 `dedupe_key` 重复触发只产生 1 条 |
| 角色工作台 | admin/operator/user 默认可见组件集合不同；权限不因布局扩大 |
| 工作台首屏 | 已有 Suspense 并行取数；P95 不高于当前基线 + 20% |
| 现有微信通知 | 4 条链路无回归；失败仍不影响主流程 |

### 4.3 范围

#### In Scope

1. 消息数据模型：`notifications`、`notification_recipients`、`notification_delivery_logs`、`user_preferences`。
2. 统一 `NotificationService`：事件创建、收件人解析（用户/角色/权限）、去重、站内信持久化、微信渠道适配。
3. 消息 API：列表、未读数、单条已读、全部已读、偏好读写。
4. 前端：侧边栏/移动端铃铛、未读角标、消息抽屉/页面、偏好设置。
5. 角色工作台：`workbench` 配置 API、角色默认布局（`system_configs`）、用户覆盖（`user_preferences`）、组件注册表、5 个新卡片。
6. 现有员工侧微信通知**双写站内信**（招募新线索、我的客户新线索/状态）；C 端营销上新/调价、估价授权价变更本期仍仅走微信（C 端站内信后续迭代扩展 `/public/notifications`）。
7. 权限与审计：消息只读自己的；系统广播/角色布局管理需 admin；操作留痕。

#### Out of Scope

- 小程序消息中心页面（保留现有微信订阅与「我的客户」角标）。
- 邮件/短信/Web Push。
- SSE/WebSocket 实时推送（MVP 用 SWR 轮询 + 窗口聚焦刷新；实时化放后续）。
- 复杂通知模板编辑器/多语言。
- 工作台拖拽自由布局（MVP 先「显示/隐藏 + 上下移动」，拖拽可作为 stretch）。

### 4.4 方案设计

#### 4.4.1 数据模型

```sql
CREATE TABLE notifications (
    id            UUID PRIMARY KEY,
    category      VARCHAR(30) NOT NULL,      -- lead/project/marketing/growth/finance/key/system/security
    type          VARCHAR(60) NOT NULL,      -- lead.assigned / project.todo_due / ...
    title         VARCHAR(200) NOT NULL,
    body          VARCHAR(500),
    action_type   VARCHAR(20),               -- route / miniapp / none
    action_url    VARCHAR(500),              -- 站内路由或小程序页面
    payload       JSONB,
    priority      VARCHAR(10) NOT NULL DEFAULT 'normal', -- low/normal/high/urgent
    dedupe_key    VARCHAR(200) UNIQUE,       -- 幂等键；可空
    source_module VARCHAR(30),
    source_id     VARCHAR(64),
    created_by    VARCHAR(36),
    expires_at    TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE notification_recipients (
    id              BIGSERIAL PRIMARY KEY,
    notification_id UUID NOT NULL,           -- 逻辑外键
    user_id         VARCHAR(36) NOT NULL,    -- 逻辑外键
    read_at         TIMESTAMPTZ,
    archived_at     TIMESTAMPTZ,
    delivery_status JSONB,                   -- {"in_app":"sent","wechat":"skipped"}
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (notification_id, user_id)
);
CREATE INDEX idx_notification_recipients_user_unread
    ON notification_recipients (user_id, read_at) WHERE read_at IS NULL;

CREATE TABLE notification_delivery_logs (
    id              BIGSERIAL PRIMARY KEY,
    notification_id UUID NOT NULL,
    user_id         VARCHAR(36) NOT NULL,
    channel         VARCHAR(20) NOT NULL,    -- in_app / wechat
    status          VARCHAR(20) NOT NULL,    -- sent / skipped / failed
    error_code      VARCHAR(50),
    error_message   VARCHAR(500),
    attempt         INTEGER NOT NULL DEFAULT 1,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_notification_delivery_logs_notification
    ON notification_delivery_logs (notification_id, user_id, created_at DESC);

CREATE TABLE user_preferences (
    id         UUID PRIMARY KEY,
    user_id    VARCHAR(36) NOT NULL,         -- 逻辑外键
    namespace  VARCHAR(50) NOT NULL,         -- workbench.layout / notification.preferences
    value      JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (user_id, namespace)
);
```

> 迁移走迭代一的注册表：`version=78+`，`kind=schema`，`backup=none`。

#### 4.4.2 事件字典（MVP）

| 事件 | category | 收件人 | 渠道 | dedupe_key |
|------|----------|--------|------|------------|
| `lead.assigned` | lead | 被分配员工 | 站内 + 微信可选 | `lead:{id}:assigned:{user_id}` |
| `lead.status_changed` | lead | 线索归属员工 | 站内 + 微信可选 | `lead:{id}:status:{status}` |
| `customer.new` | growth | 分享归属员工 | 站内 + 微信 | `customer:{module}:{id}:new:{user_id}` |
| `customer.status_changed` | growth | 归属员工 | 站内 + 微信 | `customer:{module}:{id}:status:{status}` |
| `project.todo_due` | project | 项目业务负责人/团队 | 站内 | `todo:{rule}:{project_id}:{date}:{user_id}` |
| `project.status_changed` | project | 项目团队 | 站内 | `project:{id}:status:{status}` |
| `recruit.new_lead` | growth | 推荐员工 | 站内 + 微信 | `recruit:{lead_id}:new:{user_id}` |

#### 4.4.3 服务流程

```text
业务事件（commit 后）
  └─ NotificationService.emit(event)
       ├─ 解析收件人（user_ids / role_codes / permission_codes / assignee）
       ├─ 过滤用户偏好（category × channel；system/security 不可关）
       ├─ 按 dedupe_key 幂等插入 notifications
       ├─ 批量插入 notification_recipients
       ├─ 站内信：仅 B 端事件；DB 插入即对收件人可见
       ├─ 微信：WeChat channel adapter；best-effort，失败写 delivery_logs
       └─ 返回 created/skipped 计数
```

关键约定：

- **commit 后触发**：通知不能在业务事务提交前发；优先在 Service 完成 commit 后调用，或使用 `after_commit` 事件。
- **收件人解析最小化**：禁止默认全员广播；必须有明确 audience。
- **幂等**：`dedupe_key` 唯一；重复触发返回既有通知，不重复插入收件人。
- **微信不改额度模型**：营销订阅额度仍由现有 `l4_marketing_subscriptions` 管理；消息中心只做旁路站内信与统一日志。
- **失败不影响主流程**：沿用现有 `notify_*` best-effort 语义。

## 5. 迭代三：Prometheus 指标 + 慢查询告警

### 5.1 问题陈述

系统已有 274 个 API、2 个 uvicorn worker、PostgreSQL + Redis，但线上只有：

- `/health`（进程/DB 连通）
- stdout / `app.log` 文本日志（有 `X-Request-ID`）
- 用户反馈与人工 `pg_stat_activity`

**没有**请求量/错误率/延迟时间序列、没有连接池指标、没有慢查询阈值与告警。一次慢查询或连接池打满，只能等页面变慢/用户投诉才发现；274 个 API 中哪个最慢、错误率最高，无法回答。

### 5.2 目标与成功指标

**目标**：以最小依赖接入 Prometheus，覆盖 **HTTP / DB / 连接池 / 迁移 / 通知** 五类指标；慢查询可记录、可计数、可告警；`/metrics` 不暴露公网。

**成功指标**：

| 指标 | 目标 |
|------|------|
| 路由覆盖率 | 100% 已注册路由有 `route` 模板标签（未匹配归 `unmatched`） |
| 多 worker 正确性 | 2 worker 下指标为聚合值，不是单 worker 的一半 |
| 慢查询捕获 | 超过阈值（默认 500ms）的 SQL 100% 记录日志并计数（本期不抽样） |
| 告警时效 | 关键告警 ≤10 分钟；后端宕机 ≤2 分钟 |
| 安全性 | 公网访问 `/metrics` 返回 404/403；仅内网/带 token 可抓取 |
| 开销 | 指标采集导致的 P95 延迟增加 < 5%；内存增加 < 50MB |
| 可验证 | `promtool check rules` + `promtool test rules` 通过；慢查询注入用例通过 |

### 5.3 范围

#### In Scope

1. `prometheus-client` 依赖 + multiprocess 模式（2 worker 必需）。
2. HTTP 指标中间件：请求数、延迟直方图、进行中、异常。
3. SQLAlchemy 事件监听：查询耗时直方图、慢查询计数、慢查询日志（无参数/无 PII）。
4. 连接池指标：checked out / checked in / overflow。
5. 迁移指标：成功/失败计数、耗时（消费迭代一注册表）。
6. 业务指标（最小集）：通知发送/失败、线索/预约创建（可选）。
7. `docker-compose.observability.yml`：Prometheus + Alertmanager + postgres_exporter + redis_exporter（Grafana 可选）。
8. 告警规则 + Alertmanager 路由（webhook；可选接迭代二消息中心）。
9. 运行手册与抓取/告警验证。

#### Out of Scope

- OpenTelemetry / 分布式追踪 / APM。
- Loki/ELK 日志聚合。
- 全量业务指标治理（只做最小集）。
- Grafana 托管/复杂看板（提供基础 JSON，可选）。
- 对 274 个 API 逐个自定义 SLO。

### 5.4 方案设计

#### 5.4.1 多 worker 指标（关键）

生产 `WEB_CONCURRENCY=2`，`prometheus_client` 默认是**每进程独立**的。若不处理，Prometheus 每次抓取只会命中一个 worker，指标随机减半。

方案：

- 设置 `PROMETHEUS_MULTIPROC_DIR=/tmp/profo-prometheus`（所有 worker 共享）。
- backend 启动前 `mkdir -p` 并清空该目录（entrypoint），避免上次运行残留。
- `/metrics` 使用 `CollectorRegistry + multiprocess.MultiProcessCollector` 聚合所有 worker 的 mmap 文件。
- `Gauge` 必须显式 `multiprocess_mode`（如 `livesum`）。
- 不使用 multiprocess 不支持的 `Info`/`Enum`；应用版本用 `Gauge` 标签或 `profo_app_info` 自定义。
- worker 退出时调用 `multiprocess.mark_process_dead(pid)`（可选，防止 stale 文件）。
- 开发环境单 worker：直接使用默认 registry，不启用 multiprocess。

#### 5.4.2 指标清单

| 指标 | 类型 | 标签 | 说明 |
|------|------|------|------|
| `profo_http_requests_total` | Counter | `method,route,status` | 请求总数；`route` 用模板，不用原始路径 |
| `profo_http_request_duration_seconds` | Histogram | `method,route` | 延迟；buckets 0.005–10s |
| `profo_http_requests_in_progress` | Gauge(livesum) | `method` | 进行中请求 |
| `profo_http_exceptions_total` | Counter | `route,exception_type` | 未处理异常 |
| `profo_db_query_duration_seconds` | Histogram | `operation,source` | SQL 耗时；`source=request/migration/background` |
| `profo_db_slow_queries_total` | Counter | `operation,source` | 超阈值 SQL 次数 |
| `profo_db_pool_connections` | Gauge(livesum) | `state` | checked_out/checked_in/overflow |
| `profo_migrations_total` | Counter | `status` | applied/failed |
| `profo_migration_duration_seconds` | Histogram | `migration` | 单迁移耗时（77+，标签有界） |
| `profo_notifications_total` | Counter | `category,channel,status` | 迭代二消息发送 |
| `profo_business_events_total` | Counter | `event,module` | 最小业务事件（可选） |

**禁止**：把原始 URL、query、user_id、手机号、SQL 原文作为标签；`route` 只取 FastAPI `APIRoute.path` 模板；未匹配归 `unmatched`。

#### 5.4.3 HTTP 指标实现

- 使用自定义 ASGI/HTTP 中间件，在 `call_next` 后读取 `request.scope.get("route").path`（FastAPI 会写入 `scope["route"]`）。
- 排除 `/metrics`、`/static`、`/health`；健康检查由 Prometheus `up{job="profo-backend"}` 覆盖。
- 状态码按实际值记录（200/400/401/403/404/409/422/429/500/502/503 等），基数和可控。
- 异常路径：中间件 `try/except` 记录异常并重新抛出；异常类型用类名，不用消息。
- 延迟用 `time.perf_counter()`。
- 若中间件无法拿到 route（404/405），归 `unmatched`。

#### 5.4.4 慢查询实现

- 在 `db.py` 创建 engine 后注册 SQLAlchemy 事件：
  - `before_cursor_execute`：`conn.info["query_start"] = perf_counter()`。
  - `after_cursor_execute`：计算 `duration`；记录直方图；若 `duration >= SLOW_QUERY_THRESHOLD_MS/1000`：
    - `profo_db_slow_queries_total.inc()`
    - `logger.warning("慢查询 duration_ms=... source=... route=... request_id=... operation=... sql=...")`
    - SQL 截断 500 字符；**不记录 parameters**；去除换行；多语句只取首段。
- `source` 由 contextvar 标记：请求中间件设为 `request`，迁移执行器设为 `migration`，后台线程/任务设为 `background`，默认 `other`。
- `request_id` 复用现有 `X-Request-ID` contextvar；为避免 `main.py` ↔ `utils` 循环依赖，抽出 `utils/observability.py` 存 contextvars。
- 连接池：请求/定时采集 `engine.pool.checkedout()` / `checkedin()` / `overflow()`，写入 `profo_db_pool_connections`。可用后台线程每 15s 采集（避免每次请求开销）。
- 迁移指标只对**实际执行**的迁移计数/记耗时；advisory lock 下其他 worker 的 no-op 不计数，避免 2 worker 下 applied 翻倍。
- 可选 DB 侧：PostgreSQL `pg_stat_statements`（`shared_preload_libraries`）配合 postgres_exporter，覆盖后台任务与所有 SQL；本期作为增强项，不阻塞。

#### 5.4.5 告警规则

`deploy/observability/alerts.yml`：

```yaml
groups:
  - name: profo-api
    rules:
      - alert: ProfoApiHigh5xxRate
        expr: |
          sum(rate(profo_http_requests_total{status=~"5.."}[5m]))
          /
          clamp_min(sum(rate(profo_http_requests_total[5m])), 0.001) > 0.02
        for: 5m
        labels: { severity: critical }
        annotations:
          summary: "API 5xx 比例 > 2%"
          description: "当前值 {{ $value | humanizePercentage }}"

      - alert: ProfoApiP95LatencyHigh
        expr: |
          histogram_quantile(0.95,
            sum(rate(profo_http_request_duration_seconds_bucket[5m])) by (le, route)
          ) > 1
        for: 10m
        labels: { severity: warning }
        annotations:
          summary: "路由 {{ $labels.route }} P95 延迟 > 1s"

      - alert: ProfoDbP95LatencyHigh
        expr: |
          histogram_quantile(0.95,
            sum(rate(profo_db_query_duration_seconds_bucket[5m])) by (le)
          ) > 0.5
        for: 10m
        labels: { severity: warning }

      - alert: ProfoDbSlowQueries
        expr: sum(increase(profo_db_slow_queries_total[5m])) > 1
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "慢查询 > 1 次/5 分钟"

      - alert: ProfoDbPoolSaturated
        # pool_size=10 + max_overflow=20 = 30；80% = 24
        expr: sum(profo_db_pool_connections{state="checked_out"}) > 24
        for: 5m
        labels: { severity: warning }

      - alert: ProfoMigrationFailed
        expr: increase(profo_migrations_total{status="failed"}[10m]) > 0
        for: 0m
        labels: { severity: critical }

      - alert: ProfoBackendDown
        expr: up{job="profo-backend"} == 0
        for: 1m
        labels: { severity: critical }
```

- 告警接收：
  - 默认 `webhook_configs` 指向 `ALERT_WEBHOOK_URL`（企业微信/飞书机器人）。
  - **推荐**：接入迭代二 `NotificationService` 的 `/api/v1/internal/alerts`（API Key 鉴权），把告警写入 admin 的站内信 + 可选微信；Alertmanager 只负责去重/分组/抑制。
  - 抑制规则：`ProfoBackendDown` 时抑制 API/慢查询告警，避免风暴。
- `promtool check rules` + `promtool test rules` 纳入 CI（GitHub Actions 或本地脚本）。
- **迁移失败语义**：当前迁移失败会阻止后端启动，`/metrics` 不可抓取，因此 `ProfoMigrationFailed` 只在「允许启动后继续」或「CLI/Pushgateway 推送」场景有效；生产首要信号仍是 `ProfoBackendDown` + 部署日志 + 迭代一 `schema_migrations.status=failed`。

| 慢查询日志含 PII | 合规风险 | 不记录 parameters；SQL 截断；日志脱敏测试 |
| 告警疲劳 | 运维忽略 | 阈值分级；抑制规则；分组/重复间隔；先观察一周再收紧 |
| `/metrics` 暴露 | 信息泄漏 | 仅内网/allowlist/token；公网 E2E 验证 |
| 指标开销 | 延迟上升 | 直方图 buckets 精简；关闭高成本可选项；压测对比 |

**迭代三回滚**：`METRICS_ENABLED=false` 关闭 `/metrics` 与中间件；监控 compose 使用独立 profile，不启动即不影响生产；告警规则删除/停用即可。

## 9. 决策记录（ADR 摘要）

| ID | 决策 | 理由 | 替代方案（放弃原因） |
|----|------|------|----------------------|
| D1 | 不迁 Alembic；在现有 77 个幂等迁移上叠加版本表/注册表 | 迁移成本低、风险可控；现有函数已验证 | Alembic：需重写 77 个迁移，收益低 |
| D2 | 既有库 baseline 采用「执行一次并登记」，不盲目标记 applied | 确保 schema 真实一致；幂等函数可安全重跑 | 直接标记：无法验证 schema |
| D3 | 补偿以「备份恢复」为最终兜底，脚本补偿只覆盖可逆项 | 数据删除/加密/多表修正无法可靠逆运算 | 为 77 个迁移都写 down：不现实且危险 |
| D4 | 站内信是消息中心事实源；微信是 best-effort 渠道 | 站内信可持久化/已读/偏好；微信受额度/模板限制 | 只做微信：无兜底、不可查询 |
| D5 | 角色默认布局放 `system_configs`，用户覆盖放 `user_preferences` | 复用现有 KV，避免新表；用户偏好未来可复用 | 新建 workbench 表：本期过重 |
| D6 | Prometheus 必须 multiprocess | 生产 2 worker；否则指标减半 | 单 worker：牺牲并发；sidecar：复杂 |
| D7 | 监控优先独立主机；单机仅验证 profile | 1.6G 内存余量不足 | 同机全量：OOM 风险 |
| D8 | `route` 标签只用模板；慢查询不记参数 | 控制基数与 PII | 原始路径/参数：基数爆炸、合规风险 |
