| 7 | 筹钱渠道 | `S.usedBorrow.credit > 0` | 不用 | **是** | 进过筹钱屏（`S.walked` 含 `borrow`；资金充足不进，[handlers-flow.ts#L55-L58](file:///Users/wither-e/Desktop/profo/miniapp/pages/house-simulator/utils/handlers-flow.ts#L55-L58)） |
| 8-11 | 签约 4 个**代价型**项 | `S.con[k]`，k = `chan` / `date` / `arrears` / `stuff` | `"do"` | **是** | 恒出现 |
| 12 | 尾款扣押 | `S.handHold` | — | **否**（注 1） | 恒出现 |
| 13-15 | 装修 3 决策点 | `S.renovPkg` / `S.renovTier` / `S.renovCon` | 见 §5.3 | **合并计 1**（注 2） | 未跳过装修（`S.renovDone && !S.renovSkipped`） |

> **注 1（`handHold` 不计分）**：交房屏的「问题」由选择本身触发（`ho:ok` → 4 项全 ok；`ho:hold` → 才出现欠费 / 户口问题，[handlers-flow.ts#L244-L255](file:///Users/wither-e/Desktop/profo/miniapp/pages/house-simulator/utils/handlers-flow.ts#L244-L255)），状态上无法区分「没问题没扣押」（合理）与「有问题没扣押」（踩坑），无客观对错；其风险后果已由签约项 `holdback` / `arrears` / `stuff` 的学费行覆盖。复盘清单照常展示，但不进准确率。
>
> **注 2（装修 3 点合并计 1）**：装修增项是三个决策的**共同结果**，无法逐点归因——判定取 `S.renovExtra > 0`（结账价 > 合同价）计 1 坑；设计师档位（free/d100/d400）在数据模型上无客观后果联动（只加设计费，不改增项 / 工期，[renov-data.ts#L180-L196](file:///Users/wither-e/Desktop/profo/miniapp/pages/house-simulator/utils/renov-data.ts#L180-L196)），单独不可判。复盘展示仍列 3 点，计分合并。

**计分公式（v4）**

- **计分决策点分母** = 表中「计分 = 是」且「出现条件」满足的点数：恒出现 6 个（越线 / 中介费 / 签约 4 项）+ 到手价（有卖方税费时）+ 筹钱（进过筹钱屏时）+ 装修（未跳过时）→ **分母 6-9 个**
- **踩坑数（分子）** = 逐点判定为「坑」的个数；**不要用 `lossRows` 行数**（它含 8 个 cost=0 风险型签约项与到手价行，与计分点集不同，极端时行数 > 分母、准确率为负）
- **直觉准确率** = (1 − 踩坑数 ÷ 分母) × 100%
- **两个命名指标，不得混用**（v4 修正）：
  - **「0 坑」**（count 口径，探索称号用）= 踩坑数 = 0
  - **「0 多花」**（money 口径，结果卡费用栏用）= `lossRows(S)` 合计 = ¥0，**充要条件是 5 个**：`chan` / `date` / `arrears` / `stuff` 写 `"do"` **+ `netDeal` = false**（v3 漏了最后一条——答应到手价必有 netprice 行，[calc.ts#L271-L278](file:///Users/wither-e/Desktop/profo/miniapp/pages/house-simulator/utils/calc.ts#L271-L278)）
- **0 坑率目标 ≥5%**：按「0 坑」（count 口径）统计。可达性：清单 `why` 前置 + 未跳过装修时全包 + 13 项写清即可 0 增项；首轮不越线（soft / chat 恒安全）。探索态关闭提示后难度上升，**先测基线再定阈值**，若 <2% 则回退用「0 多花」口径
- **称号（探索路线专属）**：0 坑 →「直觉满分 · 老江湖」；1-2 坑 →「小有失误 · 复盘型选手」；≥3 坑 →「新手保护期 · 学费已交」。稀有标签：「一坑没踩 · 直通交房」
- 避坑路线仍展示通用「签约 12 项 + 交割 4 项」清单（用户是来学流程的），**两条路线共用同一份结果卡模板，只换第三栏与称号**

### 5.5 「不可回退」的边界（v2 会导致用户卡死）

v2 写「决策一经确认不可回退」——必须限定范围，否则用户会卡住：

| 行为 | 探索态 | 理由 |
|---|---|---|
| `backSelect` 换房 | **保留** | 谈崩 / 缺口过大 / 限购的**唯一出口**（[handlers-setup.ts#L176-L179](file:///Users/wither-e/Desktop/profo/miniapp/pages/house-simulator/utils/handlers-setup.ts#L176-L179)） |
| 重开一局 `reset` | **保留** | 必须有的退出 |
| `nego1` / `nego2` 重选 | 关闭 | 「选择有代价」的核心 |
| `loanType` / `feeNego` 改选 | 关闭（去掉 `on` 选中态重选） | 同上 |
| 签约清单 `cl:do/no` 反复切换 | 关闭（选定即锁） | 同上 |

> ⚠️ **风险提示**：`toSelect()` 会重置 `nego*` / `con` / `hand` / `netDeal`（[handlers-setup.ts#L23-L45](file:///Users/wither-e/Desktop/profo/miniapp/pages/house-simulator/utils/handlers-setup.ts#L23-L45)）——探索态下「换房」等于本次判断全部作废，文案上必须说明（如「换房 = 这条路的判断作废」）。

## 九、风险与合规

1. **规避诱导分享**：微信对「诱导分享/诱导关注」红线明确。我们的机制全部是「结果自然值得分享」：称号/结果卡/双路线都是体验产物，非「分享才给奖励」。
2. **探索路线不能变成「劝退」**：答案后置 ≠ 不给答案，每个决策点在结尾复盘时都要给出「标准做法 + 你的代价」；并保证两条路线都可顺利走完，不设硬性卡点（§5.5 已保留换房/重开两个出口）。
3. **带参小程序码的登录代价（新增）**：方案 B 需 C 端登录，会在"最想分享的那一刻"插入登录门槛。建议 P0 走方案 A（path 带参、免登录），P1 再评估登录转化损失。
4. **本机存档的隐私边界（新增）**：只存模拟进度（scene / route / 金额 / 选择结论），不含身份信息；对齐 PRD「不收集用户真实个人信息」。
5. **微信生态外引流合规**：后续 P2 若启动，小红书笔记不得直接放外链/二维码到微信，用「搜索关键词」+「品牌号主页」引导。
6. **房产口径合规**：模拟器结果是「演示口径」（`final` 屏已标注「演示口径 · 以官方为准」，沿用），任何对外内容携带同款免责声明，避免税务/贷款承诺。
7. **口径一致性（新增）**：结果卡必须复用 `money()` / `lossRows()` / `contractPriceOf()` 等既有函数，禁止为海报另算一套数字——两套口径是这类"结果沉淀"功能最常见的翻车点。

## 十、一句话总结

**产品已完成「让人体验」的 80 分，缺的是「让人愿意带回家」的 20 分**——但在补这 20 分之前，得先把三件地基打好：**能计量（埋点）、能续玩（存档）、能带走（结果卡）**。

结果卡把交易与装修的账、工期、避坑清单做成一张能带走、能用上的工具卡；探索路线则让用户第一次为自己的判断负责、走完才知道踩了几个坑——结果卡就从「一张清单」变成「一份战绩」，分享欲自然生长。
