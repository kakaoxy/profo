# 营销订阅通知 · Admin 可见性与调价交互迭代方案

> 撰写：2026-10-05  
> 角色视角：admin 运营者（营销房源管理）  
> 前提：订阅通知后端闭环已上线（commit `4425185c` / `32095a2a`），真实微信模板已配置（上新 208 / 调价 6496），E2E 已验证 skipped/failed/success 三态与额度扣减  
> 核心目标：让运营**看得见订阅数据**（多少人订阅、每套房源调价推送效果、哪些房源新上/调价）；**详情与编辑合并为单一详情页**（抽屉内查看态/编辑态切换）；调价拆为详情页内的**内联区块**；C 端房源详情页支持**房源级调价订阅**（外部列表页订阅 = 全房源频道订阅，详情页订阅 = 只盯这一套）

## 零、四个问题的根因定位（先读这一节）

逐条对照代码事实，区分「数据没有」与「数据有但没暴露」——两者改法完全不同：

| # | 问题                | 根因定位                                                                                                                                                                                                                                                                       | 缺口性质            |
| - | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| 1 | 看不到多少人订阅了上新       | 数据**有**：`l4_marketing_subscriptions` 表（每人一行，`new_listing_quota`/`price_change_quota`）。但后端**没有全局统计端点**，前端统计卡（[marketing-stats.tsx](../frontend/src/app/\(main\)/admin/marketing/_components/marketing-stats.tsx)）只有房源维度 4 张卡                                                | API 缺口          |
| 2 | 每套房源有多少调价订阅数据     | **累计送达数已有**：`notify_summary.price_change_count`（notify_logs success 口径）已显示在列表「通知」列与详情 Sheet。真正缺的是**调价历史维度**——`l4_marketing_price_changes` 表存了每次调价，但**没有 API 暴露列表**，且 notify_logs **无法精确关联到某一次调价**（无 `price_change_id` 列，只能按时间窗近似对齐）                                        | API 缺口 + 数据关联缺口 |
| 3 | 看不出哪些房源有价格变化/新上   | 数据**有**：列表响应已含 `is_new_listing` / `latest_price_change`（7 天窗口），前端也有调价副行。但**列表不支持按此筛选**（[projects.py#L73-L76](../backend/routers/marketing/projects.py) 仅 publish_status/project_status/consultant/community 四参数），新上房源在 admin 列表**无任何视觉标记**（C 端 miniapp 有黑标，admin 没有）       | 筛选参数缺口 + UI 缺口  |
| 4 | 没有单独调价组件，直接编辑房源整体；详情页与编辑页割裂 | 双重现状：① 详情（抽屉）与编辑（独立页 `/admin/marketing/[id]/edit`）分离，看一眼细节要开抽屉、改一个字要跳整页；② 调价 = 进编辑页改总价保存整表单。而后端 `PUT /admin/marketing/projects/{id}` **已支持局部更新**（`model_dump(exclude_unset=True)`），调价会自动写 `price_changes` 历史并触发订阅推送——**后端零改动**：合并详情/编辑为抽屉内双态 + 调价内联区块，全是前端重构 | 纯前端交互重构 |

**结论**：4 个问题中只有 #2 需要一处 schema 变更（notify_logs 加列），其余全部是 API 补端点/补参数 + 前端组件。#4 的解法（详情/编辑合并，见 P0-1）是 P0-2 的前置：先合并，调价区块才有内联落点。

**v3 补充——产品口径变更（问题 #5）**：现行调价提醒是**频道级**（列表页订阅 = 所有已发布房源的调价都推），语义过宽。产品口径修正为**双轨**：
- **频道级**（现状保留）：列表页入口，订阅后所有已发布房源调价均推送——「房源动态」的泛订阅；
- **房源级**（新增）：房源详情页入口，订阅后仅该套房源调价推送——「只盯这一套」；
- 推送范围为两者**并集**（去重：同一用户同一房源只发一条、只扣一次额度），详见 P2-1。

## 二、分期方案

> 原则：P0 全部无 schema 变更、可独立上线；P1 含一次幂等加列迁移。P0-1 是 P0-2 的前置（调价区块内联详情页），P0-3 与 P1 相互独立可并行。

### P0-1 详情/编辑合并为单一详情页（问题 #4 地基）

**现状与目标**：详情是抽屉（`marketing-detail-sheet.tsx`，纯查看）＋编辑是独立页（`[id]/edit/page.tsx` → `EditMode` 整表单，270 行）。合并后**只有一个详情页（抽屉）**，内部 `view`/`edit` 双态切换，编辑不再离开当前上下文。

**状态机设计**：

```
MarketingDetailSheet（抽屉 = 唯一详情页）
├─ mode: "view" | "edit"（useState，抽屉内部态，不进 URL）
├─ view 态（宽度 sm:max-w-3xl，现有内容不动）
│    MarketingInfoSection → BasicConfigSection → 订阅与调价卡片(P0-2) → PhotosSection
│    Header: [调价] [编辑房源] [预览] [×]
└─ edit 态（宽度切换 sm:max-w-5xl，容纳原编辑页 lg:col-span-8/4 双栏栅格）
     EditMode(embedded)：MarketingInfoFields + StageDatesFields + DualPhotoManager ｜ BasicConfigFields
     Header/底部: [取消] [保存]（原 Fixed Bottom 操作栏在 embedded 模式改 sticky 于滚动容器）
```

**实现要点**：

1. `SheetContent` 宽度按 mode 动态切换：`mode === "edit" ? "sm:max-w-5xl" : "sm:max-w-3xl"`；
2. `EditMode` 增加 `embedded?: boolean` props：
   - `embedded=true`：**不渲染 `fixed bottom-8 left-1/2` 操作栏**（fixed 相对 viewport 定位，在 Sheet 内会错位出屏），改由 Sheet 底部 sticky 栏渲染「取消/保存」（复用 `useMiniProjectForm` 的 `isSubmitting`）；
   - 新增 `onSaved(project)` 回调替代跳转列表：保存成功 → toast → `mode` 切回 view → 重新 `loadDetailData(project.id)` 刷新详情 → `onRefresh()` 刷新列表（总价副行/通知统计同步更新）；
   - 新增 `onCancelEdit()`：表单 `isDirty` 时弹确认（「未保存的修改将丢失」），确认后切回 view；
   - `mode="create"` 的独立创建页（`new/page.tsx`）**沿用非 embedded 模式，零改动**；
3. 数据加载：edit 态复用现有 `loadDetailData`（请求缓存已是单次 Promise 语义，保存后重新调用即取到新数据，无需失效逻辑）；
4. **路由清理**：删除 `[id]/edit/page.tsx`；`action-cell.tsx` 行内「编辑」改为回调打开抽屉并直接置 `mode="edit"`（列表 → 抽屉透传初始 mode）；`view/ViewMode.tsx` 与 `MiniProjectForm` 的 `mode="view"` 分支一并删除（避免双套只读视图并存）；
5. 权限显隐不变：编辑/调价按钮受 `l4_marketing:write` 控制（沿用列表页现有按钮权限模式）。

**验收点**：

- [ ] 列表行点击开抽屉（view 态），点「编辑房源」→ 抽屉拉宽进编辑态，URL 不变、不跳页；
- [ ] 保存 → toast → 抽屉回 view 态且数据已刷新；关闭抽屉后列表行总价/调价副行/通知统计已更新；
- [ ] 编辑中直接点 × / 遮罩关闭：isDirty 弹确认，确认后丢弃回 view 态；
- [ ] 创建页（new）行为与现状完全一致（回归）；
- [ ] 访问 `/admin/marketing/[id]/edit` 返回 404（路由已删）。

### P0-2 调价内联区块（问题 #4 核心诉求，依赖 P0-1）

**交互设计**（调价不再是弹窗，而是详情页「订阅与调价」卡片内的内联表单态）：

```
详情抽屉 view 态 · 「订阅与调价」卡片（notify-section.tsx 升级）
├─ Header: 「订阅与调价」 + [调价] 按钮（仅 publish_status=发布 且 l4_marketing:write 显示）
├─ 送达统计卡（现状保留：上新 N 人 · 调价 M 人）
├─ [调价] 点击 → 卡片内切换内联表单态（不弹窗、不跳页，其余区块不动）
│    ├─ 当前总价：只读展示（tabular-nums）
│    ├─ 新总价：Input（z.number().positive("总价必须大于0")，复用 form-schema 口径）
│    ├─ 实时预览：差价 chip（↓ 直降 N 万 绿 / ↑ 上调 N 万 灰 / 价格未变化 禁用提交）
│    └─ [取消] [确认调价]（sticky 于卡片底部，复用 Sheet 编辑态操作栏样式语言）
├─ 确认调价 → updateL4MarketingProjectPriceAction(id, total_price)
│    成功 → toast「调价成功，订阅用户将收到推送」→ 退出表单态 → 时间线/统计卡刷新（router.refresh）
└─ 调价历史时间线（P1-2 落地后展示在统计卡下方）
```

**实现要点**：

1. `actions/projects.ts` 新增 `updateL4MarketingProjectPriceAction(id: number, totalPrice: number)`，内部 `client.PUT("/api/v1/admin/marketing/projects/{project_id}", { body: { total_price } })`——**只传 total_price 一个字段**，依赖后端 `exclude_unset` 局部更新语义；
2. 内联表单态是 `notify-section.tsx` 内部 `useState`（`pricing: boolean`），非独立路由/弹窗；表单 `react-hook-form + zodResolver`，schema 独立定义（`priceChangeSchema = z.object({ total_price: z.number().positive() })`）；
3. 「确认调价」在 `new_price === old_price` 时禁用（同值变更后端不触发通知，前端提前拦截避免无效请求）；
4. 成功文案不承诺「已通知 N 位订阅用户」——通知是后台任务异步执行，PUT 响应拿不到数字（诚实原则）；
5. 编辑态（P0-1 edit mode）下「调价」按钮隐藏：同一房源不允许两套编辑入口同时进行，整表单内改总价仍可用（编辑页表单保留总价字段）。

**验收点**：

- [ ] 已发布房源详情 view 态显示「调价」，草稿不显示；edit 态下调价入口隐藏；
- [ ] 点调价 → 卡片内出现表单态，输入新价实时显示方向 chip；同值禁用提交；
- [ ] 提交 → toast → 退出表单态，时间线出现新记录（P1-2 后），关闭抽屉后列表行总价/调价副行已刷新；
- [ ] 后端 `l4_marketing_price_changes` 新增一条记录、订阅用户收到推送（留痕 success/skipped）。

### P2-1 房源级调价订阅（v3 新增 · 产品口径变更，问题 #5）

**现状与目标**：现行调价提醒是频道级——列表页订阅后，**所有**已发布房源的调价都推送（`_fetch_subscribers` 取全部 `price_change_quota > 0` 的行）。用户关注的是「某一套」时语义过宽：无关房源的调价也在消耗一次性授权额度。本项在**房源详情页**（`miniapp/pages/projects/detail/index`）新增价格订阅按钮，实现「只盯这一套」；频道级订阅保留，推送范围为两者并集。

**数据模型**（新增 1 张表 + 既有表不动）：

```
l4_marketing_project_subscriptions（房源级订阅表，新增）
├─ id: int PK 自增
├─ user_id: String(36) NOT NULL（逻辑外键 User）
├─ marketing_project_id: int NOT NULL（逻辑外键 l4_marketing_projects）
├─ openid: String(64) NOT NULL（授权时快照，同频道账本口径）
├─ price_change_quota: int NOT NULL DEFAULT 0（房源级一次性订阅额度）
├─ created_at / updated_at（BaseModel 时间戳）
├─ uq_l4_project_subs_user_project (user_id, marketing_project_id)  ← 一人一房源一行
└─ idx_l4_project_subs_project (marketing_project_id, price_change_quota)  ← 推送查询索引
```

**额度语义（与频道级账本完全同构）**：

- 详情页 accept 上报 → 该房源行 `price_change_quota + 1`；
- 该房源调价推送成功 → `quota - 1`（原子条件更新）；skipped/failed 不扣；
- 「全局调价额度」（频道账本）与「房源调价额度」相互独立、分别扣减；同一用户同时持有两类授权时**只发一条消息**（见下）。

**推送范围与去重（notify.py `_fetch_subscribers` 改造核心）**：

```
某房源调价推送的收件人 =
    频道账本行（price_change_quota > 0，全量）          ← 「所有房源都订阅」
  ∪ 房源级订阅行（该项目 id + price_change_quota > 0）  ← 「只盯这一套」
  去重：同一 user_id 只保留一条（优先房源级，因其语义更精确）；
        微信 43101 天然幂等（同模板同用户未授权只收一条），重发风险为零
```

- 收件人结构从「订阅行列表」抽象为 `Recipient(openid, user_id, channel)`，channel ∈ {`channel`, `project`}，扣减时按 channel 路由到对应表的额度列（均为原子条件更新）；
- 留痕：`notify_type` 不新增枚举值（仍为 `price_change`，admin 统计口径不变），新增 `sub_source` 列区分来源（`channel`=频道级 / `project`=房源级；P1-2 加列时已预留，此处只写入）。

**C 端 API**（2 个新端点 + 1 个复用，对齐现有 `/public/marketing/subscriptions/*` 风格）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/public/marketing/projects/{id}/subscription` | 查询当前用户对该房源的订阅状态（额度/最近订阅时间），未登录返回 401（前端静默） |
| POST | `/public/marketing/projects/{id}/subscription/report` | accept 上报 → 房源级额度 +1（模板 ID 映射复用 `project_price_change` 配置） |
| — | subscribe-template | **复用现状**，无需新增（房源级与频道级用同一个调价模板 ID） |

Service：`MarketingSubscriptionService` 新增 `get_project_status(user_id, project_id)` / `report_project_result(user_id, project_id, results)`——upsert 逻辑复用 `_upsert_row` 模式（唯一约束冲突回退重查）。

**C 端 UI**（`miniapp/pages/projects/detail/index`）：

├─ 未订阅 → [🔔 降价提醒]（tap 手势内同步 requestSubscribeMessage → accept 上报 → toast「已开启，该房源降价时提醒你」）

## 四、E2E 验证清单（本仓库唯一测试机制）

前置：admin 登录 + 至少 1 个真实订阅用户（真机授权 accept）。

2. **调价内联区块**：详情 view 态 → 调价 → 输入新价提交 → 断言 200 + 时间线新记录 + 列表副行出现 + price_changes 新增 + notify_logs 留痕（skipped/failed 均不扣额度）；

## 五、风险与边界

| 风险 | 缓解 |


|---|---|  
| 抽屉 edit 态与调价内联态并发写同一房源 | 互斥已内建：edit 态下调价按钮隐藏；调价表单态下点「编辑房源」先退出表单态。仍存在双开浏览器标签的极端场景，PUT 为最后写优先（既有语义），不做乐观锁，记录为已知边界 |
| 抽屉编辑中误关丢失表单 | isDirty + 关闭确认拦截（P0-1 验收点）；保存动作只有显式「保存」按钮 |
| Sheet 内 fixed 定位错位 | P0-1 已明确 embedded 模式不渲染 fixed 操作栏，改 sticky 于滚动容器；E2E 第 1 步覆盖 |
| 删除 edit 路由后旧链接/书签失效 | Next.js notFound 兜底；列表页/抽屉入口同版本更新，无外部书签依赖（admin 内部系统） |
| P2-1 去重后频道账本少扣一次额度（优先房源级扣减） | 一次性订阅语义下额度对用户是「可收条数」，只发一条只扣一处是正确账目；两账本独立展示不产生用户困惑；若产品后续要求「双轨都扣」，仅改扣减路由一处 |
| P2-1 收件人并集放大单次推送量（频道级 + 房源级叠加） | 去重按 user_id 合并后总量 ≤ 原频道级全量 + 新增房源级增量，`_MAX_BATCH=500` 截断策略不变；房源级订阅天然分散在不同房源，单房源级收件人远小于频道全量 |
| 房源级表随订阅关系增长（一人可订多套） | 行数 = 用户 × 关注房源数，C 端场景人均关注个位数；(user_id, project_id) 唯一约束 + 推送走 (project_id, quota) 索引，量级无忧 |

| price_change_id 加列后新旧留痕混杂 | 旧留痕该列为 NULL，时间线只按调价记录聚合，NULL 天然不参与，无脏数据风险 |
