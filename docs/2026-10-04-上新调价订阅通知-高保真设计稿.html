SEC 01 · REQUIREMENTS

需求与口径

房源列表页（pages/projects/list/index，tabBar 首页）目前没有任何订阅通知能力：C 端用户无法在「新房源上架」「房源调价」时得到提醒，只能反复手动刷列表。本方案在零新增框架的前提下补齐该链路 —— 后端已有微信订阅消息完整基建（send_subscribe_message / access_token 缓存 / 模板 ID 配置模式），小程序端已有一次性订阅授权先例（valuation-notify.ts），缺的只是订阅关系存储、业务触发点与列表页入口。

R1 · 入口
计数行旁「订阅提醒」铃铛按钮
「共 N 套房源」计数行右侧新增铃铛按钮，点击弹半屏订阅弹层；列表底部与空态再给一次订阅引导。已订阅态按钮反白 + 额度角标。
R2 · 授权模型
一次性订阅 · 额度累计
微信订阅消息每次「允许」仅可收 1 条。授权结果上报后端按模板累计额度（quota），推送成功扣减 1；额度 0 后静默停止，按钮转「续订提醒」。
R3 · 受众
所有订阅用户（频道型）
上新/调价是公共频道通知：推给所有剩余额度 > 0 的订阅用户，不筛预约/浏览关系。额度模型天然限流，无需额外频控。
R4 · 调价方向
涨降都推
降价推「总价下调 X 万」（营销点），涨价推「总价已更新」（中性文案）。仅已发布房源的总价变更触发；草稿态编辑不推。
R5 · 徽标增强
列表卡「新上 / 调价」徽标
C 端列表响应新增 is_new_listing（发布 ≤ 7 天）与 latest_price_change：缩略图右上「新上」黑标，价格旁「↓5万」绿 chip（涨价为中性灰）。
R6 · 功能开关
模板未配置 = 功能关闭
对齐 valuation 模式：两个模板 ID 均走 settings env 配置，空 = 下发 subscribe_enabled:false，小程序入口整体隐藏，零风险灰度。
FLOW · 全链路（一次调价从操作到送达）
admin 调价PUT /admin/marketing/projects/{id}
→
Service 检测total_price 变更 · 已发布态
→
写调价记录l4_marketing_price_changes
→
run_in_threadpool 推送筛选额度 > 0 的订阅行 → 扣额度 → subscribe/send
→
微信服务通知点击直达房源详情页
口径决策依据 / 说明
订阅入口 计数行右侧铃铛按钮 + 半屏弹层；列表底部 / 空态二次引导 一次性订阅额度会被消耗，必须设计「反复补额度」的低摩擦入口弹层内展示两类提醒与各自剩余额度
推送受众 所有额度 > 0 的订阅用户 频道型语义；额度模型限流，无需频控/去重表openid 在订阅上报时快照入库，发送免回查
调价方向 涨降都推；降价营销文案 / 涨价中性文案 用户确认口径；方向按 old → new 比较，写 price_changes.direction
触发点 ① 创建即发布 ② 草稿 → 发布 ③ 已发布房源 total_price 变更 均在 MarketingProjectService.create/update 内检测published_at 仅首次发布写入，防重复「上新」
消息回跳 pages/projects/detail/index?id={marketing_project_id} 单房源事件直达详情页，比回列表页转化路径更短
徽标窗口期 「新上」= published_at ≤ 7 天；调价 chip = 最近一次调价 ≤ 7 天 超窗口不展示，避免陈旧信息；窗口期硬编码（后续可入 system_configs）
失败策略 通知链路任何异常仅记日志，绝不影响主流程 对齐 leads/notify.py · recruit/attribution.py 既有模式

SEC 03 · ARTBOARD 02

订阅弹层 · 状态机

弹层随额度状态切换文案与控件，均由同一个 Sheet 组件承载（Artboard 01-A 已可交互演示开启流）。

状态触发弹层表现
未订阅 quota 均为 0 · 首次点击 两卡片额度「可收 0 条」灰 chip；主按钮「开启提醒」
已订阅 · 有额度 任一 quota > 0 对应卡片额度「可收 N 条」apricot chip；主按钮「继续补额度」；列表页按钮反白「已订阅 · 可收 N 条」
额度耗尽 推送消费后 quota 归 0 列表页按钮「续订提醒」+ rust 圆点；弹层副文案「订阅额度已用完，续订后继续接收动态」
ban（曾拒收） requestSubscribeMessage 返回 ban 不弹订阅面板，modal「无法开启提醒」→「去设置」引导 wx.openSetting（对齐 valuation 先例）
功能关闭 模板 ID 未配置 铃铛入口整体隐藏（subscribe_enabled:false），不占布局

SEC 06 · IMPLEMENTATION PLAN

完整迭代方案

三端改动一览：后端（配置 + 3 表 + 通知服务 + 触发点 + 3 个 C 端端点）、admin 前端（列表通知列 + 详情 Sheet 区块）、小程序（订阅工具 + 入口 + 弹层 + 徽标）。零新增框架，全部复用既有模式。

PHASE P0 · 本次落地（MVP）
订阅闭环：授权 → 存储 → 触发 → 送达 → 展示
  • 后端：2 个模板 ID 配置 · 3 张新表幂等迁移 · notify.py 通知服务 · create/update 触发点 · 3 个 C 端端点
  • admin：列表通知列 + 总价调价副行 · 详情 Sheet「订阅通知推送」区块
  • 小程序：utils/marketing-notify.ts · 计数行铃铛入口 · 订阅弹层 · 新上/调价徽标
PHASE P1 · 后续可选
精细化运营（不阻塞 P0）
  • 通知发送日志独立页（admin：按项目/类型/状态筛选，失败原因可见）
  • 关注小区定向订阅（按 community_id 收窄推送范围）
  • 详情页调价记录时间线（复用 price_changes 表）
  • 每周新房源汇总推送（需引入定时调度，当前后端无 scheduler 基建）
DATA · 数据层（migrations/__init__.py 幂等迁移，_table_exists/_column_exists 守卫）
对象定义用途
l4_marketing_subscriptions id · user_id(uq) · openid · new_listing_quota · price_change_quota · last_subscribed_at · created_at/updated_at索引：uq(user_id) · idx(new_listing_quota) · idx(price_change_quota) 订阅额度账本：授权 accept 后 quota+=1，推送成功后 with_for_update 扣减
l4_marketing_notify_logs id · user_id · marketing_project_id · notify_type(new_listing/price_change) · template_id · send_status(success/failed/skipped) · error_msg · created_at索引：(marketing_project_id, notify_type) 发送留痕：admin 统计 + P1 日志页数据源 + 排障
l4_marketing_price_changes id · marketing_project_id · old_price · new_price · direction(up/down) · created_at索引：(marketing_project_id, created_at) 调价历史：C 端降价/涨价徽标 + admin 调价历史时间线
l4_marketing_projects 加列 published_at DateTime(timezone=True) NULL仅首次 publish_status→发布 时写入 「上新」唯一事实源（created_at 不能区分草稿期）；消息卡上架时间 + C 端新上徽标
API · 端点契约（统一 /api/v1 前缀；C 端 c_access_token 鉴权，模板下发 skipAuth）
方法 · 路径鉴权请求响应
