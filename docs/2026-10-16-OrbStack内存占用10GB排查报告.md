# OrbStack 内存占用 10GB 排查报告

- **排查日期**：2026-10-16
- **环境**：本机 16GB 内存；OrbStack 2.2.3 承载开发用 PostgreSQL + Redis（`docker-compose.yml` + `docker-compose.dev.yml`）；backend/frontend 按 `dev-start.sh` 在宿主机直跑（不在 Docker 内）
- **现象**：长时间运行后，Activity Monitor 中 OrbStack 相关进程内存合计约 10GB；期间（10-14）通过 `admin/building-dictionary/import` 上传过楼盘字典全量包；电脑已重启，重启后基线正常
- **排查方式**：`docker system df` / `docker stats` / `docker system events` / 容器内 `free`+`psql` 实查 / 导入链路代码逐行审查（`dict_import_service.py`、`dict_import_loader.py`）/ OrbStack 官方文档与 issue 佐证

---

## 1. 结论速览

**10GB ≈ OrbStack Linux 虚拟机 ~8GB（默认内存上限）+ OrbStack 宿主进程 ~2GB。** OrbStack 的 VM 内存是"动态按需增长"模型：容器与构建活动吃多少就涨多少，且**依赖内存压力才归还**——长期运行 + 重度 I/O 后会停在高位（官方已知行为，见 issue #355：容器停止后 VM 内存不立即归还）。

把 VM 内存推到高位的**持续来源按贡献排序**：

| 排序 | 来源 | 证据 | 定性 |
|---|---|---|---|
| 1 | **反复执行 `deploy-local.sh` 生产镜像构建** | Build Cache 149 条 / **13.76GB**（全部 2 周前）；每次构建都是 VM 内跑跨平台（amd64）Next.js/uv 构建，本身就是内存大户，且 GB 级层写入全部变成 VM page cache | **主因** |
| 2 | **楼盘字典全量导入**（10-14 当天 25 分钟内 3 次全包处理） | `bd_import_tasks` 7 条：2 次全量成功（装载 7,337,493 行，耗时 307s / 232s）+ 1 次失败；`bd_rooms` 表新增 **1025MB**、`bd_buildings` 189MB，伴随 WAL / autovacuum / COPY staging 大量 I/O → VM page cache 抬高 | **放大器（一次性事件）** |
| 3 | **OrbStack 动态内存回收不彻底** | 官方文档：内存按需分配、"unused memory is automatically returned"，但重度 page cache + 无内存压力时不主动 drop；issue #355 实测容器停了 VMS 内存也不降 | **机制性因素** |

**回答用户疑问：楼盘字典导入是诱因之一，但不是 10GB 的唯一/主要原因。** 它对 OrbStack 内存的贡献是 VM page cache 短时抬高（GB 级写入），本身不驻留内存；真正持续把水位顶上去的是反复的生产镜像构建。导入对**宿主机**的影响另见 §4（zip 全量解压进内存的隐患）。

## 2. 重启后实测（基线，证明问题在"运行期累积"）

| 指标 | 实测值 | 说明 |
|---|---|---|
| 宿主总内存 | 16 GB | — |
| OrbStack 进程 RSS 合计 | **~2.9 GB**（VM 服务 2.4GB + App 145MB + docker CLI 29MB） | 重启后仅 db+redis，即回落正常 |
| VM 内 `free` | total 8004MB / used 295MB / buff+cache 728MB | VM 动态分配到 8GB 档，实际用量很小 |
| 容器内存 | db 172MB（limit 384m）/ redis 12MB（limit 32m） | 容器级限制生效，不是问题源 |
| VM 内 swap | 9028MB / 已用 13MB | 基本未用 |
| PostgreSQL 活动连接 | 16（shared_buffers 128MB / work_mem 4MB） | 生产调优参数在 dev 同样生效 |

→ 重启后一切正常。**10GB 是运行期累积态**，重启清零符合预期。

## 3. 10GB 的构成拆解

1. **VM 部分（~8GB）**：`machine.docker.memory_mib: 0`（动态模式，默认封顶 8GB）。VM 内 Linux 会把空闲内存拿去做 page cache——13.76GB 构建缓存写入、1GB+ 表数据写入、WAL、autovacuum 全部经过它；只要宿主机没有内存压力，这部分缓存不会被回收，OrbStack 就维持高位 RSS。
2. **OrbStack 宿主进程（~1.5-2GB）**：App、Helper（vmnet/文件共享等）、VM 服务本体。Helper 存在随容器生命周期缓慢增长的已知泄漏（issue #2710，约 60MB/次），长期不重启会额外累积。
3. 两者相加即 Activity Monitor 里看到的 ~10GB。

|---|---|---|---|---|

| d9368a31 | 楼盘字典-上海.zip | **failed**（0.07s 即失败，"装载失败，详见服务日志"） | — | 0 |
| 467461fd | test_xiaobao.zip | completed | 0.26s | 5,682 户 |

| fa173b3b | 东体小区.txt | completed | 0.13s | 2,933 户 |
| e268e85f | 楼盘字典-上海.zip | completed | **232s** | 19,657 小区 / 0 新增（幂等重跑） |

### 4.2 代码审查结论（`dict_import_service.py` / `dict_import_loader.py`）

**已做对的部分**（均有代码佐证）：
- 上传 M3 修复：Content-Length 预检 + 1MB 分块流式写盘，2GB 上限下不会全量读入内存 ✅
- COPY 链路：临时 CSV `delete=False` + `finally unlink`、staging 表 `ON COMMIT DROP`、1MB chunk 流式 COPY ✅
- 容器侧安全网：db `mem_limit: 384m`、redis `--maxmemory 24m` ✅

**发现的问题（按严重度）**：

1. **⚠️ zip 全量解压驻留内存（隐患，建议修复）**：`DictImportProcessor._execute` 中 `txt_entries.append((name, zf.read(info)))` 把**包内所有 txt 一次性读进内存**后才逐个处理。上海全域包按 733 万行 × 每行 40-60B 推算解压后约 300-500MB（⚠️ 推算值，见 §8），本次峰值即此量级——但这是**宿主机 uvicorn 进程**的内存，不在 OrbStack 内，任务结束即释放。真正风险在 2GB 上限口径下：最坏情况宿主进程可冲到数 GB。建议改为**逐条目流式处理**（`zf.open(info)` 边读边传给解析器），与 M3 流式写盘修复同一逻辑闭环。
2. **⚠️ 三个 zip 任务的落盘文件（`bd_*.zip`）在 `backend/temp/uploads/` 已不存在**：代码中只有 90 天归档清理（`cleanup_expired_archives`）且**无任何调用方**，任务失败/完成路径也不删原始文件 → 疑似被人为清理，导致无法复核解压后真实体积。
3. **失败任务无法定位原因**：d9368a31 0.07s 即失败，但 `backend/logs/` 目录不存在（日志未落盘），仅 DB 里有 "装载失败，详见服务日志" 一句话，形成死胡同。
4. 幂等重跑第二次全包（e268e85f）做了 232s 的纯冲突校验（730 万行 ON CONFLICT），属预期设计（BR-16），非缺陷。

### 4.3 对 OrbStack 内存的净影响

COPY/INSERT/WAL/autovacuum 产生的 ~GB 级写入抬高 VM page cache → **有贡献，但属一次性事件，解释不了"长期运行后持续增长"**。且 PG 进程本身被 384m cgroup 限制，页面缓存是 VM 级现象。

## 6. 建议处置

**立即（本机执行）**：
1. `docker builder prune -af` → 回收 ~12.9GB 磁盘，并消除后续构建的页缓存压力
2. `docker image prune -a` 清理悬挂/残留镜像层（⚠️ 执行前确认 `profo-backend:prod`/`profo-frontend:prod` 可随用随建）
3. 给 OrbStack 设内存上限：`orb config set machine.docker.memory_mib 4096`（当前 0=动态封顶 8GB；dev 场景 db+redis 远用不满 4GB）→ 从机制上杜绝再次冲高
4. 若长期不重启后 OrbStack 内存停高位：`orb restart docker` 或退出重开 OrbStack 即归还，无需重启整机

**长期**：
5. 在 `deploy-local.sh` 末尾或 `scripts/` 增加定期 `docker builder prune --keep-storage 2gb`（保留近端缓存，防无限累积）
6. 导入侧优化（P2）：`dict_import_loader.py` zip 逐条目流式处理，消除全量驻留内存隐患
7. 失败任务可追溯：确认日志落盘配置（当前 `backend/logs` 不存在），或失败时把堆栈摘要写回 `error_message`

## 7. 复验方法（可重跑）

```bash
# 1) OrbStack 当前内存（应随空闲回落，重启后基线 ~2.9GB）
ps aux | grep -i OrbStack | grep -v grep | awk '{s+=$6} END {printf "%.0f MB\n", s/1024}'

# 2) VM 内实际用量（used 应远小于 total）
docker exec profo-db-1 free -m

# 3) 构建缓存（prune 前 13.76GB / prune 后应 <2GB）
docker system df

# 4) 内存上限设置后确认
orb config get machine.docker.memory_mib   # 期望 4096
```

1. 10-14 当天 10GB 出现的确切时刻无采样数据（活动监视器截图未留存），构成拆解（VM ~8GB + 进程 ~2GB）基于 OrbStack 机制 + 重启后基线反推。
2. 上海 zip 解压后真实体积 300-500MB 为按行数推算，原始 zip 文件已被清理无法复核。
3. d9368a31 任务 0.07s 失败的具体堆栈无法还原（日志未落盘）。
4. `bd_*.zip` 原始文件消失的路径（人为清理 vs 其他）未定位。
5. OrbStack 版本 2.2.3 较旧，#2710/#355 的修复状态需以当前最新版行为为准，建议顺手升级。
