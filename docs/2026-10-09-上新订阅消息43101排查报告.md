# 泗塘五村（项目 305）上新订阅消息未送达排查报告

- **排查日期**：2026-10-09
- **排查方式**：SSH 登录生产服务器（139.224.162.134 / /root/profo），检索 docker backend 日志 + 直查 PostgreSQL 业务表 + 对照本地代码链路
- **现象**：admin 在小程序 C 端订阅了「上新提醒」，admin 后台新上泗塘五村房源（`admin/marketing/305`）后未收到微信订阅消息推送

---

## 1. 结论速览

推送链路本身**正常触发、正常调用微信 API**，消息在微信侧被拒绝：

- 微信 `subscribe/send` 返回 **`errcode=43101`（user refuse to accept the msg）**，即该 openid 在微信侧**没有可用的订阅授权次数（或用户已整体拒收）**；
- 但本地额度账本 `l4_marketing_subscriptions` 中 admin 的 `new_listing_quota = 6`（从未消费）——**本地账本与微信侧授权状态失同步**，本地虚高的额度让推送「有资格发」，微信侧却「没有授权可消费」；
- 后端按设计将该次发送留痕为 `skipped` 且不扣额度，之后不会再重试，也无任何 admin 可见的异常信号——**用户无感知，正是本次问题的表象**。

⚠️ 不确定项（显式标注）：43101 是聚合错误码，服务端无法区分用户微信侧具体处于哪种拒收状态（授权耗尽 / 勾选「总是拒绝」/ 关闭了小程序订阅消息总开关 / 开发者工具模拟授权不产生真实配额），需按 §5 自查步骤在微信端确认。

## 4. 根因分析

### 4.1 直接原因

微信订阅消息是**一次性授权模型**：用户在小程序内每次 `requestSubscribeMessage` 弹窗点「允许」= 微信侧 +1 次发送配额；开发者每成功送达 1 条消耗 1 次。`43101` 表示发送时该 openid 对该模板**配额为 0 或用户已整体拒收**。

### 4.2 深层原因：本地账本与微信侧授权失同步，且无对账机制

本地 `new_listing_quota=6` 说明小程序端上报过 6 次 accept。微信侧却无可用配额，候选场景（按可能性排序）：

1. **开发期在微信开发者工具中授权**：工具内点击「允许」是模拟行为，**不产生微信服务器侧真实配额**，但小程序代码照常上报 accept → 本地 +1。admin 属内部测试人员，10-06~10-07 正是该功能刚上线联调期，高度吻合。
2. **用户在微信中关闭了本小程序的订阅消息总开关**（小程序右上角「…」→ 设置 → 订阅消息）：授权记录仍在、本地额度未消费，但微信对所有 send 统一返回 43101。
3. **用户曾在授权弹窗勾选「总是保持以上选择」且选择了拒绝**：此后微信静默拒收，send 一律 43101。
4. **模板在微信公众平台被删除/重建导致旧授权作废**（可能性低：模板失效时小程序端 `requestSubscribeMessage` 通常直接 fail，难以完成 6 次 accept 上报）。

⚠️ 以上场景服务端日志无法进一步区分，需按 §5.1 在微信端确认；如需精确定位可持 rid `6ac84a09-08b2970f-743d481a` 联系微信侧查证。

### 4.3 为什么「无感知」（可观测性缺陷）

- `43101` 被归类为「预期业务态」：留痕 `skipped`、不扣额度、**不重试、无告警**——这设计对「授权暂时不可用」是合理的，但副作用是失同步用户的每次上新推送都会静默白发一轮 43101，admin 与用户均无感知。
- 留痕表 `error_msg` 仅存 `errcode=43101`，未存 errmsg/rid（服务端日志里有），排障少了一手证据。
- 上新推送任务没有入口日志（如「开始推送：project_id=N，收件人 N 人」），只能靠留痕表间接还原。
- admin 订阅统计页只展示本地额度（6/6），无法暴露「微信侧实际收不到」的失同步。

## 5. 修复建议

### 5.1 立即恢复（无需改代码）

admin 在**手机微信**（非开发者工具）中执行：

1. 打开小程序 → 右上角「…」→ 设置 → 确认「订阅消息」开关为开启状态；
2. 进入「房源列表」页 → 点铃铛 → 点「开启提醒」→ 在弹窗中点「允许」（若提示曾被总是拒收，按弹窗引导去设置开启）；
3. 授权成功后上报会使微信侧配额 +1，之后新上一套测试房源即可验证能收到推送。

> 注：小程序端 `onSubscribeConfirm` 不设额度门槛、每次都拉起授权，该自助路径可用；若在真机上仍收不到，优先怀疑场景 2（总开关被关）。

### 5.2 短期改进（可观测性，低成本高收益）

1. **留痕增强**：`WeChatAuthService.send_subscribe_message` 返回值透传 errmsg（含 rid），`_safe_log` 写入 `error_msg`（现有 200 字符截断 + 凭据脱敏逻辑可直接复用）；
2. **任务入口/出口日志**：`_notify_projects_published` 开始时打印 `project_id`、收件人数、模板 ID source（db/env），结束时打印 success/skipped/failed 计数——一行日志即可还原每次推送全貌；
3. **admin 订阅统计页**：对「近 N 次推送均为 skipped」的用户标注「微信侧授权疑似失效，请引导重新订阅」，把失同步变成 admin 可见。

### 5.3 中期机制（需产品决策）

1. **43101 额度对账策略**：当前「skipped 不扣额度」会导致本地额度永久虚高。可考虑：同一用户对同一频道**连续 K 次（建议 K≥3）skipped 且 errcode=43101** 时，将该频道本地额度清零/冻结，并在 C 端订阅状态页显示「微信授权已失效，请重新开启」；用户重新 accept 时自动恢复（现有 `last_subscribed_at`/上报链路已支持）。不宜一次 43101 即清零（微信偶发限流误伤）。
2. **开发环境隔离**：开发者工具/体验版的授权上报不产生真实配额，联调期建议用独立测试账号或测试模板，避免污染生产额度账本。

### 5.4 运维项（顺手发现）

- backend 容器 docker 日志驱动为默认 json-file 且**未配置轮转**（`docker inspect` 显示 `map[]`），日志会无限增长。建议在 `docker-compose.yml` backend 服务加：

```yaml
logging:
  driver: json-file
  options:
    max-size: "50m"
    max-file: "5"
```
