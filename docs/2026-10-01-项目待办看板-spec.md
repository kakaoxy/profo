## 一、定位与范围

### 1.1 一句话定位

**规则驱动的体检报告**，不是任务系统：后端按 R1~R10 规则对「签约 + 装修」两个阶段的项目实时计算待办，不落库、只读展示。核心目标 = 一眼看出来哪些项目的哪些事项要处理。

### 1.2 范围（In）

| 层 | 内容 |
|---|---|
| 后端 | 规则引擎（R1~R10，纯函数）+ 聚合端点 `GET /api/v1/projects/todo-board` + 响应 Schema + 工序阈值常量 |
| 前端 | `/admin/projects/todo-board` 页面（RSC 首屏 + 客户端筛选）、单行工具栏（4 指标 + 阶段 Tabs + 优先级/负责人筛选）、3 列项目卡片网格、待办明细 Popover（移动端底部 Sheet）、空状态 |
| 注册 | 侧边栏菜单「业务」分组、移动端「更多」弹层（随 navMain 自动继承）、`PATH_PERMISSION_MAP` 条目 |
| 增量改动 | 项目详情页新增**一处** hash 锚点滚动 effect（见 §6.4，属必要例外） |

### 1.3 非范围（Out，与需求文档 §2.2 一致）

- ❌ 通知推送；❌ 人工待办/勾选/忽略（不落库）；❌ 在售/已售/已下架阶段检测；❌ 自动指派责任人；❌ 工作台联动（D9）。

### 1.4 关键口径收口（对需求文档 D1~D10 的实施取舍）

| # | 决策 | 实施口径 |
|---|---|---|
| D1 | 实时规则计算，不落库 | ✅ 方案 A。规则引擎输出稳定 `rule_code`，为将来落库留主键 |
| D2 | 路由归属 | `/admin/projects/todo-board`（与项目管理同族） |
| D3 | operator 可见性 | 后端 `ProjectReadPermDep`（持 project:read 即可）；前端 `PATH_PERMISSION_MAP` 同权限码。**未额外收紧为 admin-only**，收紧仅需改一行，留待业务确认 |
| D4 | R2 字段集分级 | 按需求文档草案：核心（缺任一→整条 P1）= 签约价/业务形式/交房时间/业主姓名+电话；次要（仅计数→P2）= 面积/户型/朝向/楼层/三户号。**签约日期缺失只归 R1，不进 R2（就高不重复）** |
| D5 | 阈值 | 工序标准工期：设计 14 / 拆除 7 / 水电 20 / 木瓦 25 / 油漆 15 / 交付 7 天；R6 宽限 7 天、R7 宽限 15 天。v1 放后端常量模块，待业务校准后可迁 `system_configs` |
| D6 | R4 归档升级 | 签署后超 30 天未归档 → 升 P1。签署时间用 `ProjectDocument.updated_at` 近似（无 signed_at 字段，见 §8 风险） |
| D7 | R5 业务动作 | v1 仅检测 + 跳转，不做交房确认动作 |
| D8 | 每卡 6 条 | 超出折叠「+N 还有 N 件待办，进详情查看」，无展开 |
| D9 | 工作台联动 | v2 再说 |
| D10 | 统计指标 | 四项：待办项目 / P0 阻塞 / 待办总数 / 最深逾期 |

**v2 密度口径**：3 列网格单屏 8+ 项目；工具栏单行；待办单行化；卡片无 foot 行；规则号 R* 不出现在业务界面（仅存于 API `rule_code`）。
**v2.1 口径**：全部展示信息对齐现网字段（唯一新增 = 工序阈值常量）；待办行点击 → 小弹窗（结构化 items[] + 去项目详情按钮）；hint 与 items 分离下发，前端不拼文案。
**规则适用阶段**（以设计稿 Mock 为准，修正需求文档 §5.2/5.3 的分组）：R1/R2/R5 仅签约；R6/R7/R8/R9 仅装修；R3/R4/R3a/R10 签约+装修通用（Mock 卡 C4 装修卡出现 R4）。

### 2.3 规则清单（R1~R10，字段级）

公共前提：仅 `status ∈ {signing, renovating}` 且未被软删除的项目；`today` = 服务端本地日期（Asia/Shanghai）。

| 规则 | 名称 | 阶段 | 触发条件（字段级） | 优先级 | anchor | hint 示例 | days_label（hot?） |
|---|---|---|---|---|---|---|---|
| R1 | 合同未生效 | 签约 | `contract.contract_status == "未生效"`（即 signing_date 为空） | P1 | overview | 签约日期未录入 | — |
| R2 | 基础信息缺 N 项 | 签约 | 字段集任一为空（§1.4 D4 分级；signing_date 归 R1 不重复） | 核心缺→P1；仅次要缺→P2 | overview | 签约价、户号等（前 2~3 个缺失项+等） | — |
| R3 | 文书未签署 | 通用 | documents 中 `signoff_status=="unsigned"` 计数>0；**签约合同/装修合同** 在列→P0，否则 P1 | P0/P1 | documents | 签约合同未签 | N 份（graphite） |
| R3a | 文书清单未初始化 | 通用 | `business_form is None`（文书模板根因） | P1 | overview | 先补录业务形式 | — |
| R4 | 已签署未归档 | 通用 | `signoff_status=="signed"` 且 `archive_date` 为空，计数>0 | P2；签署(`updated_at`)超 30 天→P1 | documents | 确认函等 2 份 | 超 N 天（hot，仅 >30 天时） |
| R5 | 交房逾期未确认 | 签约 | `contract.planned_handover_date < today` | P0 | overview | 约定 09-10 交房 | 逾期 N 天（hot） |
| R6 | 未安排施工方 | 装修 | `renovation.renovation_company` 为空 且 进入装修>7 天（状态日志最新 `new_status=renovating` 的 `operate_at`；无日志→静默跳过） | P0 | renovation_contract | 装修合同信息为空 | 停滞 N 天（hot） |
| R7 | 未实际开工 | 装修 | 施工方已填 且 `actual_start_date` 为空 且 进入装修>15 天；`contract_start_date` 已过→P0 | P1/P0* | renovation_progress | 无开工记录 | 停滞 N 天（hot） |
| R8 | 当前工序停滞 | 装修 | `renovation_stage ∉ {已完成}` 且 已进行天数 > 该工序阈值；已进行 = today − max(stage_completed_dates 最新值, actual_start_date)，**基准缺失→静默跳过**；超阈值 2 倍→P0 | P1/P0* | renovation_progress | 水电 27 天 · 标准 20 | 超期 N 天（hot） |
| R9 | 竣工逾期 | 装修 | `contract_end_date < today` 且 `actual_end_date` 为空 | P0 | renovation_progress | 合同约定 09-18 | 逾期 N 天（hot） |
| R10 | 委托期临近/已超 | 通用 | `end = signing_date + (signing_period + extension_period) 天`；字段缺失→静默跳过；`today > end`→已超 P0；`end − today ≤ 30 天`→临近 P1 | P0/P1 | overview | 已超：含顺延 09-25 结束 / 临近：注意工期衔接 | 已超 N 天（hot）/ 剩 N 天（graphite） |

items[] 文案规范：
- 逐条结构化，字段值 Rust 强调由前端按 `：` 前缀渲染（后端下发纯文本，如 `"当前工序：水电"`）。
- 处理建议类条目以 `"处理建议："` 开头，仅在关键规则下发（R1/R2/R3a/R4/R5/R6/R9/R10-已超）。
- 文书名称严格取自 `project_documents.document_name`（模板源 `backend/constants/documents.py`：代理 12 项/收购 18 项），不造新词。
- **业主手机号/证件为加密列（EncryptedString），任何字段不下发明文**；业主联系方式缺失只在 R2 计为「业主联系方式」一项。

### 2.4 排序与截断

- 卡片内待办：P0 → P1 → P2；同级按 `overdue_days` 降序（null 靠后），再按 rule_code 升序（R10 已超在临近前：已超与临近是同一规则互斥产出，不会同时出现）。
- 每卡截取前 6 条 → `todos`；`todo_overflow = total − 6`。
- 卡片间：`p0_count` 降序 → `p1_count` 降序 → 最深 `overdue_days` 降序（null 靠后）→ `contract_no` 升序兜底。

### 2.5 数据加载（避免 N+1）

单次批量查询（项目量级几十个）：

```python
db.query(Project).filter(
    Project.is_deleted.is_(False),
    Project.status.in_([ProjectStatus.SIGNING, ProjectStatus.RENOVATING]),
).options(
    joinedload(Project.contract),
    selectinload(Project.owners),
    selectinload(Project.status_logs),
    joinedload(Project.renovation),
    selectinload(Project.project_manager),
)
# documents 单独按 project_id in (...) in 查询一次（relationship 未建，避免额外 join）
```

- `ProjectDocument` 无 relationship（`models/project/project.py` 未注册 documents 关系）→ 用 `project_id.in_(ids)` 一次取回，内存按项目分组，过滤 `is_deleted`。
- 进入装修时刻：内存中取该项目 `status_logs` 里 `new_status == RENOVATING` 的最新 `operate_at`。
- `owners` 过滤 `is_deleted`；业主联系方式判定 = 任一未删除业主 `owner_name` 与 `owner_phone` 均非空。

### 2.6 路由注册

`routers/projects/core.py` 中 `GET /todo-board` 注册在 `GET /stats`（L173）之后、`GET /{project_id}`（L232）之前（字面路由优先于路径参数路由的既有惯例，与 `/stats`、`/export` 同位）。响应直接返回 Pydantic 模型（符合该文件头部约定）。Facade 增加委托方法 `get_todo_board()`。

### 2.7 迁移

无 Schema 变更，**不需要迁移脚本**。工序阈值是常量，非库表字段。

### 3.5 明细弹窗（v2.1 核心）

- **触发**：待办行点击（不冒泡到卡片跳转）；**关闭**：✕ / Esc / 点击遮罩（Radix Popover / Sheet 原生行为）；同屏仅一个（状态收口在 TodoBoardView）。
- **桌面**：Popover 宽 336px，圆角 16px，`shadow-steep`，锚定触发行，视口边缘自动翻转（Radix `collisionPadding=12`）。
- **移动端**（`<md`，用 `useIsMobile` 或 Tailwind 双渲染取其一）：底部 Sheet（`side="bottom"`），同一 items[] 数据源。
- **结构**：头部 = 优先级点 + 标题 + 优先级徽章 + ✕；副行 = 项目名 + 合同号；主体 = 「缺失明细」cap + items[] 逐条（`·` 前缀，`：` 前字段名/关键值用 rust 强调）；底部 = 左「→ 详情页 · {分区名}」mono 小字 + 右「去项目详情」Ink 填充胶囊按钮（`rounded-full bg-ink text-white`）。
- **跳转**：主按钮 → `/admin/projects/{id}#{anchor 映射}` 并关闭弹窗。
- 分区名映射：overview→概览 / documents→文书与附件 / renovation_contract→装修合同 / renovation_progress→装修进度。

### 3.6 视觉纪律（Steep）

画布 `bg-fog`；白卡 `rounded-cards shadow-steep` 无边框；彩色仅 Rust（P0/逾期）与 Apricot/Sky wash；字重 430/450/480，从不 bold；天数 `tabular-nums`；「剩 N 天」「N 份」用 graphite 不告警。

## 五、详情页锚点跳转（§1.2 唯一例外改动）

**问题**：详情页分区元素 id（`project-section-*`）在客户端数据渲染后才存在，浏览器原生 hash 滚动在 hydrate 前发生会失效；现有 `SectionNav` 仅响应点击。

**改动**（`project-detail-page-view.tsx`，增量 ~15 行）：新增一次性 effect——`project` 数据就绪后读取 `window.location.hash`，若匹配 `#project-section-*` 则 `scrollIntoView` 并不清理 hash（保持可分享）。带 `matchMedia` 防抖不引入；仅 signing/renovation 视图存在对应锚点（与看板 anchor 映射一致）。

> 该改动触碰需求文档 §2.2「不修改现有项目详情页」的非目标，但为 v2.1 设计稿「按钮直达 `/admin/projects/{id}#锚点`」的必要实现，属最小增量（只读 hash，不改任何现有交互）。
