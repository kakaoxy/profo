## 二、高危缺陷（3 项，均经复现验证）

### H-1【数据库/迁移】科目改名迁移（v91）登记顺序与其自身 docstring 的前置要求相反 → 既有库 baseline / LEGACY_MODE 路径启动崩溃
- **维度**：数据库交互与性能 / 契约一致性（迁移同步）
- **位置**：`backend/migrations/_finance.py:113-150`（docstring 明写「**故必须在 create_finance_subjects_table 之前执行本迁移**」）；实际顺序：seed = **v17**（`registry.py:351-353`，legacy 路径 `migrations/__init__.py:335`），rename = **v91**（`registry.py:1130-1140`，legacy 路径 `:464`）——**改名永远跑在种子之后**。
- **触发场景**（三条路径，任一即崩）：
  1. 既有生产库（`finance_subjects` 已有 `S25='投资款收入'`）+ 版本账本为空 → `runner._guard_state`（`runner.py:299-334`）阻断启动 → 运维按 runbook 执行 `manage baseline --confirm` → baseline 按版本升序重跑全部 pending → **v17 先执行**：种子以 `ON CONFLICT (name) DO NOTHING` 插入 `(id='S25', name='项目投资款收入')`——旧行名字不同不触发 name 冲突，**主键 S25 冲突不被吞** → `IntegrityError` → v17 写 `failed` → 此后每次启动被 `_guard_state` 的 failed 门禁阻断（`runner.py:310-311`）。
  2. `MIGRATION_LEGACY_MODE=true` 应急回退路径：同为种子先/改名后，每次启动崩溃。
  3. 任何「库里有旧名科目但未登记版本账本」的形态。
  - 常规增量升级路径（账本已有 v17、本次只跑 v84–v91）**不触发**：本地 dev 库实测已平安应用至 v91（`schema_migrations applied=91`，S25/S26 已改名）。
- **实证**：SQLite 同构复刻——旧行 `(S25,'投资款收入')` 存在时执行种子 SQL → `IntegrityError: UNIQUE constraint failed: finance_subjects.id`（`ON CONFLICT (name)` 语义已确认不覆盖 PK 冲突）。
- **影响范围**：本次发布在 baseline / 应急回退两条运维路径下**应用完全起不来**；且失败会持久化，修复后需手工 `manage retry`/清理记录。
- **修复建议（最小）**：把改名做成种子的**内部前置步骤**而非尾部新项——在 `create_finance_subjects_table` 插种前先按 id 原地改名（S25/S26），或将种子插入改为「先 `SELECT 1 WHERE id=:id` 命中即跳过」；因涉及修改历史 v17，需配套 `manage rebaseline 17`（runbook 已有该命令先例）并保留 v91 作为空操作兜底。禁止维持「只追加 v91 到末尾」的现状。

### H-2【并发/数据完整性】对账的 `FOR UPDATE` 只锁住了调整之间，没锁住「对账 vs 记账」→ 并发下差额算错且不可撤销
- **维度**：数据库交互与性能（竞态）/ 异常与日志
- **位置**：`backend/services/finance/fund_account.py:584-612`（`create_adjustment` 锁 `fund_accounts` 行→聚合读余额→算差额→commit，c8aeef34 修复）；记账写路径 `backend/services/projects/finance/records.py:171-260`（`create_record`）**完全不触碰 `fund_accounts` 行、不取任何锁**。
- **触发场景**：① 账户系统余额 1000；② A 发起对账 `actual_balance=1200`，锁账户行、聚合读到 1000、算出 amount=+200；③ A commit 前，B 提交一笔挂该账户的 `outflow=500` 流水并先 commit（流水 INSERT 不受账户行锁阻塞）；④ A commit。最终余额 = 1000 − 500 + 200 = **700**，而 A 对账时银行实际 1200——差额记录**错 500**；调整「只加不改不删」，只能再补一笔冲回，审计链永久含错账。
- **窗口**：行锁持有期间（聚合查询 + 插入，数十 ms～秒级）。办公室「一人对账 + 一人记账」同时操作即可复现；余额不落库的设计让此类窗口在每次对账时都存在。
- **影响范围**：账户余额静默错账（财务数据损坏），无用户可感知报错。
- **修复建议（最小）**：`create_record`/`update_record`（含换挂 `account_id`）在写入前对目标账户行取 `SELECT ... FOR UPDATE`，把「改某账户的余额成分」全部串行化到账户行锁上；`update_record` 换挂涉及新旧两账户时按 `account_id` 排序取锁防死锁。同法顺带覆盖 `delete_account` 的「有流水/调整拒删」TOCTOU（`fund_account.py:405-425`，计数无锁）。

### H-3【数据完整性/契约】v89 部分唯一索引放开后 `Project.sale`(`uselist=False`) 可命中多行 → 在售项目销售信息非确定性丢失
- **维度**：数据库交互与性能 / 契约一致性（模型与迁移漂移）
- **位置**：`backend/migrations/_project_sale_partial_unique.py:44-57, 85-100`（唯一约束改为 `WHERE is_deleted=false` 的部分索引；步骤 1 清理只删「已有活跃行接管」的软删行）；`backend/models/project/project.py:30-35`（`Project.sale` 的 `primaryjoin` **不含 `is_deleted` 条件**）；`backend/models/project/_project_sale.py:18`（模型仍写 `unique=True` 普通唯一，与部分索引矛盾）。
- **触发场景**：库中已有「项目存活 + 仅剩软删 sale 行（无活跃行）」的存量形态（正是本次修复的 409 前置状态，清理步骤保留而非清除它）→ 用户编辑项目/状态流转（`sales.py:101-119`、`state.py:158-189`、`updater.py:363-384` 的 get-or-create）→ 插入新活跃行 → 同 project_id 出现 **(1 活跃 + 1 软删)**。修复前该插入被 409 拒绝（ loudly 失败）；修复后**静默成功**。此后 `joinedload(Project.sale)` / 惰性加载无法消歧：
  - 实证 A（活跃行先插入）→ 取到 `在售/is_deleted=False`；实证 B（软删行先插入）→ **取到 `已售/is_deleted=True`**，并触发 `SAWarning: Multiple rows returned with uselist=False for lazily-loaded attribute 'Project.sale'`。
  - 消费端 `internal/builder.py:266-269` 判 `if not sale or sale.is_deleted:` → **在售项目的挂牌价/成交信息/销售团队角色在详情页与列表页整体清空**（`query.py` 列表同样 `joinedload(Project.sale)`）。
  - 模型 drift 的次生后果：`Base.metadata.create_all` 建的测试库（SQLite）仍是普通 UNIQUE，**同一 project_id 第二行直接被测试库拒绝 → E2E 结构性测不到本缺陷**。
- **修复建议（最小）**：① `Project.sale` 的 `primaryjoin` 加 `& (ProjectSale.is_deleted == False)`（或改显式查询活跃行）——消除非确定性读取的必要条件；② 模型 `project_id` 列改为部分唯一索引声明 `Index("uq_sale_project_active", "project_id", unique=True, postgresql_where=text("is_deleted = false"))`（项目内已有正确写法 `_project_contract.py:63-68`），消除模型/迁移漂移并让测试库形态对齐；③ 追加新版本迁移重复执行「同 project_id 有活跃行时清理冗余软删行」（已 applied 的 v89 不会重跑）。
