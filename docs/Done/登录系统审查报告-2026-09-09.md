# 登录系统审查报告：静置后跳转页面报「后端无法连接」

> 审查日期：2026-09-09
> 审查方式：静态代码审查（前端认证链路 + 后端 Token 机制 + nginx 分流 + 提交历史）
> 症状：A 页面静置一段时间 → 点击 B 页面 → 提示"后端无法连接/连接后端失败" → 手动刷新后恢复

---

## 一、结论（TL;DR）

1. **症状与 access_token 过期高度吻合**，但触发器不是"连接"本身：
   - access_token 有效期 **30 分钟**（`backend/settings.py:151`），refresh_token 7 天（`:152`）。
   - **点击链接（客户端 RSC 导航）不会经过 proxy 层的自动刷新**（`frontend/src/proxy.ts:171-175` 仅处理 `Accept: text/html` 的请求），因此 B 页面的 Server Component 会带着**过期的 access_token** 请求后端 → 401。
   - **手动刷新 = 整页 HTML 请求 → proxy 层自动刷新 token → 恢复**。这正是"刷新就好"的根本原因。
2. **401 恢复链路存在真实薄弱点**：RSC 导航遇到 401 时，依赖 `fetchClient → redirect("/api/auth/refresh?next=...")` 这条重定向链（`frontend/src/lib/api-server.ts:99-113`）。而 `/api/auth/refresh` 路由的 POST/GET **直接调用 `adapter.refreshToken`，没有经过 `dedupServerRefresh` 去重**（`frontend/src/app/api/auth/refresh/route.ts:47,143`），与 proxy（`auth-middleware.ts:167`）和 api-server（`token-refresh-server.ts:83`）的去重机制不一致。后端 refresh token 是**一次一换（rotation，原子撤销旧 jti）**（`backend/services/system/auth.py:473-482`），两个并发的刷新请求中必有一个拿旧 token 失败 → 触发 fail-closed **清除 cookie**（`route.ts:86-88`）→ 会话被误杀。
3. **用户原有两个猜想均得到验证**：
   - "静置失效"本质 = access_token 30 分钟过期 ✅
   - 前端确实存在把 401/其他错误统一显示为"连接后端失败"的兜底文案（`properties/page.tsx:52`、Server Action 的"网络错误，请稍后重试"等），**误导排查方向** ✅

## 二、登录链路架构（已核实事实）

### 2.1 Token 机制

| 项 | 值 | 证据 |
|---|---|---|
| access_token 有效期 | 30 分钟 | `backend/settings.py:151` |
| refresh_token 有效期 | 7 天 | `backend/settings.py:152` |
| refresh 轮换 | 原子 UPDATE 撤销旧 jti，一次性使用 | `backend/services/system/auth.py:473-482` |
| token_version 校验 | 密码修改/禁用后旧 Token 全部失效 | `backend/services/system/auth.py:314-318, 459-463` |
| refresh 接口限速 | 10 次/分钟 | `backend/routers/system/auth.py:213` |
| Token 存储 | httpOnly cookie（admin: `access_token`/`refresh_token`；C 端: `c_access_token`/`c_refresh_token`） | `admin-auth.ts:189-190`、`auth.ts` |
| 后端认证读取 | 直接读 cookie（匹配前端 cookie 名） | `backend/dependencies/auth.py` |

### 2.2 三条 Token 刷新路径（关键！）

| 路径 | 触发条件 | 是否有去重 | 落盘方式 |
|---|---|---|---|
| ① proxy 层 | admin：仅 `Accept: text/html`（整页加载）；C 端保护路径：所有请求 | ✅ `dedupServerRefresh` | 响应 Set-Cookie + 覆盖请求 cookie（`proxy.ts:61-86`） |
| ② api-server（Server Component / Server Action） | 请求后端返回 401 | Server Action 路径 ✅；Server Component 路径改为 `redirect()` 不直接刷新 | Server Action 可写 cookie；Server Component 靠 `/api/auth/refresh` 路由落盘 |
| ③ 浏览器客户端（api-client / swr fetcher） | 浏览器请求返回 401 | ✅ 浏览器侧 `refreshTokensDedup`（2s 窗口） | POST `/api/auth/refresh`（Route Handler 写 cookie） |

**三条路径最终都汇聚到 Route Handler `/api/auth/refresh` 或 `adapter.refreshToken`，但路径②的 redirect 版本与路径③走的 Route Handler 自身没有服务端去重** —— 这是竞态的入口（详见第四节）。

### 2.3 nginx 分流（已核实无问题）

- `/api/v1/*` → 直连 FastAPI:8000（`profo.nginx.backup:115-130`）
- `/api/auth/*` → Next.js:3000（Route Handler，`:133-140`）
- 其余 → Next.js（`:143-154`）

## 三、按五层排查法逐层定位

| 层 | 问题 | 本项目的答案 |
|---|---|---|
| 第一层：浏览器 | 有没有请求发出去？ | **有**。点击 B 会发出 RSC 导航请求（带 `RSC: 1` 头，非 HTML）；401 后还会发出 `GET /api/auth/refresh?next=...` 或浏览器 `POST /api/auth/refresh` |
| 第二层：请求是什么错误？ | 401 还是网络错误？ | **大概率 401**（静置 > 30min 必然过期）。注意 Network 面板里 `/api/v1/*` 显示 401 后，紧跟的 `/api/auth/refresh` 若也失败（401），就是刷新链断裂 |
| 第三层：FastAPI 收到了吗？ | 收到 → 查后端；没收到 → 查前端 | FastAPI **会收到**第一个业务请求（401 = token 过期/轮换撤销/版本不匹配）。若 Network 里连 401 都没有 → 查 Next.js RSC 渲染 |
| 第四层：FastAPI 为什么 401？ | 具体原因 | 后端日志 `log_auth_event("refresh_failure")` 会记录 reason：`AuthenticationError`（刷新令牌无效/已失效）= 轮换竞态或真过期 |
| 第五层：静置造成什么失效？ | Token/Cookie/Session/前端状态 | **access_token cookie 过期（30min）**。Cookie 本身、React Context、Router 缓存均无静置失效问题（token 全在 httpOnly cookie，前端无内存态 Token） |

## 四、根因分析：RSC 导航与整页刷新的关键差异

这是解释"点击 B 出错、刷新就好"的核心：

```
场景 1：点击链接（RSC 客户端导航）—— Accept: */*（非 text/html）
  浏览器 ──RSC fetch──▶ proxy（跳过 admin 认证刷新！proxy.ts:173-175）
                      └─▶ B 页面 Server Component 带过期 access_token
                          └─▶ FastAPI 401
                              └─▶ fetchClient 检测非 Server Action（无 next-action 头）
                                  └─▶ redirect("/api/auth/refresh?next=/B")   ← api-server.ts:112
                                      └─▶ NEXT_REDIRECT 抛出
                                          ├─ 页面无 try/catch 或有 isRedirectError 守卫
                                          │   → 浏览器跳转 /api/auth/refresh?next=/B
                                          │   → 刷新成功 → 303 回 /B → 恢复（整页加载）
                                          └─ 刷新失败（轮换竞态/后端瞬时故障）
                                              → clearTokenCookies → 跳登录页
                                              → 或页面渲染 401 兜底文案「连接后端失败」

场景 2：手动刷新（整页 HTML 请求）—— Accept: text/html
  浏览器 ──HTML──▶ proxy（执行 adminAuth 中间件，auth-middleware.ts:146-179）
                └─▶ access_token 过期/距过期 <60s（DEFAULT_REFRESH_THRESHOLD_SECONDS=60）
                    → adapter.refreshToken（有 dedupServerRefresh 去重）
                    → Set-Cookie 新 token + 覆盖请求 cookie（proxy.ts:61-86）
                    → Server Component 拿到新 token → 一切正常 ✅
```

**结论：整页刷新有一层"保险"（proxy 刷新），客户端导航没有，完全依赖 401 重定向链。链路任何一环断裂，用户看到的就是各页面的错误兜底文案。**

### 4.1 竞态如何发生（最可能的断裂点）

后端 rotation 是"旧 refresh_token 用一次即废"。以下并发场景中，两个刷新请求都携带同一个旧 refresh_token，**后到的必然失败**：

1. **RSC redirect 的 GET 刷新 vs 浏览器中间件的 POST 刷新**：
   点击 B → RSC 401 → `GET /api/auth/refresh?next=/B`；同时 B 页面客户端组件（或 A 页面尚未卸载的 SWR 请求，`revalidateOnReconnect: true`，`swr-provider.tsx:24`）401 → `POST /api/auth/refresh`。两者都绕过服务端去重（route.ts:47/143 直接调 adapter），一个成功后另一个带着已撤销的旧 token 失败 → **fail-closed 清 cookie**（route.ts:86-88）。
2. **Link 预取（prefetch）风暴**：Next.js 默认预取侧边栏链接。token 过期后，多个预取 RSC 请求并发 401 → 各自触发 redirect 刷新，cookie 更新存在时间差，后到的刷新全部失败 → cookie 被清。
3. **SWR 错误重试**：`errorRetryCount: 3`（`swr-provider.tsx:26`），401 重试与刷新重试叠加。

### 4.2 为什么用户看到的是"后端无法连接"而不是"请重新登录"

- `properties/page.tsx:51-53`：对**任意** error（含 401 透传）渲染「连接后端失败，请稍后重试」。
- Server Action 的 catch 块统一返回「网络错误，请稍后重试」（`investments/actions/create.ts:97` 等十几处）。
- `error-utils.ts:56` 把 fetch 异常映射为「网络连接失败，请检查网络后重试」。
- 这些文案没有按 HTTP 状态码区分，**401（会话过期）被包装成了连接类错误**，与真实故障（后端宕机）不可区分。

## 六、动态验证协议（复现时只做这 5 步）

> 目的：确认断裂点在"重定向链的哪一环"。全程不要刷新页面。

1. **登录 admin，在 A 页面静置 31+ 分钟**（超过 30 分钟 access_token 有效期；后端 `log_auth_event("refresh_failure")` 日志可佐证时间点）。
2. **打开 DevTools → Network + Console，点击 B 页面**，出现错误后保持现场。
3. **Network 里按顺序核对三个请求**：
   - B 页面的 RSC 请求（带 `RSC: 1` 头）：预期 **401**；
   - `GET /api/auth/refresh?next=/B`（Next.js 路由）：看状态——**200/303** = 刷新成功（问题在别处）；**401 或 (canceled)** = 刷新链断裂 → 竞态或 refresh_token 失效；
   - 若无任何请求 → 问题在 Next.js 渲染层（RSC 报错被 ErrorBoundary 吞掉，看 Console 与 Next.js 容器日志）。
4. **看 FastAPI 控制台**：是否收到 `/api/v1/...` 401 与 `/api/v1/auth/refresh` 请求；`refresh_failure` 日志的 reason（`AuthenticationError` = 旧 token 已被轮换撤销 → 证实竞态）。
5. **对照实验**：静置后**先切走标签页再切回来**（触发 SWR `revalidateOnReconnect`）再点 B，若失败率明显高于"静置后直接点击"，进一步证实 POST/GET 双刷新竞态。

## 七、修复建议（按优先级）

### P0：给 refresh 路由补上去重（改动最小、收益最大）

`frontend/src/app/api/auth/refresh/route.ts` 的 POST 与 GET 中，将：

```ts
const tokens = await adminAuth.adapter.refreshToken(refreshToken);
```

改为：

```ts
const tokens = await dedupServerRefresh(refreshToken, () =>
  adminAuth.adapter.refreshToken(refreshToken),
);
```

与 `proxy.ts`/`token-refresh-server.ts` 的既有机制对齐。C 端 `/api/auth/c/refresh` 路由同步检查修改。

### P1：错误文案按状态码区分（立刻能做）

- `properties/page.tsx`、`governance/page.tsx` 等页面的 `if (error)` 分支：`response.status === 401` 时显示「登录已过期，请重新登录」而非「连接后端失败」。
- Server Action catch 块改用 `extractApiErrorMessage` 并透传 401 语义。

### P1：放宽 fail-closed

`route.ts` 刷新失败时区分：仅当后端明确返回 401（refresh_token 无效/撤销）才清 cookie；网络错误/5xx/超时保留 cookie 并返回 503，让上层重试，避免瞬时故障放大为登出。

### P1（可选，治本）：把 admin RSC 导航纳入 proxy 刷新

`proxy.ts` 第 4 步的 HTML 判断增加 RSC 请求识别（如 `request.headers.get("RSC") === "1"` 或放宽为导航类请求），让客户端导航也享受 proxy 层的"过期自动换新"，从源头消除 30 分钟静置窗口。需评估与 Route Handler 刷新的并发去重（P0 修复后天然共享 `dedupServerRefresh`）。

### P2：规范 NEXT_REDIRECT 守卫

将"数据加载 try/catch 必须放行 `isRedirectError`"写入 `AGENTS.md` 编码规范（后端章节已有类似规约），或增加 ESLint 自定义规则/模板函数 `withRedirectGuard(fn)` 统一封装。
