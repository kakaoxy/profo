# 小程序钥匙管理「网络异常，请重试」——普通员工 403 结论报告

- 日期：2026-10-09
- 现象账号：`zhiwuping1`（普通员工，主角色 `user` + 附加角色 `customer`，active）
- 现象：在小程序打开「钥匙管理」列表页显示「网络异常，请重试」，但该账号是 11 套房源的渠道经理/房产业务员（相关人），按设计应正常显示关联房源。

## 一、结论（TL;DR）

**不是网络问题，是后端 403。** `GET /api/v1/keys/properties` 对 `user` 角色员工一律返回
`403 {"code":403,"message":"仅管理员/运营人员可访问员工工作台"}`；小程序端仅特判 401（去登录），
其余非 2xx 统一进 error 态，把 403 渲染成了「网络异常，请重试」。

根因是钥匙模块路由层与服务层的权限口径自相矛盾：

- **路由层**（`backend/routers/keys/shares.py`）复用了评估工作台的
  `CurrentCInternalUserDep`（C 端令牌 + **admin/operator 角色复核**），把 `user` 角色整体挡在门外；
- **服务层**（`backend/services/projects/key_access.py`）的权限设计明确写着
  「role_code=admin：全量房源；**其他用户：按相关人五字段匹配，仅见关联房源**」——
  这段为普通员工设计的相关人匹配逻辑，因路由层先 403 而**成为不可达代码**。

> 产品口径已于 2026-10-09 确认：钥匙管理对**所有有权限的人开放**（admin 全量 +
> 相关人员，不限于管理员），且**无权限者不应看到入口**。修复方案见第六节。

## 二、调用链与阻塞点

```
小程序「我的」→「钥匙管理」入口（pages/profile/index/index.ts:44，对所有内部员工可见，无角色门槛）
  → pages/keys/list/index.ts:138  GET /keys/properties（request.ts 按 /keys/* 前缀自动带 c_access_token，aud=c）
    → backend/_infer_audience_from_path：/api/v1/keys/* → aud=c ✓（令牌受众校验通过）
    → CurrentCInternalUserDep（dependencies/auth.py:270）
        第 1 关 require_roles(["customer"])：查 DB 角色 → zhiwuping1 有附加 customer ✓
        第 2 关 _c_side_internal_checker：查 DB 角色 ∈ {admin, operator} → zhiwuping1 是 user ✗
    → 403 「仅管理员/运营人员可访问员工工作台」   ← 阻塞点，service 层根本没执行到
  → pages/keys/list/index.ts:151-159 catch：statusCode !== 401 且无缓存
    → state = "error" → index.wxml:12 渲染「网络异常，请重试」
```

关键代码位置：

| 位置 | 内容 |
| --- | --- |
| backend/dependencies/auth.py#L270-L294 | `_c_side_internal_checker`：C 端令牌后再复核 admin/operator，否则 403「仅管理员/运营人员可访问员工工作台」 |
| backend/routers/keys/shares.py#L27-L33 | `GET /keys/properties` 等 6 个端点全部挂 `CurrentCInternalUserDep` |
| backend/services/projects/key_access.py#L1-L9 | 服务层声明的权限口径：admin 全量、其他用户按相关人五字段匹配 |
| backend/services/projects/key_access.py#L120-L160 | `list_accessible_projects`：为非 admin 设计的相关人匹配（含 `user` 角色），实际不可达 |
| backend/routers/system/auth.py#L46-L88 | 小程序登录签发 C 端令牌时 role_claim=customer 只写进 JWT，**不改变 DB 角色**；`require_roles` 校验的是 DB 角色 |
| miniapp/pages/keys/list/index.ts#L151-L159 | 页面仅特判 401 → needLogin，其余一律 error 态「网络异常，请重试」 |

## 三、复现验证（可重跑）

本地环境（2026-10-09 实测，后端 :8000，数据为服务器备份恢复库）：

1. **DB 事实**：`zhiwuping1` 主角色 `user` + 附加角色 `customer`；作为
   `project_sales.channel_manager_id`（11 套）/`property_agent_id`（9 套）关联多套在售房源——
   服务层 `list_accessible_projects` 本应返回这些房源。
2. **令牌签发**：按小程序登录内部员工分支完全同口径
   （`AuthService.create_tokens_for_user(db, user, audience="c", role_claim="customer")`）
   为 zhiwuping1 签发 C 端令牌。
3. **请求**：`curl http://127.0.0.1:8000/api/v1/keys/properties -H "Authorization: Bearer <c_token>"`
   → `HTTP 403 {"code":403,"message":"仅管理员/运营人员可访问员工工作台"}`
4. **对照**：同口径为 `admin`（主角色 admin + 附加 customer）签发令牌请求同一接口
   → `HTTP 200`，正常返回房源列表（首条「金杨七街坊 - 枣庄路810弄44号401」）。

同一签发路径、同一接口，唯一变量是 DB 角色 ⇒ 阻塞点锁定为 `_c_side_internal_checker` 的角色复核。

## 四、影响面

1. **小程序钥匙全模块对 `user` 角色员工不可用**：`/keys/*` 共 6 个端点
   （房源列表、创建分享、分享记录、分享详情、回收、延期）全部挂同一依赖，全部 403。
2. **钥匙详情页存在第二道同性质门槛**：详情页走 admin 令牌请求
   `/projects/{id}/keys*`（backend/routers/projects/keys.py），挂 `CurrentInternalUserDep`
   （同样仅 admin/operator）——即使放开 `/keys/*`，`user` 角色员工打开详情仍会 403；
   admin Web 端的钥匙管理卡同样被此依赖挡住 `user` 角色。
3. **与其他员工功能口径不一致**：带看/装修/记账等页面走 `/projects/*` 核心端点的
   `ProjectReadPermDep`（权限码 `project:read`，`user` 角色具备）→ 正常可用；
   钥匙是唯一用「角色硬门槛」的员工侧模块。
4. **服务层相关人逻辑成为死代码**：`list_accessible_projects`/`ensure_key_access`
   的非 admin 分支，在两类路由门槛下永远不会被 `user` 角色触达。

## 五、测试缺口

`backend/tests/test_key_share_reveal_disabled.py` 等钥匙 E2E 构造的员工是
**customer 主角色 + admin 附加角色**（测试专用组合），真实世界员工是
**user 主角色 + customer 附加角色**——后者从未被测试覆盖，导致路由层与
服务层的口径矛盾漏检。

## 六、修复方案（2026-10-09 产品口径已确认，待实施）

**产品决议**：钥匙管理对所有有权限的人开放（admin 全量 + 相关人员，不限于管理员）；
**无权限的人不应看到入口**。即按方案 A 执行，方案 B 作废。

### 6.1 后端：路由层对齐服务层权限口径

1. 新增依赖（如 `CurrentCEmployeeUserDep`）：C 端令牌 + `has_backend_identity`
   复核（admin/operator/user 任一即可），`/keys/*` 6 个端点
   （backend/routers/keys/shares.py）换用，替换 `CurrentCInternalUserDep`；
2. `/projects/{id}/keys*`（backend/routers/projects/keys.py）的
   `CurrentInternalUserDep` 同步放宽为「后台身份」复核，
   细粒度控制交还 Service 层 `ensure_key_access`（相关人五字段匹配，无关 403）；
3. 联动确认：admin Web 端钥匙管理卡将同步对 `user` 角色相关人放开（同一端点，
   行为一致，符合「所有有权限的人开放」口径）。

### 6.2 入口可见性：无权限者不渲染「钥匙管理」入口

现状：小程序「我的」页 `INTERNAL_ENTRIES` 为静态列表
（miniapp/pages/profile/index/index.ts:39），凡持 admin 令牌（aud=admin，
即具备后台身份）的内部员工一律可见「钥匙管理」——修复 6.1 后内部员工
（admin/operator/user）均能通过 `/keys/*` 门槛，纯 C 端用户本就看不到内部区块；
因此「无权限」的精确范围 = **具备后台身份、但与任何房源无相关人匹配的非 admin 员工**
（此类用户当前会看到入口，点进去得到空列表）。

实施方案：

1. 后端在员工侧身份响应（`/auth/me` 的 UserResponse 或 profile 专用字段）增加
   `keys_accessible: bool`：`admin` 恒 `true`（全量口径）；`operator`/`user`
   按相关人五字段（project_manager / renovation.contact_person / sale 三字段）
   exists 查询判定——服务层设计中 operator 与 user 同属「其他用户」，非全量；
2. 小程序 profile 页按 `keys_accessible` 过滤 `INTERNAL_ENTRIES` 中的「钥匙管理」项，
   无权限时不渲染入口（而非渲染后报错/空态）。

### 6.3 体验兜底与回归

1. 小程序 keys 系列页面对 403 兜底展示「无权限」类明确文案，而非笼统的
   「网络异常，请重试」——401/403/5xx 语义不同，不应同态渲染
   （miniapp/pages/keys/list/index.ts#L151-L159 等同构处）；
2. 补一条「user 主角色 + customer 附加角色 + 相关人」的 E2E 用例锁住新口径：
   断言 `/keys/properties` 200 且仅返回关联房源、无关员工 403、
   `keys_accessible` 与入口渲染一致。
