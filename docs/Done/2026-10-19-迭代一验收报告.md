## 5. 实施中发现并修复的缺陷（非计划内，均为实测暴露）

### 缺陷 1：恢复命令用错客户端（**会导致事故时无法恢复**）

- **现象**：`restore-hint` 原输出用 `docker compose exec db pg_restore`。实测报
  `pg_restore: error: unsupported version (1.16) in file header`
  （本机 `pg_dump 18.6` 产出归档格式 1.16，db 容器内 `pg_restore 16.15` 读不了）。
- **二次验证**：用 PG17 的 `pg_restore` 亦失败（17 的 `pg_dump` 同样产出 1.16）。
- **根因**：归档格式版本随 client 升级；恢复端 client 必须 ≥ 产出端。
- **修复**：
  1. `BackupResult.client_version` + `schema_migrations.backup_client` 列记录产出备份的版本；
  2. `restore-hint` 按 `backup_client` vs `server_version` 输出命令，跨大版本时打印告警与两条可行路径；
  3. 恢复命令改在 **backend 容器**（装有产出备份的同一客户端）执行；
  4. `backup.assert_client_compatible()` 在备份前校验 `client major ≥ server major`。
- **复验**：`restore_check` 恢复 977 行 == 生产 977 行。

### 缺陷 2：`--data-only --table=` 静默灌 0 行（**最隐蔽**）

- **现象**：`pg_restore -d restore_check --data-only --table=public.leads <dump>` **退出码 0、无任何报错**，
  但目标表 0 行。去掉 `--table=` 过滤后正常灌入 977 行。
- **风险**：操作者看到「成功」会误判备份可用，事故时才发现备份无效。
- **修复**：`restore-hint` 输出的配方**明确去掉 `--table` 过滤**，并在注释里写明实测结论；
  runbook §5 增补两段式配方（schema-only dump/restore → data-only 灌入）+ 行数核对步骤。

### 缺陷 3：`str(engine.url)` 把密码变成 `***`

- **现象**：`pg_dump` 认证失败 `password authentication failed for user "profo"`。
- **根因**：SQLAlchemy `URL.__str__` 默认隐藏密码；`make_url(str(url)).password` 长度 3（`***`）。
- **修复**：`build_dump_command(database_url: str | URL)` 直接接受 `URL` 对象；调用处传 `engine.url`。
- **守护**：`test_subprocess_run_not_called_with_password_in_argv` 断言 argv 无密码且 `PGPASSWORD` 正确。

### 缺陷 4：`restore-hint` 打印宿主绝对路径

- **现象**：本机账本记录 `/Users/.../backups/migrations/x.dump`，但恢复命令在容器内执行。
- **修复**：`_container_backup_path()` 统一映射为 `/app/backups/migrations/<name>`。

> 以上 4 条对应总纲 §1 新增的 **B9 / B10**（已按变更控制追加进表）。
