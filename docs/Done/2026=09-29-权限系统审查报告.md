# Next.js FastAPI Template 用户与权限体系调研暨 ProFo 迭代指引

**调研对象**

* `vintasoftware/nextjs-fastapi-template`
* `kakaoxy/profo`

**调研基准**

2026 年 9 月 28 日，以两个公开仓库当前 `main` 分支可见代码、README、项目文档为主；对模板源码细节辅以 DeepWiki 索引资料。模板官方定位是一个“production-ready authentication”基础模板，其认证能力建立在 FastAPI-Users 之上，并提供 JWT、密码重置、邮箱验证等完整账号生命周期。

---

# 一、执行摘要

## 1. 核心结论

对 ProFo 研发团队而言，最重要的结论不是“把 ProFo 的权限体系改造成 `nextjs-fastapi-template` 的样子”，而是：

> **借鉴模板在“认证基础设施”和“用户生命周期管理”上的工程化方式，保留并继续发展 ProFo 已经建立起来的“细粒度 RBAC + 业务身份约束 + 审计 + Token 失效”体系。**

两者解决的问题层级实际上不同。

`nextjs-fastapi-template` 主要解决：

**“这个人是谁？他能不能登录？账号是否激活？邮箱是否验证？密码忘了怎么办？管理员如何管理用户？”**

而 ProFo 当前已经进一步解决：

**“这个用户可以做什么？属于什么角色？权限什么时候生效？权限变化后原 Token 是否继续有效？谁修改了什么业务数据？C 端身份和 B 端业务身份如何隔离？”**

从代码和文档来看，模板的用户模型核心仍然是：

* UUID 用户 ID
* email
* password hash
* `is_active`
* `is_verified`
* `is_superuser`

授权侧主要围绕“活跃用户”和“超级用户”这两个维度展开，并由 FastAPI-Users 提供用户管理路由。当前模板主程序直接注册 JWT login/logout、register、reset-password、verify 和 users 管理路由。

而 ProFo 已经建立了更完整的授权域：

* `users`
* `roles`
* `user_roles`
* `permissions`
* `role_permissions`
* `operation_logs`
* `api_keys`
* `refresh_tokens`
* `token_version`

并形成了 `PermissionService`、`require_permission`、`CurrentUserDep`、`CurrentAdminUserDep`、`CurrentInternalUserDep` 等机制。

因此，对 ProFo 的建议不是“照搬模板”，而是：

### ProFo 下一阶段应围绕四条主线继续演进

**第一条：身份模型标准化**

把“账号身份”“角色”“权限”“数据范围”四个概念彻底拆开，避免继续把它们混在 `admin/operator/user/customer` 这类角色编码中。

**第二条：从 RBAC 走向 RBAC + Data Scope**

ProFo 现在已经有 `resource:action` 级权限，这是一个好的基础。下一步真正会遇到的问题不是“有没有权限”，而是：

> “有这个权限的人，到底能看谁、改谁、导出谁的数据？”

因此下一阶段的核心不是继续无限增加权限码，而是增加 **数据范围（Data Scope）**。

**第三条：Session / Token 从“认证技术”升级为“安全控制面”**

ProFo 已经有 refresh token 持久化以及 `token_version` 机制，这比模板基础认证更进一步。下一步建议演进为“会话中心 + 会话级撤销 + Token Rotation + Replay Detection + Authz Version”。

**第四条：把权限控制从 API 层下沉到 Service 层，同时覆盖前端**

ProFo 当前已经强调 Service 层二次防御，这一点应继续坚持；同时前端也应该逐渐从“登录态控制”进入“权限态控制”，形成统一的 `can()` / `useCan()` 权限判断体系。

# 二、nextjs-fastapi-template 的用户与权限体系到底是怎样的

# 2.1 它的本质：Authentication First

模板官方描述非常明确：它提供的是一个已经配置好的生产级认证基础，包括 FastAPI-Users、安全密码哈希、JWT、邮件密码恢复等能力。

当前后端 `main.py` 直接将 FastAPI-Users 提供的几个 Router 注册进系统：

* `/auth/jwt`
* `/auth`
* `/users`

其中包含：

* JWT 登录
* JWT 登出
* 用户注册
* 忘记密码
* 重置密码
* 邮箱验证
* 用户自身信息读取与修改
* 用户管理

所以它的体系可以抽象成：

```text
                  ┌──────────────┐
                  │     User     │
                  └──────┬───────┘
                         │
          ┌──────────────┼───────────────┐
          │              │               │
      Authentication   Lifecycle      Admin Control
          │              │               │
       JWT Login      Verify Email     User CRUD
       JWT Logout     Password Reset   Superuser
       Current User   Account Active
```

也就是说，它首先解决“用户是谁”，而不是试图建立一个复杂 IAM / RBAC 平台。

---

# 2.2 User 模型：简单、清晰、够用

模板用户模型的核心字段包括：

```text
id
email
hashed_password
is_active
is_superuser
is_verified
```

源码同时使用 `UUIDIDMixin`，说明用户 ID 在认证层采用 UUID 模式。

其中几个字段职责比较明确：

### `is_active`

表示账户是否可以正常作为活跃用户访问系统。

模板后端通过：

```python
current_active_user = fastapi_users.current_user(active=True)
```

统一得到当前活跃用户。

### `is_verified`

表示邮箱等验证流程是否完成。

### `is_superuser`

这是模板最重要的管理权限分界线。

也就是说：

```text
普通用户
   │
   ├── 是否 active
   └── 是否 verified

超级用户
   └── 是否具有管理员能力
```

这个设计非常适合基础型后台，但它不等价于完整 RBAC。

---

# 2.3 UserManager：模板很值得 ProFo 借鉴的部分

模板没有把“注册之后做什么”“忘记密码发送什么”“验证邮件怎么处理”等逻辑散落在 Router 中，而是提供了 `UserManager`。

当前源码中的 `UserManager` 负责：

* 密码生命周期
* reset password secret
* verification secret
* 注册后的 hook
* forgot password hook
* verify token hook
* 密码安全策略

同时密码规则集中定义，例如当前实现要求：

* 至少 8 个字符
* 不能包含邮箱
* 至少一个大写字母
* 至少一个特殊字符

这体现出一个很重要的工程思想：

> **认证相关的“生命周期副作用”和“安全策略”应该有统一归属，而不是散落在各个业务 API 中。**

这非常适合 ProFo 借鉴。

---

# 2.4 Token / JWT 机制

模板使用：

```text
BearerTransport
      +
JWTStrategy
      +
ACCESS_SECRET_KEY
      +
ACCESS_TOKEN_EXPIRE_SECONDS
```

源码显示 Token 的签发基于 JWTStrategy，并使用独立的 Access Secret 与 Token Expiration 配置。

模板还把以下安全 Secret 拆开：

```text
ACCESS_SECRET_KEY
RESET_PASSWORD_SECRET_KEY
VERIFICATION_SECRET_KEY
```

而不是所有流程共用一个 secret。官方文档也明确列出了这些配置。

这个设计值得 ProFo 保留并继续扩展。

---

# 2.5 前端认证链路

模板前端的设计也值得研究。

其典型流程是：

```text
Login Form
   ↓
Zod Validation
   ↓
Next.js Server Action
   ↓
FastAPI JWT Login
   ↓
Cookie
   ↓
Middleware
   ↓
/users/me
   ↓
Authenticated Session
```

登录、注册、密码找回、退出均通过 Server Actions 等模式封装，Middleware 负责登录态检查；DeepWiki 对其源码结构的补充说明也显示，前端会检查 Cookie，并通过 `/users/me` 验证会话。

这一点给 ProFo 的启示并不是“必须采用 Server Actions”，而是：

> **认证状态、Token 管理、路由保护应该形成统一基础设施，业务页面不应该自己重复实现。**

# 三、nextjs-fastapi-template 在“权限”方面到底做到什么程度

这是本次调研里最重要的判断。

从当前模板模型与 Router 注册方式来看，其授权模型主要围绕：

```text
User
 ├── is_active
 └── is_superuser
```

以及 FastAPI-Users 对超级用户管理接口的保护展开。当前代码并没有呈现 ProFo 那种：

```text
Permission
Role
RolePermission
UserRole
DataScope
OperationLog
```

这样的独立授权域模型。

所以应该把两个概念严格区分：

### 模板的核心能力

**Authentication**

```text
注册
登录
JWT
登出
邮箱验证
密码找回
密码重置
活跃用户
超级用户
用户管理
```

### 模板没有重点解决的事情

**Authorization**

```text
项目:查看
项目:编辑
客户:分配
财务:审核
报表:导出
数据范围
部门隔离
租户隔离
角色继承
临时授权
权限审批
权限变更审计
```

这并不意味着模板设计不好，而是它的产品目标不同。

事实上，模板的价值恰恰在于：

> **把“基础认证”作为公共基础设施解决掉，然后让业务项目在此之上建立自己的授权模型。**

这恰好非常适合 ProFo。

# 四、ProFo 当前用户与权限体系现状

ProFo 当前已经不是一个简单的“用户登录系统”。

从仓库 README 与源码结构来看，ProFo 已经形成如下体系：

```text
User
  │
  ├── Role
  │     └── RolePermission
  │              └── Permission
  │
  ├── RefreshToken
  │
  ├── API Key
  │
  ├── WeChat Identity
  │
  ├── token_version
  │
  └── OperationLog
```

项目 README 明确将以下内容作为安全能力：

* JWT + API Key
* httpOnly Cookie
* `X-API-Key`
* 细粒度 Permission
* `Permission / OperationLog / role_permissions`
* 权限变化递增 `token_version`
* 业务身份双通道校验
* Service 层二次防御
* CSRF
* refresh token 持久化
* Redis

这意味着：

> **ProFo 的授权体系已经明显超出 nextjs-fastapi-template 的基本授权范围。**

---

# 五、ProFo 当前设计中最值得保留的能力

## 5.1 PermissionService + require_permission

这一层是 ProFo 最重要的架构资产之一。

当前仓库已经形成：

```text
PermissionService
        ↓
require_permission
        ↓
[resource]:[action]
```

例如可以抽象为：

```text
projects:read
projects:create
projects:update
projects:delete
```

这种设计比：

```python
if current_user.role == "admin":
```

更加稳定。

因为它把：

> “角色是谁”

与

> “他能做什么”

进行了分离。

这应该成为 ProFo 长期演进的核心。

---

# 5.2 多角色模型

ProFo 当前存在：

```text
roles
user_roles
role_permissions
```

也就是说，用户并不一定只能绑定一个 Role，而是已经具备多角色关系。仓库文档同时列出了 `admin / operator / user / customer` 等核心角色。

这为未来发展：

```text
销售
销售主管
项目经理
设计师
施工负责人
财务
财务主管
运营
平台管理员
客户
```

等复杂组织角色留下了空间。

---

# 5.3 Permission 动态化

ProFo 的权限已经是数据库实体，而不是散落在代码里的 if/else。

权限表包含：

```text
code
name
module
category
sort_order
is_system
```

角色和权限通过 `role_permissions` 关联。

这一点非常重要。

因为一旦产品进入真实运营环境，开发团队无法接受：

> 每增加一个权限都必须改代码、发版、改硬编码。

ProFo 现在已经跨过了这一阶段。

---

# 5.4 权限变化触发 Token Version

README 明确记录：

> 权限变更会递增 `token_version`，使原有 Token 失效。

这是一个很好的安全设计，因为权限变化并不是普通业务变更。

例如：

```text
张三原来：
finance:settle = true

管理员改为：
finance:settle = false
```

如果旧 Access Token 继续有效，则可能形成：

```text
数据库已经取消权限
        ↓
旧 Token 仍然被接受
        ↓
用户仍可执行高危操作
```

`token_version` 至少解决了这一类“授权变更传播延迟”问题。

---

# 5.5 Service 层二次防御

这是 ProFo 比很多简单 RBAC 项目更成熟的一点。

当前文档明确强调：

> Permission Dependency + Service 层二次防御。

也就是：

```text
HTTP Router
   ↓
Permission Check
   ↓
Service
   ↓
Business Identity Check
   ↓
Database
```

而不是：

```text
HTTP Router
   ↓
直接调用 Service
```

这是一条应该继续坚持的安全边界。

因为未来一定会出现：

```text
HTTP API
Background Job
Celery Task
Scheduled Job
Internal Script
Admin Tool
```

多个调用入口。

如果权限逻辑只写在 Router 层，那么后台任务和内部服务就容易绕过权限检查。

| 能力              | nextjs-fastapi-template | ProFo 当前              | ProFo 建议                               |

> **ProFo 没有必要在“基础登录功能”上重新造轮子，但应该把模板的认证工程方法吸收进现有授权体系。**

# 七、对 ProFo 最重要的第一条架构建议：彻底分离四个概念

未来 ProFo 最容易出现的架构债务，是把以下四个东西混在一起：

```text
User
Role
Permission
Data Scope
```

建议正式建立如下概念边界：

```text
                    Account
                       │
          ┌────────────┼────────────┐
          │            │            │
      AccountType     Status      Identity
          │
    internal/customer/service
                       │
                       ↓
                     Roles
                       │
                       ↓
                  Permissions
                       │
                       ↓
                   Data Scope
```

---

# 八、AccountType 不应该再由 Role 隐含表达

ProFo 当前存在：

```text
admin
operator
user
customer
```

这些名称实际上同时承担了两个维度：

### 维度 A：身份类型

```text
customer
internal
service
```

### 维度 B：角色

```text
admin
sales
finance
operator
manager
```

这两个维度最好不要混合。

建议建立：

```text
account_type

internal
customer
service
```

然后：

```text
internal → admin / sales / project_manager / finance
customer → customer
service → api_service
```

即：

```text
User
 ├── account_type = internal
 └── roles = [sales, project_manager]
```

而不是：

```text
role = operator
```

然后在各种代码里猜“operator 究竟是不是内部账号”。

这样做的价值很大。

---

# 九、第二条核心建议：从 RBAC 升级为 RBAC + Data Scope

这是 ProFo 下一阶段最应该解决的问题。

当前：

```text
projects:update
```

只能回答：

> “这个人可以修改项目吗？”

但是业务最终会问：

> “他可以修改哪些项目？”

例如：

### 销售

```text
projects:update
scope = own
```

只能修改自己的项目。

### 项目经理

```text
projects:update
scope = team
```

可以修改本团队项目。

### 区域经理

```text
projects:update
scope = region
```

可以修改所在区域项目。

### 总管理员

```text
projects:update
scope = all
```

可以修改全部。

因此未来授权模型最好变成：

```text
Permission
  =
  Resource
  +
  Action
  +
  Scope
```

例如：

```text
projects:update:own
projects:update:team
projects:update:region
projects:update:all
```

不过这里有一个架构建议：

**不要真的把 Scope 全部编码成 Permission Code。**

更推荐：

```text
permission
---------------------
projects:update

role_permission
---------------------
role_id
permission_id
scope_type
scope_value
```

这样模型更加清晰：

```text
Role
  ↓
Permission
  ↓
Scope
```

而不是制造成百上千个：

```text
projects:update:own
projects:update:team
projects:update:region
projects:update:all
...
```

# 十、第三条核心建议：建立正式的 Authorization Context

当前 ProFo 的 `CurrentUserDep`、`CurrentInternalUserDep`、Permission Dependency 已经构成了不错的基础。

下一步建议统一成一个内部授权上下文：

```python
AuthzContext(
    user_id=...,
    account_type=...,
    status=...,
    role_codes=[...],
    permission_codes=[...],
    auth_source=...,
    session_id=...,
    authz_version=...,
)
```

请求进入以后统一经历：

```text
1. Authenticate
      ↓
2. Resolve User
      ↓
3. Check Account Status
      ↓
4. Resolve Auth Context
      ↓
5. Permission Check
      ↓
6. Data Scope Check
      ↓
7. Business Rule Check
      ↓
8. Execute Service
      ↓
9. Audit
```

这会让 ProFo 的权限系统从“一组依赖函数”升级成真正的授权基础设施。

---

# 十一、第四条核心建议：把 Role 变成“授权集合”，而不是业务身份

推荐让 Role 永远回答一个问题：

> “这一组用户默认拥有哪一组能力？”

例如：

```text
Role: sales

Permissions:
  leads:read
  leads:update
  leads:assign
  projects:read
  projects:create
  projects:update

Scope:
  own
```

而不是：

```text
if role == sales:
    ...
```

业务代码永远应该问：

```python
require_permission("projects:update")
```

而不是：

```python
if user.role == "sales":
```

角色只负责组装权限。

# 十二、第五条核心建议：保留 token_version，但进一步 Session 化

ProFo 当前：

```text

+
token_version
```

是正确方向。

下一步建议建立正式的：

```text
sessions
```

或把 refresh token 发展成 Session 实体。

推荐结构：

```text

---------
id

refresh_token_hash
device_id
user_agent
ip
```

这样以后可以实现：

# 十三、token_version 与 authz_version 应逐步分离

建议未来区分：

```text
token_version
```

和：

```text
authz_version
```

### token_version

更偏向：

> “这个账号之前签发的 Token 是否还全部有效？”

例如：

* 密码泄漏
* 强制登出全部设备
* 账号安全事件

### authz_version

更偏向：

> “这个账号当前权限版本是否变化？”

例如：

```text
用户角色变化
角色权限变化
数据权限变化
高危授权撤销
```

这样以后可以做到：

```text
普通 profile 更新
    ≠
权限变化
    ≠
全局安全事件
```

减少无必要的全设备退出。

# 十四、第六条核心建议：API Key 必须脱离“人的完整权限”

ProFo 已经支持：

```text

```

并存储：

```text

expiry
last_use
```

这部分设计方向是合理的。

但未来必须避免：

```text
User A
   ↓
API Key
   ↓
继承 User A 的所有权限
```

否则 API Key 一旦泄漏，相当于：

> 用户整个账号权限被复制了一份。

更推荐：

```text

        ↓
API Key
        ↓
Scoped Permissions
```

例如：

```text

```

而不能：

```text
*
```

API Key 未来应该具备：

```text

owner
scope
expires_at
last_used_at
revoked_at
created_by
```

必要时增加：

```text
IP allowlist
environment
service identity
```

# 十六、权限修改本身必须成为高等级审计事件

很多系统会审计：

```text
谁删除了项目
```

却忘了审计：

```text
谁给张三增加了财务权限
```

而后者往往更危险。

因此建议对权限操作定义专门等级：

```text

```

例如：

```text

permission:grant
permission:revoke
api_key:create
api_key:revoke
session:revoke_all

```

这些操作必须：

1. 有操作者
2. 有被操作者
3. 有前后状态
4. 有 request_id
5. 有 IP / session
6. 不允许普通日志更新覆盖

# 十七、第八条核心建议：业务身份和权限判断必须明确分层

ProFo 已经存在“业务身份双通道”和 Service 层二次防御。

建议把它正式抽象成：

```text
Authentication
       ↓
Authorization
       ↓
Business Invariant
```

例如：

```text
Authentication:
用户登录了吗？

Authorization:
用户有 projects:update 吗？

Business Invariant:
这个项目属于他所在的组织吗？
项目当前状态允许修改吗？
财务结算后还能修改吗？
```

这三层不要混在一起。

尤其不要：

```python
if user.is_internal and user.role == "operator" and project.status != "closed":
```

全部写在一个函数里。

应该拆开：

```text
require_authenticated_user()
require_permission("projects:update")
require_project_scope(project)
validate_project_state(project)
```

这样可测试性和未来演进都会明显更好。

# 十八、第九条核心建议：前端需要进入“Permission-aware UI”阶段

ProFo 当前已经有受保护的 `(main)` 路由，前端 layout 会请求 `/api/v1/auth/me`，并有 browser/server 双 API Client、401 refresh/redirect 机制。

这解决的是：

> “用户是否登录？”

但是下一阶段还需要解决：

> “用户登录以后，哪些 UI 能看？哪些按钮能操作？”

推荐建立：

```typescript
can("projects:read")
can("projects:update")
can("projects:delete")
can("finance:settle")
```

统一前端权限接口：

```typescript
useCan("projects:update")
```

以及：

```typescript
<Can permission="projects:update">
    <EditProjectButton />
</Can>
```

但需要特别强调：

> **前端权限判断只能用于 UX，不可以作为真正的安全边界。**

真正授权仍必须在 FastAPI / Service 层完成。

# 二十五、哪些模板设计不建议 ProFo 直接采用

## 1. 不建议以 `is_superuser` 替代 Role/Permission

可以存在：

```text

```

作为紧急系统级安全能力，但不应成为业务授权的主模型。

推荐：

```text

=
System Emergency Authority
```

而：

```text

=
Normal Business Authorization
```

## 2. 不建议把权限硬塞进 JWT

ProFo 已经有动态权限和 Token Version。

未来更不应该让：

```text
JWT
=
所有权限的永久快照
```

否则：

```text
Role Permission Change
```

将变得难以实时生效。

更合理的是：

```text
JWT
  ↓
user_id
session_id
token_version
authz_version
```

权限由授权层解析，并通过缓存加速。

## 3. 不建议继续增加大量 Role

典型错误是：

```text
admin
admin2
admin_finance
admin_finance_manager
finance_manager
finance_manager_region

...
```

Role 应该代表稳定的能力集合。

```text

Scope
Organization
Resource Ownership
```

# 二十六、Redis 在 ProFo 权限体系里的最佳用途

ProFo 已经引入 Redis，因此不应该只把 Redis 当作普通缓存。

推荐把 Redis 用于：

```text
Effective Permissions Cache
Session Revocation
Authz Version
Rate Limit
Short-lived Security State
```

例如：

```text
authz:user:{user_id}:v:{authz_version}
```

缓存：

```text
{
  permissions: [...],
  roles: [...],
  scopes: [...]
}
```

权限发生变化：

```text
authz_version += 1
```

旧缓存自动失效。

这样：

```text
Database = Source of Truth
Redis = Authorization Acceleration Layer
```

比把权限本身全部塞到 JWT 更容易保持实时性。

# 四十、最终建议：ProFo 不要复制模板，而应该“吸收模板 + 继续超越模板”

可以把两个项目的关系理解成：

```text
nextjs-fastapi-template
        │
        ├── Authentication Foundation
        ├── User Lifecycle
        ├── Password Management
        ├── Verification
        ├── JWT
        └── Basic Admin User Management
                 │
                 ↓
                ProFo
                 │
        ┌────────┴─────────┐
        │                  │
  Identity Foundation    Authorization
        │                  │
        │             Role / Permission
        │                  │
        │             Data Scope
        │                  │
        │             Delegation
        │                  │
        │             Audit / Security
        │                  │
        └────────┬─────────┘
                 ↓
             Enterprise IAM
```

因此，对 ProFo 研发团队最明确的产品/架构判断是：

> **不要用 `is_admin / is_superuser` 继续扩展业务权限；不要继续堆 Role；不要把越来越多的权限塞进 JWT；不要把前端权限判断当成安全边界。**

应该正式确立：

```text
User
→ Account Type
→ Role
→ Permission
→ Scope
→ Business Rule
```

以及：

```text
Authentication
→ Authorization
→ Business Authorization
→ Audit
```

两条清晰的职责链。

# 四十二、一句话给 ProFo 研发团队

**`nextjs-fastapi-template` 值得 ProFo 学的是“如何把 Authentication 做成稳定、清晰、可维护的基础设施”；而 ProFo 真正应该继续建设的，则是基于现有 Role + Permission + Audit + Token Version 之上的“Authorization Platform”。**

换句话说：

```text
模板解决：
“你是谁？”

ProFo 当前解决：
“你能做什么？”

ProFo 下一阶段应该解决：
“你能对谁的数据做什么，为什么能做，谁授予你的，
什么时候失效，以及这一切是否可追溯？”
```

这将是 ProFo 用户与权限体系从“功能可用”走向“长期可演进、可运营、可审计”的关键一步。

**核心参考：**

模板当前 GitHub 主干及官方文档显示，其认证体系基于 FastAPI-Users，覆盖 JWT、用户注册、密码重置、邮箱验证、用户管理，并通过 `is_active`、`is_verified`、`is_superuser` 等用户属性完成基础用户与管理能力。

ProFo 当前仓库则已经具备动态 Permission、Role/RolePermission、UserRole、OperationLog、API Key、Refresh Token、Token Version、业务身份双重校验及 Service 层权限防御等机制。
