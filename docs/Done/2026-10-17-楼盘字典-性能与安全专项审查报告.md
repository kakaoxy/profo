## 一、高危缺陷 · 安全（必须立即修复）

### S1 · 存量绑定接口可写入「跨小区脏关联」——楼栋/户室归属校验存在缺口

- **维度**：输入校验与权限控制 / 数据完整性
- **位置**
  - `backend/services/property/dictionary_link_service.py:61-69`（`room_id` 分支缺归属校验）
  - `backend/schemas/building_dict.py:353-358`（`DictionaryLinkRequest` 的 `building_id/room_id` 均为可选，未按 `biz_type` 禁用）
- **问题**：`link()` 只在 `body.building_id is not None` 时校验楼栋归属；当请求**只传 `room_id`、不传 `building_id`** 时，走的是「户室存在 → 户室所属楼栋 → 但**从不比对 `room_building.community_id != body.community_id`**」的分支：

  ```python
  # dictionary_link_service.py:61-69
  if body.room_id is not None:
      room = db.get(BdRoom, body.room_id)
      ...
      room_building = db.get(BdBuilding, room.building_id)
      if body.building_id is not None and room_building and room_building.id != body.building_id:
          raise ValidationError("户室与楼栋不匹配")   # ← 只校验「户室 vs 请求里的楼栋」
  # 缺：room_building.community_id != body.community_id 的归属校验
  ```

  对比同文件 `dict_ownership.validate_dict_ownership()`（`services/property/dict_ownership.py:49-62`）在主表单链路里**是有**这条校验的，说明是本接口的实现缺口而非口径差异。
- **触发场景（已实测）**
  ```bash
  # 户室 3644130 属于小区 A(45813373-…)；请求把单据绑到小区 B(42dd16f1-…)
  PUT /api/v1/admin/marketing/projects/1/dictionary-link
  {"community_id": "42dd16f1-1e6d-4ebd-952f-5d7bc7d4c1ce", "room_id": 3644130}
  → 200 {"success":true,"dict_status":"linked"}
  ```
  实测落库结果：`l4_marketing_projects.id=1` → `community_id=B, room_id=3644130`（该户室实际属于 A）。审计日志同步记录了这个脏变更（`before.community_id=8078a001… → after.community_id=42dd16f1…`）。
- **影响范围**：项目/线索/营销/房源四个 `dictionary-link` 端点共用该服务，均可写入「单据小区 ≠ 户室所属小区」。写入后该单据在**任何**后续编辑（含只改状态/发布态）时会被 `validate_dict_ownership` 以「字典户室不属于所选小区」**永久 400**，形成不可编辑的死单据；且字典统计（`linked_project_count`、小区户室数）随之失真。
- **修复建议**：`room_id` 分支补 `room_building.community_id != body.community_id` → 400；更彻底的做法是**直接复用** `dict_ownership.validate_dict_ownership(db, community_id=..., building_id=..., room_id=...)`，删除本服务内的重复校验（单一入口，避免两处口径漂移）。
- **验证**：修复后 `PUT .../dictionary-link {"community_id": B, "room_id": <A 的户室>}` 必须返回 400「字典户室不属于所选小区」。

### S2 · 归档（已合并）小区仍可被详情读取与 PATCH 修改

- **维度**：输入校验与权限控制 / 状态机
- **位置**
  - `backend/services/property/dict_read_service.py:400-404`（`get_community_detail` 只按 id 查，无 `is_active` 条件）
  - `backend/services/property/dict_write_service.py:583-596`（`patch_community` 同样只按 id 查）
- **问题**：合并后小区被置 `is_active=False`（软归档，`merger._archive_communities`），总览页通过 `Community.is_active.is_(True)` 过滤不可见；但详情/修正画像两个端点没有任何状态校验，归档小区可被直接操作。
- **触发场景（已实测）**
  ```bash
  # 师大新村(徐汇) 已被合并归档 is_active=false
  GET   /admin/building-dictionary/communities/bbffd266-…  → 200（返回完整画像）
  PATCH /admin/building-dictionary/communities/bbffd266-… {"ring":"内环内"} → 200，落库成功
  ```
- **影响范围**：
  1. 运营通过 URL/历史链接可对**已并入主档的子档**做画像修正，修正值在主档视角不可见（详情页从主档进），形成「改了看不见、且与主档数据冲突」的静默脏数据；
  2. 与 H3 修复的「解除合并可逆」口径冲突：解除合并回迁后，子档携带的是合并期间被偷偷改过的画像；
  3. 详情端点返回归档小区会让前端抽屉呈现一个「在总览里永远搜不到」的小区，用户误判为数据丢失。
- **修复建议**：`get_community_detail` / `patch_community` 增加 `is_active.is_(True)` 条件（或显式返回 409「该小区已并入『主档名』，请在主档维护」并给出 `merged_into_id`）。读接口建议返回 404 + 提示，写接口 409。
- **验证**：对 `is_active=false` 的小区 GET 详情应 404、PATCH 应 409；对主档操作不受影响。

## 二、高危缺陷 · 数据与稳定性（必须立即修复）

### H1 · 导入「单条目 512MB」防线与实际内存放大不符 —— 512m 容器仍会被打爆

- **维度**：数据库交互与性能 / 可用性
- **位置**
  - `backend/services/property/dict_import_loader.py:57-65`（`MAX_SINGLE_ENTRY_BYTES = 512MB`，注释称「与容器 mem_limit 对齐」）
  - `backend/services/property/dict_import_loader.py:392-396, 404-406`（仅按 `info.file_size` / 落盘大小拦截）
  - `backend/services/property/dict_parser.py:271-363`（`parse_community_txt` 一次性 `splitlines()` + `result.rooms` 列表）
- **问题**：防线按「**原始字节数**」设定，但解析链路的真实内存放大是 **13.1 倍**（实测，见下）。即 512MB 条目实际需要约 6.7GB 常驻内存，即使按 nginx 100MB 网关上限、包内单条目 38MB，也需要约 509MB —— 已经逼近 `docker-compose.yml:90` 的 `backend mem_limit: 512m`，而同进程还要承载 FastAPI/SQLAlchemy/其他业务。
- **实测数据（tracemalloc，同一份 GBK 数据）**

  | 输入字节 | 解析户室行 | 峰值内存 | 放大倍数 |
  |---|---|---|---|
  | 19.4 MB | 700,000 | 254 MB | 13.1× |
  | 38.7 MB | 1,400,000 | 509 MB | 13.1× |
  | 105.1 MB | 3,800,000 | 1,378 MB | 13.1× |

  （放大来源：`data.decode()` 生成 str 副本 → `text.splitlines()` 生成行列表 → 每行 `line.split(";")` 生成分段列表 → `result.rooms` 持有 4 元组。四份数据同时驻留。）

  > 注意：`dict_import_loader.py:60-61` 的注释自称「约 3-4× 膨胀」，**实测为 13.1×**，该注释严重低估了实际放大倍数——这也是防线定在 512MB 的认知来源，修复时须一并更正注释。
- **触发场景**：任一合法但偏大的单 txt（约 40MB，仍在网关 100MB 内、也远低于 512MB 单条目上限）经 `POST /admin/building-dictionary/import` 上传 → 后台线程 `parse_community_txt` → 容器 RSS 冲到 ~500MB+ → OOMKilled（`restart: unless-stopped` 后反复重启，任务永远停在 processing）。本周已修的「任务恢复」迁移只能事后把 processing 标记 failed，**无法阻止 OOM 本身**。
- **影响范围**：导入是运营高频动作，OOM 会连带打断同进程的其他 API 请求（FastAPI 单进程多线程），属**全站可用性**问题，而非仅导入失败。
- **修复建议**（按性价比排序）：
  1. 把单条目上限按「放大倍数」反算：`MAX_SINGLE_ENTRY_BYTES` 降到 **16MB**（16 × 13.1 ≈ 210MB，留一半余量），并在注释里写明放大倍数来源与实测方法；
  2. `parse_community_txt` 改流式：按行迭代（`io.StringIO(text)` 逐行）而不是 `splitlines()` 全量，且 `rooms` 落临时 CSV 而非内存列表（与 `load_community_by_copy` 的 COPY 链路天然契合）；
  3. 装载线程加内存闸门：解析前 `psutil.Process().memory_info().rss` 预检，超阈值直接失败并给出「请拆分单文件」提示。
- **⚠️未覆盖**：未在真实 512m 容器内做 OOM 复现（本机直接跑后端，无 mem_limit），倍数为本机 tracemalloc 实测；容器内由于 allocator 差异可能略低，但量级结论不变。

### H2 · 待审「小区」下新建的楼栋永久无法转正（审核链断链）

- **维度**：异常处理 / 状态机 / 契约一致性
- **位置**
  - `backend/services/property/dict_submit_service.py:239-246, 258-264`（`parent_kind="community"` 返回 `community_id`；`parent_kind="pending_community"` 返回 `community_id=None`）
  - `backend/services/property/dict_submit_service.py:375-394`（`submit_dict_chain` 在无实表小区时用 `pending_community` 作为楼栋父级）
  - `backend/services/property/building_review_service.py:454-459`（`_create_building_from_pending` 要求 `entry.community_id` 非空）
  - `backend/services/property/building_review_service.py:247-256`（`_resolve_create` 转正父级小区时**不回填子级的 `community_id`**）
- **问题**：录入端「新建小区 → 在该小区下新建楼栋」链路（`dict-address-picker` 的 `handleCreateCommunity` + `handleCreateBuilding`，前端 `index.tsx:325-393`）会落成：

  ```
  小区 pending(id=745)  status=pending
  楼栋 pending(id=746)  parent_kind=community, parent_id=745, parent_is_pending=true, community_id=NULL, community_scope=NULL
  ```

  父级小区 `create` 转正时，`_resolve_create` 只写 `entry.resolved_target_id` 并把**楼栋**（`kind=BUILDING`）的子级户室改指实表楼栋，**没有**把「父级是 pending 小区」的楼栋条目 `community_id` 回填成新小区 id。于是楼栋条目转正时命中 `_create_building_from_pending` 的守卫直接 400。
- **触发场景（已实测）**
  ```bash
  POST /admin/building-dictionary/pending {"kind":"community","name":"__AUDIT_CHAIN_COMM"}          → pending_id=745
  POST /admin/building-dictionary/pending {"kind":"building","name":"8号楼",
       "parent_kind":"pending_community","parent_id":"745"}                                          → pending_id=746
  POST /review/745/resolve {"action":"create"}   → 200 已落库（communities 新建成功）
  POST /review/746/resolve {"action":"create"}   → 400 {"code":400,"message":"楼栋 pending 缺少归属小区"}
  ```
  落库状态核对：`746` 仍为 `pending`，`community_id=NULL`，父级 `745` 已 `created` 且 `resolved_target_id=31311aa8-…`。
- **影响范围**：审核池里这类楼栋条目**永久卡死**，唯一出路是 merge/reject 掉——用户提交的新楼栋永远进不了字典，且前端 toast 只提示「请调整目标」，运营无从判断原因。这是本周 H2 修复（`parent_is_pending` 语义列）**没有覆盖到的另一半**：它修好了「待审楼栋下的户室」，但「待审小区下的楼栋」同样断链。
- **修复建议**：
  1. `_resolve_create` 在 `entry.kind == COMMUNITY` 落库成功后，同步 `UPDATE bd_pending_entries SET community_id = :new_id, community_scope = :new_id WHERE parent_is_pending = true AND parent_id = :entry_id AND kind = 'building'`（与既有「楼栋转正改指子级户室」对称）；
  2. 补一条幂等迁移，修复存量同类悬挂行（本次实测库内为 0 条，但线上存在同类路径产生的历史数据风险）；
  3. E2E 补用例：小区+楼栋两级 pending → 依次 create，两级都必须成功。
- **⚠️不确定**：`_check_topology` 对楼栋条目**是**生效的（父级 pending 时拦截），所以这条链路是「父级先转正后子级 400」，而不是「可绕过拓扑」；但对运营而言结果同样是死条目。

### H3 · 引用账本永久滞留：25 条 open 引用无任何收敛路径，`pending-backfill` 永远处理 0 条

- **维度**：异常处理与日志 / 数据一致性
- **位置**
  - `backend/services/property/building_review_backfill.py:163-185`（`run_pending_backfill`）
  - `backend/services/property/building_review_service.py:394-426`（`_resolve_reject`）
  - `backend/services/property/building_review_queue.py:85`（`reference_count = len(e.references or [])`）
- **问题（经实测修正后的准确根因）**：`run_pending_backfill` 的主循环是

  ```python
  for ref in refs:                              # refs = status='open' 的引用
      entry = db.get(BdPendingEntry, ref.pending_id)
      if not entry or not entry.resolved_target_id:
          continue                              # ← 不置终态、不计数、不记日志
      backfill_reference(db, ref, target_value=entry.resolved_target_id)
  ```

  即**只要 pending 条目的 `resolved_target_id` 为空，其 open 引用就被永久跳过**，且跳过分支完全静默（无日志、无计数）。实测库内 `open` 引用 **26 条**，其中 **25 条**的条目 `resolved_target_id IS NULL`，全部被这条 `continue` 静默丢弃：

  | 条目状态 | open 引用数 | `resolved_target_id` |
  |---|---|---|
  | `rejected` | 12 | 全为 NULL |
  | `pending` | 13 | 全为 NULL |

  这 25 条引用的 `biz_id` 全部指向**已不存在的项目**（`00000000-0000-0000-0000-09…` 系列，实测 `projects` 表 0 命中），属历史测试/审计脚本遗留的脏引用。

- **触发场景（已实测）**
  ```bash
  POST /admin/building-dictionary/review/pending-backfill
  → {"success":true,"message":"回填任务已执行，处理 0 条引用"}
  # 连点两次结果完全一致；库内 open 引用数恒为 26（本轮探针追加 1 条后为 26）
  ```

  同时实测确认**当前代码路径本身是收敛的**：新造「project 来源 + 带引用」的 pending，走 `reject`（带 target）→ 引用变 `resolved`、项目 `dict_status=linked`；走机器链路 `reject`（无 target）→ 引用变 `resolved`、房源 `dict_status=rejected`。**因此这不是「驳回时漏处理」，而是「历史脏数据 + 回填任务缺兜底分支」的组合缺陷**（上一轮报告 M5 的收敛修复只覆盖了「有 target」的路径）。

- **影响范围**：
  - 运营点「重试回填」永远显示「处理 0 条」，脏引用既不可见也不可清理，形成"永远成功但永远没变化"的假成功；
  - 审核池 `reference_count` 用 `len(e.references)`（含 open + resolved），与「待回填引用数」语义不符，运营看到的是历史累计而非待处理量；
  - 脏引用占用 `uq_bd_pending_ref_biz (biz_type, biz_id, field)` 唯一约束槽位，若未来同 id 单据被重建（测试环境重置、数据恢复），会因唯一约束无法写入新引用。

- **修复建议**：
  1. `run_pending_backfill` 的跳过分支必须收口：`entry` 不存在 / 条目已是终态且无 target → 按「无回填对象」调 `mark_reference_rejected` 或直接置 `RESOLVED` 并 `logger.warning`（与 `backfill_reference` 内部对脏数据的处理口径一致，`building_review_backfill.py:110-113`）；
  2. 补一次性幂等迁移：清理「`biz_id` 指向不存在单据」的 open 引用（可复用 `_is_valid_biz_id` + 存在性探测）；
  3. `reference_count` 改为 `sum(1 for r in e.references if r.status == OPEN)`，并同步前端列名（「引用」→「待回填」）；
  4. `run_pending_backfill` 返回值语义明确为「本次实际回填条数」，跳过数单独记日志。

- **验证**：清理后连续两次 `pending-backfill` 均应返回「处理 0 条」且库内 `open` 引用数为 0；`reference_count` 与实际 open 数一致。
- **⚠️不确定**：这 25 条脏引用的具体产生路径无法从现有数据完全反推（`projects` 表已无对应行、`bd_pending_entries` 也无 `resolved_by`），可能是历史 E2E/审计脚本绕过服务层直写 DB 造成；本报告的结论限定为「当前代码无兜底收敛路径」这一可复现事实，不推定其来源。

## 三、中危问题 · 性能（本迭代内修复）

### P1 · `bd_buildings.room_count` 对账迁移在 53 万行上逐行相关子查询 —— 启动阻塞 1.5s+ 且随数据量线性恶化

- **维度**：数据库交互与性能
- **位置**：`backend/migrations/_bd_audit_20261017_fixes.py:250-270`（`_reconcile_room_count`），注册在 `migrations/__init__.py:409`（每次启动都执行）
- **问题**：SQL 为 `SELECT bd.id, (SELECT count(*) FROM bd_rooms r WHERE r.building_id = bd.id) FROM bd_buildings bd`，对 530,894 个楼栋各执行一次相关子查询。
- **实测（`EXPLAIN ANALYZE`）**：
  ```
  Update on bd_buildings  (actual time=1455.695..1455.718 rows=0)
    SubPlan 2 -> Aggregate (actual time=0.002..0.002 rows=1 loops=530894)
       -> Index Only Scan using uq_bd_room_no ... (actual time=0.001..0.002 rows=14 loops=530894)
  Execution Time: 1476.766 ms
  ```
  即**每次后端启动固定多花约 1.5 秒**，且 `loops=530894` 说明成本与楼栋数成正比（上海全域再翻倍即 3 秒）。
- **影响范围**：启动耗时（开发环境 `--reload` 每次改代码都触发一次迁移，本地体感明显）；对账本身只在有漂移时才需要写。
- **修复建议**：改成一次聚合 JOIN：
  ```sql
  UPDATE bd_buildings b SET room_count = c.cnt
  FROM (SELECT building_id, count(*) cnt FROM bd_rooms GROUP BY building_id) c
  WHERE b.id = c.building_id AND b.room_count IS DISTINCT FROM c.cnt;
  ```
  该写法一次聚合扫描 `bd_rooms`（7.3M 行）即可。**实测改写后耗时 571ms**（同库同事务内 `ROLLBACK` 验证，`rows=0` 说明当前无漂移），相比原写法 1477ms 降低约 61%；进一步可加「仅当存在漂移时执行」的快速预检，把无漂移场景压到 <50ms。

### P2 · 审核池 `status` 查询参数未做枚举校验 —— 非法值直接 500

- **维度**：输入校验 / 异常处理
- **位置**：`backend/routers/property/building_dict.py:377`（`status: Annotated[str | None, Query(max_length=20)]`）、`backend/services/property/building_review_queue.py:30`（直接 `filter(BdPendingEntry.status == status)`）
- **问题**：`status` 是自由字符串，SQLAlchemy 会把它绑成 `bdentrystatus` 枚举值，非法值在 PG 层抛 `InvalidTextRepresentation`，被全局处理器映射成 500。
- **实测**：
  ```bash
  GET /admin/building-dictionary/review?status=bogus
  → 500 {"code":500,"message":"数据格式错误或超出字段长度限制"}
  ```
  （PG 原始错误：`invalid input value for enum bdentrystatus: "bogus"`）
- **影响范围**：前端筛选下拉是固定值所以正常路径不触发；但任何脚本/爬虫/手改 URL 都能稳定打出 500 并刷 `SQLAlchemyError` 日志，属「可被外部输入触发的 500」。
- **修复建议**：`status` 改为 `BdEntryStatus | None`（FastAPI 自动 422），或在 service 层做 `_STATUS_VALUES` 白名单校验 → 400。
- **验证**：`?status=bogus` 应返回 400/422 而非 500。

### P3 · 楼栋详情返回全量户室，无分页/上限（单楼栋最多 928 户）

- **维度**：数据库交互与性能 / 契约一致性
- **位置**：`backend/services/property/dict_read_service.py:604-627`（`room_items` 由 `building.rooms` 全量构造）、`backend/routers/property/building_dict.py:252-271`
- **问题**：`BdBuilding.rooms` 关系是 `lazy="selectin"`，详情接口一次性加载并序列化该楼栋**全部**户室；实测库内最大楼栋 **928 户**（`bd_rooms` 按 `building_id` 聚合 top1），>500 户的楼栋 26 个、>300 户的 163 个。当前实测响应 20~30ms / 928 条（响应体 87.9KB），尚可接受；但接口无 `page_size` 上限，且前端 `dict-address-picker` 的户室网格是**一次全渲染**（`visibleRooms.map`），928 个按钮同屏。
- **影响范围**：当前量级可用；一旦出现上千户的超大楼栋（或未来接入其他城市数据），单次响应体与前端渲染都会线性膨胀；与同模块楼栋列表「20/页」的分页口径也不一致。
- **修复建议**：详情接口增加 `page/page_size`（默认 200，上限 500）并对 `rooms` 分页；前端户室网格配合「加载更多」。若产品要求「一屏看全层」，至少按楼层分组懒加载（已有 `/floors` 端点可复用）。
- **⚠️未覆盖**：未在浏览器侧实测 928 按钮的渲染耗时（本报告只测了接口耗时与响应体大小）。

### P4 · 导入上传：DB 写失败时已落盘文件不清理（孤儿文件堆积）

- **维度**：资源泄漏 / 可维护性
- **位置**：`backend/services/property/dict_import_service.py:101-123`
- **问题**：文件先流式写入 `temp/uploads/bd_{uuid}.txt`，随后才 `db.add(task); db.commit()`。若 commit 失败（如文件名超 `String(255)`、DB 抖动），`except FileProcessingError` 只覆盖「超限」分支，**DB 异常不在捕获范围内**，文件留在磁盘且没有任何任务行指向它——`cleanup_expired_archives()` 只按 `bd_*` 前缀 + 90 天清理，会留下 90 天孤儿。
- **实测**：用 300 字符文件名上传（`filename` 列 `String(255)`）：
  ```bash
  POST /admin/building-dictionary/import  (filename=bbb…300.txt)
  → 500 {"code":500,"message":"数据格式错误或超出字段长度限制"}
  # temp/uploads 文件数 124 → 125，且 bd_import_tasks 无对应行
  ```
- **影响范围**：可被反复触发（不消耗磁盘限额的微量泄漏，但每次 100MB 上限下最坏 100MB/次）；同时 500 而非 422，运营无从知道是文件名太长。
- **修复建议**：
  1. `filename` 在 `create_task` 入口截断/校验（`max_length=255` 的 Pydantic 校验或 `filename[:255]`）→ 422 明确提示；
  2. 把 `db.add/commit` 包进 `try/except`，失败时 `stored_path.unlink(missing_ok=True)` 后重抛。
- **验证**：超长文件名上传应 422，且 `temp/uploads` 文件数不变。

## 四、中低危 / 合规

### L1 · 批量补录的逐条重试分支只捕获 `IntegrityError`，其他 DB 异常会让 `_promote_matching_pendings` 整体跳过

- 位置：`backend/services/property/dict_write_service.py:203-222`（楼栋）/`292-310`（户室）
- 问题：主路径失败后走「逐条 commit 重试」，该分支**只捕获 `IntegrityError`**：
  1. 若逐条重试过程中抛出其他 DB 异常（连接中断、超时、序列化失败），异常直接冒到路由 → 500，而此时**前面几条已 commit 成功**，`_promote_matching_pendings`（第 224 行）不会执行 → 楼栋/户室已入库但对应的待审 pending 不转正、引用不回填，形成「字典有了、审核池还挂着」的漂移；
  2. 重试分支里 `created_map[no] = building.id` 在 `db.commit()` **之后**读取，Session 默认 `expire_on_commit=True`（已实测确认），访问 `building.id` 会额外发 1 条 SELECT 回查——每补录一条多一次往返（批量上限 60 栋 / 200 户，最坏多 200 次往返）。
- **实测确认**：`expire_on_commit=True`，`commit()` 后访问主键会触发 1 次 refresh 查询（`before_cursor_execute` 计数验证）。
- 影响：第 1 点低概率（需并发撞 uq 后又有 DB 异常）但会造成数据漂移；第 2 点是确定的性能损耗，只在重试路径生效。
- 建议：重试循环改用 `db.begin_nested()`（SAVEPOINT）逐条隔离，异常时只回滚当条；`created_map` 改为在 `flush()` 后立即取值（主路径已是 `flush()` 后取，重试路径应保持一致）；`_promote_matching_pendings` 放到 `finally` 或确保异常路径也执行。

### L2 · `_resolve_room_parent` / `_create_room_from_pending` 的 `int()` 转换无异常兜底

- 位置：`backend/services/property/building_review_service.py:228, 230`（`int(parent_entry.resolved_target_id)` / `int(entry.parent_id)`）
- 问题：`resolved_target_id` 是 `String(64)`，若历史/脚本写入非数字串，`int()` 抛 `ValueError` → 500（而非 400）。同类问题在 `backfill_reference.apply_backfill` 里已用 try/except 包住，审核链路没有。
- 建议：统一用「解析失败 → `ValidationError("父级数据异常，请联系管理员")`」。

### L3 · 坐标（lng/lat）无值域校验

- 位置：`backend/schemas/building_dict.py:214-215`（`BdCommunityPatchRequest.lng/lat`）、`257-258`（`BdCommunityCreateRequest.lng/lat`）
- 实测：`PATCH {"lng":999.5,"lat":-888.1}` → 200 并原样落库。
- 现状数据：库内已有 **536 条** `lng=0.0, lat=0.0` 的占位坐标（导入链路未过滤）。
- 影响：BD-09 坐标越界会让后续地图/距离计算出现异常值；`0,0` 占位会被当作「有坐标」展示（SRS 说「约 97% 楼栋带坐标」，这 536 条实为无效）。
- 建议：`lng` 加 `ge=73, le=136`、`lat` 加 `ge=3, le=54`；导入解析时对 `(0,0)` 与越界值置空。

### L4 · 类型强转仍在：字典模块 13 处 `as unknown as`

- 位置（`grep` 实测）：`community-drawer.tsx:93,125`、`floor-room-panel.tsx:66,74`、`community-images-section.tsx:41`、`merge-dialog.tsx:55`、`review-target-picker.tsx:100,119,138`、`review-client.tsx:76`、`import-client.tsx:91`、`dict-address-picker/index.tsx:296`
- 问题：`pnpm gen-api` 已生成完整类型（`api-types.d.ts` 本轮 +23302 行），这些强转绕过了生成类型，接口字段改名时不会编译报错。属上一轮报告已提、本轮未收敛的技术债。
- 建议：逐个改为直接消费 `components["schemas"]["..."]`，`tsc` 会在字段不匹配时报错。

### L5 · `retry_backfill` 的 `noqa: ARG002` 注释与实际不符

- 位置：`backend/services/property/building_review_service.py:551-557`
- 问题：注释写「审计由 run_pending_backfill 内部记录」，但 `building_review_backfill.py` 全文**没有任何审计调用**（`grep audit` 仅命中 docstring）。运维点「重试回填」这个写操作**不留审计痕迹**，与 NFR-03 不符。
- 建议：`retry_backfill` 内补 `operation_log_service.log_action(action="bd_pending_backfill_retry", ...)`，或修正注释并接受无审计（需产品确认）。
