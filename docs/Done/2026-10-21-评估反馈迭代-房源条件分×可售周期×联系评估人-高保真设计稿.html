Steep · 评估反馈迭代 · High-Fidelity Design Spec

让评估反馈变成一句人话，
和一个能打出去的电话

v1.0 · 2026-10-21 admin 5 处 · 小程序 3 页 · C 端 Web 1 处 房源条件分 1–5 装修后可售天数 联系评估人 5 项后端依赖 · 逐项标注降级

当前评估反馈只回 一个价格 + 一段备注（LeadEvalHistory 四列：eval_price / remark / evaluator_id / evaluated_at）。员工看完这条反馈，仍要自己判断「这套房子好不好、值不值得跟」； 客户看完只有一个数字，没有参照系，也没法就这个数字找人问一句 —— 反馈链路在价格处断掉了。

本轮做三件事把链路接上：① 房源条件分（单一综合分 1–5）给「好不好」一个刻度； ② 装修后可售天数给「多久能出手」一个预期；③ 联系评估人给「有疑问找谁」一个出口。 三项都长在既有卡片里，不新增页面、不改员工现有操作路径。

设计纪律：数字退位、结论前置。详情页首屏先给一句人话结论（serif 引文），评分与周期是它的佐证， 而不是反过来让人去读三个数字。任何裸数据旁边都必须有翻译 —— 45 天 旁永远有 约 1.5 个月，4 分 旁永远有 良好。

SEC 00 · 口径

三项新增，各自的锚点与降级规则

三项信息都必须是员工能快速给、客户能一眼读的。下面的锚点表决定了「4 分」在不同员工手里 是否指同一件事 —— 没有锚点的一致性，跨人评分就等于噪声。

表 1 · 房源条件分锚点（单一综合分，1–5）

分档只看两件员工一定掌握的事实：户型是否好卖、楼层是否有折价。 综合分 = 员工的整体判断，锚点只保证同一事实不出两种结论。

分值短标签锚点（员工自我对照）典型情况
5 / 5 优质 户型方正通透、当前楼层段在小区里最好卖，几乎无硬伤 南北通透三居 · 中高楼层 · 无遮挡
4 / 5 良好 主流户型，楼层可接受，有 1 项需在带看时说清的短板 南向两居 · 中间楼层 · 采光一般
3 / 5 一般 户型或楼层有一项明显折价，需要靠价格补 南北两居 · 顶楼 / 临街
2 / 5 偏弱 户型与楼层同时偏弱，或存在硬伤需重装化解 朝北异形 · 低楼层 · 需重装
1 / 5 难售 结构性难卖，通常伴随长周期或需要显著让价 暗厅暗卫 · 一层 · 产权复杂
为什么合成一个分而不是拆户型 / 楼层：拆分后员工要打两次分、客户要读两个数字再自己综合， 与「对数据不敏感」直接冲突。拆分的价值（可统计哪一项拖分）暂时让位于可读性 —— 若后续要做 批量分析，可用 remark 中的结构化标签补，不必改评分结构。

表 2 · 装修后可售天数：录入连续值，展示分档

员工只填一个天数（整数，1–365），系统派生出档位短句与「约 N 个月」的人话翻译。 存储保留连续值，是为了将来能算均值、能做「我的预估 vs 实际」对比。

区间档位词展示文案卡片形态
≤ 30 天快 预计 N 天可售出 · 约 1 个月 深底 vchip--days rush（Rust 实底白字，全列表唯一强色块）
31 – 60 天正常 预计 N 天可售出 · 约 1.5 个月 Fog 底 Ash 字
61 – 90 天偏慢 预计 N 天可售出 · 约 3 个月 Fog 底 Ash 字
> 90 天慢 预计 N 天可售出 · 约 N/30 个月 灰底 Graphite 字（slow，弱化但仍在）
基线对比是可选增强，不是必答项：「快于小区平均 N 天」需要小区级平均去化天数， 当前后端无此聚合（services/reports/aggregations.py 现有 absorption_months 是商圈级、按月、非单套）。设计为有基线才显示、无基线只显示档位， 不伪造对比。降级形态见 ART 05 右侧第二台手机。

表 3 · 联系评估人：可见性与留痕

复用项目既有的 PublicConsultantContact 范式（routers/public/projects.py:333）： 列表 / 详情只给脱敏号，真实号走独立端点按需拉取，且每次拉取落入审计与跟进记录。既不浪费也无隐蔽收集。

角色看到什么动作留痕
C 端客户（线索创建人） 评估人昵称 + 角色 + 脱敏号 138****6688 「拨打」按钮 → 拉真实号 → 面板内 拨打电话 / 复制号码 写入 lead_followups：method=phone，content 形如「客户致电评估人 王建房」
内部员工（admin / operator） 同上（admin 侧直接给真实号，减少一次点击） 小程序：拨号面板；Web：tel: 直呼 小程序同样写跟进；Web 侧写审计日志（audit_logs）
非归属员工（无该线索权限） 不渲染评估人区块 — 端点返回 403

表 4 · 模型变更：lead_eval_histories 新增两列

列类型可空语义与取值
condition_score SmallInteger 是 （存量兼容） 房源条件分 1–5。DB 层加 CHECK (condition_score BETWEEN 1 AND 5)； Pydantic 层 Optional[int] = Field(None, ge=1, le=5)。 可空是为了存量记录，新写入路径强制非空（由 Schema 层校验）。
expected_sale_days SmallInteger 是 （存量兼容） 装修后预计可售天数。DB 层加 CHECK (expected_sale_days BETWEEN 1 AND 365)； Pydantic Optional[int] = Field(None, ge=1, le=365)。 档位词（快 / 正常 / 偏慢 / 慢）不入库，由前端纯函数派生 —— 档位阈值会调，不该改数据。
为什么不加 score_tier / cycle_tier 冗余列： 档位是展示层的阈值判断，写进库意味着阈值一改就要刷全表。 派生逻辑用一份共享纯函数（前端 lib/lead-verdict.ts、后端 utils/lead_verdict.py）保证两端一致。

表 7 · 迁移脚本

新建 backend/migrations/add_lead_eval_verdict_fields.py， 参照既有 add_lead_eval_history_and_expected_price.py 的写法（_column_exists 幂等检查）：

步骤内容
1 · 幂等加列 _column_exists(engine, "lead_eval_histories", "condition_score") → 不存在则 ALTER TABLE ... ADD COLUMN condition_score SMALLINT；expected_sale_days 同理。
2 · 加约束 同一 engine.begin() 内加 CHECK 约束（PowergreSQL 12+ 支持 ADD CONSTRAINT ... CHECK ... NOT VALID 再 VALIDATE， 避免大表长时间持锁；表格当前量级小，可直接 ADD）。
3 · 注册 在 migrations/__init__.py 的 import 区与执行序列末尾注册，紧跟 add_lead_eval_history_and_expected_price 之后。
4 · 回滚 在 migrations/compensations/ 登记 DROP COLUMN 补偿（既有框架已支持）。
不加 NOT NULL + 默认值：存量 LeadEvalHistory 行没有真实评分， 用默认值填空会把「没评过」伪装成「评了 3 分」。可空 + 前端降级（ART 04 的灰底 chip）是唯一诚实做法。
