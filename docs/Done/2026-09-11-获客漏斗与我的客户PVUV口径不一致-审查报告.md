# 获客漏斗看板 PV/UV 与小程序「我的客户」不一致 审查报告

- 审查日期：2026-09-11
- 审查对象：
  - 后台 `/admin/growth-center/funnel`（漏斗看板，`GrowthFunnelService`）
  - 小程序「我的客户」统计卡 `pages/customers/mine`（`MyCustomerService.share_stats`）
- 审查方式：源码逐层比对 + 本地开发库（PostgreSQL 16，`profo-db-1:5432`）实测复算 + 直接调用运行中的后端接口（`localhost:8000`）取真值
- 代码基线：工作区当前 HEAD（含 `932df120 refactor(share-stats): 统一分享统计的线索过滤口径`）

## 一、结论摘要

**这不是计数缺陷（bug），而是两端四个维度的统计口径不同。** 证据：把口径拉齐到「同一员工 × 同一链路」时，两端数值**完全一致**（见第三节还原表）。

用户观感「漏斗远低于我的客户」，直接来源是两个口径叠加：

1. **聚合范围不同**：漏斗 Tab 一次只展示**一个模块**的**模块全量**（含未归因自然流量）；「我的客户」展示**四链路求和**且**只含归属当前员工**的流量。
2. **UV 聚合方式不同**：小程序把四条链路的 UV **直接相加**（招募=登录态 `openid_hash`，其余=匿名 `visitor_id`，两个命名空间、两种去重强度），得到的是一个**语义不成立的"UV 和"**，数值系统性偏高。

叠加本库实测：招募 Tab UV=4（`openid_hash` 把 76 次打开压到 4 个不同登录用户）对小程序累计 UV=32 —— 差 8 倍，这就是"远低于"的观感来源。

> **⚠️ 未覆盖**：本次只在本地开发库验证（数据量小、时间跨度 2026-08-15 ~ 08-29）。生产库若存在**超过 90 天**的历史埋点，还会有第五个差异（窗口上限 90 天 vs 累计全时段），偏差会进一步放大。

## 二、两端口径对照（源码事实）

| 维度 | 漏斗看板 `/admin/growth-center/funnel` | 小程序「我的客户」统计卡 |
|---|---|---|
| 入口 | `/funnel?module=&days=` | `/public/customers/my/share-stats` |
| 服务 | `backend/services/growth_center/funnel.py` | `backend/services/growth_center/my_customers.py:198` → `services/utils/share_stats.py` |
| **统计范围** | **单模块**（Recruit/Valuation/Booking/Sheet，Tab 切换） | **四链路逐字段求和** |
| **归属过滤** | 模块**全量**（不按 referrer 过滤，含未归因流量） | 强制 `referrer == 当前登录员工` |
| **时间窗口** | **近 7 / 30 / 90 天**（`FUNNEL_DAYS_OPTIONS`，**无累计选项**） | **累计（全时段，无时间过滤）** + 今日（CST 自然日） |

| **UV 去重键** | 招募=`RecruitVisit.openid_hash`；其余=`visitor_id` | 各链路沿用自身键，**四值直接相加，不做跨链路去重** |

- 小程序 UV 求和：`my_customers.py:216-222`

  ```python
  parts = [Valuation..., PublicProject..., PropertySheet..., Recruit...]
  ```

- 累计口径无时间过滤：`share_stats.py:81-97`（累计 4 项无时间条件，仅今日 4 项带 `t_start/t_end`）

## 四、「远低于」逐项归因

| 用户可能在看的位置 | 漏斗值 | 小程序累计 | 差距性质 |
|---|---|---|---|
| **招募 Tab（默认）UV** | 4 | 32 | 低 **8 倍** —— `openid_hash` 登录态去重（76 次打开 → 4 人）+ 单模块 vs 四链路求和 |
| 招募 Tab **PV** | 76 | 57 | 反而**更高**（漏斗含 49 次未归因自然流量） |
| **估价 Tab** | PV 1 / UV 1 | 57 / 32 | 极低 —— 该链路本就只有 1 次访问埋点 |
| **房源单 Tab** | PV 0 / UV 0 | 57 / 32 | 极低 —— 本库 `property_sheet_visits` **0 行**（埋点未产生数据，非计算错误） |
| **员工下钻表（唐欣帆1 行）** | 招募 23 / 4 | 招募段 23 / 4 | **一致**，此处不会出现差异 |

**招募链路是本库 UV 差距的主因**：`count(*) = 76`，`count(distinct openid_hash) = 4`（76 行 `openid_hash` 全非空），PV:UV ≈ 19:1。而小程序把这条"重去重"的 UV 与另外三条匿名 `visitor_id` 的 UV 相加，分母口径不同却直接相加，得到 32。

## 五、问题清单

### P0｜小程序「访客 UV」由四条链路 UV 直接相加，语义不成立

`MyCustomerService.share_stats` 对 8 个字段一律 `sum()`，其中 `uv` 跨越两种互不可比的去重键：

- 招募：`openid_hash`（登录态，**按人**去重，重去重）
- 估价 / 预约 / 房源单：`visitor_id`（匿名，**按设备**去重，轻去重）

后果：同一个客户在"房源→估价→房源单"三条链路各出现一次，会被计成 **3 个 UV**；这是"我的客户 UV 远高于任一单链路漏斗 UV"的直接来源。虽然页面脚注已写"各线 UV 口径不同，数据不可横向对比"（`pages/customers/mine/index.wxml:57`），但**卡片仍把不可相加的数求了和**，展示口径与脚注自相矛盾。

- 相关：`backend/services/growth_center/my_customers.py:198-222`、`backend/services/utils/share_stats.py:32-99`

### P1｜漏斗看板无「累计 / 全部时间」口径，两端无法对账

漏斗窗口硬编码 `[7, 30, 90]`（`funnel-constants.ts:14`），而「我的客户」展示的是**全时段累计**。运营在漏斗页找不到任何一个窗口能与小程序"累计"行对齐；生产库沉淀超过 90 天后，漏斗会**系统性低于**累计值。

### P1｜默认 Tab 为「招募」且不展示四链路合计，第一屏必然对不上

`parseFunnelTab` 默认 `recruit`（`funnel-constants.ts:22-27`），首屏只看到招募单模块、且招募是四链路中 UV 去重最狠的一条。用户拿它对比"我的客户"的四链路合计，必然得出"远低于"。

此外漏斗页脚注只解释了"UV 不可跨模块横向对比"，**未说明"本页是单模块全量 / 不含四链路合计"**，缺少防误读提示。

### P2｜招募 PV 含大量未归因自然流量，放大 PV 与 UV 的割裂

本库招募 76 次打开中 **49 次未归因**（`referrer_employee_id is null`），占 64%。因此招募 Tab 的 PV 远大于归属该员工的 PV（23），而 UV 又只有 4，同一张卡上 PV/UV 比例失真感很强。这是既有设计（"打开含非分享自然流量，转化率可 >100%"），但缺少可视化提示。

### P2｜附带发现：漏斗组件硬编码色值，偏离 Steep 视觉规范

| 文件 | 行 | 问题 |
|---|---|---|
| `funnel/_components/funnel-view.tsx` | 33、43 | `border-[#ececee]` 裸色值（应用 `border-dove/30` 等令牌透明度） |
| `funnel/_components/funnel-compare.tsx` | 102 | amber 三件套 `bg-[#fef3c7] border-[#f5d97a] text-[#92400e]`，规范明确禁用 amber |
| `funnel/_components/funnel-stats.tsx` | 24 | `bg-[#3a3d42]` 裸灰阶 |

（与本次数据问题无因果关系，顺带记录。）

## 六、修复建议

### 方案 A（推荐，最小改动）：让「我的客户」的 UV 不再是一个假求和

任选其一，改动均在 `my_customers.py:198-222` 与 `pages/customers/mine/*`：

1. **拆开展示**：卡片 `访客 UV` 改为两格 ——「登录访客 UV（招募）」与「匿名访客 UV（估价/预约/房源单，跨链路去重后取并集）」；
2. **保守做法**：把卡片 `访客 UV` 字段直接下线，只保留「分享 / 打开 PV / 留资」三个可跨链路求和的指标，UV 移入各链路明细；
3. **最小代价兜底**：不改接口，仅把 `累计/今日` 行的 UV 标注改为「各链路 UV 之和（非去重访客数）」。

### 方案 B：漏斗看板补「累计」口径，使两端可对账

- 在 `FUNNEL_DAYS_OPTIONS` 增补 `0 = 累计（不限窗口）`，`resolve_window` 侧对 `days<=0` 返回全时段左开窗口（`start` 取 `datetime.min` 的时区安全替代，如 `2000-01-01`）；
- 或退一步：在漏斗页右上角增加「查看口径对照」浮层，说明「同一员工同一链路，与小程序对应链路数值恒等，差异只来自求和/窗口」。

### 方案 C：漏斗页显式提供「四链路合计」行（UV 分列、不相加）

在 `FunnelCompare` 底部增加合计行，但 **UV 必须拆成 `openid_hash` / `visitor_id` 两列**分别求和，避免把方案 A 的错误复制到后台。

### 方案 D：修正默认视图

`parseFunnelTab` 默认值改为 `compare`（全部对比），或把 `recruit` 的默认 `days` 从 30 改为 90，减少"打开即对不上"的第一印象。

## 九、追加排查：用户反馈「30 日只有 4 个 UV，而我的客户今日 UV 就有 10 个」

> 追加时间：2026-09-11 22:55。该现象在**单一数据源内数学上不可能**（30 日窗口必然包含今日），因此优先排查"两侧是否同源"。结论：**否——两侧读的是两个不同的数据库。**

### 9.1 决定性证据：本地库与线上库是两份数据

| 项 | 本地 `http://127.0.0.1:8000`（容器 `profo-db-1`） | 线上 `https://fangmengchina.com` |
|---|---|---|
| `/public/stats/platform` | `{owners:207, on_sale:3, sold:294}` | `{owners:208, on_sale:7, sold:294}` |
| 2026-09-11 今日访问埋点 | **0 条**（四张 visit 表全部为 0） | 有今日活跃数据（小程序今日 UV=10 的来源） |
| 2026-09-11 今日线索 / 分享 | **0 / 0 条** | — |
| 各表最后一条数据 | `recruit_visits` 2026-08-29、`leads` 2026-08-30、`recruit_leads` 2026-08-15、`project_bookings` 2026-08-29 | — |

**本地库根本没有"今日"的任何访问记录**，不可能产生"今日 UV 10"。故小程序读的不是这份库。

### 9.2 数据源路由（为什么两边不一致）

| 端 | 配置位置 | 实际请求地址 |
|---|---|---|
| 后台前端（含本地 `localhost:3000`） | `frontend/src/lib/config.ts:17`（`NEXT_PUBLIC_API_URL`），`frontend/` 下**不存在 `.env.local`**，只有 `.env.example` → 走默认值 | **`http://127.0.0.1:8000`**（本地库） |
| 小程序 | `miniapp/utils/config.ts:12-17`，`develop` / `trial` / `release` **三个环境全部** | **`https://fangmengchina.com/api/v1`**（线上库） |

即：**本地后台 = 本地库（数据停在 2026-08-30）；微信开发者工具里的小程序 = 线上库（有今日数据）**。这是最典型的"本地调后台 + 小程序连线上"联调场景，`4` 与 `10` 分别来自两个库，不可相减比较。

### 9.3 30 秒自查（确认自己在看哪份数据）

1. 打开 `/admin/growth-center/overview`，看「今日线索」卡 —— **为 0** 说明是本地库；
2. 或看漏斗页「招募 · 打开 PV」—— **恰好 76** 说明是本地库（本报告第三节实测值）；
3. 或打开任一线索列表，最新线索时间停在 **2026-08-30** 之前 → 本地库。

### 9.4 处置建议

- **想验证真实线上口径**：改用线上后台 `https://fangmengchina.com/admin/growth-center/funnel`（与小程序同库），此时回到第三节/第四节口径表——招募单模块 30 天 UV 对四链路合计今日 UV，仍不是同一指标，UV 侧仍需按 P0 修复。

- **不建议**为对齐两端而修改任何统计逻辑 —— 本次差异与计数实现无关。

## 十、受控实验（生产语境）：注入 UV 数据验证 admin 是否实时同步

> 追加时间：2026-09-11 22:59。用户在**生产环境**观察到「30 日 4 个 UV < 今日 10 个 UV」。为排除"admin 读取滞后/缓存/少算"，在**本地测试环境**做受控注入实验：造 10 个新 UV，看 admin 是否跟着变。

### 10.1 实验设计

向本地库 `recruit_visits` 注入 10 行，`referrer_employee_id='admin-user'`、10 个**互不相同**的 `openid_hash`、`entered_at=now()`（即"今天来的 10 个新访客"），标记为 `id like 'diag-visit-%'` 便于回收。

### 10.2 实验结果：两端同步 +10，无任何滞后

| 观测口径 | 注入前 | 注入后 | 增量 |
|---|---|---|---|
| admin 漏斗 · 招募 · **近 1 天** PV / UV | 0 / 0 | **10 / 10** | +10 / +10 |
| admin 漏斗 · 招募 · **近 30 天** PV / UV | 76 / 4 | **86 / 14** | +10 / +10 |
| admin 漏斗 · 招募 · **员工下钻（唐欣帆1）** | 23 / 4 | **33 / 14** | +10 / +10 |
| 我的客户 · 招募段 · **今日** PV / UV | 0 / 0 | **10 / 10** | +10 / +10 |
| 我的客户 · 招募段 · **累计** PV / UV | 23 / 4 | **33 / 14** | +10 / +10 |

**关键：admin 侧是通过完整 Next.js 16 页面链路（`GET localhost:3000/admin/growth-center/funnel?module=recruit&days=30`，带登录 cookie 取真实渲染 HTML）验证的**，不是只打后端 API。页面 HTML 中渲染出的数值序列为 `21 / 86 / 14`（分享 / 打开 PV / 打开 UV），与后端 API、与我的客户口径**三方一致**。

### 10.3 结论

1. **admin 漏斗的读取链路是实时的**：无 Next Data Cache、无 Router Cache、无 nginx 缓存（已核对 `profo.nginx.backup`：全局无 `proxy_cache`，仅静态资源 `expires`）、无少算；
2. **不存在"admin 统计不到我的客户那些访问"的情况**——同一链路同一员工，注入多少，两边就同步变多少；
3. 因此**生产环境的差异不可能来自计数逻辑**，只能来自口径。

### 10.4 纯逻辑推导：为什么生产上「今日 10」可以大于「30 日 4」

前提（均为源码事实）：

- 我的客户「今日 UV」= **四链路 UV 相加**（`my_customers.py:216-222`）；
- admin 漏斗「招募 Tab · 30 日 UV」**只含招募一条链路**；
- 招募 UV 去重键 = `openid_hash`（按**人**）；估价/预约/房源单 = `visitor_id`（按**设备**）；
- **三条匿名链路共用同一个设备 UUID**（`miniapp/utils/visitor.ts:9-29`，storage key `profo_visitor_id`，跨会话稳定）。

推导：

> 招募今日 UV ≤ 招募 30 日 UV = **4**
> ⟹ 我的客户「今日 UV 10」中，**至少 6 个必然来自估价/预约/房源单**这三条匿名链路
> ⟹ 这 6 个是被**同一设备 UUID 在三条链路上重复计数**的结果（一个客户逛 3 条链路 = 3 个"UV"）
> ⟹ 「10」对应的真实人数很可能就是 **4 个人左右**，与招募 30 日 UV 的 4 完全自洽

本地库已实证同设备跨链路重复：`visitor_id = bb18624c-8f12-45cd-9c76-ab90dbdbd05d` **同时出现在 `project_visits` 与 `valuation_visits`**（该数据很稀疏的情况下都能撞上，生产必然更严重）。

### 10.5 生产自查（3 步，无需改代码）

1. 漏斗页依次切 **房源预约 / 估价 / 房源单** 三个 Tab，窗口统一选「近 30 天」，记录各自的**打开 UV**；
2. 三个数相加，得到"匿名链路 UV 合计"。**它应当 ≥ 我的客户「今日 UV」(10)**（今日 ⊆ 近 30 天）——若成立，说明口径自洽，无缺陷；
3. 差额部分 = 匿名链路对同一设备的**重复计数**，即为 P0 问题（本报告第五节）在生产上的量化体现。

> **⚠️ 口径更正**：第九节把用户现象归因为"本地库 vs 线上库"。该结论对**当时的观察环境**成立（本地库当日的确 0 条埋点），但用户在**生产**语境下提出该现象，故以本节为准：**生产侧的差异是口径问题（单链路 vs 四链路求和 + 匿名 UV 按设备跨链路重复计数），而非环境或计数缺陷。**

### 11.1 关键前提：项目上线不足 90 天 ⟹ 窗口差异被彻底排除

既然全站数据都落在 90 天内，漏斗「近 90 天」**就等于全时段**，与我的客户「累计」窗口**完全等价**。第九～十节讨论的"窗口不可比"在生产上**不成立**，可以不考虑。

### 11.2 恒等式（本报告的核心判据）

因为漏斗是**模块全量**、我的客户是**该员工归属**，且我的客户 = 四链路归属值相加，所以必然成立：

> **漏斗四个 Tab 的同一指标之和 ≥ 我的客户对应指标**

| 指标 | 我的客户（累计） | admin 招募 Tab（90 天，单模块） | 其余三条链路**应当**贡献 | admin 四 Tab 相加**应有值** |
|---|---:|---:|---:|---:|
| 分享 | 47 | 25 | ≥ **22** | ≥ **47** |
| 打开 PV | 326 | 89 | ≥ **237** | ≥ **326** |
| 打开 UV | 190 | 4 | ≥ **186** | ≥ **190** |

**这是一个可证伪的判据**：如果 admin 四个 Tab（招募/估价/房源预约/房源单，一律选「近 90 天」）的对应值相加 **小于** 上表右列 → 才是真缺陷；如果 **≥** → 说明口径自洽，页面上那两个数本来就不是同一件事。

### 11.3 生产副本复现（本地库即生产快照）

### 11.4 我的客户 UV=190 的正确解读（量级拆解）

- 招募段贡献 **≤ 4**（上界就是招募模块的 4，因为按 `openid_hash` 按人去重）；
- 剩下 **≥ 186 来自估价 / 房源预约 / 房源单**三条匿名链路；
- 这三条链路**共用同一个设备 UUID**（`miniapp/utils/visitor.ts:9-29`），同一客户逛 3 条链路 ⇒ 计 3 次；
- 实测该重复计数规模：本地副本 34 条匿名 PV / 28 个匿名 UV 中，有 **6 个 `visitor_id` 跨表重复**（≈ 20% 虚高）。**所以 190 的主因是"四条链路相加"本身，跨链路设备重复是次要放大项（约两成），不是主因。**

即：**190 不是"190 个访客"，而是"四条链路、两种去重口径、且同设备未跨链路去重"的一个求和值**，与招募模块的 `4`（4 个不同登录用户）不可比。

### 11.5 阻塞自助对账的 UI 缺陷（建议修）

用户想自己核 11.2 的判据时会卡住：**「全部对比」卡只渲染百分比，不渲染原始 UV 数值**。

- `frontend/src/app/(main)/admin/growth-center/funnel/_components/funnel-compare.tsx:89-95`：`打开UV` 行只输出 `uv_percent`（如 `350.0%`）；原始 `uv` 仅隐含在 `uv_percent × share_count` 里；
- 头部只给了各模块 `分享 {share_count} · 基准 100%`。

因此运营无法在「全部对比」一屏内读出四模块的 UV 合计，只能逐个 Tab 点开——这本身也是"看不出两边其实自洽"的原因之一。

**建议（小改，未实施）**：在 `CompareRow` 的百分比旁并列原始值（如 `28 (350.0%)`），或在每个模块块头部补齐 `打开 UV {uv}`。这样四个 Tab 的和可以在一屏内目视核对。

## 十二、最终结论（三轮排查汇总）

1. **无计数缺陷**：受控注入实验（第十节）证明 admin 漏斗端到端实时同步，注入 +10 PV/UV 两端同步 +10，且经完整 Next.js 页面链路验证；生产副本上"员工四链路相加 = 我的客户接口值"逐位相等。
2. **无窗口差异**：项目上线不足 90 天，漏斗 90 天窗口 = 全时段。
3. **无环境串库**：生产后台与小程序同源（`admin.fangmengchina.com` 不解析，后台走 `fangmengchina.com/admin` 同域；nginx 无 `proxy_cache`）。
4. **唯一成因：聚合维度不同。** 漏斗默认视图是「招募 · 单模块 · 模块全量」（`openid_hash` 按人去重）；我的客户是「四链路相加 · 该员工归属」（其中三条匿名链路按设备 `visitor_id` 去重，且共用同一设备 UUID 不去重）。`4` 与 `190` 不是同一件事。
5. **待办**：按第五节 P0（修正我的客户 UV 的求和语义）与本节 11.5（「全部对比」补原始 UV）修复；两处均**尚未实施**，等待确认。
