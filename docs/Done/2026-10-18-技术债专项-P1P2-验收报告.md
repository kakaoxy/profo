| ⑤ | D9 建议参数 `pathPrefixGuard?` | 保留运行时 pathname 判定仍会破坏组件中立性 | 改为**路由组显式登记身份**（`SessionIdentityBridge`），请求层在 401 时读取登记结果；组件在哪个路由组渲染就用哪套端点 |

## 6. ⚠️ 未覆盖 / 不确定（Fail Loud）

1. **`lead_attr_channel` 种子不是生产盘点结果**：仅按代码内已知上报值播种（`card/poster/timeline/direct`）。生产库 distinct 值盘点需连生产环境执行；本地库实测存在 `share`(661 条) 等字典外值，属正常未纳管态，需运营在管理页「转正」。
2. **`recruit_source` 未解除枚举发版约束**：字典只提供展示名/排序/停用；`recruit_leads.source`/`recruit_visits.source` 仍为 PG enum + Pydantic 枚举，新增来源值 = 改代码 + 迁移。
3. **小程序未切换公开字典端点**：`miniapp/utils/recruit-logic.ts` 仍从 openapi 类型取枚举（spec §8 原样）；`miniapp/types/api-types.d.ts` 已随 `gen-api` 同步但无消费点。
4. **F1「C 端页面复用 admin 组件」无真实实例**：当前仓库引用 `client` 的共享组件（`dict-address-picker`/`dict-link-card`）只被 admin 页面使用。反向语义以「身份登记单测 + 双侧 E2E（C 页面 401 只打 C 端点 / admin 页面只打 admin 端点）」等价覆盖；若未来新增此类复用，建议补一条真实反向用例。
5. **多 worker 下公开字典缓存**：`_PUBLIC_CACHE` 为进程内缓存，写入仅在**当前进程**失效；`--workers 2` 部署下其他 worker 最迟 60s 生效（与 spec §3.3「≤60s」口径一致，但「立即生效」不成立）。
6. **覆盖率门限口径未核实**：`fail_under=82` 在 `pytest tests --ignore=tests/e2e` 下不可达（65.47%），仓库未文档化实际门限命令；本轮未改 `addopts`。
7. **基线既有失败未修**：`test_admin_lead_create_creator_is_employee`（201 vs 200）、`info-inline-editor.test.tsx`（多 combobox）、`bd-iteration-fix.spec.ts` 2 条。均已在基线 worktree 复现，超出本专项范围，**未修**。
8. **`e2e_pw_channel` 常驻测试条目**：`admin-dict-manage.spec.ts` 第二条用例按「API 只增不删」口径保留一条**停用**字典项（对公开端点与前台不可见），重复执行不再新增。测试过程中创建的临时账号/项目已在执行后清理（账号经 API 软删除后 SQL 物理清理；项目为软删除）。
9. **`dict:manage` 授予 admin 的口径风险**：若某环境曾**刻意**把 `dict:manage` 从 admin 移除，重启会被迁移补回（与新权限点语义冲突极小，故接受）。

| 1 | `db.query(BizDictItem).filter(BizDictItem.id == "<真实uuid字符串>").first()` | **命中**（返回 `poster` 行），非 None |
| 2 | 编译 SQL / PG 参数类型推断 | SQLAlchemy `Uuid` 在原生 uuid 方言下**无 bind processor**，字符串原样下发；PG 依据 `id = $1` 上下文把参数推断为 `uuid` 并解析，故比较成立 |
| 3 | 既有 HTTP E2E 记录（`e2e-biz-dicts-20261018-122225.txt`） | `✓ 改展示名: (200, 'E2E渠道改名')` ——即用字符串 `item_id` 走 PUT 已真实成功 |

> 结论：字符串比较不是缺陷，「始终返回 None」在 PostgreSQL 上不成立。故**未**按报障建议改为 `uuid.UUID(item_id)` 直连查询（那只是写法差异，不解决任何问题）。

### 但复核中发现真实缺陷（已修复）

| 缺陷 | 证据 | 影响 |
|------|------|------|
| 非法 UUID 格式（如 `/items/not-a-uuid`）会直达 PG，抛 `psycopg.errors.InvalidTextRepresentation (DataError)`，再被 `except Exception: db.rollback()` **兜成 404** | `db.query(... BizDictItem.id == "not-a-uuid")` → `DataError` | ① 用宽泛 `except Exception` 掩盖**真实**数据库/编程错误（连接中断、SQL 写错也会变成「条目不存在」）；② 逻辑依赖 PG 隐式转型，脆弱 |

**修复**（`backend/services/system/biz_dict.py`）：

- 新增 `_parse_item_id(item_id) -> uuid.UUID`：应用层解析，非法格式 → `ResourceNotFoundError`（404），不再触达 PG；
- `_get_item` 去掉 `except Exception` 兜底，改为 `filter(BizDictItem.id == _parse_item_id(item_id))`；真实 DB 异常正常上抛（Fail Loud）。

## 6.2 追加验证：`request` 参数「未使用」报障复核（2026-10-18）

**报障断言**：`create_dict_item` 把 `request` 传给 `biz_dict.create_item`，但服务层未使用（仅用 `operator_id`），可移除。


行为证据 ②（反事实实验，同一服务函数仅改变 `request`）：
