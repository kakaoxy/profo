# 登录系统「A 页面静置 → 点击 B 页面失效 → 刷新恢复」排查报告

- 日期：2026-09-09
- 范围：`frontend`（Next.js 16.3.0 App Router）+ `backend`（FastAPI）登录/鉴权/刷新全链路
- 方法：静态代码走查 + **本地真实运行时逐跳实测**（前端 :3000、后端 :8000、Postgres/Redis 在 OrbStack）
- 变更：**未修改任何项目代码**；所有探针脚本写在 `/tmp`，未落库
- 结论口径：区分「实测证实」「代码事实」「待运行时确认」

---

## 0. 结论速览

| # | 结论 | 状态 |
|---|------|------|
| 1 | 现象不是「后端连不上」，而是 **admin 侧整页刷新与软导航走了两条不同的鉴权路径**：proxy 只在 `Accept: text/html` 时刷新 token，点击 `<Link>` 的软导航（RSC 请求）**完全不刷新** | ✅ 实测证实 |
| 2 | 软导航过期时，服务端返回的是 **HTTP 200 + 内含 `NEXT_REDIRECT` 的 RSC 载荷**（无 Location、无 Set-Cookie），随后由客户端 router 再走一条 **4 跳**（RSC → Route Handler → 303 → RSC）的补救链；这条链任一环失败 → 跳登录页/白屏 | ✅ 实测证实 |
| 3 | refresh_token 是 **rotation 制**（每次刷新立即撤销旧 jti），加上 access_token 只有 **30 分钟**，静置 30 分钟后必然进入刷新路径；**只要有一次「刷新成功但新 cookie 没落盘」= 永久登出** | ✅ 实测证实 |
| 4 | `layout.tsx` 把 **500 / 网络错误 / 超时也当成"未登录"** 处理（只有 401、429 被区分），一次后端抖动就会把用户踢到登录页 | 代码事实 |
| 5 | 纯前端分支：`PermissionGuard` + `usePermission`（SWR 拉 `/api/v1/auth/me`）拿不到权限就 `router.replace("/admin")`，表现为「点了 B 又弹回工作台 / 菜单只剩工作台」 | 代码事实 |
| 6 | 「连接后端失败，请稍后重试」确有出处：`frontend/src/app/(main)/admin/properties/page.tsx:52` —— **只要 `client.GET` 返回非 2xx（含 401）就渲染这句**，把 401 直接显示成"连接失败" | ✅ 代码事实（用户的第二个猜想被证实） |
| 7 | `/api/auth/refresh` 路由（POST/GET）**直接调 `adapter.refreshToken`，没有 `dedupServerRefresh` 去重**，与 proxy、api-server 两条路径不一致；叠加 rotation，两个并发刷新必有一个失败并触发 fail-closed 清 cookie | ✅ 代码事实 |

**一句话**：Token 过期只是导火索，真正的病根是 **「整页刷新能续期、点击跳转不能续期」的路径不对称**，叠加 **rotation 令牌不可回退** 与 **刷新链缺少去重**，把一次本该静默修复的 401 放大成"点击就坏、刷新就好"，并在并发时直接把用户登出。

## 1. 关键事实（实测）

### 1.1 令牌与 Cookie 生命周期

| 项 | 值 | 来源 |
|---|---|---|
| access_token 有效期 | **1800 秒（30 分钟）** | 实测 `POST /api/v1/auth/token` 返回 `expires_in: 1800`；`backend/settings.py` `jwt_access_token_expire_minutes = 30` |
| refresh_token 有效期 | 7 天 | `settings.py` `jwt_refresh_token_expire_days = 7` |
| Cookie maxAge | 由 JWT `exp` 反推剩余秒数 | `frontend/src/lib/auth/core/cookies.ts:20-39` |
| 刷新策略 | **rotation**（每次刷新撤销旧 `jti`） | `backend/routers/system/auth.py` `/refresh` → `AuthService.refresh_user_token` |
| 刷新限流 | 10 次/分钟 | `RateLimits.AUTH_REFRESH` |

> 推论：登录后 `access_token` cookie 的 Expires = 登录时刻 + 30 分钟。**静置超过 30 分钟，浏览器会直接删掉这个 cookie**，此时点任何链接都必须走刷新路径 —— 这正是「静置一段时间后才容易失败」的时间常数。

### 1.2 两种导航方式的实测对比（均只携带 `refresh_token`，`access_token` 缺失）

**A. 整页刷新（`Accept: text/html`，等价于 F5 / 地址栏回车）**

```
[hop0] 200 text/html /admin/leads
       Set-Cookie: access_token=eyThUX… & refresh_token=eykmK1…
       └ 最终 200，187634 字节，HTML 页面
```

→ proxy 在 middleware 里**静默完成刷新并下发新 cookie**，页面正常渲染。**这就是"刷新又好了"。**

**B. 软导航（`RSC: 1` + `Accept: text/x-component`，等价于点击侧边栏链接）**

```
[hop0] 307 /admin/leads?_rsc=probe  -> Location: /admin/leads?_rsc
[hop1] 200 text/x-component /admin/leads?_rsc
       └ 16507 字节，无 Location，无 Set-Cookie
```

载荷结尾（关键）：

```
36:E{"digest":"NEXT_REDIRECT;replace;/api/auth/refresh?next=%2Fadmin%2Fleads;307;",
     "stack":[["fetchWithAutoRefresh",…],["getUser","DashboardLayout"],…]}
86:E{"digest":"NEXT_REDIRECT;replace;/api/auth/refresh?next=%2Fadmin%2Fleads;307;",
     "stack":[["fetchWithAutoRefresh",…],["Promise.all","LeadsPage"],…]}
```

→ **proxy 没有刷新**（`Accept` 不是 `text/html`），Server Component 用空 token 打到后端拿到 401，于是 `api-server.ts` 抛出 `redirect("/api/auth/refresh?next=…")`。注意：**HTTP 状态是 200，不是 307**，跳转信息被编码在 RSC 载荷里。

**C. 客户端拿到 B 之后的补救链（服务端逐跳实测）**

```
[hop0] 307 /api/auth/refresh?next=%2Fadmin%2Fleads
         -> /api/auth/refresh?next=%2Fadmin%2Fleads&_rsc=OxBCQ2sR9P8GlKR3
[hop1] 303 /api/auth/refresh?next=%2Fadmin%2Fleads&_rsc=…
         -> http://127.0.0.1:3000/admin/leads
         | SetCookie: refresh_token=eyNAxj… & access_token=eyLiEE…
[hop2] 307 /admin/leads -> /admin/leads?_rsc=…
[hop3] 200 /admin/leads?_rsc=…   （37716 字节 RSC 载荷）
```

即：客户端 `RedirectErrorBoundary`（`next/dist/.../redirect-boundary.js`）捕获 `NEXT_REDIRECT` 后执行 `router.replace('/api/auth/refresh?next=…')`，**对一个 Route Handler 发起 RSC 请求**，Next 先因缺少 RSC 缓存参数回 307，再由 Route Handler 落盘 cookie 后 303 回跳。**整条链 4 跳，依赖三件事同时成立**：① 重定向中间的 Set-Cookie 被浏览器接受；② 客户端 RSC 重定向重放逻辑（`fetch-server-response.js`，上限 20 跳）正常工作；③ 沿途 refresh_token 没被撤销。

**D. refresh_token 已被撤销时（rotation 的代价）**

```
[hop0] 307 /admin/leads -> /admin/login?redirect=%2Fadmin%2Fleads
```

→ 用已消费过的 refresh_token 再刷新，**直接跳登录页**。实测中我用同一个 refresh_token 做第二次实验就复现了这一点。

## 2. 五层链路逐层结论

### 第一层：浏览器有没有发请求？

- **有请求**。软导航会发 `/admin/xxx?_rsc=…`（RSC）而不是整页文档请求；页面上客户端组件（侧边栏权限、SWR 数据）还会发 `/api/v1/auth/me` 等 XHR。
- 这一层最容易误判：RSC 请求状态显示为 **200**，看起来"请求成功了"，实际内容是一个重定向错误载荷。
- 另一种"看起来没请求"的情况来自 `PermissionGuard`：客户端权限为空时直接 `router.replace("/admin")`，Network 里只有一次 RSC 请求，看不到 401。

### 第二层：请求到底是什么错误？

| 状态 | 真实含义（本项目） | 出处 |
|---|---|---|
| 401 | `{"code":401,"message":"无法验证凭据"}` —— access_token 过期/缺失 | `dependencies/auth.py:176` + `error_handlers.service_exception_handler` |
| 403 | 账号未激活、权限不足、或 CSRF 头缺失 | `dependencies/auth.py` / `main.py` `csrf_protect` |
| 429 | `{"code":429,"message":"请求过于频繁，请稍后重试"}` | `rate_limit_handler` |
| 500 | `服务器内部错误，请稍后重试`（含 Redis/DB 抖动） | `general_exception_handler` |
| 502/504 / `(failed) net::ERR_*` | nginx 与后端之间、或浏览器与 nginx 之间 | 与登录系统无关，**属于网关/网络层** |

⚠️ **本项目最重要的错误混淆点不在 UI 文案，而在 `layout.tsx` 的分支判断**（见第 4 条根因）：除 401、429 外的一切错误（500/超时/网络异常）都会走 `return data`（通常为 `undefined`）→ `!user` → `redirect("/admin/login")`，**等价于把一次后端抖动判成"未登录"**。

### 第三层：FastAPI 有没有收到请求？

- 401 场景下**一定收到了**。`service_exception_handler` 会打印 `WARNING 服务层业务异常: 401 - 无法验证凭据`，这是第 4 步里最可靠的判据。
- 若后端控制台**没有**这条日志，说明请求没到后端：要么是前端没发（客户端守卫/路由层），要么是 nginx 层就失败（502/504）。

### 第四层：FastAPI 为什么失败？

后端自身几条可能触发"静置后首次失败"的点：

1. **DB 连接**：`db.py` 已配 `pool_pre_ping=True` + `pool_recycle=3600`，**已覆盖**连接被静默断开的常规场景。
2. **Redis 单例连接无保活**：`utils/redis_client.py:61-66` 用 `Redis.from_url(..., socket_connect_timeout=5, socket_timeout=5)`，**没有** `socket_keepalive` / `health_check_interval` / `retry_on_timeout`。而 `SlowAPIMiddleware` 对**每个请求**都要访问 Redis。若连接被中间设备静默回收，第一次请求会失败或阻塞 5 秒，重试即恢复 —— 症状同样是"静置后首次坏、刷新就好"。**待运行时确认**（见第 5 节）。
3. **限流**：`AUTH_REFRESH = 10/minute`。若一次导航并发触发多次刷新（多标签页 / 预取），可能撞限流返回 429，`layout.tsx` 虽有 429 分支，但客户端 `fetcher` 会把 429 当普通错误抛出。

### 第五层：静置造成的状态失效

| 状态 | 是否随静置失效 | 说明 |
|---|---|---|
| access_token cookie | **是**（30 分钟） | 过期后浏览器直接删除 |
| refresh_token cookie | 否（7 天） | 但**每次刷新即撤销旧的** |
| React Context / SWR 缓存 | 是 | `usePermission` 的 SWR 数据在 401 后若未重新验证，会一直为空 |
| Next Router Cache | 弱 | `layout.tsx` 设了 `dynamic = "force-dynamic"`，影响较小 |
| API 封装中的旧 token | 否 | `api-server.ts` 每次请求都从 cookie 现读，**没有缓存旧 token 的问题** |

**注意**：`getAccessTokenFromCookie()`（`token-refresh-server.ts:45`）**不校验 exp**，直接把 cookie 原文发出去，所以软导航必然先浪费一次 401 往返 —— 不会造成错误，但让"点击"比"刷新"多一跳，放大了失败概率。

## 3. 根因排序

| 优先级 | 根因 | 证据 | 与症状的对应 |
|---|---|---|---|
| **P0-1** | admin 侧 proxy 仅在 `Accept: text/html` 时刷新 token（`frontend/src/proxy.ts:171`） | 实测 A vs B | "刷新就好、点击就坏"的直接原因 |
| **P0-2** | 软导航兜底是 4 跳的 RSC→Route Handler→303→RSC 链，且首跳 HTTP 200 无 Location | 实测 B、C | 一旦某跳失败 → 白屏/跳登录 |
| **P0-3** | refresh rotation 不可回退 + access 仅 30 分钟 | 实测 D、`settings.py` | 一次抖动 = 永久登出 |
| **P0-4** | `/api/auth/refresh` 的 POST/GET **没有 `dedupServerRefresh` 去重**（`route.ts:47,143` 直接调 `adapter.refreshToken`），与 proxy（`auth-middleware.ts:167`）、api-server（`token-refresh-server.ts:83`）不一致 | 代码事实 + rotation（`services/system/auth.py:465-491`） | 并发刷新必有一个拿已撤销的旧 token 失败 → fail-closed 清 cookie → **被登出**；也是 401 逃过 `redirect()`、渲染出"连接后端失败"的入口 |
| **P1-1** | `layout.tsx` 把 5xx/网络错误当未登录 | `app/(main)/layout.tsx:22-47,65-69` | 后端抖动也被显示成"登录失效" |
| **P1-2** | `PermissionGuard` 在权限为空时 `router.replace("/admin")` | `components/permission-guard.tsx:22-28` | "点了 B 又弹回工作台"/"Network 里看不到请求" |
| **P1-3** | Redis 客户端无保活，限流中间件每请求访问 Redis | `utils/redis_client.py:61-66` | 可能是"静置后首次 500"的另一来源（待确认） |
| **P2-1** | 首个请求不校验 exp，必然 401 一次 | `token-refresh-server.ts:45` | 增加失败面 |
| **P2-2** | C 端与 admin 端不对称：C 端受保护路径**不判断 Accept**，软导航也刷新 | `proxy.ts:131` vs `proxy.ts:171` | 同一份代码两套行为，易回归 |
| **P2-3** | `/api/auth/refresh` 在任何刷新失败时都 `clearTokenCookies`（fail-closed） | `app/api/auth/refresh/route.ts:87,154` | 后端 5xx/网络抖动也会被判成"会话失效" |

## 4. 「后端无法连接」文案溯源（用户的第二个猜想：成立）

**B 页面 = `/admin/properties`（房源列表）**。真实文案在：

```ts
// frontend/src/app/(main)/admin/properties/page.tsx:51-53
if (error) {
  return <div className="p-8 text-error">连接后端失败，请稍后重试</div>;
}
```

`openapi-fetch` 对任何非 2xx 都会返回 `{ data: undefined, error }`，**401 也不例外**。因此：

- 后端返回 401（token 过期）→ `error` 为真 → 页面显示 **「连接后端失败，请稍后重试」**；
- 后端真的连不上（网络/502）→ 同样显示这句话。

**这就是"401 被错误地提示成后端无法连接"的确凿证据**，也是本次排查被误导的根源。同类兜底还有：

| 文案 | 位置 |
|---|---|
| `连接后端失败，请稍后重试` | `admin/properties/page.tsx:52` |
| `logger.error("连接后端失败:", error)` | `admin/properties/governance/page.tsx:34` |
| `网络错误，请连接后端服务` | `(c)/register/actions.ts:96` |
| `网络错误，请稍后重试` | `app/(main)/admin/**/actions/*.ts` 的 catch 兜底 |
| `加载失败` / `xxx页面数据加载出错` | 各 `error.tsx` 错误边界 |
| `登录失败` / `Token 刷新失败` / `登录服务响应超时，请稍后重试` | `frontend/src/auth.ts` |

**判定方法**：Network 里若出现 `(failed) net::ERR_CONNECTION_*` 或 `502/504` → 浏览器/网关层，与登录系统无关；若看到 401 且伴随 `/api/auth/refresh` → 就是本报告的根因链，那句"连接后端失败"是误报。

> 为什么 401 有时能走到这行、有时被 `redirect()` 拦下？见 §5 的 P0-4：`MAX_RETRIES` 用尽或并发 race 下，`fetchWithAutoRefresh` 会把 401 原样返回给调用方。

## 5. 修复建议（按优先级）

### P0-1 让软导航也走 proxy 刷新（治本）

`frontend/src/proxy.ts:171` 把

```ts
const isHtmlRequest = request.headers.get("accept")?.includes("text/html");
if (!isHtmlRequest) { return applyCsp(nextWithNonce(request, nonce), nonce); }
```

改为：**排除静态资源/预取后，admin 路径一律走 `resolveAdminAuth`**（`dedupServerRefresh` 已存在，2 秒窗口内并发只发一次刷新）。两个必须同时做的保护：

1. **跳过预取**：`request.headers.get("next-router-prefetch") === "1"` 时不要刷新 —— 否则视口内所有 `<Link>` 的预取都会触发刷新，既撞 `AUTH_REFRESH 10/分钟` 限流，又会疯狂 rotation refresh_token。
2. **沿用已有的请求头覆盖**：`buildAdminRequestHeaders()` 已把刷新后的 token 写回请求 cookie，Server Component 侧无需改动即可读到新 token。

### P0-2 缩短补救链（治标但重要）

- `api-server.ts` 在 Server Component 上下文 401 时，改为 **先尝试"用 refresh_token 换 token 并把新 token 写进请求头继续渲染"** 是不可行的（不能写 cookie）；因此更稳妥的做法是让 P0-1 生效，使这条链根本不被触发。
- 若短期无法改 proxy，至少把 `redirect()` 的目标改为**页面路径**而非 Route Handler（例如 `/admin/refresh?next=…` 做成一个真实页面），避免"对 Route Handler 发 RSC 请求"这种非标准用法。

### P0-3 让刷新失败可逆

- `app/api/auth/refresh/route.ts:82-89,149-162`：区分错误类型 —— 只有后端明确返回 **401/403** 才 `clearTokenCookies`；**5xx / 网络异常 / 超时保留 cookie**，让后续请求还能再试一次。这是防止"一次抖动 = 永久登出"的关键改动。
- 后端可考虑：refresh 时对"同一 refresh_token 在 N 秒内被重复使用"返回旧 token 而非 401（grace window），进一步降低 rotation 竞态。

### P0-4 给 `/api/auth/refresh` 补服务端去重

`app/api/auth/refresh/route.ts:47` 与 `:143` 改为经过 `dedupServerRefresh(refreshToken, () => adminAuth.adapter.refreshToken(refreshToken))`，与另外两条刷新路径保持一致。这一条改动最小、收益最大：**消除"并发刷新 → 旧 jti 已撤销 → 清 cookie 登出"的整条失败链**。

### P1

- `admin/properties/page.tsx:52`：按状态码区分文案 —— 401/403 提示"登录状态已失效，正在重新验证…"，5xx/网络错误才提示"后端连接失败"。**这一条能立刻终止排查被误导的问题。**
- `app/(main)/layout.tsx`：`getUser()` 只在 **401** 时返回 `null` 跳登录；5xx/网络错误应渲染可重试的错误态（或透传给 `error.tsx`），不要静默跳登录。
- `components/permission-guard.tsx`：`isLoading === true` 或请求出错时**不要** `router.replace`，避免误弹回。
- `utils/redis_client.py`：加 `socket_keepalive=True`、`health_check_interval=30`、`retry_on_timeout=True`；限流组件对 Redis 异常降级为放行（fail-open）并记录告警。
- `token-refresh-server.ts`：`getAccessTokenFromCookie()` 增加 exp 校验，过期就直接走刷新，省掉一次 401 往返。
- `proxy.ts`：C 端与 admin 端的刷新策略对齐，避免两套行为。

## 6. 复现与自证清单（5 步，建议照做一次）

1. 登录后台 → DevTools → Application → Cookies，记下 `access_token` 的 Expires（应为登录时刻 +30 分钟）。
2. 静置到过期；**想快速复现可直接删掉 `access_token` cookie 或把值改乱**（保留 `refresh_token`）。
3. **不要刷新**，点击侧边栏另一个页面，看 Network：
   - 出现 `/admin/xxx?_rsc=…`，状态 200、`content-type: text/x-component`、响应体含 `NEXT_REDIRECT…/api/auth/refresh` → **命中 P0-1 / P0-2**；
   - 出现 `/api/v1/auth/me` 401，随后 `/api/auth/refresh` → **命中 P0-3 / P1-2**；
   - 出现 `(failed) net::ERR_*` 或 502/504 → **网关/网络层，与登录系统无关**。
4. 同时看 FastAPI 控制台：401 时必有 `服务层业务异常: 401 - 无法验证凭据`。**没有这条 = 请求没到后端。**
5. 按 F5 刷新同一页面对比：首条 `/admin/xxx` 返回 **200 且响应头带 `Set-Cookie: access_token/refresh_token`** = proxy 静默刷新成功 —— 与第 3 步形成对照，即可确认"路径不对称"这一根因。
