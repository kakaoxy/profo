## 一、高危缺陷（必须立即修复）

### H1 · 跨小区同名「待审楼栋」被错误复用，引用串到别的小区

- **维度**：契约一致性 / 数据完整性
- **位置**
  - `backend/services/property/dict_submit_service.py:100-110`（复用查询）
  - `backend/services/property/dict_submit_service.py:146-152`（并发冲突回退查询）
  - `backend/models/property/building_dict.py:229-236`（`uq_pending_open` 只含 `kind, COALESCE(parent_id,0), normalized_name`）
- **问题**：小区 A 提交「8号楼」时 `parent_kind=community` → `parent_id` 被语义化为常量 `0`（`dict_submit_service.py:200-206` 注释「存 0 表示父级为实表小区」），归属小区只落在 `community_id` 列，**不进唯一索引**。于是小区 B 提交同名「8号楼」时命中 `parent_id=0 + normalized_name` 直接 `reused=True`，复用 A 小区的条目。
- **触发场景**（脚本 `F1`）：A 小区 POST `/pending {kind:building,name:8号楼,parent_kind:community,parent_id:A}` → `pending_id=286`；B 小区提交同名 → `{"pending_id":286,"created":false,"reused":true}`，两条引用都挂在同一 pending 上。
- **影响范围**：上海 1.97 万小区，楼栋号「1」「2」「A」「8号楼」重名极普遍。审核 create 后楼栋只落在 A 小区，B 小区单据的 `building_id` 被回填成 A 小区的楼栋 → **跨小区脏关联**；B 小区永远不会新增这栋楼。
- **修复建议**：唯一性判定加小区维度。二选一：
  1. `bd_pending_entries` 增加 `community_scope`（building 条目落 `community_id`，room 落父楼栋所属小区），`uq_pending_open` 改为 `(kind, community_scope, COALESCE(parent_id,0), normalized_name)`；
  2. 复用查询加 `community_id` 条件（`parent_id=0` 时按 `community_id` 区分），并同步重建唯一索引（`migrations/_building_dictionary.py` 里已有「重建索引」的幂等分支可复用）。
  建议 1，能同时堵住并发窗口（`uq` 才是真锁）。

### H2 · 待审楼栋下新建户室后，该楼栋审核永久失败（审核链路死锁）

- **维度**：异常处理 / 状态机
- **位置**
  - `backend/services/property/dict_submit_service.py:225-231`（`parent_kind=pending_building` 返回 `BdEntryKind.BUILDING`）
  - `backend/services/property/building_review_service.py:414-420`（`_create_room_from_pending` 用 `db.get(BdBuilding, entry.parent_id)`）
  - `backend/services/property/building_review_service.py:191-197`（`_check_topology` 只认 `entry.parent_kind=="community"`）
- **问题**：`pending_building` 分支返回 `parent_kind=BdEntryKind.BUILDING`，户室条目的 `parent_kind` 被落库成 `"building"`，语义上与"父级是实表楼栋"完全无法区分。前端在新建楼栋后引导用户到「待审楼栋」下继续新建户室（`dict-address-picker/index.tsx:404-412`），走的正是这条分支。
- **触发场景**（脚本复现，`/tmp` 一次性用例）：
  1. `POST /pending {kind:building, name:3, parent_kind:community, parent_id:A}` → `id=278`
  2. `POST /pending {kind:room, name:202, parent_kind:pending_building, parent_id:278}` → `id=279`，落库 `parent_kind=building, parent_id=278`
  3. 审核楼栋 278 `create` → 成功落库 `bd_buildings.id=1173xxx`
  4. 审核户室 279 `create` → **400「父级楼栋不存在（父级未转正或已删除）」**（`parent_id=278` 永远不是实表楼栋 id）
  5. 户室条目永久卡在 pending，唯一出路是被 merge/reject 掉
  - 线上现状：`bd_pending_entries` 已存在同类悬挂行（`id=175,193,259,266,271,273,275,277`，`parent_kind=building` 但 `parent_id` 指向 pending 条目）
- **影响范围**：审核池里这类户室条目无法转正，用户提交的户室永远缺失，且前端不提示原因（toast 只说「请调整目标」）。
- **修复建议**：
  1. 增加可区分语义：`parent_kind` 用 `pending_building` 落库（模型枚举需扩展）或增加 `parent_is_pending` 布尔列；
  2. 转正时把子级 pending 的 `parent_id` 改写为实表楼栋 id —— 该逻辑 `_resolve_create:228-243` 已有（`child.parent_id = int(entry.resolved_target_id)`），但它是按 `parent_id == entry.id` 匹配的，**在修复 1 之前根本匹配不到**，属同一缺陷的两半；
  3. 存量 8 条悬挂行需一次性迁移修复（父级楼栋 278 已转正的可直接改指实表 id）。

### H3 · 小区合并（治理）不迁移字典楼栋/户室，合并后删除主档即整树丢失

- **维度**：数据库交互 / 数据完整性
- **位置**
  - `backend/services/market/merger.py:259-280`（`_migrate_properties` 只迁 `PropertyCurrent`，`_archive_communities` 只置 `is_active=False`）
  - `backend/services/property/dict_write_service.py:673-680, 735-740`（`delete_community` 只拦截「被并入的小区」，**不拦截"本小区被合并到别处"**）
- **问题**：字典合并信息区块（FR-14）把小区软归档并写 `merged_into_id`，但 `bd_buildings.community_id` / `bd_rooms` 仍指向被并小区，主子档之间没有数据迁移。此时：
  - 被并小区仍是 `bd_buildings` 的持有者，但已 `is_active=False`，总览不可见（`query_communities` 过滤 `is_active`）；
  - `delete_community` 的合并拦截条件是 `merged_into_id == 本小区`（即"我有被并子档"），**不覆盖"我是被并子档"**；
  - 于是可以直接删掉被并小区，`delete_community` 会连带 `DELETE bd_buildings / bd_rooms`（`dict_write_service.py:748-753`），**整棵树物理删除且不可恢复**（表上有该小区名的数据，业务单据若未引用则全部静默消失）。
- **触发场景**：`POST /admin/communities/merge {primary_id:B, merge_ids:[A]}` → A 被归档 → `DELETE /admin/building-dictionary/communities/{A}` → 200，A 的楼栋/户室全部消失。
- **影响范围**：字典核心资产（733 万户室）的无提示丢失，且总览/详情都看不出丢数据。
- **修复建议**：
  1. `delete_community` 增加拦截条件：`merged_into_id IS NOT NULL`（本小区是子档）时 409，提示「请先解除合并」；
  2. 合并时把 `bd_buildings.community_id` 迁移到主档（与 `_migrate_properties` 同事务），否则主档看不到被并小区的楼栋，FR-14 的"数据情况"统计（`dict_read_service.py:_community_merged_children`）与真实归属长期不一致；
  3. 两条都要补 E2E（unmerge 后楼栋归属可逆）。

### H4 · 审核 create 户室后 `bd_buildings.room_count` 冗余计数漂移

- **维度**：数据库交互 / 数据一致性
- **位置**：`backend/services/property/building_review_service.py:437`
  ```python
  parent_building.room_count = db.query(BdRoom).filter(BdRoom.building_id == parent_building.id).count() + 1
  ```
- **问题**：`db.add(room); db.flush()` 之后 `count()` 已经包含这户，再 `+1` 造成重复累加。
- **触发场景**（脚本 `F2`）：楼栋已有 2 户 → 审核 create 第 3 户 → `room_count=4`，实表 `count(*)=3`。
- **影响范围**：楼栋列表「户室数」、总览「小区户室数」（`sum(room_count)`）、楼栋详情 `room_count` 全部偏高；每次审核新增户室偏差 +1 且不可自愈（无对账任务）。当前生产数据 `room_count` 与实表一致（0 行不一致），说明是本周新增代码引入的**新缺陷**。
- **修复建议**：去掉 `+ 1`；并补一条幂等对账迁移（`UPDATE bd_buildings SET room_count = 实际 count`），覆盖已经产生的偏差。

## 二、中危缺陷（本迭代内修复）

### M1 · 楼栋列表的 pending 叠加不受分页与 keyword 约束

- **维度**：数据库交互 / 契约一致性
- **位置**：`backend/services/property/dict_read_service.py:416-418`（分页只作用于实表 `BdBuilding`），`452-470`（pending 无条件全量叠加）
- **触发场景**（脚本 `F3a/F3b`）：小区有 pending 楼栋时，`page=1&page_size=5` 与 `page=2&page_size=5` **都返回该 pending 行**；`keyword=nothingmatch` 仍返回该 pending 行（脚本 F3b 留档为 FAIL，属复现异常需重跑确认，但代码路径确定：pending 查询未拼 `keyword`）。
- **影响**：跨页重复渲染同一待审楼栋；搜索"找不到该楼栋可新建"的引导语在有待审楼栋时永远不出现，用户会重复提交同名 pending（叠加 H1 后进一步污染）。
- **修复建议**：pending 查询拼 `keyword` 过滤；pending 行从 `total` 中剔除（或明确文档化"待审行不计入 total 且只在本页展示一次"），至少不能每页重复。

### M2 · 审核 merge 无小区/父子拓扑校验，可跨小区改指

- **维度**：输入校验 / 权限边界
- **位置**：`backend/services/property/building_review_service.py:274-300`（merge 分支只查目标存在）
- **触发场景**（脚本 `F4b` + 真实单据链路）：A 小区提交楼栋 pending → `merge target_id=属于 B 小区的楼栋` → 200，来源线索 `community_id=A` 而 `building_id` 指向 B 小区楼栋（实测 `leads` 回填为该状态）。
- **影响**：与 M1 修复的 `validate_dict_ownership` 目标相反，从审核侧绕过归属校验；单据详情会显示"小区A / Q1号"但实际上 Q1 属于 B；后续编辑该单据时 `validate_dict_ownership` 会 400，形成**无法编辑的死单据**。
- **修复建议**：merge 分支加校验 —— 楼栋 `target.community_id == entry.community_id`、户室目标所属楼栋小区一致；同时补 `_check_topology`（当前只有 create 调用，merge/reject 未调用）。

### M3 · 字典导入只解析「区域板块」不落 `district/business_circle`，总览筛选口径失真

- **维度**：契约一致性
- **位置**
  - `backend/services/property/dict_import_loader.py:111`（`district_area` 标注 `noqa: ARG001 落库不单独存列`）
  - `backend/services/property/building_review_service.py:376`（审核转正只写 `payload.district`）
  - `frontend/.../overview-client.tsx:52-55`（`DISTRICT_OPTIONS` 硬编码「黄浦、徐汇…浦东」共 16 个**无「区」后缀**名称）
- **数据证据**：生产库 21707 个小区中 `district` 有值仅 4613（21%），且值域是「浦东区 / 闵行区 / 闸北区」等**带「区」后缀**；`DISTRICT_OPTIONS` 选「黄浦」命中 6 条、选「黄浦区」命中 19 条 —— 同一行政区被拆成两个值域，前端下拉选不到绝大多数数据。`business_circle` 覆盖 4610（21%），SRS FR-01 要求的"板块"筛选维度前后端**均未实现**（路由有参数但前端无入口）。
- **影响**：总览页 79% 小区无法按区域筛选；已能筛选的部分也有静默漏数；SRS FR-01 双维筛选未交付。
- **修复建议**：导入时把 `district_area`（如「青浦盈浦」）拆成 `district`（标准化为「青浦区」）+ `business_circle`；`DISTRICT_OPTIONS` 改为从后端 distinct 值拉取（或统一去/加「区」后缀归一）；补板块筛选入口。属功能缺口，需与产品确认口径后再动。

### M4 · 线索更新链路缺字典归属校验，与创建链路不对称

- **维度**：输入校验
- **位置**：`backend/services/leads/core.py:361-415`（`update_lead` 直接 `setattr`，无 `validate_dict_ownership`）；对比 `leads/core.py:121`（创建有）、`marketing/project.py:553`、`projects/core.py:545` 均已有
- **触发场景**：`PUT /leads/{id} {community_id: A, building_id: 属于B的楼栋}` → 200 成功落库（已实测返回 `building_no:"Q1"` 跨小区）。
- **影响**：M1 修复（`dict_ownership`）在四个入口中漏了线索编辑，脏关联可从该入口写入；且 `community_id` 被清空时 `building_id` 仍残留（`validate_dict_ownership` 在 `community_id=None` 时不校验归属）。
- **修复建议**：`update_lead` 在 `setattr` 前调用同位校验（`community_id=update_dict.get("community_id") or lead.community_id`，`building_id/room_id` 取更新值回退现值）；顺带确认前端编辑态是否清空 `community_id` 时同步清 `building_id/room_id`。

### M5 · 审核期间 `resolved_target_id` 未落引用状态，`pending-backfill` 重试端点空转

- **维度**：契约一致性 / 可维护性
- **位置**：`backend/services/property/building_review_backfill.py:96-120`（`run_pending_backfill`）、`backend/services/property/building_review_service.py:360`（返回 `已合并…{len(refs)} 条引用已改指`）
- **实测**：`POST /review/{id}/resolve {action:merge}` 返回「1 条引用已改指」，但 `bd_pending_references` 仍 `status=open`；`POST /review/pending-backfill` 连点两次都返回「处理 13 条引用」，引用数不变（38 open / 9 resolved 恒定）。原因：`backfill_reference` 对不存在的 `biz_id`（脏 UUID、`__audit_*`、`null`）走异常分支只 `logger.exception`，`status` 永不变，既污染日志又让批量回填每轮重复处理同一批脏数据。
- **影响**：`pending-backfill` 无法收敛（永远返回处理成功但零变化）；脏引用永久停留 open，`reference_count` 展示与实际不符；`已改指 N 条` 文案与实际不符。
- **修复建议**：脏引用（单据不存在 / id 非法）应置为 `resolved` 并标记原因（或新增 `failed` 状态 + 运营待办），保证批次可推进；`biz_id` 写入前校验格式（UUID / int / `ds:spid`）。

### M6 · 同一字典业务逻辑在 leads / projects / marketing 三处复制粘贴

- **维度**：可维护性
- **位置**：`backend/services/leads/core.py:_submit_dict_pendings`、`backend/services/projects/core.py:_submit_project_dict_pendings`、`backend/services/marketing/project.py:_submit_marketing_dict_pendings`（三份近乎相同的 90 行）

## 三、低危 / 合规问题

### L2 · `BdImportTask.created_at` 用 `datetime.now`（naive）落 timestamptz

### L3 · 导入任务预扫描三计数（`total_communities/total_buildings/total_rooms/warnings_count`）恒为 0

### L4 · 单个 zip 条目损坏导致整包任务 failed，已装载小区不回滚也无续跑入口
- 位置：`backend/services/property/dict_import_loader.py:432-470`（`for idx, (filename, data) in enumerate(entries)` 不在 try 内，`zf.read()` 抛 `BadZipFile` 直接冒到 `process_task`）。
