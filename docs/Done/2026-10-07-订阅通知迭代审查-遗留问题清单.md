## 二、代码类遗留问题（M 系列）

### M3 — 订阅通知逐收件人串行 HTTP，占用 anyio 线程池

- **维度**：数据库交互与性能表现（并发/资源）
- **位置**：`backend/services/marketing/notify.py:540`（上新循环）、`backend/services/marketing/notify.py:684`（调价循环）；上游 `backend/services/system/wechat.py` 4 处 `httpx.Client(trust_env=False)`（`fetch_wechat_miniapp_access_token` L405 等）
- **现状**：后台任务入口内逐收件人**同步串行**调用 `send_subscribe_message`，每次发送一个 `httpx.Client` 往返。httpx 默认超时经实测为 **5.0s**（`Timeout(timeout=5.0)`），未针对本场景收紧。上新最坏 `订阅数 × 5s`、调价最坏 `(频道全量 + 房源级增量) × 5s`，且整个任务跑在 starlette `BackgroundTasks` 的 anyio 线程池（默认 40 token）里。
- **触发场景**：房源上新/调价触发通知，同时有其他请求走 `run_in_threadpool`（如 `PUT /admin/marketing/projects/{id}` 本体）→ 通知任务长时间占用线程 token，其他线程化请求排队，延迟放大面超出通知功能本身。
- **影响范围**：极端情况（微信上游抖动叠加订阅规模上升）拖垮后台线程池，影响并发请求吞吐；订阅用户收到通知的时延变高。属可用性风险，非数据正确性风险。
- **建议**：① 对本场景显式设 `httpx.Timeout(读 3s / 连接 2s)`，压缩最坏占用时长；② 收件人分批并发（受控并发度，如 `max_workers≈8`）而非纯串行；③ 必要时将推送从 `BackgroundTasks` 迁移到独立工作队列。
- **优先级**：中低（订阅规模尚小，当前 `notify_logs` 仅个位数留痕，未构成线上压力）。

### M5 — admin PUT/POST 响应恒不回填聚合字段，且注释与实现不符

- **维度**：契约一致性与可维护性
- **位置**：`backend/routers/marketing/projects.py:180`（`create` 返回裸 Pydantic）、`backend/routers/marketing/projects.py:234`（`update` 返回裸 Pydantic）；对比 `list`（L110）、`get`（L200）走 `aggregate_notify_fields` 回填
- **现状**：`L4MarketingProjectResponse` 含 `latest_price_change` / `notify_summary` / `is_new_listing` 三个服务端聚合字段，但**仅 GET 列表/详情**回填；POST 创建、PUT 更新返回体里这三项恒为 `null`/`false`。前端 `price-change-card.tsx:219` 注释却声称「新价以 PUT 响应渲染（total_price/unit_price/latest_price_change 均在响应中）」——`latest_price_change` 实际为 `None`（已实测确认）。
- **触发场景**：详情页内联调价成功 → `PriceChangeCard` 用 PUT 响应渲染新总价；但同响应里 `latest_price_change` 为 `None`，靠宿主 `handlePriceChanged → reloadDetail` 重新 GET 详情才补齐。若后续有人直接消费 PUT 响应的 `latest_price_change`，会拿到 `null` 而非最新调价条。
- **影响范围**：目前被 `reloadDetail` 兜住、用户无感；隐患在于误导后续维护者，属可维护性问题。
- **建议**：要么在 PUT/POST 返回前同样过一次 `aggregate_notify_fields`（口径统一），要么改正 `price-change-card.tsx:219` 注释为「总价取自 PUT 响应；调价摘要由 reloadDetail 补齐」。二选一，勿留矛盾注释。
- **优先级**：低。

### M6 — `is_new_listing=false` / `has_price_change=false` 被当作「不过滤」

- **维度**：契约一致性（OpenAPI 声明 bool，实为三态）
- **位置**：`backend/services/marketing/project.py:79`（`if is_new_listing is True:`）、`backend/services/marketing/project.py:86`（`if has_price_change is True:`）
- **现状**：查询参数类型为 `bool | None`，但仅判定 `is True`。传 `false` 与不传等价（都不加过滤条件），无法表达「仅非新上 / 仅未调价」。已实测：`?is_new_listing=false` 返回 total=302（= 全集，与不带该参数一致），`?is_new_listing=true` 返回 0。
- **触发场景**：客户端（或后续 admin 需求）期望 `false` 表示「排除新上」，实际拿到全量列表，静默错语义。
- **影响范围**：当前前端只用正向筛选（`badge_filter=new|price` 映射为 `true`），未触发；属契约不严谨的潜在坑。
- **建议**：`false` 时加反向过滤（`published_at IS NULL OR published_at < window` 等），或将参数收紧为 `Literal[True]` / 三态枚举并在 description 明确「仅支持正向筛选」。
- **优先级**：低。

>
> **可复现验证（Chrome 不需要，直驱 :8000，脚本已按约定删除、步骤留档）**：

> 实测结果（2026-10-07）：
> 1. **同 IP 双用户**：A 连打至首个 429（118×200 后命中 120/min 移动窗口）→ 紧随其后同 IP 的 B 请求 **200**（IP 键下 B 必 429，反证键确为用户）
> 2. **同用户跨 IP**：A 已 429 后携 `X-Forwarded-For: 203.0.113.9` 再请求 → **仍 429**（额度桶跟用户不跟 IP）；对照 B 换 XFF 仍 200
> 四项断言全 PASS，M8 用户维度限流确认生效。C 端 429 可感知提示（`marketing-notify.ts` toast）已于 16123ffd 落地。

- **维度**：输入校验与权限控制（限流粒度）/ 异常处理
- **位置**：`backend/routers/public/marketing.py`（6 个端点全部 `@limiter.limit(RateLimits.VALUATION_SUBSCRIBE_TEMPLATE)`）；`backend/utils/common.py:239`（`60/minute`）、`common.py:82`（`key_func=_get_client_ip`）
- **现状**：6 个营销订阅端点（含 `POST /subscriptions/report`、`POST /projects/{id}/subscription/report`）复用的是评估模块的 `60/minute` 限流，且限流键为**客户端 IP**（非登录用户）。公司/校园等 NAT 出口共享同一 IP 时 60/min 会先触顶。撞 429 后，`request.ts` 对非 2xx 静默 reject，前端 `catch` 返回 `null`，调用方按「未登录/失败」降级——用户点了「开启提醒」却看不到失败原因。
- **触发场景**：多人共用一个出口 IP 集中订阅，或短时高频上报 → report 返回 429 → 额度未累加、UI 静默无反馈。
- **影响范围**：授权已 accept 但额度上报丢失，用户以为已订阅实则没有；限流误伤，非安全漏洞。
- **建议**：① 上报/状态类端点改用登录态维度限流（`key_func=get_user_identifier`）或独立更宽松的 `RateLimits`；② C 端对 429 给可感知提示（区别于未登录）。
- **优先级**：中低（受订阅活跃度影响，放量后需关注）。

### M11 — 订阅快照 `openid` 列宽 `String(64)` 小于来源列 `String(100)`

- **维度**：数据库交互（列宽一致性）/ 契约一致性
- **位置**：`backend/models/marketing/l4_marketing.py:474`、`:556`（两张订阅表 `openid = String(64)`）；来源 `backend/models/user/user.py:127`（`wechat_openid = String(100)`）
- **现状**：订阅表把 openid 作为快照存储，列宽定为 64，而上游 `users.wechat_openid` 允许 100。openid 实际约 28 字符（已实测当前库），64 目前够用；但若出现更长的 openid（unionid 体系/历史数据异常），上报写入会触发 PG `value too long` → 500（`sqlalchemy_exception_handler` 兜底为标准错误，但订阅失败）。
- **触发场景**：超长 openid 上报 accept → `_upsert_row` 或原子 UPDATE 写 `openid` 列 → DataError。
- **影响范围**：当前无触发（列宽余量充足），属潜伏的列宽不对齐。
- **建议**：与来源列对齐为 `String(100)`，并补一条幂等迁移 `ALTER COLUMN openid TYPE varchar(100)`（`_column_exists`/宽度守卫）。
- **优先级**：低。

### O1 — 历史日志/采集链路中的凭据无法回溯清除（H1 关联）

### O3 — `bind-account` 合并成功后调用 `clearCUserState()` 是否应清 `c_protocol_agreed`

- **背景**：H3 修复让「显式登出」清 `c_protocol_agreed`（撤回本机知情同意）。但 `miniapp/utils/token.ts:88` 的 `clearCUserState()` 同时被 `pages/bind-account/index/index.ts` 在**账号合并成功**后调用——该处 `clearCUserState()` 也会删 `c_protocol_agreed`。
- **不确定点**：合并场景用户仍处登录态（随后 `applyMergeTokens` 写入新令牌），并非「撤回同意」。此处清掉 `c_protocol_agreed` 会导致：合并后若令牌过期，冷启动静默续登因缺同意标记而失效，用户需重新手动勾选登录。是否可接受，取决于产品对「合并即重置同意态」的预期。
- **建议处置**：明确语义后二选一——① 合并成功不应撤回同意：给 `clearCUserState` 加参数区分（登出清标记、合并只清 `c_user_temporary`/`c_phone_prompted`）；② 若产品认为合并即需重新确认，维持现状并在 bind-account 处补注释说明。
- **优先级**：中（影响静默续登可用性，非安全）。
