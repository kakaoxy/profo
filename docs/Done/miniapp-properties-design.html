设计决策记录

1. 卡片布局选择：横向紧凑而非纵向大图

projects/list 使用纵向大图卡片（4:3 缩略图在顶部），适合 C 端公开房源展示。但房源查询是内部员工高频检索工具， 单屏可扫描的房源数量直接影响效率。横向卡片（64×72 缩略图 + 右侧四行信息）在 375px 宽度下单屏可显示 4-5 条， 是纵向大图卡片（单屏 2 条）的 2 倍密度。这与 admin 移动端 property-card-list 的设计选择一致。

2. 筛选维度压缩：3 chip 而非 9 项全展开

admin 端有 9 类筛选（状态/小区/商圈/户型/楼层/价格/面积/区域/排序），桌面端用左侧固定面板全展开。 小程序端将「状态」提为顶部 tab（全部/在售/成交），「小区搜索」提为顶部搜索框并扩展为小区/商圈搜索， 剩余 3 维度（户型/楼层/排序）压缩为 chip 行。移除了价格范围、面积范围筛选（依据迭代计划审查修正记录）， 并移除独立商圈筛选项（本次落地方案改动，商圈检索并入搜索框）。

3. 排序集成进 chip 行而非独立按钮

排序与筛选在交互上同质（点击展开浮层 → 选择 → 列表更新），合并到同一 chip 行保持视觉一致性。 排序 chip 文案带方向箭头（如「成交时间↓」），当前排序状态一眼可见。排序面板右对齐浮出，与其他筛选面板左对齐区分。

6bis. 顶部导航栏：复用小程序原生导航栏

header 复用小程序默认导航栏（navigationStyle: default），不作自定义绘制—— 标题居中、左上角原生返回箭头、状态栏由系统处理。相比自绘导航栏，省去对齐状态栏高度与安全区的成本。

4. 状态色映射：apricot（在售）vs fog（成交）

对齐 projects/list 的徽标色体系：在售 = 暖橘底（hsl(32, 85%, 92%)），成交 = 冷灰底（hsl(220, 14%, 92%)）。 过期状态（updated_at 超 30 天的在售房源）用红色底（hsl(0, 70%, 94%)）但仅在筛选 tab 中可选，不在默认列表强制区分（计划默认列表展示全部状态）。

5. 价格强调色：暖赤褐而非品牌红

admin 端用 text-error（Tailwind red-500 系）显示价格。小程序端改为暖赤褐（hsl(14, 72%, 42%)）， 与暖色画布更协调，同时保持足够的视觉跳出度。价格数字 19px / 600 是卡片内最大的视觉元素，确保一眼定位到价格。

6. 无底部 TabBar

房源查询从「我的」页内部入口进入，是 drill-in 页面而非顶层 tab。配合复用原生导航栏（决策 6bis）， 返回由原生返回箭头处理。底部留出安全区高度即可。

⚠️ 待确认项

  • 小区/商圈搜索组件复用：components/community-search 当前硬编码 /public/communities/search（C 端公开接口）。 房源查询需调 admin 接口 /api/v1/properties/communities/search，并叠加商圈字典匹配。需参数化改造 （props 传入搜索 url 与响应类型 / 支持多源结果），并回归验证 valuation/submit 不受影响。
  • 小区/商圈搜索的下拉交互：搜索建议需同时展示「小区」与「商圈」两类结果，需区分类型标签。 是否在 community-search 组件能力范围内实现，还是新做轻量搜索建议组件，待交互评审。
  • 户型图取数规则：getFloorPlan() 依赖 data_source（贝壳/我爱我家/其他）有特殊匹配规则。 小程序端是否完全复用此规则，还是简化为首图，待确认。
