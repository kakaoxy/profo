## 三、中低危问题

### M-01 刷新接口把 500/429 等服务端临时异常当作令牌失效，用户会被强制登出（已修复）

- **维度**：异常处理与日志 / 鉴权体验
- **位置**：[miniapp/utils/request.ts:183-191](miniapp/utils/request.ts#L183-L191)、[miniapp/utils/request.ts:261-269](miniapp/utils/request.ts#L261-L269)
- **触发场景**：access_token 或 c_access_token 临近过期（提前续期 30s 窗口）→ 主动刷新时 `/auth/refresh` 或 `/public/auth/refresh` 返回 500、429（发布抖动、限流）→ 原实现只要非 2xx 就删除本地 access+refresh 令牌。
- **原因**：`refreshAccessToken()` / `refreshCAccessToken()` 的 `success` 回调没有区分「refresh_token 明确失效（400/401/403）」与「服务端临时异常（5xx/429）」；c61e3b80 新增主动续期后，该分支在每次令牌过期前后都会更频繁地触发。
- **影响**：用户被直接踢下线，需要重新登录；限流时可造成一批用户同时掉线，属于用户可感知的登录态退化，不涉及数据损坏。
- **修复**：新增 `isRefreshTokenRejected(statusCode)`，仅 400/401/403 清令牌；5xx/429 和网络异常保留令牌并返回 null，后续请求可重试。
- **验证**：`request.test.ts:510-543` 新增后台/ C 端 500 保留令牌用例；定向 `pnpm vitest run test-utils/utils/request.test.ts` 通过（全量 2 个 `url.test.ts` 环境失败见 §一）。

### M-02 纯 C 用户刷新只更新 C 槽，主槽长期保留过期 access_token（已修复）

- **维度**：类型规范 / 鉴权契约一致性
- **位置**：[miniapp/utils/request.ts:247-253](miniapp/utils/request.ts#L247-L253)、[miniapp/utils/request.ts:168-175](miniapp/utils/request.ts#L168-L175)、[miniapp/pages/valuation/submit/index.ts:723-728](miniapp/pages/valuation/submit/index.ts#L723-L728)
- **触发场景**：纯 C 用户登录时 `wechat-auth.ts` 按约定把同一组令牌写入主槽 `access_token/refresh_token` 与 C 槽 `c_access_token/c_refresh_token`；30 分钟后 `/public/*` 请求触发 `refreshCAccessToken()`，原实现只更新 C 槽，主槽 `access_token` 仍是已过期的旧 JWT。
- **影响**：`getToken()`（读取主槽）返回非空过期值；估价提交页 `handleUnauthorized()` 只判断 `this.getToken()` 是否非空，会把纯 C 用户误判为「有后台令牌」，提示「当前账号无估价权限」而不是重新登录；其他以主槽做登录判断的页面也可能误判。
- **修复**：`refreshCAccessToken()` 在刷新成功且主槽 refresh token 属于纯 C 场景（主槽与 C 槽同值，或主槽 refresh token 的 `aud === "c"`）时同步写主槽；`refreshAccessToken()` 对称同步 C 槽；新增 `isCRefreshToken()` 兼容历史双槽不一致数据。
- **验证**：`request.test.ts:545-659` 新增纯 C 同步双槽、历史不一致、内部员工不覆盖后台主槽、纯 C 401 清双槽等用例；`pnpm vitest run test-utils/utils/request.test.ts test-utils/utils/request-concurrency.test.ts` 37 passed。
