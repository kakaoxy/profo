## 缺口明细

### GAP-V04-01 REQ-M06-006 二维码落地页未消费 scene，扫码注册链路不可达
- 缺失验收项：AC-V04-019（扫码注册自动绑定 + bind_source=二维码邀请 + inviter 正确）；场景变更 SCN-05 的扫码入口。
- 期望行为：员工出示门店二维码 → 经纪人扫码 → 小程序打开经纪人注册页并携带 `code` → 注册成功后自动绑定该门店。
- 现状（文件:行）：二维码 `page` 固定为 `pages/merchant/home/index`，`scene` 只放短码（`backend/services/merchant/broker_qr.py:23,46-47`；`backend/services/system/wechat.py:481-540` 仅传 `scene`+`page`）；而 `miniapp/pages/merchant/home/index.ts`（117 行）只有 `onShow/onPullDownRefresh/loadStores/...`，**无 `onLoad`，不解析 `options.scene`**；全仓业务代码无 `options.scene` 处理，唯一进入经纪人页的入口是 `miniapp/pages/profile/index/index.ts:586-589` 的无参跳转。经纪人页本身已支持 `options.code`（`miniapp/pages/merchant/broker/index.ts:126-130`），但扫码永远到不了该页。
- 建议修复：在 `miniapp/pages/merchant/home/index.ts` 增 `onLoad(options)`，读取 `options.scene`（需 `decodeURIComponent`）后 `wx.redirectTo({url: "/pages/merchant/broker/index?code=" + scene})`；或将二维码 `page` 直接改为 `pages/merchant/broker/index` 并在该页 `onLoad` 兼容 `options.scene`。修复后需真机扫码验证（后端测试 `test_merchant_broker.py:332` 只覆盖接口，不覆盖扫码入口）。
- 严重级：**P0**（核心场景 2 端到端不可用；后端能力已具备，仅差入口接线）

### GAP-V04-02 REQ-M05-001 员工分享注册未传 referrer，AC-024 不可达
- 缺失验收项：AC-V04-024（员工分享注册后 `inviter_employee_id`=分享员工、`bind_source=员工分享`）；BR-M05-007。
- 期望行为：员工分享小程序卡片带 `referrer`（员工 ID）→ 用户打开注册经纪人 → 档案写入 `inviter_employee_id` 与 `bind_source=share`。
- 现状（文件:行）：后端已支持 `req.referrer` 且校验 referrer 具备后台身份后写 `bind_source=share`（`backend/services/merchant/broker.py:156-169`）；但小程序注册只提交 `{name, qrcode_code}`（`miniapp/pages/merchant/broker/index.ts:276-280`），`onLoad` 只读 `options.code`（`:126-130`），全仓无任何页面把 `referrer` 传给 `/brokers/register`（`grep referrer` 仅命中 valuation-share/recruit-logic/生成类型 `miniapp/types/api-types.d.ts:10289-10291`）。
- 建议修复：经纪人页 `onLoad` 读取 `options.referrer`（及分享 path 的 query），注册请求体补 `referrer`；员工侧分享入口（`onShareAppMessage`）统一拼 `referrer=<employee_id>`。补一条"分享注册→档案归属员工"的 E2E。
- 严重级：**P1**（场景变更第 6 条明确要求"员工分享小程序被用户打开并注册为经纪人后自动归属该员工"）

### GAP-V04-03 REQ-M05-002 完善手机号流程不同步 broker.phone/phone_hash
- 缺失验收项：AC-V04-015（手机号变更后重算 hash 且不影响绑定）；BR-M05-001/002/003。
- 期望行为：经纪人通过现有 `PUT /api/v1/public/users/phone` 或 `/phone/wechat` 改号后，`merchant_brokers.phone`（加密）与 `phone_hash` 自动同步，并处理唯一冲突；绑定关系不变。
- 现状（文件:行）：`backend/services/system/user/profile.py:56-70` `update_phone()` 只改 `users.phone/phone_hash`，全仓无 broker 同步钩子；`backend/services/merchant/broker.py:211-250` 的 `update_me()` 要求 `req.phone == user.phone` 才同步（:223-228），而小程序编辑资料只提交 `name/remark`（`miniapp/pages/merchant/broker/index.ts:322-326`），因此该同步分支实际不可达。改号后 `merchant_brokers.phone` 与 `phone_hash` 仍是旧值，招募匹配（:1053-1062）与后台按手机号搜索（:668-673）随之失真。
- 建议修复：在 `update_phone`/`set_initial_phone` 成功后按 `user_id` 同步 broker 记录（同事务或补偿任务），冲突时回滚并提示；同步后重跑 `_match_recruit_lead`。或在 `broker` 侧做惰性校正（读取时比对 users.phone）。
- 严重级：**P1**（BR-M05-002 要求 phone_hash 与 users 一致；数据会静默漂移）

### GAP-V04-04 REQ-M06-003/M06-004 绑定审批"拒绝"分支未写审计
- 缺失验收项：BR-M06-017/019（审核通过或拒绝均写审计，记录操作人/时间/意见）。
- 期望行为：运营在后台通过或驳回换绑/解绑申请，均产生审计日志（action、operator、remark、before/after）。
- 现状（文件:行）：`backend/services/merchant/broker.py:561-617` `approve_binding()` 拒绝分支（:584-589）仅置 `status=rejected`、拼接 reason 后 `commit()` 直接 `return`，**未调用 `add_audit_log`**；通过分支有审计（:605-614）。
- 建议修复：拒绝分支补 `add_audit_log(action="reject_binding", resource_type="merchant_broker_binding", ...)`，写入 `remark` 与操作人；后台 `approveBinding` 的固定文案"后台驳回"（`frontend/src/app/(main)/admin/merchant/brokers/page.tsx:193`）建议改为可输入意见。
- 严重级：**P1**（合规审计缺失，且拒绝是高频操作）

### GAP-V04-05 REQ-M05-003 停用后存量 pending 申请仍可审批绑定
- 缺失验收项：BR-M05-011（停用状态不可被新绑定）、AC-V04-014。
- 期望行为：经纪人停用后，其已提交的换绑/解绑申请不应再产生有效绑定；审批时应拒绝或自动作废。
- 现状（文件:行）：`backend/services/merchant/broker.py:789-818` 停用只解绑当前门店并置 `disabled`，未关闭 pending 记录；`approve_binding()`（:561-617）通过分支不校验 `broker.bind_status == disabled`，运营点"通过"即可把已停用经纪人重新置为 `bound`（:596-603）。另 `change_status_admin` 未做"目标状态与当前一致则不产生变更"短路（重复停用会重复写审计）。
- 建议修复：`approve_binding()` 开头校验 `broker.bind_status != disabled`（或停用时批量置 `rejected` 并写原因）；`change_status_admin` 增加同状态短路。
- 严重级：**P1**（违反停用语义，且可由后台误操作触发）

### GAP-V04-06 REQ-M05-004 招募关联只写不展示，手机号变更不重匹配
- 缺失验收项：AC-V04-013（招募匹配写 `recruit_lead_id`）；BR-M05-013~015（只读关联、可查看）。
- 期望行为：经纪人档案可看到关联的招募线索（只读），后台可查；手机号变更后重新匹配。
- 现状（文件:行）：`recruit_lead_id` 仅落库（`backend/services/merchant/broker.py:1062`）并写入审计快照（:1094）；`BrokerResponse`/`BrokerListItem`/`BrokerAdminDetail` 均无该字段（`backend/schemas/merchant/broker.py:89-101,223-248`），后台页无展示列（`frontend/src/app/(main)/admin/merchant/brokers/page.tsx` 全文无 recruit）；`update_me`（:211-250）与 `update_admin`（:748-790）改号后都不重跑 `_match_recruit_lead`。
- 建议修复：`BrokerResponse` 增 `recruit_lead_id`（或线索摘要），后台详情/列表展示；手机号变更后重匹配并留审计。
- 严重级：**P2**（数据已落库，属可见性与一致性缺口）

### GAP-V04-07 REQ-M05-006 注册流程缺少"三选一"步骤

- 现状（文件:行）：注册页只有姓名输入 + 手机号提示 + "提交认证"（`miniapp/pages/merchant/broker/index.wxml:31-43`），注册成功后直接进档案页；三个入口藏在"我的门店"空态（:80-83 "绑定已有门店"/"创建新门店"），无"暂不绑定"显式选项（仅默认不绑）。
- 建议修复：注册成功回调弹出三选一（或注册页第二步），"暂不绑定"显式展示并写 `bind_source=none`。

### GAP-V04-09 REQ-M06-006 二维码无签名、生成权限放宽、自建店绑定来源误写
